### 1b. Choices made by this plan (DECISION)

- **P1. One route, no child routes.** The wizard is `SetupPage` at `/setup`; the current step is component state, not a URL. `app.routes.ts` and `setup-auth.routes.ts` do not change. Source: the unit asks for no step URLs (lines 15 to 20); `plans/DECISIONS.md` line 2925 and `plans/SAU-06.md` section 5 (SAU-11 row) say `pathMatch: 'full'` is removed only "when it adds child paths", which SAU-11 does not. Closes point 8.
- **P2. Buttons and what they write.** Only an explicit author action writes a step state. "Next" moves on and writes nothing. "Mark done" writes `done` and moves on. "Skip" writes `skipped` and moves on. "Skip the rest" posts `SETUP_CONTINUE_ROUTE` and goes to `LANDING_PATH`. On the last step, "Finish" posts `SETUP_CONTINUE_ROUTE` and goes to `LANDING_PATH`; on the last step, "Mark done" and "Skip" write their state and then finish (post continue). The matrix:

  | Step | Buttons, in order |
  |---|---|
  | 1 Access | Next, Skip the rest |
  | 2 Tailscale, 3 Model providers, 4 Preferences | Mark done, Skip, Next, Skip the rest |
  | 5 First project | Mark done, Skip, Finish |

  Source: unit line 15 (Access cannot be skipped; skip; finishing or skipping the rest sets `complete`), line 16 (write only what the author changed: a re-run passes a step with Next without changing its stored state), line 18 (finishing a skipped step: Mark done), line 19 (the "skip the rest" path stays); the API writes one step per POST (`setStep`) and only continue writes `complete`. Closes point 3.
- **P3. Access step.** Body as SAU-06 (1b-3, 1b-4). Access cannot be skipped (unit line 15), so it has no Skip. Next does not write `access`. The stored access stays `pending`, which the status shows as `done` (`statusBody`, `setup-status.service.ts` line 31), and continue marks it `done` (`continuedSteps`, line 41).
- **P4. Placeholders for steps 2 to 5.** Text only, in `step-body.ts`: Tailscale "Tailscale is unavailable."; Model providers "Model providers are not set up yet."; Preferences "Preferences are not set up yet."; First project "The first project is not set up yet.". No text contains "Scriba". SAU-12, SAU-13, SAU-14 and SAU-20 each replace one `@case` (section 5). The controls of P2 are the same for steps 2 to 4, Tailscale included: no step but Access is special-cased (unit line 15 names only Access as an exception), and the Tailscale step's own controls are SAU-20's ("a visible skip", `units/SAU-20-tailscale-ui.md` line 15). Closes point 5.
- **P5. Opening step and states list.** On every load the wizard opens at Access, re-run included. An ordered list shows the five steps as `title: state`, with the state words of the contract (`SETUP_STEP_STATES`, `status.ts` line 12): `pending`, `done`, `skipped`. The stored states shown on a re-run are the "prefilled defaults" of SAU-11 (point 1). Source: unit line 15 gives the order from Access; opening elsewhere would need a rule the unit does not state. Closes point 9.
- **P6. Read order.** Identity first, as in SAU-06. Only after it answers 200 is the status read; a failure of that read uses the same error mapping as the identity read. Without a 200 identity, no status is read, no control, list or compose warning shows, and the notice, explanation or alert is the only content (1b-3).
- **P7. Compose warning component.** SAU-15 created `compose-warning.ts` first (commit `4238cb3`); SAU-11 imports it unchanged and does not create or edit it (section 5, SAU-15 row). It holds `ComposeWarning` (selector `app-compose-warning`, input `compose`) and the exported constant `COMPOSE_UPDATE_COMMAND = 'docker run --rm -e SETUP=true bbartolome/scriba | bash'` (the text of `units/SAU-10-compose-version-status.md` line 21). For `unknown` it says the install does not report its compose version. Both then show the one-liner in one `<code>`. It has no `role="alert"`, because the e2e's `getByRole('alert')` in state 4b would match two elements in strict mode. It sits after the heading and shows only once the status is loaded (P6). On `/setup` the page renders it only when `loaded.compose.state !== 'ok'` (the page gate), so for `ok` no `app-compose-warning` element exists; W2 checks this by the element count, and M3 mutates this gate.
