## 1. Decisions this plan obeys

### 1a. Settled by the unit, the module and earlier plans

- **D1 Fields.** The author display name and the default genre pack, both text. The genre pack offers choices from the built-in packs and keeps free text as the fallback. Source: unit line 15.
- **D2 The choices are built-in genre packs, and only those.** `core` is not a genre choice: it is always active and comes with the project's genre pack (`modules/genre-packs.md` line 40). The built-in packs are `core`, `nonfiction` and `fiction` (`modules/genre-packs.md` line 3; `packages/contracts/src/tool-registry/constants.ts` line 55, `BUILTIN_ORIGINS`). User packs are not offered: the unit adds them only "if listed by the Tool registry" (unit line 15), and no route on `main` lists pack names. A tool summary carries only an `origin` (`packages/contracts/src/tool-registry/catalog.ts` line 31), and `user` is the one user origin (`constants.ts` line 52). Which built-in names are offered is open point 1.
- **D3 The theme is device-local.** The step embeds the Shell's `ThemeToggle` (`apps/web/src/app/shell/index.ts` line 9). The choice is kept in this device's storage under `scriba.theme` (`apps/web/src/app/shell/theme.ts` line 8) and sends no request. The theme is in no POST body: `preferencesSchema` holds only `authorName` and `defaultGenrePack` (`packages/contracts/src/setup-auth/settings.ts` lines 7 to 11). Sources: unit lines 16 and 21; `modules/shell.md` line 82 (the toggle is for "Setup & auth (compose warning, preferences step)"); `plans/SHL-04.md` line 17 (the component is neutral, with no margin) and line 175; `plans/SAU-09.md` line 122.
- **D4 Save sends only the changed fields.** The page posts the changed keys to `PREFERENCES_ROUTE` (`packages/contracts/src/setup-auth/routes.ts` line 14). The API merges them field by field (`apps/api/src/modules/setup-auth/setup-flow.controller.ts` lines 22 and 28 to 33; `setup-status.service.ts` `savePreferences`, lines 105 to 118). Sources: unit line 17; `units/SAU-09-setup-flow-api.md` line 20; `plans/SAU-15.md` line 51 (D6: the form emits only the changed keys and its button is disabled when none changed).
- **D5 Save marks the step done.** After the preferences POST succeeds, the page posts `{state: 'done'}` to the step route, in a second request. Source: unit line 17 ("marks the step done"); `plans/SAU-09.md` line 122 ("its preferences step state is a separate `POST steps/preferences` call"); `units/SAU-09-setup-flow-api.md` line 18.
- **D6 Prefill.** The stored values are the field defaults. Source: unit line 20 ("Prefills saved values"); `plans/SAU-11.md` section 1a ("Stored values") and P12 (line 77).
- **D7 Runtime contract values come through the loader.** `PREFERENCES_ROUTE` and `preferencesSchema` are read through `loadSetupAuthContract`. Types come only with `import type`. Source: the header of `apps/web/src/app/features/setup-auth/setup-contract.ts` (lines 1 to 8: the dynamic loader is the feature's only runtime contract reference); `plans/SAU-11.md` P9.
- **D8 The step's controls are its own.** Each step unit states its marking rule and changes its own controls in `setup-page.ts`. Source: `plans/SAU-11.md` line 79 (P14); unit line 17.
- **D9 Errors.** A 401 shows the sign-in notice, a tailnet code shows its explanation, any other error shows its message. This is the existing `fail()` (`setup-page.ts` line 235). Source: `modules/setup-auth.md` line 42; `plans/SAU-11.md` section 1a.
- **D10 No API change and no contract change.** The preferences GET and POST and `POST /api/setup-auth/steps/:step` exist and are done (SAU-09). Source: `units/SAU-09-setup-flow-api.md` lines 18 to 20; `setup-flow.controller.ts` lines 22 and 28; `packages/contracts/src/setup-auth/status.ts` line 41 (`stepUpdateSchema`).

### 1b. Small decisions (taken here, the simplest option)

- **S1 Controls of the step.** The form's own button, `Save preferences`, is the done path (D4, D5). Below it the page shows `Skip`, `Next` and `Skip the rest`. `Mark done` is not shown on this step. This replaces the step's SAU-11 matrix row (`plans/SAU-11.md` P2, the row for step 4).
- **S2 Save stays on the step.** After a successful save the page shows the saved values and the updated list. The author moves on with `Next`. Reason: the form already works this way on the settings page (`plans/SAU-15.md` D6, "then sets `stored` from the answer"), and it keeps the first-project body out of this unit's tests.
- **S3 Save needs a change.** The form's button is disabled when no field differs from the stored value (`apps/web/src/app/features/setup-auth/preferences-form.ts` line 88, `hasChanges`). So a Save with no change does not happen, and the step is not marked done without one. `Next` writes nothing (unit line 16; `plans/SAU-11.md` P2). `Skip` writes `skipped`.
- **S4 The stored values are read on entry.** The page reads `GET PREFERENCES_ROUTE` when it moves onto the `preferences` step, not at load. No existing test in `setup-page.spec.ts` enters that step (its clicks are `Next`, `Skip`, `Skip the rest` and `Mark done` on steps 1 to 3, lines 145 to 545), so no existing test gets a new answer. A read at load would add an answer to every test that answers the status.
- **S5 The step body.** The `preferences` case of `step-body.ts` renders `<app-preferences-form>` once the stored values have loaded, the paragraph `Theme is kept on this device only.`, and `<app-theme-toggle />`.
- **S6 The form is reused, and the settings page gets the same choices.** The step uses `PreferencesForm` (SAU-15, done). `units/SAU-15-settings-page.md` line 16 says the settings page has "same fields as the step", so one form serves both pages. The settings page therefore also shows the choices. The implementer's step 4 run checks that `settings-page.spec.ts` still passes; this plan assumes it does (section 7).
- **S7 Where the choices live.** `GENRE_PACK_CHOICES` is exported from `preferences-form.ts`. The genre pack input gets `list="genre-pack-choices"`, and the form renders `<datalist id="genre-pack-choices">` with one `<option>` per choice. The text input stays, so free text is accepted.
- **S8 Names and files.** One new spec file, `apps/web/src/app/features/setup-auth/preferences-step.spec.ts`, with the tests PR1 to PR8. Its helpers (`renderSetup`, `rootOf`, `buttonNamed`, `settle`, `stepItems`) are copied from `setup-page.spec.ts`, as `plans/SAU-12.md` step 7 copies its own. `setup-page.spec.ts` is not changed by this plan. Every `vi.waitFor` in the new file gets an explicit `timeout: 5000`, as `settle` does (`setup-page.spec.ts` line 131). Reason: in the MPR-11 check on `main`, `setup-page.spec.ts` C1b timed out at 5000 ms under load (`plans/DECISIONS.md`, the MPR-11 failed check of 2026-11-16, lines 4527 to 4531). The Shell's wait rule (SHL-22) is the same.
- **S9 The providers panel is stubbed.** The spec overrides `StepBody` with a stub of `app-providers-panel`, in the form SAU-12 uses (`plans/SAU-12.md` step 6): `TestBed.overrideComponent(StepBody, { remove: { imports: [ProvidersPanel] }, add: { imports: [ProvidersStub] } })`. The tests pass through the providers step on the way to preferences, and a real panel would make requests the test does not answer.
- **S10 Next and Skip drop unsaved drafts.** No prompt. The draft text is lost with the step.
- **S11 Body checks are exact.** Request bodies are checked with `toStrictEqual`, because `toEqual` ignores keys whose value is `undefined`. The first-save body must have only `defaultGenrePack`.
- **S12 Opening step.** No change: the wizard still opens at Access (`plans/SAU-11.md` P5).
