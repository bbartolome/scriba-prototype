## 1. Decisions this plan obeys

### 1a. Settled by the unit, the module, the contract, the done plans and main

- **D1 What is written, and where.** One JSON Lines file per run, `logs/recipe-runs/<runId>.jsonl`, with one JSON line per entry in the contract's shape. Every line is written through the Project store's in-process `appendLog`. The logs are the source of truth, and there is no run-log index (deferred). The Agent loop's transcripts are a separate format. Source: unit line 18; `modules/graph-runner.md` line 45 (`logs/recipe-runs/`) and line 65 (index deferred); `packages/contracts/src/graph-runner/constants.ts` line 47 (`RUN_LOG_FOLDER`).
- **D2 Entry types.** Six types, discriminated on `type`: `run-started` (`graphId`, optional `target`, `inputs`), `node-status` (`nodeId`, `status`, optional `error`), `tool-call` (`nodeId`, `arguments`, `output`, `sourcesUsed`), `error` (optional `nodeId`, `code`, `message`), `pending-change` (`nodeId`, `pendingChangeId`, `path`) and `run-ended` (`status`, optional `reason`). Each entry has `type`, `at` and `runId`. Every top-level object is strict, so no other key may be written. A file input carries `hash` (in `sha256:` form). Source: `packages/contracts/src/graph-runner/log.ts` lines 22 to 34 (`runLogInputSchema`) and 38 to 87 (`runLogEntrySchema`).
- **D3 Restart recovery (unit line 19, as reworded in `0565ae7`).** On API start, the most recent run of the active project is rebuilt from its log. A run with no end entry is reported as `stopped` with reason `interrupted`, and an end entry is appended. Source: unit lines 19 and 20; `constants.ts` lines 53 to 57 (`RUN_REASONS` holds `interrupted`). The active project is persisted in `settings.yaml` (`project-store.service.ts` `activeId()`, lines 50 to 56; PST-04 line 28). A run is active only in the active project at a crash, because a switch stops the run of the project it leaves (GRR-05).
- **D4 Scope.** The unit's "scope" is the run's `target`. An absent `target` means the whole recipe, as GRR-01 plan C15 says. The in-scope nodes are the nodes that have a `queued` node-status line. Source: GRR-01 plan line 94; unit line 18.
- **D5 Pending-change entries are GRR-07's.** GRR-06 wrote no log code, and on main the output branch makes no log call. GRR-07 writes the `pending-change` entry in that branch. This is the GRR-06 output step, which then emits the ids through this logger, as unit line 18 says. Source: CHECKED on main, `apps/api/src/modules/graph-runner/runs.service.ts` lines 417 to 427 (no log call); `plans/GRR-06.md` P13 (line 42) and section 6 point 2 (line 151, option (a)).
- **D6 Where each entry is written.** The `run-started` entry comes after the registration (`runs.service.ts` line 269) and before its publish (line 271). Each node status change is written in `setStatus`, the one place where a status changes (GRR-04 plan P12, line 44; `runs.service.ts` lines 578 to 590). The `run-ended` entry is written in `finish`, after the reason is set (GRR-05 plan section 4.8, line 120; section 6, GRR-07 notes, lines 199 to 204).
- **D7 No await between a stop check and a propose.** Every log call is synchronous. `FilesService.appendLog` is synchronous and returns `void` (`files.service.ts` line 436). Source: GRR-05 plan D2; GRR-06 plan D7; `runs.service.ts` line 418.
- **D8 Reads never mutate.** Recovery writes only at boot, never on a GET. Source: `units/README.md` line 132; `modules/graph-runner.md` line 41.
- **D9 Boundaries.** graph-runner never imports the Agent loop, and it imports other modules only through their entry files. So the transcript reader is not imported, and its reading rules are written again in graph-runner code. Source: `modules/graph-runner.md` line 38; `units/README.md` line 131; `units/GRR-08-engine-gate.md` line 19.
- **D10 Active-project rule.** `FilesService.list` and `read` go through `projectFor`, which calls `requireActive` (`files.service.ts` lines 512 to 519). They refuse a project that is not active. `appendLog` refuses a project that is not `ok` and a path outside `logs/`, but it accepts an `ok` project that is not active (lines 434 to 448; `project-status.ts` lines 15 to 48). So a run that a switch stopped can still finish its log. Source: `modules/project-store.md` line 48; `plans/PST-07.md` line 78 (P10) and line 165; `units/AGL-04-transcripts-history.md` line 18.
- **D11 A failed write (open point 1, settled: option (a)).** The Agent loop's rule applies. The first failed write is logged once, the run goes on, and the later lines of that run are not attempted. Source: `plans/AGL-04.md` line 65 (D5); `apps/api/src/modules/agent-loop/transcript-writer.ts` lines 73 to 105 (`failed` is set at line 99, and there is one `logger.warn` at line 101).
- **D12 No contract change.** Every name that the plan uses exists: `RUN_LOG_FOLDER`, `RUN_REASONS`, `runLogEntrySchema`, `runStateSchema`, `currentRunSchema` and `errorCodeSchema`. Contracts change by expand–contract once they are published (`units/README.md` line 136). Open point 2 was settled with no change.
- **D13 Error codes.** A node error, or an error that escapes the engine, uses the code and the message that `failureOf` gives (`runs.service.ts` lines 142 to 147). No new code is added. Source: `log.ts` lines 64 to 71; `runs.ts` lines 64 to 68; `errorCodeSchema` is a pattern (`platform/errors.ts` line 21).
- **D14 Test seam.** The tests check external behaviour only: HTTP responses and files on disk. The log file is read from disk. Source: `units/README.md` line 139; `modules/graph-runner.md` lines 49 to 51.

### 1b. Choices this plan makes (names, layout, rule details)

- **S1 Files.** Two new pure modules, as GRR-06 did with `output-targets.ts`: `run-log.ts` (path, line, parse) and `run-recovery.ts` (rebuild and repairs). Both import only `@bbartolome/scriba-contracts/graph-runner`. The rest of the change is in `runs.service.ts`.
- **S2 One writer.** `RunsService` gets one private method, `log(record, entry)`. If `record.logFailed` is true, it returns. Otherwise, inside one `try`, it computes `runLogLineOf(entry)` and calls `this.files.appendLog(record.projectId, runLogPathOf(runId), line)`. `runLogLineOf` returns `JSON.stringify(runLogEntrySchema.parse(entry))`, so the line holds only the contract's keys. Any throw (a parse error or a refused append) sets `record.logFailed = true` and gives one `logger.warn`, with the run id and the error message (D11). `log` never throws. The `at` of each entry is `new Date().toISOString()`, taken when the entry is written. The module logger is `const logger = new Logger('GraphRunner')`, as `transcript-writer.ts` line 10 does.
- **S3 `node-status` and order.** `setStatus` writes `{type: 'node-status', at, runId, nodeId, status}`, plus `error` when `extra.error` is set. It never writes `result`, because the member is strict and the results are in the `tool-call` and `pending-change` lines. A log line is written before the SSE publish of the same change, in the start, in `setStatus` and in `finish`.
- **S4 `run-started`.** Written after `this.entryOf(projectId).active = record` (line 269) and before the `run-started` publish (line 271). `inputs` keeps each input's value, but a file input also takes `hash` from `record.files.get(inputId).hash`. `target` is written only when `state.target` is set. `targets` is not written (open point 2). A failed write follows D11.
- **S5 `tool-call`.** Written inside `toolStep`, directly after the executor returns. The line `return this.executor.execute(...)` (line 487) becomes `const result = await this.executor.execute(...)`, then the log line, then `return result`. `arguments` is `checked.arguments` (`ToolArguments`, `call.ts` lines 7 and 41), `output` is `result.output` and `sourcesUsed` is `result.sourcesUsed` (`call.ts` lines 71 to 75). A call that rejects (an abort or an error) has no `tool-call` line. A call that returns after a stop request is logged, because the call happened.
- **S6 `pending-change`.** Written in the output branch, between `record.state.pendingChangeIds.push(change.id)` (line 424) and `setStatus(record, id, 'done', ...)` (line 425). The fields are `nodeId: id`, `pendingChangeId: change.id` and `path: change.targetPath`.
- **S7 `error`.** A node error writes `error` with `nodeId`, and with `code` and `message` from `failureOf(error)`. It is written before `setStatus(record, id, 'error', ...)` (line 438). An error that escapes the engine writes `error` with no `nodeId`, in the `.catch` of `start()` (lines 279 to 281), before `finish`. A stop's abort writes no `error` line (the GRR-05 rule, lines 433 to 437).
- **S8 `run-ended`.** `finish` writes `run-ended` with `status`, and with `reason` when one is set. It writes after `endedAt` and the reason are set, and before its publish (line 617). The once-only guard stays as it is.
- **S9 Content.** Nothing is scrubbed and nothing is truncated. The unit and the contract name no such rule, and no criterion needs one. The entries hold validated arguments, tool output, input references and fixed messages (`MESSAGES` echoes no input, `runs.service.ts` line 47). The contract sets no size limit, so none is added.
- **S10 Trigger.** `RunsService` implements `OnApplicationBootstrap`, with `onApplicationBootstrap()`. The precedents are `search.service.ts` line 71 and `project-watcher.service.ts` line 54. `createTestApp` calls `app.listen` (`create-test-app.ts` line 91), which runs the hooks before the app answers requests. So no GET sees a stale run. Platform's settings hook runs first, because Nest runs the deepest modules first (`providers.seeding.ts` lines 23 to 26).
- **S11 Scope of recovery.** Only the active project: `const projectId = this.store.activeId()`. If it is `null`, recovery does nothing. The whole recovery is in one `try`. A failure (for example a refused `list` or `read`) is logged once with `logger.warn`, and the boot goes on. No other project is read (D3, D10).
- **S12 Reading.** `this.files.list(projectId, {path: RUN_LOG_FOLDER})`. A `NOT_FOUND` `ModuleError` means that there are no runs (`files.service.ts` lines 238 to 239; `transcript-reader.ts` lines 301 to 313 handles it the same way). Keep the entries of kind `file` whose path ends in `.jsonl`. Read each one with `this.files.read`, and parse it with `parseRunLog`: split the text on `\n`, then skip each blank line and each line that fails `JSON.parse` or `runLogEntrySchema.safeParse` (the precedent is `transcript-reader.ts` lines 85 to 104).
- **S13 Most recent.** The most recent run is the file whose `run-started` `at` is the latest. A tie is broken by file path, as `byRunOrder` does (`transcript-reader.ts` lines 75 to 78). A file with no `run-started` line is not a run.
- **S14 Rebuilt state (`recoveredRunOf`).** `runId`, `graphId`, `target` and `startedAt` (its `at`) come from `run-started`. `inputs` also comes from `run-started`, with `hash` dropped. `targets` is `{}` (open point 2). `pendingChangeIds` comes from the `pending-change` lines, in order. Each node's status, and its `error`, come from its last `node-status` line. A node's `result` is set only when its final status is `done`. A tool node takes `{output, sourcesUsed}` from its `tool-call` line, and an output node takes `{pendingChangeId, path}` from its `pending-change` line. `status`, `reason` and `endedAt` come from `run-ended` when it is present. A node with no `node-status` line (an out-of-scope node) is absent from `nodes` (see section 6, GRR-13). The result is checked with `runStateSchema.parse` in the test (C2), not in the service.
- **S15 Repair.** The latest run may have no `run-ended` line. Then a `node-status` `stopped` repair line is made for each node that is still `queued` or `running`, in the order of their first line. This is the rule of `endStopped` (`runs.service.ts` lines 593 to 601). Then the repair `run-ended` line is `{status: 'stopped', reason: 'interrupted'}`. Every repair line has the boot instant as its `at`. The rebuilt state gets the same values: those nodes are `stopped`, `status` is `stopped`, `reason` is `interrupted` and `endedAt` is the boot instant. The rebuilt state is put in the registry first. Then the repair lines are appended one at a time through `appendLog`. The first failure stops the appends and is logged once (D11), and the state stays reported. Only the latest run is repaired.
- **S16 Where the rebuilt run lives.** `ProjectRuns` gets `recovered?: RunState`. `current()` returns `active`, else `last`, else `recovered`, else `null`. Only `active` blocks a start (`RUN_ACTIVE`), so a recovered run never blocks one. `stop(runId)` with the recovered run's id returns without an error and does nothing, because that run has ended. This is the same as a stop of the ended `last` run, through `requestEnd`. Any other unknown id still gives `RUN_NOT_FOUND`.
- **S17 No shutdown hook.** Shutdown writes nothing. A run that a restart cuts off has no end entry, and recovery reports it. So a graceful stop and a crash leave the same log. `RUN_REASONS` has no shutdown reason, and the unit names none.
- **S18 Record fields; no constructor change.** `RunRecord` gets `logFailed: boolean` (set to `false` in `start()`) for D11. The constructor is not changed: recovery uses `this.store` (`ProjectStoreService.activeId()`) and `this.files`, which are already injected (lines 156 and 161).
- **S19 Tests.** Two new test files (section 5). Each test builds its own library and app. The GRR-04 and GRR-06 kits are reused read-only, and no new kit file is made.

## 7. Open points (settled by the reviser)

1. **What a failed log write does. Settled: option (a), the Agent loop's rule (D11, S2).** The first failed write (a parse or an append) is logged once. The run goes on, and the later lines of that run are not attempted. Reason: it is the one rule already on main for `appendLog` (AGL-04 D5). It lets a run that a switch stopped finish, and it keeps GRR-04's start order and GRR-05's stop path. Option (b) (end the run as `error`) would make a stop unable to finish its log. Option (c) (refuse the start) would change the order that GRR-04 P7 fixed. No other unit is affected.
2. **The targets of a recovered run. Settled: option (a), `targets: {}` (S14).** Reason: no contract change. No unit reads the `run-started` log member (section 2a grep), and the unit's list of start fields (line 18: graph id, scope, input values) does not include targets. The effective output paths survive in each output's `pending-change` line and in its node result. Option (b) would expand a published contract for no current need.
3. **Record only (GRR-06 open point 1, decided there).** Generated output names get no suffix. So two output nodes of one kind that have no target share a path in one run. This is GRR-06's decision and is not a GRR-07 task. GRR-07 logs the path as it is.
