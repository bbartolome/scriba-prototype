Unit: GRR-07 (module graph-runner, phase:engine, M4). `units/GRR-07-run-logs-recovery.md`: front matter lines 2 to 9 (`blocked_by: [GRR-04]`, `parallel_with: [GRR-05, GRR-06]`, `unblocks: [GRR-08]`); Why line 15; Decisions lines 18 and 19; criteria lines 22 and 23. Acceptance criteria, verbatim (unit lines 22 and 23):

## 1. Decisions this plan obeys

### 1a. Settled by the unit, the module, the contract, the done plans and main

- **D1 What is written, and where.** One JSON Lines file per run, `logs/recipe-runs/<runId>.jsonl`, one JSON line per entry in the contract's shape, written through the Project store's in-process `appendLog`. The logs are the source of truth; there is no run-log index (deferred). The Agent loop's transcripts are a separate format. Source: unit line 18; `modules/graph-runner.md` line 45 (`logs/recipe-runs/`) and line 65 (index deferred); `packages/contracts/src/graph-runner/constants.ts` line 47 (`RUN_LOG_FOLDER`).
- **D2 Entry types.** Six types, discriminated on `type`: `run-started` (`graphId`, optional `target`, `inputs`), `node-status` (`nodeId`, `status`, optional `error`), `tool-call` (`nodeId`, `arguments`, `output`, `sourcesUsed`), `error` (optional `nodeId`, `code`, `message`), `pending-change` (`nodeId`, `pendingChangeId`, `path`), `run-ended` (`status`, optional `reason`). Each has `type`, `at` and `runId`. Every object is strict, so no extra key may be written. A file input carries `hash` (`sha256:` form). Source: `packages/contracts/src/graph-runner/log.ts` lines 22 to 34 (`runLogInputSchema`) and 38 to 87 (`runLogEntrySchema`).
- **D3 Restart recovery.** On API start, the most recent run of each project is rebuilt from its log. A run with no end entry is reported as `stopped` with reason `interrupted`, and an end entry is appended. Source: unit line 19; `constants.ts` lines 53 to 57 (`RUN_REASONS` holds `interrupted`).
- **D4 Scope.** The unit's "scope" is the run's `target` (absent means the whole recipe), as GRR-01 plan C15 says. The in-scope nodes are the nodes with a `queued` node-status line. Source: GRR-01 plan line 94; unit line 18.
- **D5 Pending-change entries are GRR-07's.** GRR-06 wrote no log code. On main the output branch makes no log call. GRR-07 writes the `pending-change` entry at that step. Source: CHECKED on main, `apps/api/src/modules/graph-runner/runs.service.ts` lines 417 to 427 (no log call); `plans/GRR-06.md` section 1b P13 (line 42) and section 6 point 2 (line 151, option (a)).
- **D6 Where each entry is written.** The `run-started` entry after the registration (`runs.service.ts` line 269) and before its publish (line 271). Each node status change in `setStatus`, the one place a status changes (GRR-04 plan P12, line 44; `runs.service.ts` lines 578 to 590). The `run-ended` entry in `finish`, after the reason is set (GRR-05 plan section 4.8, line 120; section 6, GRR-07 notes, lines 199 to 204).
- **D7 No await between a stop check and a propose.** Every log call is synchronous. `FilesService.appendLog` is synchronous and returns `void` (`files.service.ts` line 436). Source: GRR-05 plan D2; GRR-06 plan D7; `runs.service.ts` line 418.
- **D8 Reads never mutate.** Recovery writes only at boot, never on a GET. Source: `units/README.md` line 132 ("Reads are GET and never mutate"); `modules/graph-runner.md` line 41.
- **D9 Boundaries.** graph-runner never imports the Agent loop, and imports other modules only through their entry files. So the transcript reader is not imported; its reading rules are written again in graph-runner code. Source: `modules/graph-runner.md` line 38; `units/README.md` line 131 (PLT-09 bans cross-module implementation imports); `units/GRR-08-engine-gate.md` line 19.
- **D10 Ok-only writes.** `appendLog` refuses a project that is not `ok`, and refuses a path outside `logs/`. It accepts an `ok` project that is not the active one, so a run stopped by a switch can finish its log. Source: `files.service.ts` lines 434 to 448; `project-status.ts` lines 15 to 48; `plans/PST-07.md` line 78 (P10) and line 165; `units/AGL-04-transcripts-history.md` line 18.
- **D11 A failed append.** The Agent loop's rule: the first failed write is logged once, the run goes on, and later lines of that run are not attempted. Source: `plans/AGL-04.md` line 65 (D5) and line 205 (open point 3); `apps/api/src/modules/agent-loop/transcript-writer.ts` lines 73 to 105 (`failed` set at line 99, one `logger.warn` at line 101). This plan applies it, subject to open point 1.
- **D12 No contract change.** Every name the plan uses exists: `RUN_LOG_FOLDER`, `RUN_REASONS`, `runLogEntrySchema`, `runStateSchema`, `currentRunSchema`, `errorCodeSchema`. Contracts change by expand–contract once published (`units/README.md` line 136). Source: CHECKED on `packages/contracts/src/graph-runner/`. Open point 2 would be the one exception.
- **D13 Error codes.** A node error or an error that escapes the engine uses the code and message that `failureOf` gives (`runs.service.ts` lines 142 to 147). No new code. Source: `log.ts` lines 64 to 71; `runs.ts` lines 64 to 68.
- **D14 Test seam.** External behaviour only: HTTP responses and files on disk. The log file is read from disk. Source: `units/README.md` line 139; `modules/graph-runner.md` lines 49 to 51.

### 1b. Choices this plan makes (names, layout, rule details)

- **S1 Files.** Two new pure modules, as GRR-06 did with `output-targets.ts`: `run-log.ts` (path, line, parse) and `run-recovery.ts` (rebuild and repairs). Both import only `@bbartolome/scriba-contracts/graph-runner`. The rest of the change is in `runs.service.ts`.
- **S2 One writer.** `RunsService` gets one private method, `log(record, entry)`. It checks the entry with `runLogEntrySchema.parse` before it writes, so a shape error fails in a test rather than on disk. The `at` of each entry is `new Date().toISOString()`, taken when the entry is written.
- **S3 Order.** A log line is written before the SSE publish of the same change, in the start, in `setStatus` and in `finish`.
- **S4 `run-started`.** Written after `this.entryOf(projectId).active = record` (line 269) and before the `run-started` publish (line 271). `inputs` keeps each input's value, except a file input, which takes `hash` from `record.files.get(inputId).hash`. `target` is written only when `state.target` is set. A failed write follows D11.
- **S5 `tool-call`.** Written inside `toolStep`, directly after the executor returns. The line `return this.executor.execute(...)` (line 487) becomes `const result = await this.executor.execute(...)`, then the log line, then `return result`. `arguments` is `checked.arguments`, `output` is `result.output`, `sourcesUsed` is `result.sourcesUsed`. A call that rejects (an abort or an error) has no `tool-call` line. A call that returns after a stop request is logged, because the call happened.
- **S6 `pending-change`.** Written in the output branch, between `record.state.pendingChangeIds.push(change.id)` (line 424) and `setStatus(record, id, 'done', ...)` (line 425). Fields: `nodeId: id`, `pendingChangeId: change.id`, `path: change.targetPath`.
- **S7 `error`.** A node error writes `error` with `nodeId`, `code` and `message` from `failureOf(error)`, before `setStatus(record, id, 'error', ...)` (line 438). An error that escapes the engine writes `error` with no `nodeId`, in the `.catch` of `start()` (lines 279 to 281), before `finish`. A stop's abort writes no `error` line (the GRR-05 rule, lines 433 to 437).
- **S8 `run-ended`.** `finish` writes `run-ended` with `status` and, when set, `reason`. It writes after `endedAt` and the reason are set, and before its publish (line 617). The once-only guard stays as it is.
- **S9 Content.** Nothing is scrubbed and nothing is truncated. The unit and the contract name no such rule, and no criterion needs one. The entries hold validated arguments, tool output, input references and fixed messages (`MESSAGES` echoes no input, `runs.service.ts` line 47). The Agent loop scrubs because its transcripts record model messages (`plans/AGL-04.md` D7 and D8). The contract sets no size limit, so none is added.
- **S10 Trigger.** `RunsService` implements `OnApplicationBootstrap`, with `onApplicationBootstrap()`. The precedents are `search.service.ts` line 71 and `project-watcher.service.ts` line 54. Nest runs the hook before the app answers requests, so no GET sees a stale run.
- **S11 Scope of recovery.** Each project that `ProjectsService.discover()` reports (`projects.service.ts` lines 55 to 57) with `yaml.status === 'ok'`. Each project is handled in its own `try`. A failure is logged once with Nest's `Logger`, and the boot goes on.
- **S12 Reading.** `FilesService.list(projectId, {path: RUN_LOG_FOLDER})`. NOT_FOUND means no runs (`files.service.ts` lines 238 to 239; the same handling is in `transcript-reader.ts` lines 301 to 313). Keep the entries of kind `file` whose path ends in `.jsonl`. Read each with `FilesService.read`, split the text on `\n`, parse each line with `runLogEntrySchema`, and skip a line that fails (precedent `transcript-reader.ts` lines 85 to 104).
- **S13 Most recent.** The file whose `run-started` `at` is latest. Ties are broken by file path, as `byRunOrder` does (`transcript-reader.ts` lines 75 to 78). A file with no `run-started` line is not a run.
- **S14 Rebuilt state (`recoveredRunOf`).** `startedAt` comes from `run-started`. `inputs` come from `run-started` with `hash` dropped. `target` comes from `run-started`. `pendingChangeIds` come from the `pending-change` lines, in order. Each node's status comes from its last `node-status` line, and `error` from that line. A node's `result` is set only when its final status is `done`: a tool node takes `{output, sourcesUsed}` from its `tool-call` line; an output node takes `{pendingChangeId, path}` from its `pending-change` line. `status`, `reason` and `endedAt` come from `run-ended` when it is present. A node with no `node-status` line is absent from `nodes` (see section 6, GRR-13).
- **S15 Repair.** For the latest run of a project that has no `run-ended` line: append a `node-status` `stopped` line for each node still `queued` or `running`, in the order of their first line. That is the rule of `endStopped` (`runs.service.ts` lines 593 to 601). Then append `run-ended` with `{status: 'stopped', reason: 'interrupted'}`. `at` is the boot instant, and the rebuilt state gets the same values (`status` `stopped`, `reason` `interrupted`, `endedAt` the boot instant). Only the latest run is repaired (unit line 19). An unended older run is left alone; under these rules it can exist only if a repair write failed.
- **S16 Where the rebuilt run lives.** `ProjectRuns` gets `recovered?: RunState`. `current()` returns `active`, else `last`, else `recovered`, else `null`. Only `active` blocks a start (`RUN_ACTIVE`), so a recovered run never blocks. `stop(runId)` for the recovered run's id returns without error and does nothing, because that run has ended. Any other unknown id still gives `RUN_NOT_FOUND`.
- **S17 No shutdown hook.** Shutdown writes nothing. A run cut off by a restart has no end entry, and recovery reports it. A graceful stop and a crash therefore leave the same log. `RUN_REASONS` has no shutdown reason, and the unit names none.
- **S18 Constructor.** `RunsService` takes `private readonly projects: ProjectsService` as a new last parameter, after `pending`. `ProjectsService` is in the Project store entry file (`project-store.module.ts` lines 25 to 31, and its `exports` array). `RunRecord` gets `logFailed: boolean` for D11.
- **S19 Tests.** Two new test files (section 3). Each test builds its own library and app. The GRR-06 kit is reused read-only, and no new kit file is made.

## 5. Acceptance criteria and tests

Test names start `run logs, C<n>:`. Exactly one test per criterion (C1 and C2). Every HTTP answer's status is checked. The responses are parsed with `runStartResultSchema`, `currentRunSchema` and `runLogEntrySchema`. The log is read from disk with `readFileSync`, from `join(harness.library, 'book', 'logs', 'recipe-runs', `${runId}.jsonl`)`. ## 7. Open points

Each point below is a decision the sources do not settle. The Navigator decides. The procedure takes option (a) of points 1 and 2 until the Navigator says otherwise.

1. **What a failed log write does.** The unit does not say (unit line 18 names the log, not the failure). Options:
   - (a) The Agent loop's rule (D11): the first failed write is logged once, the run goes on, and later lines of that run are not attempted. The log may then be incomplete, and a repair at the next boot happens only if the project is `ok` then. This is the one rule already on main, and it lets a run stopped by a switch finish (AGL-04 unit line 18). **The procedure takes (a).**
   - (b) A failed write ends the run as `error` (as a refused propose does, `runs.service.ts` lines 432 to 446). This keeps the log complete, but a project that turns non-ok mid-run fails every later run, and a stop could not finish its log.
   - (c) Refuse the start when the `run-started` line cannot be written. The write must then come before `active = record` (line 269), so step 8 moves. This changes the order GRR-04 P7 fixed.
2. **Targets of a recovered run.** `runStateSchema.targets` holds the request's `targets` (`runs.ts` line 103), but `run-started` has no field for them (`log.ts` lines 39 to 46), so the log cannot give them back. Options:
   - (a) The rebuilt state has `targets: {}`. No contract change. The output paths survive in each output's `pending-change` line and its node result. The rebuilt state then differs from the live state for a run that had request targets. **The procedure takes (a).**
   - (b) Add an optional `targets` field to the `run-started` member of `runLogEntrySchema` (an expand of a published contract), write it in `start()`, and rebuild from it. This makes the rebuilt state equal to the live one, at the cost of one contract line and one write.
3. **Record only (GRR-06 open point 1, decided there).** Generated output names get no suffix. Two output nodes of one kind with no target in one run share a path. This is GRR-06's decision (option (a)) and is not a GRR-07 task. GRR-07 records the path as it is.
4. **Record only (unit line 18 against GRR-06's code).** The unit says GRR-06 emits pending change ids "through this logger"; GRR-06 emits none, and GRR-07 writes them (D5, `plans/GRR-06.md` section 6 point 2). The unit text is left as it is.
