## 1. Decisions this plan follows

### 1a. Settled by the unit, the module, the shell and the contracts

- **Route (D1).** One project-scoped entry in `PROJECT_ROUTES` (`apps/web/src/app/app.routes.ts`): `path: 'manuscript'`, `pathMatch: 'full'`, `data: { scope: 'project', minDeviceClass: 'phone', nav: { label: 'Manuscript', icon: 'article', order: 32 } } satisfies ShellRouteData`, and `loadChildren` of `manuscriptRoutes`. Source: unit line 17; `modules/compile-export.md` line 39; `modules/shell.md` line 66 (F3); the route-table owner registers its own entry (`modules/shell.md` line 52); `ShellRouteData` (F23). Order 32 is unused by the other nav items (F26), and it sorts Manuscript between Files (30) and Graphs (35). The icon name is the planner's choice (A9).
- **Outline (D2).** Three sections, headed Front matter, Body and Back matter, each a list `ul[data-part]` (`front`, `body`, `back`). Each row is an `li[data-path]` holding the file name as an open-file link, a status select, a part select, the word count and, for a graph-ordered row, the text `Graph order`. Source: unit line 18; `modules/compile-export.md` line 47 (graph-ordered files are a leading body block).
- **Open-file link (D3).** `/projects/:projectId/files?path=<path>`, built with `routerLink` and `queryParams`. Source: unit line 18; the Shell route row (F3, `modules/shell.md` line 63); the files page reads `path` from the query string (F38).
- **Totals, order source, warnings (D4).** Text: `Body: N words. Manuscript: M words.` from `totals` (F11). Order source from `orderSource` (F13): `alphabetical` shows `Order: alphabetical`, `project` shows `Order: project.yaml`, `graph+project` shows `Order: story graph, then project.yaml`. Each warning shows one line: `graphCycle` shows `Story graph cycle among <files, comma-separated>. The graph is ignored.`; `invalidGraph` shows `Story graph skipped as invalid: <path>.`; `staleEntry` shows `Order entry for a missing file ignored: <path>.`. Source: unit line 19; F11; `modules/compile-export.md` line 58 (external behaviour only).
- **Status and part (D5).** Native `select` elements, one status and one part per row, with `aria-label="Status of <file name>"` and `aria-label="Part of <file name>"`. Options are the contract's values (F14). Source: unit lines 18 and 27; `modules/compile-export.md` lines 49 and 50.
- **Graph-ordered rows (D6).** A graph-ordered row cannot be dragged (`cdkDragDisabled`), and its part select is disabled, because the server refuses any part change of a block member: `setPart` changes the block when a body member moves out of the body (F21, `manuscript-write.service.ts` lines 121 to 123). Its status select stays enabled, because a status write keeps positions (F21, `setStatus` 98 to 106). Source: unit line 18 (the badge; rows that cannot be dragged); CEX-03 unit line 15 ("graph-ordered files locked") and line 20 (the block is fixed).
- **Drag (D7).** Angular CDK drag and drop (F43), on tablet and desktop only (D14). A drag moves a row only inside its own part list: the three `cdkDropList` lists are not connected, so a cross-part move cannot start. The server requires the same (F21, `reorder` 74 to 79: a reorder lists every file once, in its own part). Only the row's handle starts a drag (`cdkDragHandle`), so that the selects and the link do not start one. Source: unit line 20; F21.
- **Drag above the graph block (D8).** The body list's `cdkDropListSortPredicate` refuses any index below the number of graph-ordered body rows, which lead the body (`modules/compile-export.md` line 47; F13). The drop handler repeats the same refusal, because a stray event can bypass the predicate. The server would refuse such an order too (F21, `reorder` 82 to 93, `COMPILE_GRAPH_ORDERED_MOVE`).
- **Reorder request (D9).** Built from the current view: the three lists of paths, one per part (`front`, `body`, `back`), with the dragged path moved inside its own list by `moveItemInArray` (F43, line 1372). Sent as POST `{revision, front, body, back}` with the view's `revision` (F11, lines 62 to 67). Source: unit line 20; CEX-03 unit line 18.
- **Status and part writes (D10).** POST `{revision, path, status}` and POST `{revision, path, part}` (F11, lines 70 to 81). The `revision` is the one the page holds from its last answer. Source: unit line 27; CEX-03 unit line 18.
- **Write answers (D11).** Each write answers with a `manuscriptViewSchema` body (F20). The page adopts that view at once (its rows and its `revision`), and then the `manuscript-updated` event refetches (D13). No write waits for the event. There is no in-flight lock: a second write sent before the first answers carries the old revision and gets the conflict prompt, which is the designed path (F21, `begin` 131 to 133).
- **Conflict (D12a).** A 409 with code `COMPILE_ORDER_CONFLICT` (F12) shows an alert with the server's own message (F21, lines 39 and 40) and a button `Reload manuscript`. The button reads the manuscript again. A successful read clears the alert. Any other failure shows the `ApiError` message, or `The request failed.` when the error is not an `ApiError` (the files page does the same, F38, lines 115 to 117). Source: unit lines 20 and 26.
- **Refetch triggers (D13).** (a) `manuscript-updated` from `compile-export` whose `data.projectId` equals the route's project id (F10; unit line 21). (b) `files-changed` from `project-store` whose `data.projectId` equals the route's project id and whose `paths` include `project.yaml`, `drafts` or a path under `drafts/` (F16; unit line 21). Only the filter is applied; the refetch is the same GET. These two are the only triggers: the page does not subscribe to the Shell's reconcile tick (`reconcile$`, F29), because the unit does not name it and no criterion needs it (section 8, open point 2).
- **Phone is read-only (D14).** `editable` is true when `DeviceClassService.deviceClass()` is `tablet` or `desktop` (F24). When it is false, the drag lists and the row handles are disabled, both selects are disabled, and the drop and change handlers return without a request. Downloads (CEX-18) and open-file links are not affected. Source: unit line 22 and criterion 4 (line 28); `modules/shell.md` line 70 (the device-class gate).
- **Project id (D15).** The page reads its project id from `ActiveProjectSignal` (F30), as the files page does (F38, line 274). The server's active project is the one the guard checked (F31). Source: `modules/shell.md` line 80.

### 1b. Planner's choices (the simplest option the sources allow)

- **P1 Files.** One entry file, one page file, one copies file and two spec files (section 3). The page is a single standalone component `ManuscriptPage` in `manuscript-page.ts`. No Shell file changes.
- **P2 Entry file.** `compile-export.routes.ts` exports `manuscriptRoutes`, with one child at `''` (`pathMatch: 'full'`) whose `loadComponent` imports `./manuscript-page`, as the graph-runner and files routes do (F37). The lint rule admits this file as an entry (F35).
- **P3 Contract use.** The page imports the contract only as types, through the Shell's barrel for Shell values (F27). The contract's runtime values the page needs are copied by hand into `manuscript-contract.ts`, checked by a parity spec in Node (F44, F45, F39).
- **P4 Test seam for the route.** The criterion tests render `provideRouter([{ path: 'projects/:projectId/manuscript', children: manuscriptRoutes }])`, as the files-page spec does (F40), with no active-project guard, so they need no `ACTIVE_PROJECT_ROUTE` answer. Only T1, which renders `App` with `APP_ROUTES`, answers `GET /api/project-store/active` (F46; F41).
- **P5 Drag seam.** A drag is simulated by emitting `dropped` on the part's `CdkDropList`, found through the debug node of its `ul[data-part]` (F42). The pointer gesture itself is not tested (F42, the `canvas-page.spec.ts` comment at lines 1228 to 1231).
- **P6 Fixtures.** Revisions are `sha256:` followed by 64 hex digits (F15); the fixtures use `'1'.repeat(64)`, `'2'.repeat(64)` and `'3'.repeat(64)` after the prefix.
- **P7 Events are filtered by project.** A `manuscript-updated` or `files-changed` event for another project does not refetch (D13).
- **P8 Reads never break the stream.** Each GET is wrapped so that a failed read ends only that read, not the subscription that triggers the reads (a `Subject` piped to `switchMap`).
- **P9 Native selects.** The status and part controls are native `select` elements. They are simpler than Material's form fields, and the tests drive them through `change` events.
- **P10 Duplicates.** A write response replaces the view, and the event that follows refetches the same revision. The double read is accepted (D11).
- **P11 Tests.** New specs use the explicit `WAIT` timeout of the shell's SHL-22 rule (`modules/shell.md` line 15), as `graph-list-page.spec.ts` does (F41).
- **P12 Breakpoints.** The device class comes from the Shell's `DeviceClassService` (F24). The tests set the width with `stubMatchMedia` (F33): 1280 by 800 for tablet and desktop, 390 by 844 for phone (F40, line 236).
- **P13 Tick ownership.** The unit's criteria boxes are ticked by the orchestrator at merge, not by the implementer (as the CEX-06 plan records, its lines 103 and 125). The implementer edits no unit file.
- **P14 Phone nav width (open point 3).** The plan adds no 390 px fit test for the bottom nav. No criterion of CEX-17 asks for it; the shell's settled decisions fix the nav's form by device class from route `data` (SHL-05 Decisions line 21; `modules/shell.md` lines 52 and 66, which make Manuscript a phone nav item), and no criterion of SHL-05 or SHL-20 measures the nav's width (SHL-20 covers the toolbar). The Manuscript row with "Nav: yes" and "Min. class: phone" is a settled Shell decision, so the tenth phone item is required whatever its fit; the nav's layout is a Shell file (`shell/app-nav.ts`), which CEX-17 does not change (P1). T1 checks that the item is present on a phone.
- **P15 Page layout for CEX-18 and CEX-19 (open point 4).** The template of `ManuscriptPage` has this order, top to bottom: the heading `Manuscript`; the alert (D12a); the totals line, the order-source line and the warnings list (D4); then the three part sections Front matter, Body and Back matter (D2), the Back matter section last. CEX-17 adds no placeholder and no input for later panels. The page's state is private; a later panel reads its own data through its own requests and events, and a manuscript change that it causes reaches the outline through `manuscript-updated` or `files-changed` (D13). So that the three units' edits to `manuscript-page.ts` are compatible in either merge order of CEX-18 and CEX-19, the plan records where each adds its panel, as a standalone component in its own file: CEX-18 (preflight, export and settings panels) inserts its element(s) between the warnings list and the Front matter section, and CEX-19 (snapshots panel) after the Back matter section. The three outline sections lie between the two insertion points, so the template hunks do not touch. Each adds one `import` statement for its own file; the `imports` array of the `@Component` decorator is one line that both change, and the second unit to merge resolves that line by keeping both names. Neither panel changes a line that CEX-17 writes elsewhere, so the merged page is the same in either order. This is a record for the planners of CEX-18 and CEX-19, not a change of their units.
