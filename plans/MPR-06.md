### 1b. Decisions this plan makes

- **D1 Layout.** `providers.controller.ts` (new) holds the HTTP handlers. `providers.service.ts` (new) holds `ProvidersService`: the commands, the reads, the read view and the effective-model mapping. `providers.registry.ts` (edit) gains two methods: `find(id)`, which returns the config or throws NOT_FOUND through `indexOf`, and `setKeyRef(id, keyRef)`, which sets the reference or removes it in one write through `save`. Reason: the registry owns every write of the section (`providers.registry.ts` lines 16 and 17); secrets are written only through `SecretsStore`. `providers.module.ts` lists the controller and the service; its exports do not change.

- **D2 Routes and statuses.** Eleven method and route pairs, all using the contract constants:

  | Route constant | Method | Input | Calls | Status and body |
  |---|---|---|---|---|
  | `PROVIDERS_ROUTE` | GET | none | `registry.list`, read view each | 200 `{providers}` |
  | `PROVIDERS_ROUTE` | POST | `providerCreateSchema` | `registry.create` | 201 read view |
  | `PRESETS_ROUTE` | GET | none | `PROVIDER_PRESETS` | 200 `{presets}` |
  | `APP_DEFAULT_ROUTE` | GET | none | `registry.appDefault` | 200 `{appDefault}` |
  | `APP_DEFAULT_ROUTE` | POST | `modelChoiceSchema` | `registry.setAppDefault` | 200 `{appDefault}` |
  | `PROVIDER_UPDATE_ROUTE` | POST | `providerUpdateSchema` | `registry.update` | 200 read view |
  | `PROVIDER_DELETE_ROUTE` | POST | none | `registry.delete`, then `secrets.delete` | 204, no body |
  | `MODELS_ROUTE` | GET | none | `ModelResolver.modelList` | 200 `{models}` |
  | `KEY_SET_ROUTE` | POST | `keySetRequestSchema` | `find`, `secrets.put`, `setKeyRef` | 200 read view |
  | `KEY_CLEAR_ROUTE` | POST | `keyClearRequestSchema` | `find`, `setKeyRef`, `secrets.delete` | 200 read view |
  | `EFFECTIVE_MODEL_ROUTE` | GET | `effectiveModelQuerySchema` (query) | `ModelResolver.resolve` | 200 `effectiveModelSchema` |

  Not in this unit: `CONNECTION_TEST_ROUTE` (MPR-07), `PROJECT_MODEL_ROUTE` and `PROJECT_MODEL_CLEAR_ROUTE` (MPR-12). Status codes are explicit on every route: `@HttpCode(201)` on create, `@HttpCode(200)` on the other POSTs (Nest's POST default is 201), `@HttpCode(204)` on delete. Reason: SD11 and SD18 (`plans/MPR-01.md` lines 72 to 86 and 127 to 133).

- **D3 Pipes.** Bodies go through `@Body(new ZodValidationPipe(schema))` with the contract schemas in the table above; the query goes through the same pipe. Path ids are not validated: an unknown id is a 404 from the registry. Source: unit line 15; `apps/api/src/modules/platform/errors/zod-validation.pipe.ts` lines 5 to 10; `platform.module.ts` line 17 (the pipe is exported from the entry file).

- **D4 Read view.** `toRead(config)` returns the stored config (its `keyRef` included, since SD5 keeps it as an opaque reference), plus `keySet` and, only when defined, `keyHint`. `keySet` is true when `keyRef` is present and `SecretsStore.has(keyRef)` is true. `keyHint` is `SecretsStore.hint(keyRef)` only when `keySet` is true; it is absent for four or fewer characters (DECISIONS line 1880). The secrets file is read on each call; there is no cache (MPR-03 D5, `plans/MPR-03.md` line 35; `apps/api/src/modules/providers/secrets/secrets-store.ts` line 26).

- **D5 keyRef.** When a key is set on a provider without a `keyRef`, the service mints `key-` followed by `randomUUID()` from `node:crypto` (no new dependency). The reference is kept until the key is cleared (D7) or the provider is deleted (D8), and is reused when the key is replaced. Reason: `keyRef` is opaque (MPR-03), and it is not derived from the provider id, which can be freed and reused (open point 1). The `openrouter-1` in `packages/contracts/src/providers/examples.ts` line 44 is illustrative data, not a format.

- **D6 Set key.** (1) `find(providerId)`: an unknown id is 404 with no write. (2) Use the provider's `keyRef`, or mint one when it has none. (3) `secrets.put(keyRef, key)`. (4) If a reference was minted, `registry.setKeyRef(providerId, keyRef)`. (5) 200 with the read view. Reason: the secret is written before the settings reference names it.

- **D7 Clear key.** (1) `find(providerId)`. (2) With no `keyRef`, answer 200 with the read view and write nothing; the call is idempotent. (3) `registry.setKeyRef(id, undefined)`, which removes the property rather than writing `keyRef: undefined`. (4) `secrets.delete(oldKeyRef)`. (5) 200 with the read view, `keySet` false. Reason: the reference goes first, so no provider names a key being removed. If step 4 fails, an unreferenced entry stays on disk and the request answers 500.

- **D8 Delete.** (1) `registry.delete(id)`: an unknown id is 404 and the app default's provider is 409, both before any write (`providers.registry.ts` lines 59 to 68). (2) If the removed config had a `keyRef`, `secrets.delete(keyRef)`. (3) 204. Reason: the refusal keeps the key, and the secret is deleted only after the config is gone.

- **D9 App default.** GET returns `{appDefault: registry.appDefault()}`. POST takes a `ModelChoice` and calls `registry.setAppDefault(choice)`: an unknown provider is 404 `PROVIDER_NOT_FOUND` from `indexOf` with no write. The 200 reply reads the value back from the registry. No route clears the default (`plans/MPR-02.md` line 154).

- **D10 Create and update.** Create calls `registry.create(body)` and answers 201 with the read view (`keySet` false, no hint). Update calls `registry.update(id, body)` and answers 200 with the read view. The service applies no defaults (SD2). Extra body fields (`key`, `keySet`, `keyRef`, `id`) are removed by the zod parse, because the schemas are not strict (ASSUMED, see section 8; tested by E3). The registry keeps `keyRef` on update (`providers.registry.ts` lines 46 to 51).

- **D11 Model list.** `ModelResolver.modelList(id)` answers `{models}` with 200. An unknown id is 404 `PROVIDER_NOT_FOUND` (MPR-05 D10). An empty list answers `{models: []}` with 200: the empty-list error belongs to `resolve` (MPR-05 section 3a, step 6), not to this route.

- **D12 Effective model.** `ModelResolver.resolve({projectId})`, with `projectId` from the query or absent. The response is built field by field: `{choice: {providerId: config.id, model}, source, contextSize}`, plus `warning` only when it is defined. The resolved object is never spread, because it carries `key`. `projectId` is not checked against a project: the Project store is not on main (`apps/api/src/modules` holds `platform`, `providers` and `setup-auth` only), so an unknown project id gets the app default (MPR-05 D7). MPR-12 owns project checks.

- **D13 Presets and reads.** GET presets answers `{presets: PROVIDER_PRESETS}` from the contract constant (`defaults.ts` lines 34 to 66). Both GET routes write nothing.

- **D14 Errors.** No new codes and no new statuses. Registry and resolver errors reach the filter as `ModuleError` and pass through unchanged (`platform-exception.filter.ts` lines 43 to 51). A body that fails its schema is a `ZodError`, which the filter maps to 400 `PLATFORM_VALIDATION_FAILED` with the zod issues as `details` (filter lines 52 to 60; `packages/contracts/src/platform/errors.ts` lines 37 and 45). No handler puts a key into a message.

- **D15 Synchronous writes.** Every write path calls only synchronous methods (the registry and the `SecretsStore` methods are plain functions over `readFileSync` and `writeFileSync`), so a request reads and writes without an `await` between them. The reason is the one at `providers.registry.ts` lines 16 and 17. Only GET models and GET effective-model await, and neither writes.

- **D16 Guard and sweep.** No handler is `@Public()`, so every route sits behind the global guard. The invariant sweep builds its requests from the composed app's router and fails by name on a `:` template with no entry (`apps/api/test/invariant-sweep.ts` lines 134 to 144). Three entries are added to `FIXTURE_PATHS` (lines 71 to 74), each with the id `no-such-provider`, so the sweep never reaches a stored provider: `/api/providers/no-such-provider/update`, `/api/providers/no-such-provider/delete`, `/api/providers/no-such-provider/models`. The GET effective-model route has no `:`, so the sweep reaches it with the seeded `ollama` provider. `planGetHead` sends a GET and a HEAD to each template (`apps/api/test/invariant-sweep.ts` lines 398 and 399), so there are two resolutions per sweep, six in the file (`apps/api/test/invariant-get-head.test.ts` calls `sweepGetHead` three times, at lines 77, 101 and 137). Each makes a listing request to `ollama`. Cost per sweep: 18 requests, about 3.6 s of EVENT_WAIT_MS, and two resolutions that can hit the 1 s cap, about 5.6 s in all; the file's three sweeps cost about 16.8 s. PROVIDER_UNREACHABLE is retryable (`apps/api/src/modules/providers/client/errors.ts` line 145), so each resolution makes up to retries + 1 attempts. `retries` is 2 (`packages/contracts/src/providers/defaults.ts` line 9, applied to the seeded provider at `apps/api/src/modules/providers/providers.seeding.ts` line 68), so 3 attempts, with waits of 500 ms and 1000 ms (`apps/api/src/modules/providers/client/retry.ts` lines 3 to 9 for the waits and line 52 for `attempt <= retries`). No attempt writes. The sweep caps each reply at `RESPONSE_CAP_MS` (1000 ms, `invariant-sweep.ts` lines 94 and 177), so a resolution's retries cost the sweep at most that cap. Section 3, stop rule 2, sets the allowance for the file: 16.8 s.

- **D17 Test changes.** (a) `apps/api/test/providers.kit.ts` is deleted. Its comment (lines 11 and 12) says MPR-06 replaces it, and `plans/MPR-02.md` line 128 leaves its removal to MPR-06. (b) `apps/api/test/providers-create.test.ts` posts to `POST /api/providers` through `send`, through a local helper; its assertions (201 and the ids) stay. (c) `apps/api/test/providers-resolution.kit.ts` keeps the `resolve` route for C4 (DECISIONS line 1954) and loses the `models` route. (d) `apps/api/test/providers-resolution.test.ts`: every call of the resolve route except C4's now calls `GET /api/providers/effective-model`, and the assertions map `config.id` to `choice.providerId` and `model` to `choice.model`. `resolveBody` (`providers-resolution.test.ts` line 133) is repointed to effective-model and is used by MPR-05's C1 (line 156) and C2 (lines 180 and 198). The `source` assertions (lines 158, 182 and 200) and the `contextSize` assertion (line 159) stay. The file has no `warning` assertion and no no-key assertion (`warning` appears only in the `ResolveBody` interface, line 42), so neither is listed as kept; the no-key property is checked by E4 and C1 (d). E2 calls `GET /api/providers/<id>/models`. MPR-05's C4 (test at line 229) does not use `resolveBody`: it calls `getJson` with `RESOLVE_TEST_PATH?projectId=p-1` directly (`providers-resolution.kit.ts` line 8), because it needs `config` for `streamChat`, which the effective-model response does not carry. Reason: the real effective-model response has the `choice` shape (`model.ts` line 15 to 20), not the kit's `config` and `model` shape.

- **D18 Freed ids.** This unit keeps the registry's first-free-id rule (`providers.registry.ts` lines 122 to 128). Open point 1 explains the consequence.

- **D19 Stored shape.** MPR-06 changes no schema, no migration and no contract. Its only writes to `settings.yaml` go through `ProvidersRegistry.save` (`providers.registry.ts` lines 100 to 102). `keyRef` is already a stored field (`config.ts` line 17).
