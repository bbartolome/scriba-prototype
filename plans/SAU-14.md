### 1a. Settled by the unit, the module, the contracts and earlier plans

- **D1 Endpoints and shapes.** The step calls the Project store's own routes with the shapes the picker uses: list `GET /api/project-store/projects` (`packages/contracts/src/project-store/project.ts` lines 39 to 50); samples `GET /api/project-store/samples` (lines 82 to 88); New `POST …/projects/new` with `{title, folderName?, genrePack?}` (lines 53 to 57); Import `POST …/projects/import` with `{projectId}` (lines 60 to 62); Start from sample `POST …/projects/start-from-sample` with `{sampleId, folderName, title}` (lines 65 to 69); activation `POST /api/project-store/active` with `{projectId}` (lines 72 to 74), answered by `activeProjectSchema` (lines 77 to 79). Paths: `routes.ts` lines 5 to 12. Source: unit line 15; `apps/web/src/app/features/project-store/project-picker.ts` lines 268 to 289 (New), 296 to 315 (Start from sample), 317 to 325 (Import), 332 to 343 (activate).
- **D2 New carries the default genre pack.** The pack is the stored `defaultGenrePack` (`packages/contracts/src/setup-auth/settings.ts` lines 9 to 12, optional). It is sent as `genrePack` when it is not blank. When none is stored, `genrePack` is left out and the server applies `nonfiction` (`constants.ts` line 26; `project.ts` line 56). A blank value is not sent, because the schema refuses an empty `genrePack` (`min(1)`, `project.ts` line 56). Source: unit line 15.
- **D3 Create, start and import do not activate.** New and Start from sample answer the summary and leave the project inactive (`apps/api/src/modules/project-store/projects.service.ts` lines 64 to 97, the answer at line 96; `samples.service.ts` line 79, "The new project is not activated"; `samples.controller.ts` lines 13 and 14). Import answers the summary without activation (`projects.service.ts` lines 101 to 145). The picker activates after New and Start from sample (`project-picker.ts` lines 286 and 313) and not after Import (line 317). This plan follows the picker. Sources: `plans/PST-01.md` line 38 (D8); `plans/PST-05.md` line 25.
- **D4 Open is the activation.** Unit line 16 says "open (activate)". The activation is the POST of `ACTIVE_PROJECT_ROUTE` (`apps/api/src/modules/project-store/active-project.controller.ts` lines 26 to 32). Open is offered for a listed project with `status: 'ok'` that is not active. Import is offered only for `status: 'importable'`, because the server refuses `invalid` and `too-new` (`projects.service.ts` lines 111 to 130).
- **D5 Nothing is created on entry or on a re-run.** The step reads when it is shown and writes only when the author clicks a button. Source: unit line 16 ("creates nothing unless asked"; "Never re-creates anything"); `units/README.md` line 131 (reads are `GET` and never mutate); `modules/project-store.md` line 46.
- **D6 The step's rule for `firstProject`.** (a) An activation by this step (New, Start from sample, Open) that succeeds writes `firstProject: done` at once, because a project is then active (unit line 17). (b) The last step's Mark done is enabled only while a listed project is active (unit line 17). (c) Skip writes `skipped` (`plans/SAU-11.md` P2, lines 59 to 67). (d) Finish posts continue, as SAU-11 P2 says; the server then marks each step still pending as `skipped` (`apps/api/src/modules/setup-auth/setup-status.service.ts` lines 40 to 46 and line 72). Rule (d) is kept; see S9.
- **D7 Reads on entry, in a fixed order.** When the page enters the step, the step component reads with `forkJoin`, in this order: `GET PROJECTS_PATH`, `GET SAMPLES_PATH`, `GET PREFERENCES_ROUTE`. The page reads nothing at load. Source: the same rule as SAU-13 S4 and S5 (`plans/SAU-13.md` lines 32 and 33) and SAU-12 S3 and S6 (`plans/SAU-12.md` lines 27 and 30).
- **D8 The step owns its requests.** The body is a component with its own requests, as SAU-12's providers panel and SAU-13's `PreferencesStep` are (`plans/SAU-13.md` S5 and D11). The page writes step states only. Source: `plans/SAU-11.md` line 79 (P14: each step unit states its own rule and changes its own controls).
- **D9 Contract values.** A web feature imports another feature only through its entry file (`eslint.config.mjs` lines 50 to 68). The Project store's entry file, `apps/web/src/app/features/project-store/project-store.routes.ts`, exports routes and the nav only (lines 1 to 3 and 25). So the Project store's paths and readers are hand-written copies in this feature, as `features/project-store/project-store-contract.ts` (lines 10 to 12: the browser ships no runtime zod) does for its own feature. - **D10 Errors.** A 401 shows the sign-in notice, the two tailnet codes show their explanation, and any other error shows its message. This is the page's `fail()` (`setup-page.ts` lines 235 to 250). The step reports its errors to the page through an output. Source: `modules/setup-auth.md` line 42.

### 1b. Small decisions (taken here, the simplest option)

- **S1 Component and outputs.** `apps/web/src/app/features/setup-auth/first-project-step.ts`, class `FirstProjectStep`, selector `app-first-project-step`, no inputs. Outputs: `activeChanged` (`boolean`: some listed project is active), `activated` (`void`: an activation succeeded), `failed` (`unknown`). `StepBody` forwards them as `firstProjectActive`, `firstProjectActivated` and `firstProjectFailed`. The page handlers are `onFirstProjectActive(active)`, `onFirstProjectActivated()` and `onFirstProjectFailed(error)`.
- **S2 Markup.** No `<li>` element (the spec helper `stepItems` reads every `li` of the page, `setup-page.spec.ts` line 118), no heading, no `<form>`. Each button has a `(click)` handler. Each input and the select have a `name`: `newTitle`, `newFolder`, `sample`, `sampleTitle`, `sampleFolder`. Template references (`#newTitle` and so on) read the values at click time. Inputs and the select get `width: 100%` and `box-sizing: border-box`, so they fit 390 px.
- **S3 Template, in order.** (1) For each listed project, one `<div>` row with a `<p>`: the title, or the id if there is none, then `: ` and the status, then ` (active)` when the project is active, then its `error` in a second `<p>` when set. The row holds `Open` (status `ok`, not active), or `Import` (status `importable`), or nothing. When the list is empty: `<p>No project in the library yet.</p>`. (2) A New group: `<label>Title <input name="newTitle"></label>`, `<label>Folder name (optional) <input name="newFolder"></label>`, and the button `New project`. (3) A Start from sample group: `<label>Sample <select name="sample">` with one `<option [value]="id">` per sample (its title as text; the first option is selected by default), `<label>Title <input name="sampleTitle"></label>`, `<label>Folder name <input name="sampleFolder"></label>`, and the button `Start from sample`.
- **S4 No client validation.** Values are sent as typed, trimmed. A refusal of the server (an empty title, a folder name the disk refuses) reaches the page's alert line through `failed` (D10). The picker's own title check is not copied.
- **S5 Request bodies.** New: `{title}`, plus `folderName` only when the folder field is not blank, plus `genrePack` only when D2 gives one. Start from sample: `{sampleId, folderName, title}`, all three trimmed, `folderName` sent even when empty so the server's rule applies. Import: `{projectId}`. Open: `{projectId}`. The activation after a create: `{projectId: <summary id>}`.
- **S6 The chains.** New and Start from sample: POST create; then POST activation with the summary's id; then emit `activated`; then GET projects. If the activation fails: emit `failed`, then GET projects, so the new project shows (the picker does the same, `project-picker.ts` lines 328 to 331). If the create fails: emit `failed` and send nothing else. Open: POST activation; emit `activated`; GET projects. Failure: emit `failed`, nothing else. Import: POST import; GET projects. Failure: emit `failed`, nothing else. The step disables its buttons while a chain runs (its own `busy` signal).
- **S7 Reads.** Entry: the three GETs of D7. The answer sets the list, the samples and the stored genre pack (a plain field), and emits `activeChanged`. After an action: GET projects only, which sets the list and emits `activeChanged` again.
- **S8 Marking done in the page.** `onFirstProjectActivated()` calls `begin()`, then POSTs `{state: 'done'}` to `SETUP_STEP_ROUTE` with `firstProject` (`setupStatusSchema`, `takeUntilDestroyed`). On success it sets `status` and `busy` to false; on error it sets `busy` to false and calls `fail()`. It does not call `finish()`, so the page stays on the step. The helper: if SAU-13 is on the base, call its `postStep('done', () => undefined)` (`plans/SAU-13.md` step 7c). Otherwise add `private markFirstProjectDone()` with the same request. `writeState` is not changed by this unit. `onFirstProjectActive(active)` sets `hasActiveProject`, and the last step's Mark done gets `[disabled]="busy() || !hasActiveProject()"`.
- **S9 Finish keeps its rule (decided here).** Finish is SAU-11's "Finish" (P2): it posts continue, and the server marks each pending step `skipped`. So a re-run with an active project and a still-pending `firstProject` ends as `skipped` only if the author clicks Finish without Mark done. Mark done is the path for that case. The unit's text gives no other rule for Finish, and no criterion is changed by this decision. The reviser may check it against unit line 17 with the evidence of D6.
- **S10 Loader.** `setup-contract.ts`: the `Pick` of `loadSetupAuthContract` gains `'PREFERENCES_ROUTE'` and `'preferencesSchema'`, the same two lines as `plans/SAU-13.md` step 3. If they are already there, make no change. The header names the preferences route too.
- **S11 Copies.** `first-project-copy.ts` holds the six paths of D9 (`PROJECTS_PATH`, `SAMPLES_PATH`, `PROJECT_NEW_PATH`, `PROJECT_IMPORT_PATH`, `PROJECT_START_FROM_SAMPLE_PATH`, `ACTIVE_PROJECT_PATH`) and the four readers `projectListCopy`, `projectSummaryCopy`, `activeCopy` and `sampleListCopy`. Copy them from `features/project-store/project-store-contract.ts` lines 14 to 120 (the paths, the status list, the two checks, and the four readers), keeping the same checks. Types come only with `import type`. The picker's `issueLines` and `problemOf` are not copied.
- **S12 Spec layout.** `first-project-step.spec.ts` holds F1 to F5 and these helpers, copied from `setup-page.spec.ts`: `rootOf`, `buttonNamed` (line 106), `buttonTexts`, `paragraphs`, and `settle` (line 123, with `timeout: 5000`). Its `beforeEach` stubs the match media at 390 by 844 and its `afterEach` restores it (`shell/testing/match-media`), as `setup-page.spec.ts` does. `renderSetup` calls `TestBed.overrideComponent(StepBody, { remove: { imports: [ProvidersPanel] }, add: { imports: [ProvidersStub] } })`, with `ProvidersPanel` from `../providers/providers.routes` and `ProvidersStub` (selector `app-providers-panel`, empty template). This is the rule of SAU-12 and SAU-13, so the providers panel makes no request the test does not answer. Before the render it answers globally: `GET IDENTITY_ROUTE`, `GET SETUP_STATUS_ROUTE`, `GET PREFERENCES_ROUTE`, `GET PROJECTS_PATH` and `GET SAMPLES_PATH`. A test overrides any of them before its render.
- **S13 Request checks.** Bodies are checked with `toStrictEqual`. Requests are checked as a slice: `const from = doubles.api.requests.length` is taken right before a click, and the check reads `doubles.api.requests.slice(from)`. Any unit that adds a read on another step cannot change these checks.
- **S14 e2e.** `e2e/specs/setup-phone.e2e.ts` lines 252 to 254 (the assertion of `The first project is not set up yet.`) become a check that the button `Start from sample` is visible. Line 255 (`expectPhoneLayout`) and the rest of the file stay.
