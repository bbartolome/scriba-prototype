## 1. Decisions this plan follows

Settled by the unit, the module or merged decisions (source given):

- **D1** A CodeMirror 6 YAML editor built in this module, with `@codemirror/lang-yaml` and the lint extension. The browser parses no YAML. Source: unit TRG-14 line 15; unit TRG-15 line 18 ("no YAML parsing in the browser").
- **D2** Diagnostics come from save (422 `details.lint`) and from a debounced `POST /lint` while typing, shown on their lines. Source: unit line 16.
- **D3** An unreadable file opens from its `source` and `lint`, with `spec` and `views` null. Source: unit line 16; `plans/DECISIONS.md` 2026-11-14 (TRG-01 open point 2, line 3413). The API does this (`apps/api/src/modules/tool-registry/catalog.service.ts` `detailOf`, lines 398 to 416).
- **D4** For an invalid user copy of a built-in, the detail's editor reads `GET /api/tool-registry/tools/:name/user` (`TOOL_USER_ROUTE`). Source: unit line 16; `plans/DECISIONS.md` lines 3620 (TRG-01 open point 8) and 5047 to 5057 (Navigator's decision on TRG-13 open point 2, applied in `78a1678`).
- **D5** Built-ins open read-only, with **Customize** (an editable copy; save writes the user copy). **Revert to built-in** deletes the user copy. **Compare with built-in** is the Shell's read-only diff of the user copy against `GET …/builtin`. **New** starts from a blank template. **Duplicate** copies a tool. **Delete** removes a user-only tool. Source: unit line 17.
- **D6** A failed save keeps the previous version active. A save with warnings succeeds and shows them. Source: unit line 18; the API refuses lint errors before it writes (`catalog.service.ts` `save`, lines 260 to 283; `apps/api/test/tool-registry-save.test.ts` C2 at line 227).
- **D7** Preview stays the default tab of the detail's tab strip (TRG-13 plan C3, test L5 expects `Preview` selected). TRG-14 adds tabs to that strip. Source: `plans/TRG-13.md` section 5 (TRG-14 entry) and C3.
- **D8** The row rules of TRG-13 hold and are not changed: the switch rule (C4), the marker text (C7) and the detail for every row (C12). Source: `plans/TRG-13.md` C4, C7, C12.
- **D9** A phone has no detail, so it has no editor, and no `New`, `Duplicate`, `Customize`, `Revert` or `Delete` control. Source: `plans/TRG-13.md` C8; unit TRG-13 line 17 ("On the `phone` device class, only the list and toggles are reachable"), a settled decision of a done unit: `New` is neither the list nor a toggle. (Open point 3, settled by the reviser on this reading.)

Choices this plan makes (the simplest option; each one changes no criterion and no settled decision):

- **C1 Names.** Tabs `Source` and `Compare`. Buttons `Customize`, `Revert to built-in`, `Duplicate`, `Delete`, `New tool`.
- **C2 Routes read per row.** A built-in row reads `GET …/tools/:name/builtin`. A user row reads `GET …/tools/:name/user`. Each reads only when its tab or action is used, never on selection. The Source tab never reads `GET …/tools/:name`, because the TRG-05 e2e counts exactly that path (`e2e/specs/tools-preview.e2e.ts`, check (a)).
- **C3 Customize.** Offered on a built-in row only when the list has no user row of that name. Beside an invalid user copy the user row is the one to edit (its Source tab, its Revert). This avoids a Customize that would overwrite the invalid copy. (Open point 4, settled by the reviser: criterion 2 needs Customize only on a built-in with no user copy, and a valid user copy hides its built-in row, so this rule removes Customize from one case only, where Revert and the user row's editor already serve.)
- **C4 Revert and Delete.** Both call the delete route on a user row. Revert is offered when the row has `overrides`, Delete when it has none. Both ask `window.confirm` first.
- **C5 Names for New and Duplicate.** A name must match `TOOL_NAME_PATTERN` (copy of `packages/contracts/src/tool-registry/constants.ts` line 8) and must not be the name of any row in the list, built-in or user. A refused name shows `That name is in use.` or `A name is lower snake case, starting with a letter.` The reason: saving a built-in's name writes a copy of it, and saving a user name overwrites its file.
- **C6 Blank template.** `blankToolSource(name)` returns exactly the text in procedure step 4.
- **C7 Duplicate.** Offered on a valid row only (`row.valid`), because the copy of an invalid file is not valid starting YAML (criterion 4). Reads the row's own source when the name is confirmed (`/builtin` or `/user`), then sets the top-level `name:` line to the new name. No other line changes. The copy is the saved text, not unsaved edits.
- **C8 Drafts.** New and Duplicate open an unsaved draft editor in the detail. A draft is not a row of the list, so the detail shows while a draft is open even though `selectedList()` is empty. A draft has only the `Source` tab: no Preview, no Compare, and no tab of a sibling unit (TRG-16's Try tab included, if it is on main), because no tool exists yet. Save of a draft posts to the save route under its name.
- **C9 Selection after a command.** After a successful save of a copy that did not exist before (Customize, New, Duplicate), the selection moves to the user row of that name, and the `Source` tab stays selected; that row's Source tab then reads `/user` (C2). After Revert or Delete the selection is cleared. Selecting a row in the list resets the tab to `Preview` (D7). Without the first rule, TRG-13's rule ("a row that disappears closes the detail", `tools-list.ts` `selectedList`) would close the detail after Customize. The save message of C12 belongs to the editor, so after a move it is replaced by the new editor's diagnostics read from `/user` (warnings stay shown on their lines). The moved row's editor is a new editor, so its status line is empty: no `Saved.` message shows after a Customize, New or Duplicate save. A test of such a save therefore checks the save answer, the moved row's state and the written file, never the status message (T2a, T4b, T4d, E1). The status messages of C12 are tested on an editor that stays (T1a, T1b, E2).
- **C10 Lint while typing.** `linter` with `delay: 500`. The request is `POST /api/tool-registry/lint` with `{source, name}`, where `name` is the save name, so the file-name rule runs. On open, the diagnostics come from the detail's `lint`, and no lint request is sent until the first edit. A draft has no detail, so its first lint (the linter's run at start, after the delay) sends the request with the draft text. A failed lint request keeps the last diagnostics. `lintGutter()` shows the markers in the gutter.
- **C11 Placement.** A diagnostic at `line` marks its whole line: from the line start, to the line end or start + 1 when the line is empty, clamped to the document. The same diagnostics are written in a list under the editor (`line N: message`).
- **C12 Save feedback.** `Saved.` after a success with no warnings; `Saved. Warnings: N.` after a success with N warnings. `The tool was not saved. Lint errors: N.` after a 422, with the text kept in the editor as unsaved. Any other failure: `The tool could not be saved.` (The count form avoids a plural rule.)
- **C13 Unsaved text.** The editor registers with the Shell's `UnsavedTextRegistry` (`apps/web/src/app/shell/unsaved-text.ts`). It reports unsaved text when the text differs from the last saved text; a draft is unsaved from the start. Its `flush()` answers `false` (no auto-save), so leaving the route asks. The tools route gets `canDeactivate: [unsavedTextGuard]`, as `project-store.routes.ts` line 22 does. Selecting another row while the editor has unsaved text asks `window.confirm('Discard the unsaved text of <name>?')`.
- **C14 Compare.** `DiffView` with `path` = `<name>.yaml`, `base` = the built-in source, `proposed` = the user copy's source, `editable` left false. The built-in is the base, the copy is the proposed side.
- **C15 Commands reread the list.** Each successful save, delete and create reads the list again, as TRG-13's switch does (`plans/TRG-13.md` C5). A refused command reads nothing. This is the test in T1d.
- **C16 Output for TRG-15.** `app-tool-editor` emits `linted` (`{lint, views}`) after each lint answer and after each save answer. TRG-15 reads the views from it. The browser never parses the YAML.
- **C17 Test hooks.** The data attributes listed in step 6 are the only hooks the tests use.
