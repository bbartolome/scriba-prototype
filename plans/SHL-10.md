## 1. Decisions this plan follows

1. **One presentational standalone component with one required input.** `ToolCallCard` (selector `app-tool-call-card`) takes `call = input.required<ToolCallView>()` and nothing else. It injects no API client, no SSE client and no feature service. It injects two root Shell services: `DeviceClassService` (decision 4) and `ActiveProjectSignal` (decision 7). The host maps its events onto `ToolCallView` and passes a new object on each change. Source: unit lines 18 and 20 ("Presentational standalone component on a Shell-local view model"; "The Agent loop maps its stream events onto this model"). [FACT F2, F27] [DECISION]

2. **The view model: the unit's list plus one optional field.** The unit lists tool name; arguments (JSON, a key/value tree); status `pending | running | done | error`; output (Markdown or JSON); error text; sources used (project-relative paths); collapsed flag (line 18). The types, in `tool-call-view.ts`, with a TSDoc comment on each type and each field (criterion 3 says "documented inputs"):

   ```ts
   export type ToolCallStatus = 'pending' | 'running' | 'done' | 'error';
   export type ToolCallOutput =
     | { readonly kind: 'markdown'; readonly text: string }
     | { readonly kind: 'json'; readonly value: unknown };
   export interface ToolCallView {
     readonly name: string;
     readonly status: ToolCallStatus;
     readonly summary?: string; // one line, shown in the header (the addition, [OP 2])
     readonly arguments?: unknown; // JSON; absent while the model is still writing the call
     readonly output?: ToolCallOutput;
     readonly error?: string;
     readonly sources?: readonly string[]; // project-relative paths
     readonly collapsed?: boolean; // absent means "follow the device class" (decision 4)
   }
   ```

   `summary` is the only field the unit does not list. AGL-01's `tool-call-result` carries `summary` (`units/AGL-01-contract-slice.md` line 23), and the unit's "one-line summary" of a collapsed card (line 19) needs a line of text beyond the name and the status. It is optional and separable. Source: unit lines 18 and 19; AGL-01 unit line 23. [FACT F2, F13] [DECISION, OP 2]

3. **The Shell does not depend on `/agent-loop`.** No file of this unit imports `@bbartolome/scriba-contracts/agent-loop` or `zod`. The sample chat route of criterion 3 hand-writes the shapes of the four tool-call events as `unknown` `data`, following `plans/AGL-01.md` D3 to D7 (lines 39 to 43; that plan is approved) and the unit's lines 21 to 24, and labels them illustrative. Each event's `data` carries `runId` and a per-run `seq` (D3, D4). `sourcesUsed` is an array of entity ids, not paths (D6, line 42; `entityRefSchema` is `entityIdSchema`, `packages/contracts/src/project-store/entities.ts` lines 6 and 8). The card's `sources` are paths, so the sample maps ids to paths through a local table, with no HTTP, as the host must (`plans/AGL-01.md` line 141 leaves the id-to-path step to the card's host). The slice is not on `main` (`packages/contracts/src/agent-loop/index.ts` is `export {};`). The sample may import the type `SseEnvelope` from `/platform`, which the Shell consumes. Source: unit line 20; `modules/shell.md` line 43 ("It never consumes `/agent-loop` … shared components take Shell-local inputs"). [FACT F5, F13]

4. **Collapsed on phones, expanded elsewhere, from the device-class signal.** The default is a separate `computed`: `defaultCollapsed = computed(() => this.call().collapsed ?? this.deviceClass() === 'phone')`. An explicit `collapsed` wins in both directions. The card's state is `collapsed = linkedSignal({ source: this.defaultCollapsed, computation: (value) => value })`, the `source` form of `linkedSignal` (F27). The linked signal resets only when the computed's value changes (a rotation that changes the class, or the host changing the flag), not on each status update: a new view object does not change the boolean the computed returns. The shorthand `linkedSignal(() => this.call().collapsed ?? …)` would read `call()` directly, reset on every new view object, collapse an expanded phone card at each status update, and fail T4. A tap on the header toggles the state. Source: unit line 19 and criterion line 25; `plans/SHL-05.md` line 257 (the row "SHL-10 … `DeviceClassService.deviceClass` … exported from `shell/index.ts`"). [FACT F2, F8, F21, F27] [ASSUMED A1]

5. **Arguments and JSON output are one nested key/value tree.** Rows are `key: value` for a leaf and `key:` with nested rows for an object or an array (array rows are keyed by index). A string is shown as it is, any other leaf by `String(value)`. Top-level rows are at depth 0. A row at depth 7 or less whose value is an object or an array shows its children one level deeper (eight expanded levels, depths 0 to 7). A row at depth 8, the ninth level, whose value is an object or an array shows `…` as its value and no children, so a self-referencing value cannot loop. Source: unit line 18 ("arguments (JSON shown as a key/value tree)"; "output (… or JSON)"). [DECISION]

6. **Markdown output is plain text at code time; the unit that rebases second swaps in SHL-11's preview.** The unit says "Uses SHL-11's preview for Markdown output if available; otherwise plain text until SHL-11 lands (no blocking)" (line 21). Plain text is a `<div class="markdown-text">` with `white-space: pre-wrap` that shows the output's text as it is. The Navigator's rule (DECISIONS line 3102, option (a)): the unit that rebases second at `prompt.md` step 6 (lines 104 to 120) makes the swap. Step 6 takes the units one at a time in unit-id order (line 106), so SHL-10 normally reaches `main` first and SHL-11 makes the swap in its step R (`plans/SHL-11.md` lines 127 to 133). SHL-11 reaches `main` first when SHL-10 cannot complete step 6 in an iteration (a unit that cannot complete it does not stop the others, line 107), or when SHL-11's code is approved in an earlier iteration than SHL-10's (step 6 takes only units whose code approval holds, line 106). Then SHL-10 makes the swap in step R of section 3, which mirrors SHL-11's step R. At code time SHL-10 builds the plain-text block (step 1b, branch (b)) and does not wait for SHL-11; branch (a), the preview at code time, applies only if SHL-11's preview is already on `main` when SHL-10's branch is made. The swap has two edits, the same in either unit (`plans/SHL-11.md` lines 65 and 66): in the card, the plain-text block becomes `<app-markdown-preview [content]="…" />` bound to the output's text, and `MarkdownPreview` (from `./markdown-preview`) joins the card's `imports`; in the card spec, T3 changes to its branch (a) and its test bed gains only `provideMarkdown({ sanitize: { provide: SANITIZE, useValue: SecurityContext.HTML } })`. The card never imports `ngx-markdown` and never sets `innerHTML`: sanitising and front-matter hiding are SHL-11's. Source: unit line 21; `units/SHL-11-markdown-preview.md` lines 18 to 20 (the preview takes a Markdown string); DECISIONS lines 3100 to 3104; `prompt.md` lines 104 to 120; `plans/SHL-11.md` lines 42, 59 to 66, 127 to 133 and 210.
