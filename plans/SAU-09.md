### 1b. Small choices made by this plan (recorded here, not in DECISIONS)

- **D1 Shape unchanged, no migration.** The token-guard default already has the shape of the schema: `apps/api/src/modules/setup-auth/setup-auth.section.ts` lines 8 to 20 against `packages/contracts/src/setup-auth/settings.ts` lines 23 to 29. So the section stays at version 1 (`settings.ts` line 5) and `migrations: {}` (`setup-auth.section.ts` line 21) stays. Source: unit line 19 (the migration is conditional); `plans/SAU-02.md` line 134 reaches the same result.
- **D2 Step route.** `POST /api/setup-auth/steps/:step` (`SETUP_STEP_ROUTE`, `routes.ts` line 7). `:step` is parsed with `setupStepKeySchema` (`status.ts` line 14). The body is parsed with `stepUpdateSchema` (`status.ts` lines 41 to 43), which accepts only `done` and `skipped`. The step key is in the path, not in the body. Source: `plans/SAU-01.md` line 23.
- **D3 Access precedence.** `statusBody` (`setup-status.service.ts` line 21) forces `access: 'done'`. The change: a stored `access` that is not `pending` is shown as stored; a `pending` access is shown as `done`, because the caller is authenticated (`units/SAU-05-status-continue-api.md` line 15). This settles the open point that `plans/SAU-05.md` line 139 left to SAU-09. Reason: S1 and criterion 1 say that each step, access included, can be set `skipped`, so the status must show it. The API therefore accepts `access: skipped` and does not refuse it: refusing it would fail criterion 1 as written ("Each step"). The unit's Why line 15 ("Skip any step but the token") is a wizard rule, and SAU-11 line 15 already carries it ("Every step except Access can be skipped"), so the UI never sends it (section 5, SAU-11). Continue is unchanged: `continuedSteps` (line 29) writes `access: 'done'`, so after Continue a stored `skipped` access becomes `done`, because the caller is authenticated. The fresh-library and after-Continue results do not change (`apps/api/test/setup-auth-status.test.ts` lines 149 to 160 and 224; `apps/api/test/token-guard-gate.test.ts` lines 351 and 375).
- **D4 Complete is written only by Continue.** Step POSTs never write `complete`. Continue already exists: `SETUP_CONTINUE_ROUTE` (`routes.ts` line 5), `setup-status.controller.ts` lines 28 to 34, and `continueSetup` (`setup-status.service.ts` lines 48 to 53), which writes `complete: true` and marks the pending steps `skipped`. That is the "explicitly skips the remaining steps" of unit line 18. When every step is already `done` or `skipped`, Continue only sets `complete`, so it is also the "finishes" of unit line 18 (SAU-11 line 19 replaces the M1 Continue button with the wizard's completion, which calls this route). No new route is added. Criterion 1's "`complete` can be set" is met through it.
- **D5 Preferences endpoints.** `GET /api/setup-auth/preferences` and `POST` on the same path (`PREFERENCES_ROUTE`, `routes.ts` line 14). GET returns `Preferences` (`preferencesSchema`, `settings.ts` lines 9 to 12; type at line 31), or `{}` when nothing is stored. POST takes `preferencesSchema` as its body. The merge starts from the stored raw preferences object, overwrites the keys present in the body, and leaves every other key alone. The response is the merged `Preferences`.
- **D6 Empty string.** An empty string is a value: it is stored and returned as stored, by GET preferences and by the reader. It is the only way to clear a field, because a write never deletes a key (S6). CEX-04 must treat `''` as unset (open point 3).
- **D7 Response codes and errors.** Both POST routes answer 200 (`@HttpCode(200)`, as Continue does at `setup-status.controller.ts` line 30; Nest's default for POST is 201). The step POST returns the `SetupStatus` body, the same as GET status. An invalid `:step` or body gives 400 `PLATFORM_VALIDATION_FAILED`, through `ZodValidationPipe` (`apps/api/src/modules/platform/errors/zod-validation.pipe.ts` lines 5 to 11) and the ZodError branch of `platform-exception.filter.ts` (lines 52 to 58). No new error code is added.
- **D8 Reader.** `PreferencesReader` in `apps/api/src/modules/setup-auth/setup-preferences.reader.ts` (new) is `@Injectable()`. It has one method, `read(): Preferences`, which returns `SetupStatusService.preferences()`. It has no write method. `SetupAuthModule` provides and exports it, and `setup-auth.module.ts` re-exports it, because that file is the module entry. `eslint.config.mjs` line 40 defines entry files as `src/modules/*/*.module.ts`, and rule R1 at line 50 allows other modules to import only entry files. The re-export follows the `RequestIdentity` re-export (`setup-auth.module.ts` line 18).

The file I/O is synchronous (`settings.file.ts` line 1 imports the sync functions, line 25 reads, lines 53 and 54 write and rename), and the new methods contain no `await`. So two requests cannot interleave between the read and the write.
- **D10 Reads are side-effect free.** GET preferences and GET status only call `SettingsService.read` (`settings.service.ts` lines 58 to 62).
