### 1b. Small choices this plan makes (names, layout, order of checks)

- **P1 Files.** `graph-runner.module.ts` (the entry), `graph-runner.service.ts` (class `GraphRunnerService`), `graphs.controller.ts` (the six routes) and `graph-files.ts` (pure helpers). The first two names are the names PLT-09 uses for the module's target files: `scripts/boundaries.test.mjs` lines 15 to 23 and `plans/PLT-09.md` line 38. The controller is named for its prefix, as `files.controller.ts` is in the Project store.
- **P2 No active project.** `ProjectStoreService.activeId()` (`apps/api/src/modules/project-store/project-store.service.ts` line 51) gives the id. When it returns null, the service throws `ModuleError(PROJECT_ERROR_CODES.NO_ACTIVE, PROJECT_ERROR_STATUS.PROJECT_NO_ACTIVE, <fixed text>)`, the same code, status and meaning as `requireActive` (`project-store.service.ts` lines 83 to 98). The fixed text is written again in this module, because `ACTIVE_MESSAGES` is not exported. The same pattern is on main in `apps/api/src/modules/providers/providers.service.ts` lines 130 to 139. Store codes are passed through (decided, section 6 O3).
- **P3 Listing.** Only entries of kind `file` directly in `graphs/` whose name is `<stem>.json`, with a stem that matches `GRAPH_ID_PATTERN`, are graphs. Other names are ignored, because no graph id can address them. The service first lists the project root (`files.list(projectId, {path: '.'})`, not recursive). When the root has no entry `graphs` of kind `dir`, the graph list is empty and `graphs/` is not listed. Otherwise it lists `graphs`. Reason: the store's `list` answers `PROJECT_NOT_FOUND` both for a missing folder (`files.service.ts` lines 238 to 240) and for an active project whose folder is gone (`projectFor`, lines 512 to 519), so catching that code would hide the second case as an empty list. With the root listing first, a project error reaches the caller unchanged, and the `graphs` listing is called only for a folder that exists. Dot-entries are never listed by the store (`files.service.ts`, `collect`, line 568), and the store's temporary file `<target>.tmp` does not end in `.json` (`atomic-write.ts` line 8).
- **P4 Existence.** A graph exists when the listing of P3 has an entry `graphs/<id>.json` of kind `file`. Every operation on one graph (get, save, rename by name or by id, delete) first checks the id against `GRAPH_ID_PATTERN` (P5), then checks existence this way, and answers `GRAPH_NOT_FOUND` (404) when either fails, before any other store call. Get and rename-by-name then read the file with `files.read`; any store error of that read other than those P5 maps is passed through unchanged (only a race with a host delete can give `PROJECT_NOT_FOUND` there).
- **P5 Parse order.** For get, save, rename-by-name and each list row: JSON parse; then a numeric `schemaVersion` above 1 gives 409 `GRAPH_SCHEMA_VERSION_UNSUPPORTED` (for a list row, `valid` false); then the schema (`graphFileShapeSchema` for get, `graphFileSchema` for save, rename-by-name and list validity), failing with 422 `GRAPH_SCHEMA_INVALID`. A file the store refuses as not text (`PROJECT_NOT_TEXT`) or too large (`PROJECT_FILE_TOO_LARGE`) is not a graph: get answers 422 `GRAPH_SCHEMA_INVALID`, and a list row is invalid. A graph id that does not match `GRAPH_ID_PATTERN` is answered as not found.
- **P6 Id from a name (create).** `slugOf(name)` is the rule of `apps/api/src/modules/agent-loop/tools/output-routing.ts` lines 24 to 30: lower case, each run of characters outside `a-z0-9` becomes one `-`, trimmed, and `graph` when nothing is left. It is copied, not imported, because the boundaries rule R2 forbids the import. The rule is `plans/AGL-13.md` P10 (line 35). AGL-13 lines 108 and 117 say that GRR-02 must give the same id for the same name. AGL-13 line 108 also says both rules are recorded in `plans/DECISIONS.md`; the planner found no such entry (a grep of DECISIONS.md for `slug` and `suffix` finds no graph rule), so the rules are taken from AGL-13 P8 and P10 and from the code. If `graphs/<slug>.json` exists, the id is `<slug>-2`, `-3`, … (the first free one), as AGL-13 P8 gives for graphs (`plans/AGL-13.md` line 33; `withSuffix` at `output-routing.ts` lines 64 to 69). Test K1 pins `Ada Lovelace` to `ada-lovelace` and `!!!` to `graph`.
- **P7 Empty graph.** Create writes `{schemaVersion: 1, view, name, nodes: [], edges: []}` in that key order (GRR-01 plan section 2a), as canonical text (S11). The name must be non-empty (`graphCreateSchema`, `catalog.ts` line 36).
- **P8 Status codes.** Create answers 201, as `projects.controller.ts` line 30 does for a create. Every other POST answers 200, as `files.controller.ts` does (`@HttpCode(200)` at lines 60, 69, 78 and 87).
- **P9 Save body.** The save route takes `@Body() body: unknown`, with no `ZodValidationPipe`. A pipe would answer `PLATFORM_VALIDATION_FAILED` (400) before the handler, but unit line 27 requires `GRAPH_SCHEMA_INVALID`. The service runs `graphFileSchema.safeParse` itself. Create and rename bodies use `ZodValidationPipe` with the contract's schemas (`graphCreateSchema`, `graphRenameSchema`), as `files.controller.ts` line 63 does.
- **P10 Writes.** Save and rename-by-name write through `files.write(projectId, {path, content})` with no `baseHash`. Last write wins; conflicts with pending changes are the Project store's check on accept (S6). The content is the canonical text of the parsed value (S11). Save does not read the file on disk: a valid v1 body replaces the file whatever its on-disk `schemaVersion` (decided, section 6 O2). Rename-by-name reads the file first (P4), so P5 refuses it for a file on disk that is newer or invalid.
- **P11 Rename by id.** `files.move(projectId, {from, to})` (`files.service.ts` lines 357 to 397). The file is moved as it is and is not parsed, so an invalid or newer file can be renamed by id. A taken target gives `PROJECT_FILE_EXISTS` (409) (`files.service.ts` lines 370 to 372). That includes the same id, because the source exists. The rename-to-taken-id error is the one `plans/PST-07.md` line 164 hands to GRR-02.
- **P12 Delete.** `files.delete(projectId, {path})` (`files.service.ts` lines 328 to 353), with no `baseHash` and no parse. A newer or invalid file can be deleted.
- **P13 Seams for later units.** `GraphRunnerService` has two methods that are not HTTP: `readGraph(id)`, which returns the shape-parsed graph and raises the errors of get (used by GRR-04 and later units), and `issuesOf(graph)`, which returns `[]` here and is the one function GRR-03 replaces (S16). Get and save call `issuesOf`.
- **P14 Messages.** Every error text is a fixed string and echoes no input, as `FILE_MESSAGES` does (`files.service.ts` lines 49 to 65, "Fixed strings only").
- **P15 Providers.** The module exports nothing: no other module consumes it yet. GRR-04 adds its providers to the same module.
- **P16 Test literals.** The test writes its graph literals itself, in schema key order. It does not import `GRAPH_RUNNER_EXAMPLES` and does not name the examples folder, so the test-file scan of `scripts/examples-check/m1.mjs` (rules R1 and R2 at lines 28 to 32; scan at lines 201 to 222) passes. `plans/PST-12.md` D13 states the same rule.
