## 1. Decisions this plan follows

### 1a. Settled by the unit, the module, GRR-01 and the done plans

- **S1 Module shape.** One NestJS `@Module` at `apps/api/src/modules/graph-runner/`, registered with one import in the composition root. Source: unit line 18; module line 37; `apps/api/src/app.module.ts` lines 18 to 26 ("Each feature module adds one import here").
- **S2 Active project.** All routes act on the active project. Graph files are read and written only through the Project store's in-process file API (`read`, `list`, `write`, `delete`, `move`). Source: unit line 19; module line 40.
- **S3 Operations.** `/api/graph-runner/graphs`: list, get, create, save, rename, delete. Validate is GRR-03's and is not in this unit. Reads are GET, commands are POST, all behind the guard. Source: unit line 20; module line 41.
- **S4 Author saves.** A save is a direct write. It is refused only when the file fails the Zod schema (`GRAPH_SCHEMA_INVALID`, file unchanged). A semantically flawed recipe saves, with its issues in the response. Source: unit line 21.
- **S5 Newer files.** `schemaVersion` is checked before Zod parsing; a newer value gives `GRAPH_SCHEMA_VERSION_UNSUPPORTED`. v1 has no migrators; PST-23 adds them later. Source: unit line 22.
- **S6 No graph pending changes.** The module never creates a graph pending change; an author save racing one is handled by the Project store's three-way check on accept. Source: unit line 23; module line 38.
- **S7 Errors.** The `GRAPH_` codes and their statuses come from the contract: `packages/contracts/src/graph-runner/errors.ts` lines 5 to 16 (codes) and 38 to 49 (`GRAPH_ERROR_STATUS`). Source: module line 43; GRR-01 plan section 1.3 C12.
- **S8 Graph file.** `graphs/<id>.json`; the file stem is the graph id; the id is a lower-case slug (`GRAPH_ID_PATTERN`, `packages/contracts/src/graph-runner/constants.ts` line 22); `GRAPH_FOLDER` is `graphs` (constants.ts line 44). Source: GRR-01 unit line 17; module line 45.
- **S9 Contract shapes.** `graphFileSchema` (`graph.ts` line 183) refuses a duplicate node or edge id; `graphFileShapeSchema` (`graph.ts` line 174) is the same without that rule. Save, rename-by-name and list validity use `graphFileSchema`; get uses `graphFileShapeSchema`. Rename-by-id does not parse (P11). Source: GRR-01 plan C2 (section 1.3).
- **S10 Response shapes.** List `{graphs}` of rows `{id, name, view, nodeCount, mtime, valid}` (`catalog.ts` lines 11 to 25). A row for a file that cannot be read or fails the schema has `valid` false, `view` null, `nodeCount` null and `name` set to the stem (`catalog.ts` lines 9 to 10; GRR-01 plan C9). Get `{graph, issues}` (`catalog.ts` lines 28 to 32). Create and rename `{id}` (`catalog.ts` lines 49 to 52). Save returns `{issues}`. Delete has no body. Source: GRR-01 plan C9 and C10; unit line 28.
- **S11 Canonical text.** A written graph file is `JSON.stringify(value, null, 2) + '\n'` of the schema-parsed value, in schema key order. Source: GRR-01 plan C16 and its assumption A2 (section 1.4); GRR-10 unit line 25 (byte-equivalent JSON after a save without edits).
- **S12 Route constants.** The six operations use the constants of `packages/contracts/src/graph-runner/routes.ts` lines 5 to 14 (`GRAPHS_ROUTE`, `GRAPH_ROUTE`, `GRAPH_CREATE_ROUTE`, `GRAPH_SAVE_ROUTE`, `GRAPH_RENAME_ROUTE`, `GRAPH_DELETE_ROUTE`). Source: GRR-01 plan C11.
- **S13 Testing seam.** External behaviour only: HTTP responses and files on disk, through the composed app with a temp library and an active project. No model is involved, so no mock server. Unit tests never read `examples/`. Source: module lines 49 to 51 and 55; `units/README.md` line 139.
- **S14 Invariant sweeps.** A route template that contains `:` needs an entry in `FIXTURE_PATHS` in `apps/api/test/invariant-sweep.ts`, or the sweeps fail by name. The unit that adds a route adds its entry. Source: `invariant-sweep.ts` lines 4 to 5 and 71 to 72 (header and the `FIXTURE_PATHS` comment); `plans/PST-12.md` section 1a, D7; GRR-08 unit line 18 (the sweeps must pass for every `/api/graph-runner` route).
- **S15 Boundaries.** Modules import each other only through the entry file (`*.module.ts`), and `graph-runner` never imports `agent-loop`. Source: `eslint.config.mjs` line 50 (R1) and line 69 (R2).
- **S16 Validation is GRR-03's.** Get and save report validation issues "once GRR-03 lands". Source: unit line 20; GRR-03 unit line 18.

### 1b. Small choices this plan makes (names, layout, order of checks)

- **P1 Files.** `graph-runner.module.ts` (the entry), `graph-runner.service.ts` (class `GraphRunnerService`), `graphs.controller.ts` (the six routes) and `graph-files.ts` (pure helpers). The first two names are the names PLT-09 uses for the module's target files: `scripts/boundaries.test.mjs` lines 15 to 23 and `plans/PLT-09.md` line 38. The controller is named for its prefix, as `files.controller.ts` is in the Project store.
- **P2 No active project.** `ProjectStoreService.activeId()` (`apps/api/src/modules/project-store/project-store.service.ts` line 51) gives the id. When it returns null, the service throws `ModuleError(PROJECT_ERROR_CODES.NO_ACTIVE, PROJECT_ERROR_STATUS.PROJECT_NO_ACTIVE, <fixed text>)`, the same code, status and meaning as `requireActive` (`project-store.service.ts` lines 83 to 98). The fixed text is written again in this module, because `ACTIVE_MESSAGES` is not exported. Store codes are passed through: see open point O3.
- **P3 Listing.** Only entries of kind `file` directly in `graphs/` whose name is `<stem>.json`, with a stem that matches `GRAPH_ID_PATTERN`, are graphs. Other names are ignored, because no graph id can address them. A missing `graphs/` folder is an empty list: the Project store's `list` refuses a missing folder with `PROJECT_NOT_FOUND` (`files.service.ts` lines 238 to 240). Dot-entries are never listed by the store (`files.service.ts`, `collect`), and the store's temporary file `<target>.tmp` does not end in `.json` (`atomic-write.ts` line 8).
- **P4 Existence.** A graph exists when `files.list(projectId, {path: 'graphs'})` has an entry `graphs/<id>.json` of kind `file`. Save, rename and delete check existence this way and answer `GRAPH_NOT_FOUND` (404) when it does not hold. Get and rename-by-name read the file.
- **P5 Parse order.** For get, save, rename-by-name and each list row: JSON parse; then a numeric `schemaVersion` above 1 gives 409 `GRAPH_SCHEMA_VERSION_UNSUPPORTED` (for a list row, `valid` false); then the schema (`graphFileShapeSchema` for get, `graphFileSchema` for save, rename-by-name and list validity), failing with 422 `GRAPH_SCHEMA_INVALID`. A file the store refuses as not text (`PROJECT_NOT_TEXT`) or too large (`PROJECT_FILE_TOO_LARGE`) is not a graph: get answers 422 `GRAPH_SCHEMA_INVALID`, and a list row is invalid. A graph id that does not match `GRAPH_ID_PATTERN` is answered as not found.
- **P6 Id from a name (create).** `slugOf(name)` is the rule of `apps/api/src/modules/agent-loop/tools/output-routing.ts` lines 24 to 30: lower case, each run of characters outside `a-z0-9` becomes one `-`, trimmed, and `graph` when nothing is left. It is copied, not imported, because the boundaries rule R2 forbids the import. The rule is `plans/AGL-13.md` P10 (line 35). AGL-13 lines 108 and 117 say that GRR-02 must give the same id for the same name. AGL-13 line 108 also says both rules are recorded in `plans/DECISIONS.md`; the planner found no such entry (a grep of DECISIONS.md for `slug` and `suffix` finds no graph rule), so the rules are taken from AGL-13 P8 and P10 and from the code. If `graphs/<slug>.json` exists, the id is `<slug>-2`, `-3`, … (the first free one), as AGL-13 P8 gives for graphs (`plans/AGL-13.md` line 33; `withSuffix` at `output-routing.ts` lines 64 to 69). Test K1 pins `Ada Lovelace` to `ada-lovelace` and `!!!` to `graph`.
- **P7 Empty graph.** Create writes `{schemaVersion: 1, view, name, nodes: [], edges: []}` in that key order (GRR-01 plan section 2a), as canonical text (S11). The name must be non-empty (`graphCreateSchema`, `catalog.ts` line 36).
- **P8 Status codes.** Create answers 201, as `projects.controller.ts` line 30 does for a create. Every other POST answers 200, as `files.controller.ts` does (`@HttpCode(200)` at lines 60, 69, 78 and 87).
- **P9 Save body.** The save route takes `@Body() body: unknown`, with no `ZodValidationPipe`. A pipe would answer `PLATFORM_VALIDATION_FAILED` (400) before the handler, but unit line 27 requires `GRAPH_SCHEMA_INVALID`. The service runs `graphFileSchema.safeParse` itself. Create and rename bodies use `ZodValidationPipe` with the contract's schemas (`graphCreateSchema`, `graphRenameSchema`), as `files.controller.ts` line 63 does.
- **P10 Writes.** Save and rename-by-name write through `files.write(projectId, {path, content})` with no `baseHash`. Last write wins; conflicts with pending changes are the Project store's check on accept (S6). The content is the canonical text of the parsed value (S11).
- **P11 Rename by id.** `files.move(projectId, {from, to})` (`files.service.ts` lines 357 to 397). The file is moved as it is and is not parsed, so an invalid or newer file can be renamed by id. A taken target gives `PROJECT_FILE_EXISTS` (409) (`files.service.ts` lines 370 to 372). That includes the same id, because the source exists. The rename-to-taken-id error is the one `plans/PST-07.md` line 164 hands to GRR-02.
- **P12 Delete.** `files.delete(projectId, {path})` (`files.service.ts` lines 328 to 353), with no `baseHash` and no parse. A newer or invalid file can be deleted.
- **P13 Seams for later units.** `GraphRunnerService` has two methods that are not HTTP: `readGraph(id)`, which returns the shape-parsed graph and raises the errors of get (used by GRR-04 and later units), and `issuesOf(graph)`, which returns `[]` here and is the one function GRR-03 replaces (S16). Get and save call `issuesOf`.
- **P14 Messages.** Every error text is a fixed string and echoes no input, as `FILE_MESSAGES` does (`files.service.ts` lines 49 to 65, "Fixed strings only").
- **P15 Providers.** The module exports nothing: no other module consumes it yet. GRR-04 adds its providers to the same module.
- **P16 Test literals.** The test writes its graph literals itself, in schema key order. It does not import `GRAPH_RUNNER_EXAMPLES` and does not name the examples folder, so the test-file scan of `scripts/examples-check/m1.mjs` (rules R1 and R2 at lines 28 to 32; scan at lines 201 to 222) passes. `plans/PST-12.md` D13 states the same rule.
