Source: unit 23; plans/MPR-01.md line 58 (SD3); DEC 1837; DEC 1843 (D-a, D-b, D-c: lowercase first, then each run of characters other than a–z and 0–9 becomes one hyphen, and leading and trailing hyphens are trimmed).

### 1b. Small decisions made here (the unit and module do not settle them)

- **SD1 Layout.** Four files in `apps/api/src/modules/providers/`: `providers.module.ts` (the entry file), `providers.section.ts`, `providers.registry.ts`, `providers.seeding.ts`. This mirrors `setup-auth.module.ts` and `setup-auth.section.ts`. The slug function is a private helper in `providers.registry.ts`.
- **SD2 Registration.** Copy the setup-auth pattern (`setup-auth.module.ts` 20 and 26–34): a factory provider that injects `SettingsService` and calls `register(PROVIDERS_SECTION_DEF)`. `PROVIDERS_SECTION_DEF` is `{key: 'providers', version: PROVIDERS_SECTION_SCHEMA_VERSION, defaultValue: null, migrations: {}}`, typed `SettingsSectionDef`, imported as a type from `../platform/platform.module`.
- **SD3 Seeding hook.** `ProvidersSeeder` implements `OnApplicationBootstrap`. It must run after Platform's `SettingsService.onApplicationBootstrap`. Nest 12.4.2 runs the hooks deepest module first (see 7a, Nest entry). `PlatformModule` is imported by `ProvidersModule`, so it is deeper and runs first. The reverse order would break the first start. The seeder would write a file without a `setupAuth` section, and Platform would then see a changed existing file and write a `settings.yaml.bak-*` backup (`settings.service.ts` 90–93). Criterion 1 asserts that no backup exists, so a wrong order fails that test. That backup assertion is this plan's hook-order test (its choice); step 13(b) checks that it fails when the order is wrong.
- **SD4 Seeded section.** Built only from `PROVIDER_PRESETS` (the entry with id `ollama`; a missing entry is a programming error and throws) and `PROVIDER_DEFAULTS`. Validated with `providersSectionSchema.parse` before the write. Production code does not import `examples.ts`, because its header says it is "Example payloads for the contract tests and for fake API clients. Data only." (`examples.ts` 25). The tests use `PROVIDERS_EXAMPLES.seededSection` as an oracle.
- **SD5 Registry reads.** `list(): ProviderConfig[]`, `get(id): ProviderConfig | undefined`, and `appDefault(): ModelChoice | null`. They read the section through `SettingsService.read`, parse it with `providersSectionSchema`, and never write. If the section is absent, they answer from an empty in-memory section (`list: []`, `appDefault: null`). Boot refuses a section that breaks the schema (SD13), so the parse does not fail at runtime unless the file is edited while the app runs.
- **SD6 Registry writes.** `create`, `update`, `delete` and `setAppDefault` each read the section, compute the new section in memory, validate it with `providersSectionSchema.parse`, and call `SettingsService.write('providers', section)` once. The methods are synchronous, with no `await` between the read and the write, so two in-process writes cannot interleave.
- **SD7 Id rule.** The base is `presetId` when given, else the slug of `label`. The slug is `label.toLowerCase()`, then each run of characters outside `[a-z0-9]` becomes one `-`, then leading and trailing `-` are removed (DEC 1843, D-c). If the base is taken, the id is `base-2`, then `base-3`, and so on, taking the first free one. The `-N` form from 2 is the simplest choice and matches the id regex `^[a-z0-9][a-z0-9-]*$` (`config.ts` 8). Because the first free suffix is taken, a deleted provider's id can be given to a new provider (open point 5).
- **SD8 Stored config from a create body.** Drop `presetId` and `label`, add the id from SD7, keep the other fields as the body gives them (a preset only pre-fills in the UI; MPR-06 unit line 17). Validate with `providerConfigSchema.parse`.
- **SD9 Update.** `update(id, patch)` merges `patch` (a `ProviderUpdate`, `config.ts` 67) over the stored config. `id` and `keyRef` are kept, because neither is in the input schema (`config.ts` 21–24). Validate with `providerConfigSchema.parse`. An unknown id throws NOT_FOUND.
- **SD10 Delete rule.** `delete(id)` returns the removed config, so MPR-06 can delete its secret by `keyRef`. It throws DEFAULT_IN_USE (409) when `appDefault.providerId === id`. An unknown id throws NOT_FOUND. The rule lives in the registry so that every in-process caller gets it. MPR-06 maps the error and does not repeat the check.
- **SD11 Set app default.** `setAppDefault(choice: ModelChoice)`. There is no null argument. The `providerId` must be in the list, else NOT_FOUND (404). An empty `model` is allowed. The API never clears the default (coordinator decision, open point 3). The file shape of `appDefault` is `packages/contracts/src/providers/settings.ts` line 12 (`modelChoiceSchema.nullable()`), so a file may hold null, and reads accept it. `model.ts` 33–35 (`appDefaultSchema`) is the shape of the GET response only. Only a hand-edited file can hold null, and MPR-05 maps that to `PROVIDER_NOT_CONFIGURED`.
- **SD12 Errors.** Throw `ModuleError(code, status, message)` (`apps/api/src/modules/platform/errors/module-error.ts` 7–12), imported from `../platform/platform.module` (which exports it at line 16). Keys of `PROVIDER_ERROR_STATUS` are the code strings, so the status is `PROVIDER_ERROR_STATUS[PROVIDER_ERROR_CODES.NOT_FOUND]` (404), and likewise for DEFAULT_IN_USE (409).
- **SD13 Validation at startup.** `ProvidersSeeder` checks a present `providers` section with `providersSectionSchema.safeParse`. On failure it throws `BootError` (exported by `platform.module.ts` line 14) with the message `Cannot read <path>: section "providers" does not match its schema (<first issue path>: <issue message>).` `<path>` is `join(SCRIBA_BOOKS_DIR, '.scriba', 'settings.yaml')`, built from the injected `SCRIBA_ENV` (`platform.module.ts` line 13). This repeats the path rule of `settings.file.ts` 6–8 without importing it, because a module may import only the platform entry file. Nothing is written. `bootstrap.ts` 55–59 closes the app and rethrows, and `main.ts` 10–13 prints the message and exits 1. The message has the form of Platform's `cannotRead` (`settings.migrate.ts` 26). This decides open point 1 (DEC 1884). Accepted edge (MPR-02 coordinator entry, DEC line 1895, commit `76ce5fc`): "the file is left alone" holds when every default section is already present, which the extra test's fixture ensures. If a default section is missing (for example `setupAuth`), Platform's hook runs first, writes a backup and adds the missing default (`settings.service.ts` 90–95), and then the seeder refuses boot. In that case the file is changed by Platform, not by this unit; the `providers` section itself is still unchanged, and this unit does not roll Platform's write back.
- **SD14 Test seam for criterion 4.** No HTTP route exists until MPR-06, so the test needs a test-only controller. It lives in `apps/api/test/providers.kit.ts`, after the pattern of `settings.kit.ts` 22–57. The composed app does not include it. Only the two tests in `providers-create.test.ts` add `ProvidersKitModule` (criterion 4 and the extra label test, which calls `postCreate` too), through `createTestApp`'s `modules` option (`apps/api/test/create-test-app.ts` 13). It exposes `POST /api/providers-test/create`, parses the body inline with `providerCreateSchema.parse` (as `echo.controller.ts` 17–18 does), and returns the stored config with status 201. `ZodValidationPipe` is defined (`zod-validation.pipe.ts` 5–11), but no controller uses it.
- **SD15 Test requests.** Use the cookie and Origin of the invariant tests: `sessionCookie` from `apps/api/test/guard-request.ts` (line 80), host `127.0.0.1:8080` and origin `http://127.0.0.1:8080` (the constants in `invariant-sweep.ts` 38–39). The kit exports these and one helper, `postCreate`, so each test stays short.
- **SD16 Restart check.** "Stable" and "unchanged on a second start" are checked by a second `createTestApp` on the same library, comparing `settings.yaml` bytes and the backup list.
- **SD17 Imports.** `ProvidersModule` imports `PlatformModule` only, and exports `ProvidersRegistry`. `ProvidersSeeder` and the registration factory stay private.

## 5. Downstream agreement and parallel units

### MPR-05 (resolution and model list; blocked by MPR-02, MPR-03, MPR-04)

- Needs from MPR-02: `ProvidersRegistry.get(id)` for the stored config (baseURL, model, `contextSize`, timeout, retries, `keyRef`), and `appDefault()` for the app default. Both are reads and write nothing, so MPR-05 criterion 1 ("`settings.yaml` is unchanged") holds.
- On a fresh library the seeded app default is `{ollama, ''}`. The empty app-default model falls to the provider's own model, which for the seeded `ollama` is also empty, so resolution reaches `auto` (step four of MPR-05 line 19).
- `get` returns `undefined` for an unknown id. MPR-02 does not choose the error. MPR-05 decides whether that is `PROVIDER_NOT_FOUND` or `PROVIDER_NOT_CONFIGURED`.
- The schema does not check that ids are unique or that `appDefault` names a provider in the list. A hand-edited file with either still boots. Handling an app default whose provider is missing is MPR-02's requirement on MPR-05 (line 116 of this plan gives the `get` case). MPR-05 line 19 owns the order (project override, app default, provider's own model, first model listed) and `PROVIDER_NOT_CONFIGURED` when there is no app default and no override; it does not name the missing-provider case. The registry's `get`, `update` and `delete` act on the first entry with the id.
- MPR-05 must not write `settings.yaml`. Writes go through the registry (SD6).
