### 1b. Choices made by this plan

- **P1. Code layout.** The five new operations are methods of the existing `FilesService` (`files.service.ts`), which is already provided and exported by `project-store.module.ts` and re-exported from the entry file (module lines 18 to 22, 37 to 54). The module file does not change. `FilesController` gets two handlers, `delete` and `move`. No new source file.
- **P2. Delete and move act on the entry the path names.** When the path names a within-project link, `delete` removes the link and `move` renames the link. The link's target is not touched. The entry is `join(project.root, relativePath)`, and `lstat` on it shows the link. Reason: a delete must not remove a file the author did not name. The write rule of S16 is different on purpose. A moved relative link can dangle at its new place; this is accepted and tested only as "the target is unchanged" (section 6, point 8).
- **P3. Delete order.** (1) `projectFor`; (2) `resolvePath`; (3) `project.yaml` at the root gives `PROJECT_PATH_RESERVED` (P4); (4) a missing path or a folder gives `PROJECT_NOT_FOUND` with "No file was found at that path."; (5) with `baseHash`, a hash of the bytes that differs gives `PROJECT_WRITE_CONFLICT` (the bytes are read only when `baseHash` is given, so a file over 5 MiB can be deleted); (6) `unlinkSync` on the named entry, any other errno giving a plain `Error` with the errno only; (7) `files-changed` with `paths: [relativePath]`. Answer: HTTP 200 with no body (P6).
- **P4. `project.yaml` at the root is not deleted or moved.** `delete` of it, `move` from it and `move` onto it give `PROJECT_PATH_RESERVED` (400) with the existing `PATH_MESSAGES.RESERVED` text. Reason: the record of the project changes only through `updateProjectYaml`, `write` (validated), New and Import. A `move` onto it would otherwise create an unvalidated record. The unit is silent; the plan decides (N3).
- **P5. Move order.** (1) `projectFor`; (2) `resolvePath` for `from`, then for `to`; (3) either path being root `project.yaml` gives `PROJECT_PATH_RESERVED`; (4) `from` missing or not a file gives `PROJECT_NOT_FOUND`; (5) `to` existing, as a file or a folder, gives `PROJECT_FILE_EXISTS` with "A file or folder already exists at the new path."; (6) `mkdirSync(dirname(to.realPath), {recursive: true})`, where `ENOTDIR`, `EEXIST` or `EISDIR` gives `PROJECT_PATH_INVALID` with the existing `NOT_A_FILE` message; (7) `renameSync(join(root, from.relativePath), to.realPath)`, with the same errno mapping as step 6 and other errnos as plain errors; (8) `files-changed` with `paths: [from, to]`. Case-insensitive file systems are not special-cased (section 6, point 9).
- **P6. HTTP answers of delete and move.** HTTP 200 with no body. The contract has no response shape for either (only the request schemas exist), so this plan adds none; adding one would be an expansion of the contract, which this unit does not make.
- **P7. Patch of `updateProjectYaml`.** `patch` is `Record<string, unknown>`. A value of `null` or `undefined` removes the key; any other value sets it. This follows the JSON merge-patch convention (RFC 7396) and lets the kit send a removal as JSON. `set(key, undefined)` is not used, because it writes `key: null` (probe 5 in section 7).
- **P8. `updateProjectYaml` pipeline.** (1) `projectFor`; (2) `readFileAt` on the root `project.yaml` (missing gives `PROJECT_NOT_FOUND`, over the cap gives `PROJECT_FILE_TOO_LARGE`); (3) `decodeText` (`PROJECT_NOT_TEXT`); (4) too-new gives `PROJECT_SCHEMA_TOO_NEW`; (5) the text is parsed with `parseDocument`; a syntax error gives `PROJECT_INVALID` with the issues of `readYamlState(text)`; (6) the patch is applied in key order, `doc.delete(key)` for a removal and `doc.set(key, value)` otherwise; (7) `doc.toString({lineWidth: 0})`, then the framing of P9; (8) `commit(project, target, text)`, which runs the size cap, the schema check (`PROJECT_SCHEMA_TOO_NEW` or `PROJECT_INVALID` with `details`), the atomic write, `files-changed` and the answer `{path, hash, mtime}`. An invalid result is refused before any write.
- **P9. Framing the `yaml` writer does not keep.** After step 7 of P8, a BOM that the original text started with is put back in front, and when the original contains `\r\n`, every `\n` of the output becomes `\r\n`. Probe 6 shows the writer drops a BOM and turns CRLF into LF. A file with mixed line endings comes out all-CRLF (N2); H3 tests it. See the normalization note, P20.
- **P10. `appendLog` status rule.** `ProjectsService.find` gives the status of the folder. `ok` continues. `importable` gives `PROJECT_NOT_FOUND` with "That folder has no project.yaml yet. Import it first." (a new `FILE_MESSAGES` entry). `invalid` gives `PROJECT_INVALID` (422) with `PROJECT_MESSAGES.INVALID` and the issues as `details`, as `importProject` does (`projects.service.ts` lines 124 to 130). `too-new` gives `PROJECT_SCHEMA_TOO_NEW` (409) with `PROJECT_MESSAGES.TOO_NEW`. A folder not found at all gives `PROJECT_NOT_FOUND` with `PROJECT_MESSAGES.NOT_FOUND`. The unit does not give these codes; this is the shared status rule for `appendLog` and `propose` (N4). PST-15's plan must use the same codes and texts for `propose`.
- **P11. `appendLog` order and writing.** (1) the project status of P10; (2) the line: a `\r` or `\n` in it gives `PLATFORM_VALIDATION_FAILED` (400) with "A log line must be one line, with no line break in it."; (3) `resolvePath(root, path)`; (4) the canonical `relativePath` must start with `logs/` (`'logs'` alone fails), else `PROJECT_PATH_INVALID` with "A log line goes only to a file inside logs/."; this covers `logs/../x`, which the path function refuses first, and keeps `logs/./x`, which the function collapses; (5) when the folder `<root>/logs` exists, the real location of the target must lie inside `realpathSync(<root>/logs)`, which refuses a link that points out of `logs/`; (6) a target that is an existing folder gives `PROJECT_PATH_INVALID` (NOT_A_FILE); (7) `mkdirSync(dirname(realPath), {recursive: true})`; (8) `appendFileSync(realPath, line + "\n")`, prefixed by `"\n"` when the file is non-empty and its last byte is not `\n` (one byte is read with `openSync` and `readSync`); (9) nothing is published. Errnos of steps 7 and 8 map as P5 step 6 and otherwise give a plain error with the errno only.
- **P12. `stateDir` order and checks.** (1) `projectFor`; (2) `owner` must be in `MODULE_SLUGS`, else `PLATFORM_VALIDATION_FAILED` (400) with "The owner must be the slug of a module."; (3) when `<root>/.scriba` exists, its real path must equal `join(realpath(root), '.scriba')`, else `PROJECT_PATH_OUTSIDE` (400) with `PATH_MESSAGES.OUTSIDE`, before anything is created; (4) `mkdirSync(join(root, '.scriba', owner), {recursive: true})`; (5) the real path of that folder must equal `join(realpath(root), '.scriba', owner)`, else the same refusal; (6) the answer is `join(project.root, '.scriba', owner)`, not its real path, so the returned text matches the unit's form on macOS, where the temp folders sit behind a link. Errnos of step 4 give a plain error with the errno only.
- **P13. Helper messages.** Five new entries in `FILE_MESSAGES`: `EXISTS`, `NOT_A_PROJECT`, `LOG_PATH`, `LINE_BREAK`, `OWNER` (texts in P5, P10, P11 and P12). Every other refusal reuses an existing text.
- **P14. Kit routes.** `project-store-files.kit.ts` gets five routes on `FilesKitController` under `api/project-store-test` (no `:` in the template, so no `FIXTURE_PATHS` entry): `files/delete` (`{projectId, path, baseHash?}`), `files/move` (`{projectId, from, to}`), `files/update-yaml` (`{projectId, patch}`, passed as is, so `null` removes), `files/append-log` (`{projectId, path, line}`) and `files/state-dir` (`{projectId, owner}`, answering `{path}`). The kit also gets HTTP helpers `deleteFile` and `moveFile`.
- **P15. Test files.** Two new files (section 2). The kit module and the composed app are booted per test as PST-06 does. Test files export nothing, so the helper `filesChangedOf` of `project-store-files-write.test.ts` is copied, not imported (as PST-06 copies its helpers).
- **P16. Test names.** Names are letter and number. `D1`, `U1`, `L1` and `T1` are the four criteria, in unit order. `D2`, `D3`, `H1`, `H2` and `H3` are extra rules. They do not reuse PST-06's `X` and `W` names, so the two plans can be read together.
- **P17. Invariant entries.** Two `FIXTURE_PATHS` entries, for `/file/delete` and `/file/move`, added after the `file/edit` entry (`invariant-sweep.ts` lines 93 to 95). Without them the sweeps fail by name (lines 145 to 154), as PST-06 P19 explains.
- **P18. Order of checks in general.** Active check first (S2), then the path check (S3), then the object checks (existence, kind, targets), then the content checks (hash, schema, size), then the write, then the event. This is the order of PST-06.
- **P19. Commit practice.** A red commit of the tests, then the feature commit, as PST-06 and PST-08 did (`e9495e6`, `1ada6d8`, `b4da4bb`, `cf095e9`).
- **P20. Normalization note (N1, N2).** `updateProjectYaml` rewrites the whole `project.yaml` with the `yaml` writer (`doc.toString({lineWidth: 0})`) and the framing of P9. Byte-identity outside the changed key (criterion 2, unit line 29) holds for a file already in the writer's canonical layout: 2-space indentation, at most one blank line in a row, a blank line before a comment that ends the document, LF or CRLF endings used throughout, an optional BOM. A non-canonical input is normalized on write: a 4-space (or other) indentation is re-indented to 2 spaces, runs of blank lines collapse to one, a blank line is inserted before a comment that ends the document (probes 8 and 9), and a file with mixed LF and CRLF endings comes out all-CRLF (probe 11, test H3). Lines longer than 80 columns are kept on one line only because of `lineWidth: 0` (probe 7). A BOM is kept and CRLF endings are kept only because of P9 (probe 6). A removed key takes the comment lines directly above it, and the blank line before them (probe 4). These are accepted; no text splice is made.
