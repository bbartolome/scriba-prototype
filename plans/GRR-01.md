### 1.3 Small choices made by this plan (names, layout, shapes the unit leaves open)

- **C1 Names.** The names are in section 2. Each schema is named `<thing>Schema` and each type `z.infer` of it, as in the other slices.
- **C2 Uniqueness, two schemas.** `graphFileSchema` refuses a duplicate node id or edge id (D3, unit line 18). `graphFileShapeSchema` is the same schema without that rule. Save, the list's validity, and every other consumer (AGL-13, GNP-04, GNP-18, GRR-06, GRR-16, PLT-21, CEX-06) use `graphFileSchema`. The detail (GET) and the validate request use `graphFileShapeSchema`, so GRR-03 can report the `duplicate-id` error (GRR-03 line 20, last item; criterion line 27) on a graph that is open in the canvas. A save of a graph with a duplicate id is `GRAPH_SCHEMA_INVALID` (GRR-02 line 21: a save is refused only when the file fails the Zod schema, and `graphFileSchema` is that schema). GRR-02 and GRR-03 do not name the two schemas, and nothing in their text conflicts with this; their plans must use them as stated here (section 5).
- **C3 Paths.** A story or output path is `fileReferenceSchema` (a string). The schema does not refuse a path into `drafts/.versions/`, an unsafe or missing path, or a path in the wrong folder. Reason: unit line 19 states what a `path` means ("project-relative to a current file"); that a file exists and is current can only be checked against disk, and the project-store convention keeps path rules out of the contract (`files.ts` lines 4 and 5). The downstream units check exactly these cases on saved graphs, which they could not do if the schema refused them: GRR-03 line 22 (warnings: missing, unsafe, `drafts/.versions/`, entity path outside `entities/`), CEX-06 line 21 (scene or beat path missing, in a subfolder such as `.versions/`, or outside `drafts/`), PLT-21 line 17 (path exists). The meaning of line 19 is published word for word as the JSDoc of `storyNodeSchema`, and test E12 checks it in the built declaration.
- **C4 Ids.** The graph id uses the node-id pattern (D20: the graph id is the file stem, and the unit calls it a lower-case slug, line 17). The edge id is a non-empty string (the unit gives no pattern for edges, line 18).
- **C5 Port id.** `portIdSchema` is `^[a-z0-9][a-z0-9-]*\..+$`: a node id (no dot), the first dot, and a non-empty key. The key may contain dots, because the split is on the first dot (unit line 23).
- **C6 Free strings.** A tool name (`tool`) and an entity kind (`entityKind`) are non-empty strings. The unit lets this slice import port types from the Tool registry and nothing else (D1), so `TOOL_NAME_PATTERN` (`tool-registry/constants.ts` line 8) is not imported. GRR-03 reports an unknown tool (GRR-03 line 20).
- **C7 Params.** Input node `params` is required, because `type` and `label` are needed to run (D5). Output and tool `params` are optional (unit line 20 writes `params?`). Tool `params` is `z.record(z.string(), z.unknown())`, because the setting keys and the pinned-value shapes come from the tool spec, which this slice does not read; GRR-12 line 19 pins a chip into `params` and GRR-03 line 20 checks it.
- **C8 Labels.** `label` is a `z.string()` with no minimum (story nodes and input params). Graph `name` is `z.string().min(1)`.
- **C9 Unreadable files in the list.** A file that fails `graphFileSchema` (or has `schemaVersion` above 1) is still listed (GRR-02 line 28, "listed as invalid"). Its row has `valid: false`, `view: null`, `nodeCount: null`, and `name` set to the file stem. This follows TRG-01 option A (`plans/DECISIONS.md` lines 3409 to 3413).
- **C10 Envelopes the unit does not name.** `graphListSchema` is `{graphs}`. `graphDetailSchema` is `{graph, issues}` (GRR-02 line 20: get with validation issues). Save and validate return `{issues}` (GRR-02 line 21, issues in the response). Create and rename return `{id}`. Current run returns `{run: RunState | null}` (GRR-04 line 25: the active run or the most recent finished one; null before any run). Delete has no body. Start returns `{runId}`. Stop takes `{runId}` (unit line 26; GRR-05 line 19).
- **C11 Routes.** The paths are in section 2 (`routes.ts`), all under the two prefixes of module line 41. Commands are POST and reads are GET (module line 41). Validate is `POST /api/graph-runner/graphs/validate` (GRR-03 line 18, verbatim); start is `POST /api/graph-runner/runs` (GRR-04 line 18, verbatim). The `:id` segment is the graph id.
- **C12 HTTP statuses.** `GRAPH_RUN_NOT_FOUND` and `GRAPH_NOT_FOUND` are 404. `GRAPH_SCHEMA_VERSION_UNSUPPORTED`, `GRAPH_VIEW_NOT_RUNNABLE` and `GRAPH_RUN_ACTIVE` are 409 (state conflicts). `GRAPH_SCHEMA_INVALID`, `GRAPH_VALIDATION_FAILED`, `GRAPH_INPUT_MISSING`, `GRAPH_INPUT_INVALID` and `GRAPH_TARGET_INVALID` are 422. No code is 401. This mirrors `TOOL_ERROR_STATUS`, `PROJECT_ERROR_STATUS` and `AGENT_ERROR_STATUS` (section 1.2).
- **C13 Issue codes.** The unit says "issue codes" and names none. The plan names one code per rule of GRR-03 lines 20 to 22: 14 error codes and 8 warning codes. The names are kebab-case, like lint rule names. `illegal-node-kind` is a code (GRR-03 line 20, first item), although the union refuses a recipe kind in a story graph at parse: GRR-03 decides how it produces that issue (for example from the parse failure of the validate body); the contract only has to have the code, so GRR-03's criterion line 27 stays reachable.
- **C14 Run-log discriminator.** `type`, with the SSE member names: `run-started`, `node-status`, `tool-call`, `error`, `pending-change`, `run-ended`.
- **C15 Run-log content.** A file input in the log carries `hash` (`sha256:`) next to `ref` (GRR-04 line 22; GRR-07 line 18). The run-started entry records `target` (absent means the whole recipe, GRR-07's "scope").
- **C16 Examples.** The two example graphs are exported data, `GRAPH_RUNNER_EXAMPLES` (`{story, recipe}`) in `src/graph-runner/examples.ts`, typed `StoryGraph` and `RecipeGraph`, with keys written in schema order (2a). Reason: criterion 1 exports "everything above", which includes the example fixtures (unit line 32); GRR-10 line 25 loads "the contract's example story graph and recipe" from `apps/web`, which can only import the package through its `exports` map; and `setup-auth` and `providers` already publish their examples this way (section 1.2). The canonical text of an example is `JSON.stringify(value, null, 2) + '\n'`; the JSDoc of `GRAPH_RUNNER_EXAMPLES` states it, and C3 tests it. No JSON fixture file is written, so Prettier never touches the examples. Nothing reads `examples/` (module line 55).
- **C17 Run-end status.** `run-ended` takes the four run statuses, as the unit lists them (lines 27 and 29). `running` is accepted there and never sent.

### 2a. Shapes, with the key order that C3 depends on

Keys are listed in the order of the Zod object definition, which is also the order of the example literals. Every object is `z.strictObject` unless marked "object" (non-strict). Request bodies: save takes `graphFileSchema`; validate takes `graphFileShapeSchema`; create takes `graphCreateSchema`; rename takes `graphRenameSchema`; start takes `runStartRequestSchema`; stop takes `runStopRequestSchema`.

- `positionSchema`: `x`, `y` (`z.number()`).
- `storyNodeSchema`: discriminated on `kind` over three members `entity`, `scene`, `beat`. Keys: `id` (`nodeIdSchema`), `kind` (literal), `label` (`z.string()`), `path` (`fileReferenceSchema`, optional), `position` (`positionSchema`).
- `storyEdgeSchema`: `id` (`z.string().min(1)`), `from` and `to` (`nodeIdSchema`), `relation` (`z.string().min(1)`, optional).
- `recipeNodeSchema`: discriminated on `kind`:

  - `tool`: `id`, `kind`, `position`, `tool` (`z.string().min(1)`, required), `params` (`toolParamsSchema`, optional).
  - `output`: `id`, `kind`, `position`, `params` (`outputParamsSchema`, optional).
- `inputParamsSchema`: `type` (`portTypeSchema`), `label` (`z.string()`), `entityKind` (`z.string().min(1)`, optional).
- `outputParamsSchema`: `label` (`z.string()`, optional), `path` (`fileReferenceSchema`, optional).
- `toolParamsSchema`: `z.record(z.string(), z.unknown())`.
- `recipeWireSchema`: `id` (`z.string().min(1)`), `from` and `to` (`portIdSchema`). No `relation` key (strict).
- `storyGraphShapeSchema`: `schemaVersion` (`z.literal(GRAPH_SCHEMA_VERSION)`), `view` (`z.literal('story')`), `name` (`z.string().min(1)`), `nodes` (array of `storyNodeSchema`), `edges` (array of `storyEdgeSchema`).

- `outputNodeResultSchema` (object): `pendingChangeId` (non-empty string), `path` (`fileReferenceSchema`).
