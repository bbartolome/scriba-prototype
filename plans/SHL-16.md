# SHL-16 plan — editable merge view: the proposed side accepts edits and emits the edited text

Batch: [SHL-16] (Frontend shell, phase:editor, M3); batch of one. Revision 1, status draft (planner, 2026-11-16). Base: `main` at `8b7a5f2`. SHL-12 (code `a99f430`), SHL-13 (done mark `02eadc0`) and SHL-14 (`801a967`) are merged (`git merge-base --is-ancestor` holds for each). This plan changes only `plans/SHL-16.md`. Open point 1 blocks the line model of the editable side (step 3 and the emit line of step 4); the Navigator must settle it before the code stage.

## 1. Decisions this plan follows

- **D1. Extend `DiffView` in place.** `DiffView` (`apps/web/src/app/shell/diff-view.ts`) gains an `editable` input (default `false`) and a `contentChange` output. No new component and no new export. Source: unit line 20 ("an `editable` input"); `diff-view.ts` lines 63 to 66 ("SHL-16 adds an editable input here"); `units/SHL-12-readonly-diff.md` line 21.
- **D2. The read-only API and behaviour are unchanged.** The five SHL-12 inputs keep their names and types. With `editable` false the rendered DOM and the events are those of SHL-12. Source: unit line 22 ("Read-only mode is unchanged"); unit line 26; `units/SHL-12-readonly-diff.md` line 21.
- **D3. Only the proposed side is editable.** In the side-by-side layout that is the `b` editor (`.cm-merge-b`); in the unified layout it is the one editor, whose document is the proposed text. The base side keeps its SHL-12 extensions. Source: unit line 25 ("the proposed side accepts edits"); `diff-view.ts` lines 98, 111 and 112.
- **D4. The emitted text is the whole proposed text after each document change.** `contentChange` emits the full edited text on each update that changes the document, and only then. It emits nothing on creation and nothing while `editable` is false. The consumer sends it as accept `content`. Source: unit line 20 ("emits the edited text"); `units/PST-16-apply-three-way-check.md` lines 18 and 19 (accept `{content?}`, with edited `content` from the Shell's merge view); `units/PST-01-contract-slice.md` line 44. Settled here: the name `contentChange` (as the editor's output, `markdown-editor.ts` line 115) and the emit-on-change rule.
- **D5. Read-only facets are not stacked.** `EditorState.readOnly` and `EditorView.editable` take the first value of their facet (`@codemirror/state` lines 2052 and 2053; `@codemirror/view` line 1411). So the editable proposed side leaves out the two read-only extensions of `diff-view.ts` lines 72 and 73. It does not add `readOnly.of(false)` on top. Source: facts F18 and F19 (section 7a).
- **D6. The editable side has an accessible name.** The proposed content element gets `aria-label` `Proposed text for <path>` through `EditorView.contentAttributes`, only when `editable` is true. Read-only sides get no label (D2). Source: `plans/DECISIONS.md` line 3322 (the content element has no accessible name; advice); `units/SHL-19-polish-gate.md` line 21 (axe pass). Settled here: the text.
- **D7. Rebuild on input change; the component never writes back.** The effect (`diff-view.ts` lines 202 to 213) also reads `editable()` and `path()`, so a change of either rebuilds the view. `proposed` stays the consumer's input: the component does not feed its edits back into it. An edit reaches the consumer only through `contentChange`. Source: the rebuild rule of `diff-view.ts` lines 202 to 213 (layout and inputs). Settled here.
- **D8. Read-only mode keeps SHL-12's line model.** Both sides are built by `toText` (`diff-view.ts` lines 78 to 85, split on `\n` only), and the facet is `\n` (line 71). Source: unit line 22; `plans/SHL-12.md` line 65 (SHL-12 decision 5, exact text).
- **D9. The editable side's line model is NOT settled (open point 1).** `plans/DECISIONS.md` line 3628 (SHL-13 open point 3, approved) says the editable proposed side takes the dominant-rule facet of SHL-13 (`markdown-document.ts` lines 10 to 20) and the diff keeps SHL-12's LF-only split. Probe F22 shows that one document cannot have both. Steps and tests that depend on it are marked [N1].
- **D10. No package, lockfile, barrel or SHL-13 file changes.** `@codemirror/merge` 6.12.3, `@codemirror/state` 6.7.6 and `@codemirror/view` 6.43.15 are already listed in `apps/web/package.json` (F17). `DiffView` is already exported (`shell/index.ts` line 13). `markdown-document.ts` is imported and not edited. Source: F14, F17.
- **D11. Test seam.** The rendered `DiffView` in a host component under Angular's Vitest runner (jsdom), as `diff-view.spec.ts` does (imports lines 1 to 6, host lines 21 to 27, `LAYOUTS` lines 36 to 39). Edits go through `EditorView.findFromDOM` and `dispatch`, not through typing. Source: `plans/DECISIONS.md` line 3630 (the Navigator approved this seam for SHL-13 open point 7); `modules/shell.md` lines 92 and 93 (external behaviour, rendered routes). Reused here by the same reason; not a new decision.
- **D12. Layout of the tests.** The SHL-12 spec file is not changed (criterion 2 says its tests still pass). The new tests go in a new file, `diff-view-editable.spec.ts`. Settled here.
- **D13. Identical text keeps SHL-12's rule.** When base and proposed are equal, the component shows "No changes" and creates no editor, also when `editable` is true (`diff-view.ts` lines 144 and 145, 189 to 191; `plans/SHL-12.md` line 67, SHL-12 decision 6). This limits editing and is open point 3.

## 6. Open points

1. **[NAVIGATOR; blocks step 3 and the emit line of step 4] The line model of the editable proposed side.** `plans/DECISIONS.md` line 3628 says: the editable proposed side takes the dominant-rule facet, and the diff keeps SHL-12's LF-only split. Probe F22 shows that one document cannot have both. The options, with their measured results:
   - (a) The literal reading. The proposed document is split by the dominant rule (`documentExtensions`, `markdown-document.ts` lines 18 to 20). The base is split on LF (SHL-12). An LF-to-CRLF-only change has no changed chunk, so it is invisible in the editable view (probe 2). One line edited in a CRLF file marks the whole text, one chunk over `[0, 11]` (probe 2b). The text is emitted with `documentText`. C2 passes.
   - (b) The dominant rule on both sides, each side split by its own text. An LF-to-CRLF-only change is invisible (probe 3). One edited line marks that line only (probe 3b). The text is emitted with `documentText`. C2 passes.
   - (c) SHL-12's LF-only document, whose lines keep their CR, with the dominant facet set only for later inserts. An insertion at the end of a CRLF line lands after the CR: `sliceDoc` gives `"alpha\rX\r\nbeta\r\r\n"` and `toString` gives `"alpha\rX\nbeta\r\n"` (probe 4a). That is every CRLF line end, not only the mixed files of SHL-13 open point 1. The emitted text must use `toString`, because `sliceDoc` doubles the CR (probe 4d). An LF-to-CRLF change stays visible (probe 1).
   - (d) A transaction filter that moves an insertion before a trailing CR. Rejected for SHL-13 by `plans/DECISIONS.md` line 3627, for the same reason; not measured here.
   - Cost: (a) and (b) lose the LF-to-CRLF mark in the editable view, which `plans/SHL-12.md` line 67 (SHL-12 decision 6) and criterion 3 (`units/SHL-12-readonly-diff.md` line 26) require of the component. (c) keeps the mark and puts a bare CR at every CRLF line end that is edited. The plan takes no option. The Navigator chooses one, or accepts that the LF-to-CRLF mark is a read-only property (SHL-12 criterion 3 holds in read-only mode only).
2. **[NAVIGATOR] Who consumes the merge view.** SHL-16's `unblocks` (unit line 9) names PST-34, whose text does not use the merge view. `modules/shell.md` lines 9 and 88 and PST-20 lines 17 and 25 name the review queue. PST-20's `blocked_by` does not name SHL-16. `plans/DECISIONS.md` line 4084 says the PST-20 follow-up will be split "when PST-20 is planned". The plan provides the component and changes no unit. The premise that PST-34 needs the editable side is not in PST-34's text.
3. **[NAVIGATOR] Identical text in editable mode (D13).** SHL-12 decision 6 applies: no editor for identical text, so an author cannot edit a proposal equal to its base. The plan keeps that rule (test E1). If the Navigator wants an editor when `editable` is true, E1 changes.

Settled here, not open (names and layout): the `editable` input (unit line 20); the `contentChange` output; the `aria-label` text (D6); the new spec file (D12); emit on document change only (D4); rebuild on `editable` and `path` change (D7).
