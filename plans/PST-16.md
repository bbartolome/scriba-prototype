## 1. Decisions this plan follows

- **D1. Accept runs the three-way check** (unit lines 18 to 20). The captured base (`capturedBase`, stored by PST-15 decision 7) is compared with the disk, not with the proposal. If the disk matches the base (for a create: the target is absent), accept writes `content ?? proposed`. Otherwise accept persists the conflict, publishes `pending-updated` if the stored reason changed, and refuses with `PROJECT_PENDING_CONFLICT` (409). The reasons are `base-changed`, `target-missing` and `target-exists` (contract `pendingConflictSchema`, C7). Source: unit lines 18 to 20.
- **D2. Reject** (unit line 21). The change gets status `rejected` and moves to `.scriba/pending/resolved/<id>.json`. Reject does not read or write the target. PST-15 writes nothing under `resolved/`, and PST-16 creates it (PST-15 plan section 6 line 199, C5). Source: unit line 21.
- **D3. Refusals of the id** (unit line 22). Accept or reject on a resolved change gives `PROJECT_PENDING_NOT_OPEN` (409). An id that is neither open nor resolved, or that does not have the form of a pending id, gives `PROJECT_NOT_FOUND` (404) with a fixed message. The contract has no other not-found code for a change (`errors.ts`, C7), so this is the simplest choice (plan choice, settled). The form is `^\d{8}T\d{9}Z-[0-9a-f]{6}$`, the form that PST-15's `newPendingId` makes (`pending-store.ts` line 56). The form check runs before any disk access, so an id with a slash or dots never reaches a path.
- **D4. Eager conflicts** (unit line 23). A list (GET) computes each change's conflict in memory and returns it. A list never writes and never publishes. This is the module's GET rule (module line 46) and the rule that DECISIONS line 1672 cites as "PST-16 line 23". Every POST that touches a target persists the conflict when it changed and publishes `pending-updated`. The POSTs that touch a target are: accept (also when it refuses, and for the other open changes of the same target after a write), and the file API's write, edit, delete and move routes (they change the target). Reject does not touch the target. `propose` is not a POST: it is in-process only (PST-15 unit line 18), so it is not in this list (D16). Source: unit line 23, read literally (settled, open point 4).
- **D5. Versions on apply** (unit line 24). The path is settled by module line 75: `drafts/.versions/<draft file name>/<UTC timestamp>.<ext>` holds the replaced content. A `modify` change whose target is a top-level file of `drafts/` saves the disk bytes it replaces, before the write. The stamp is the compact ISO-8601 basic form with milliseconds, `YYYYMMDDTHHMMSSmmmZ`, the same as PST-15's `newPendingId` (`pending-store.ts` line 56), taken at the apply time. `<ext>` is `path.extname` of the draft file name, and is empty when the name has no extension (plan choice). When a name is taken (two applies in the same millisecond), the suffix `-2`, `-3`, ... goes between the stamp and the extension, for example `20261104T231500123Z-2.md` (plan choice, settled, open point 1; the unit says only "numeric suffix on collision"). A `create` writes no version. Author saves write no version (unit line 24; the file API keeps its behaviour).
- **D6. Events** (unit line 25, criterion line 33). Accept publishes `pending-resolved` (status `accepted`), then `files-changed` (paths `[target]`), in this order, the order in which the unit and criterion 5 list them (settled, open point 7). Reject publishes `pending-resolved` (status `rejected`). A refused accept or a changed conflict publishes `pending-updated`. Payloads: `{projectId, pendingChange}` (`pendingEventDataSchema`, C7) and `{projectId, paths}` (`filesChangedDataSchema`, C7).
- **D7. Routes and response** (unit line 26; `routes.ts` lines 38 to 41, C7). `POST …/pending/:id/accept` takes `pendingDecisionSchema` (`{content?}`) or no body (D21). `POST …/pending/:id/reject` takes no body. Both return `200`, as the file routes do (`files.controller.ts` lines 60, 69, 78, 87, C18). Both are behind Setup & auth's global guard, which is `APP_GUARD` (`setup-auth.module.ts` line 52, C26). The response is the resolved change, shaped as `pendingChangeSchema`. PST-01's route table says "pending change" for accept and reject (PST-01 plan lines 75 and 76, C23), and the contract has no other response schema (C7). No written hash is returned (settled, open point 8).
- **D8. Active rule** (module line 48; DECISIONS line 2297, which exempts only propose and appendLog). Accept and reject require the active project (`ProjectStoreService.requireActive`, `project-store.service.ts` line 66). After that check, the project is looked up as the file API does it (`FilesService.projectFor`, `files.service.ts` line 504). They do not use `requireOkProject`, because the file API's writes do not check the project's status either (plan choice).
- **D9. The three-way comparison, exactly** (module line 50 for hashes). First the sizes: if the disk file's size differs from `Buffer.byteLength(capturedBase.content, 'utf8')`, the base does not match. Only when the sizes are equal is the disk read, and then `hashOf(bytes)` must equal `capturedBase.hash`. The size shortcut keeps a list (GET) from reading a large file (plan choice). The pending text is not compared.
- **D10. Disk states.** For a `create`: an absent target matches, and a file or a folder at the target gives `target-exists`. For a `modify`: an absent target or a folder at the target gives `target-missing`, a file with a different size or hash gives `base-changed`, and a file that matches gives no conflict. A `modify` with a null base cannot occur (PST-15 decision 8 always stores a base for `modify`). If it did, it gives `base-changed` (plan choice).
- **D11. Path check again.** Accept and the list call `ProjectStoreService.resolvePath` for the target again, because the path can change after the propose (for example a folder above it becomes a link). A path refusal on accept is returned unchanged. In the list, a change whose target now fails the check is shown as `target-missing`, so one change cannot fail the whole list (plan choice, settled, open point 10).
- **D12. Order of the writes on accept** (plan choice). (1) Save the version, if D5 applies. (2) Write the target (D19). (3) Write the resolved record. (4) Remove the open file. (5) Publish `pending-resolved`, then `files-changed` (D6). (6) Call the store hook (D17), which rechecks the other open changes of the target. The version is written before the target, so the replaced text is never lost when the target write fails. A failed write leaves the open change open, and an unused version file may remain. The steps are synchronous, so no other request of the process interleaves (D20).
- **D13. Edited content is written as given** (unit lines 19 and 20; settled, open point 15). The unit says only "write `content ?? proposed` atomically", and no criterion needs a check of the edited text. Accept runs no size cap, no `project.yaml` state check and no registered validator on `content` or `proposed`; `proposed` already passed them at propose (PST-15 decision 10), and `content` is checked only by the contract (`z.string()`). Known effect, recorded: an edited text can be one that the file API's write would refuse (over 5 MiB, or a root `project.yaml` that is not `ok`). A later unit that needs a check adds it in `writeProposal` (D19), the seam PST-23 uses.
- **D14. Refusal details** (plan choice). `PROJECT_PENDING_CONFLICT` carries `details: {reason}`. The message is fixed: "The file no longer matches the base of this change. Refresh the change, or accept it anyway."
- **D15. Stored conflict fields** (plan choice). `conflict` is `{reason, detectedAt}`. `detectedAt` keeps its stored value while the reason stays the same, and is the time of the computation otherwise. A conflict-only update does not change `updatedAt`. Only a proposal, a fold, an accept or a reject changes it.
- **D16. Propose is not changed** (settled, open point 3). PST-15 decision 16 says the conflict is `null` on every change PST-15 writes and that PST-16 computes it (C5). PST-16 computes it in the list (D4) and persists it on the POSTs of D4. `propose` is in-process only (PST-15 unit line 18), so it is not "a POST that touches the target" of unit line 23, and no criterion of PST-16 needs a conflict on a new or folded change. PST-15's code (`conflict: null` at `pending.service.ts` lines 171 and 231) stays as it is. Known effect, recorded: a fold writes `conflict: null`, so a persisted flag is reset by a fold; the list and accept compute the conflict again, and the next POST that touches the target persists it again.
- **D17. The store hook** (plan choice). `ProjectStoreService` gets `onFilesChanged(handler)` and `notifyFilesChanged({projectId, paths})`, the pattern of `onProjectSwitched` and `notifyProjectSwitched` (`project-store.service.ts` lines 54 and 59, C9). `FilesService` calls the hook after its own `files-changed` publish: in `commit` (publish at lines 537 to 541, which covers write, edit and `updateProjectYaml`), `delete` (lines 344 to 348) and `move` (lines 381 to 388). `PendingService` registers its recheck in its constructor. The alternative, injecting `PendingService` into `FilesService`, makes an import cycle: `pending.service.ts` imports functions from `files.service.ts` (`hashOf`, `readFileAt`, `refuse`, ...), and Nest reads constructor parameter types when the class is defined. The recheck handler catches its own errors and discards them, because the file write has already happened and its answer must not change (settled, open point 5). Accept computes its own conflict, so correctness does not depend on the recheck.
- **D18. Folders the module owns** (settled, open point 2). The version and resolved folders are built from the approved target name and fixed segments. They are checked by their real paths inside the project, as `pendingFolder` checks `.scriba/pending` (`pending-store.ts` lines 25 to 54). No mode is added to `path-safety.ts`. PST-02 P12 and DECISIONS line 2912 forbid a mode for reserved paths that the public path check and the tests could reach, and PST-15 decision 6 made the same choice for `.scriba/pending/` (C11, C20). PST-02 item 6 (plan line 313) recommends a mode; it is a recommendation in an open point, and PST-02 line 298 leaves the choice to PST-16 and PST-18 (C21). No other plan names it as a source.
- **D19. One write function for accept** (PST-23 seam). Accept writes the target through one private method of `PendingService`, `writeProposal`, which calls `writeText` from `files.service.ts` (exported in step 4). `writeText` gives the same error mapping as the file API: `ENOTDIR`, `EEXIST` and `EISDIR` are `notAFile`, and other errors are plain errors with the errno only. PST-23 adds its lazy migration before this call (unit PST-23 line 21). PST-16 adds no migrator.
- **D20. Synchronous steps.** The check, the writes and the events of one POST run without an `await`. Another request of the same process cannot run between the check and the write (A8 assumes one server process).
- **D21. Empty body** (settled, open point 13). The installed Express is 5.3.0 with body-parser 2.4.0 (C29), and in that version a request with no body leaves `req.body` undefined (A3). A pipe with `pendingDecisionSchema` would then refuse a bodiless accept with 400. So the accept route's pipe is `new ZodValidationPipe(pendingDecisionSchema.optional())`, and the handler passes `body ?? {}` to the service. Test X5 checks both a bodiless accept and a bad body.
- **D22. The resolved record** (plan choice, settled, open point 9). It keeps `proposed` as proposed. When the author edited the text, the edited text that was written is not stored; the target holds it. `conflict` is `null`. `status` is `accepted` or `rejected`. `updatedAt` is the time of the resolution. No unit reads `resolved/` (PST-15 unit line 23: the queue lists only open changes).
- **D23. No special case.** Accept of a proposal that equals the disk still saves a version, as D5 says. Nothing in the unit excludes it.
