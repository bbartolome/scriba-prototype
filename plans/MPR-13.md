### 1b. Decided here (smaller choices, the simplest option in each case)

- **D1 Component.** `ProjectModelPanel`, selector `app-project-model-panel`, file `apps/web/src/app/features/providers/project-model-panel.ts`. Standalone, no `providers:` array (no `ProvidersStore`), state held in signals. It injects `API_CLIENT` and `SSE_CLIENT` from `'../../shell'`, the shell's entry. It is not exported from `providers.routes.ts`, because no other feature needs it.
- **D2 Heading.** An `<h2>` with `TEXTS.projectHeading` ("This project"), like the panel's sections.
- **D3 Loads.** On creation, and on every refresh, the section reads `GET /api/project-store/active` first.
  - When `active` is null, it renders nothing and sends no other request.
  - Otherwise it reads two things independently: `GET /api/providers` (the list for the select) and `GET /api/providers/effective-model` with `params: {projectId: <id>}` (the readout). They are independent so that a missing app default, which makes the readout fail, does not hide the form. Each failure shows one `role="alert"` line: the ApiError message when there is one, else `TEXTS.projectLoadFailed`.
  - Each read keeps a request counter, as `projects-state.ts` `read()` does (line 67, counter line 69), so a late reply of an older refresh is ignored.
- **D4 Refresh.** The section subscribes to `stream('project-store')` and refreshes when `envelope.type === 'project-switched'`. It does not read `data`: the active reply is the truth, so no copy of `projectSwitchedDataSchema` is needed. It also subscribes to the SSE client's `reconcile$` and refreshes on every tick, whatever the reason, so a reconnecting client reconciles through the two state endpoints it reads (`units/README.md` line 133). Both subscriptions mirror `projects-state.ts` lines 54 to 63: the stream filter on `project-switched` (line 57) and `this.events.reconcile$.pipe(takeUntilDestroyed(...)).subscribe(() => this.refresh())` (lines 61 to 63); the section uses its own `DestroyRef`. `reconcile$` is on the `SseClient` surface behind `SSE_CLIENT` (`shell/sse-client.ts` line 59) and on the fake (`test-doubles.ts` line 121). A refresh is D3 (the active read first, then the two reads), so the request counters of D3 drop a late reply. It also refreshes after a successful set or clear, so the readout is the server's. Settled by the Navigator on 2026-11-16 (open point 2).
- **D5 Form.** One select, `name="projectProvider"`, `aria-label="Provider for this project"`. Its first option is `TEXTS.useAppDefault` ("Use app default") with value `""`, then one option per provider, text and value both the provider id. One text input, `name="projectModel"`, `aria-label="Model for this project"`, free text: empty means the provider's own model (MPR-12 D12). One button, `TEXTS.saveProject` ("Save for this project"). A blank provider posts the clear. Any other provider posts the set with `{providerId, model}`.
  - The model field is free text and not the panel's model picker. `model-picker.ts` renders `name="model"` and `aria-label="Model"`, which the panel's own form also uses on the same page. Reusing it would give two controls with the same name on one page.
- **D6 Initial values.** When the source is `project`, the select starts at the readout's `choice.providerId` and the model field at the readout's `choice.model`. Otherwise both start blank. So a save with no change keeps the override in effect. An empty-model override is the one case where an unchanged save stores the resolved model, because the readout shows that model and the form shows what is in effect. This plan accepts that, and records it here.
- **D7 Readout text.** `TEXTS.modelInUse(model, providerId)` ("Model in use: {model} from {providerId}.") then one source line: `project` gives "Set for this project", `app` gives "From the app default", `auto` gives "The provider's first listed model". The warning, when present, is shown exactly as the server sent it in a `role="alert"` paragraph. The web holds no copy of the warning text.
- **D8 Commands.** A failed set or clear shows `failureMessage(error, TEXTS.genericFailure)` in a `role="alert"` line and leaves the readout as it was. This is the pattern of `providers-panel.ts` `chooseDefault`.
- **D9 Layout.** `:host { display: block; min-width: 0; }`. The select, the input and the button sit in a flex row with wrap. The section adds no horizontal overflow at 390 by 844. Form field markup follows the panel: `mat-form-field`, `mat-label`, `select matNativeControl`.
- **D10 Page.** `providers-page.ts` imports `ProjectModelPanel` from `./project-model-panel` (not from the entry file, as D4 of MPR-11 says) and adds `<app-project-model-panel />` after `<app-providers-panel />`. Its comment on line 5 is updated to name the section.
- **D11 Texts.** The new keys are appended at the end of `TEXTS` in `providers-texts.ts` (MPR-11's note: the end of `TEXTS`). Keys and exact values:
  - `projectHeading`: "This project"
  - `projectLoadFailed`: "The project model could not be loaded."
  - `projectProviderLabel`: "Provider for this project"
  - `projectModelLabel`: "Model for this project"
  - `projectModelHint`: "Leave empty to use the provider's own model."
  - `useAppDefault`: "Use app default"
  - `saveProject`: "Save for this project"
  - `modelInUse(model, providerId)`: "Model in use: {model} from {providerId}."
  - `sourceProject`: "Set for this project"
  - `sourceApp`: "From the app default"
  - `sourceAuto`: "The provider's first listed model"
  - While the section loads, it shows the existing `TEXTS.loading` line. The new button label "Save for this project" differs from the panel's "Save", so the two are told apart by name.
- **D12 Copies in `providers-copies.ts`.** Appended after the connection-test block. Path constants (`ApiPath`, no templates): `ACTIVE_PROJECT_PATH` = `/api/project-store/active`, `EFFECTIVE_MODEL_PATH` = `/api/providers/effective-model`, `PROJECT_MODEL_PATH` = `/api/providers/project-model`, `PROJECT_MODEL_CLEAR_PATH` = `/api/providers/project-model/clear`. Source names as a literal tuple, `['project', 'app', 'auto']`, as `PROVIDER_ERROR_CODE_NAMES` does. Three guards, each built field by field from the fields the contract knows:
  - `activeProjectCopy`: `active` is null or a non-empty string.
  - `effectiveModelCopy`: `choice.providerId` a non-empty string, `choice.model` a string, `source` one of the three names, `contextSize` a safe integer of at least 1, `warning` optional and a string.
  - `projectModelResponseCopy`: `projectModel` is null or a choice.
  - Types come from `import type` of `@bbartolome/scriba-contracts/providers` and `@bbartolome/scriba-contracts/project-store` only (`ModelChoice`, `EffectiveModel`, `ProjectModelResponse`, `ActiveProject`, `ProviderRead`, `ProviderList`).
- **D13 Test shape.** The spec `project-model-panel.spec.ts` mounts a host with `<app-project-model-panel />` and the fakes from `createShellTestDoubles().providers`. Each state is a new host, as `providers-panel.spec.ts` `mount()` does. Every reply is registered before the action that sends its request. The fake answers by method and path only, so a state that needs a different reply re-registers the same path first.
- **D14 Edit to an existing spec.** `providers-route.spec.ts` R2 and R3 each register `GET /api/project-store/active` with `{active: null}` before the page renders. Then the section is hidden in those tests, and no request goes unanswered (the fake errors on an unanswered route). No assertion of R1 to R3 changes.
- **D15 No store sharing.** The section keeps its own calls. The panel's list and app default are not updated by the section, and the section does not re-read when the panel changes. Settled by the Navigator on 2026-11-16 (open point 4).
