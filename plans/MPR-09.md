The panel does not use `CONNECTION_TEST_ROUTE`, `EFFECTIVE_MODEL_ROUTE`, `PROJECT_MODEL_ROUTE` or `PROJECT_MODEL_CLEAR_ROUTE`. Every contract import in a non-spec file is `import type` (`ProviderRead`, `ProviderList`, `Preset`, `PresetList`, `ModelChoice`, `AppDefault`, `ModelList`, `ProviderCreate`, `ProviderUpdate`, `KeySetRequest`, `KeyClearRequest`, `ProviderConfigInput`).

  Each guard rebuilds its value from the fields its contract schema knows and leaves out an absent optional field, as zod does (zod drops unknown keys, 7a), so an unexpected field such as `key` in a body never reaches the store. The field rules copy zod 4.6.7 exactly, including where zod changes or refuses what a plain check would keep:
  - `baseURL` (`z.url()` with no options; `config.ts` line 10, `defaults.ts` line 16). zod trims the value with `String.prototype.trim` (`schemas.js` line 268), accepts it when the URL parser accepts the trimmed text (line 269; `validateURL` lines 225 to 230 and `canParseURL` lines 214 to 224, since `z.url()` sets no `normalize`, `hostname` or `protocol`), and returns the trimmed text with every tab, LF and CR removed (line 292; `stripTabAndNewline` lines 250 to 254). So zod's `data` can differ from its input (`'  https://example.test/v1  '`, two plain spaces at each end, gives `'https://example.test/v1'`). The order, trim first and then parse, matters for one kind of value: `trim()` removes U+00A0 (NO-BREAK SPACE) and the URL parser does not, so zod accepts `'\u00a0https://example.test/v1'` while `new URL()` on the raw text refuses it. A plain space does not show this, because the URL parser itself removes leading and trailing C0 controls and spaces: `new URL(' https://example.test/v1')` is accepted (7a, zod checks). So the fixture that tests the order must contain U+00A0; this plan and the spec write it with the JavaScript escape `\u00a0`, never as the raw character. `contractUrl(value)` does the same three steps on a string (any other type gives undefined): `trim()`, then `new URL(trimmed)` in a try/catch (undefined when it throws), then `trimmed.replace(/[\t\n\r]/g, '')`. The guard returns that value, so its `data` equals zod's.
  - Numbers. `z.number()` refuses `NaN` and `±Infinity`, so `temperature` is checked with `Number.isFinite`. `.int()` accepts only safe integers (`2 ** 53` is refused, `2 ** 53 - 1` accepted; 7a), so `contextSize`, `maxTokens`, `timeout` and `retries` are checked with `Number.isSafeInteger`, then `> 0` (`contextSize`, `maxTokens`) or `>= 0` (`timeout`, `retries`).
  - The rest: `id` matches `^[a-z0-9][a-z0-9-]*$`; `kind` is `'openai-compatible'`; `model` is a string; `keyRef`, when present, is a non-empty string; `keySet` is a boolean; `keyHint`, when present, is a string of 1 to 4 characters; a preset has non-empty `id` and `label`, a `baseURL` as above, a boolean `keyRequired` and `hints` as an array of strings; a model choice has a non-empty `providerId` and a string `model`; `appDefault` is a model choice or `null`; `models` is an array of strings (`config.ts` lines 7 to 18 and 27 to 30, 46 to 48; `defaults.ts` lines 13 to 23; `model.ts` lines 5 to 8, 28 to 30 and 33 to 35).

- **D6 Add flow, and the retry-save rule.** "Add a provider" shows one button per preset from the presets response, then "Custom URL". A preset opens the form in add mode with the preset's `baseURL`, `model` empty, the five defaults from `PROVIDER_DEFAULTS_COPY`, and the preset's `hints` as notes; in add mode a key is required when `preset.keyRequired` (OpenAI, OpenRouter; `defaults.ts` lines 56 and 63). Custom URL opens the form with an empty `baseURL`, the defaults, and a required Name field (sent as `label`, no `presetId`; the server makes the id from it, and the id cannot change). Save in add mode is one sequence (the message fields follow D7's rule):
  1. `POST /api/providers` with `kind: 'openai-compatible'`, the seven editable fields and `presetId` or `label`, never a key. If it fails, the form stays in add mode, the error's message goes to the alert field (D7), and nothing else is sent.
  2. On success the new row is added to the list. If the key field holds text, `POST /api/providers/key/set` `{providerId, key}` follows, with the id from the create response. On success its reply replaces the row. On failure the row stays as the create returned it (`keySet: false`) and the alert field (D7) shows "The provider was saved, but its key was not saved. Paste the key again and press Save." In both cases the key field is cleared (D8).
  3. When step 2 has ended (or was not needed), the form switches to edit mode for the new provider and stays open, so the author can pick a model from its list; that switch requests the list (D9) and does not clear the message fields (D7).

  The retry-save rule. After a failed key save the form is in edit mode with an empty key field, and the next Save is an ordinary edit-mode Save (D7): `POST /api/providers/<id>/update`, then `key/set` if a key was pasted. It never posts a second create. Reason, simplest option: there is one Save rule in edit mode and no extra state. The other option, a Save that posts only `key/set` until the key is saved, needs a "key pending" flag, a second save path in the form and a rule for leaving that state; the update it avoids is harmless, because it sends the values the create has just stored. E6 tests the rule; control M13 breaks it.
- **D7 Edit flow, and the form's message fields.** Edit opens the same form prefilled from the saved provider. Save in edit mode always sends, in this order: `POST /api/providers/<id>/update` with the seven editable fields (`baseURL` and `model` as strings, the other five as numbers); then, only when the key field holds text, `POST /api/providers/key/set` `{providerId, key}`. This is the only Save path in edit mode, including right after an add whose key save failed (D6). If the update fails, its message goes to the alert field and no `key/set` is sent. Each successful reply replaces the row. If `key/set` fails after a successful update, the alert field shows the message of D6. After a successful update the list is requested once, when the key step has ended (D9). "Close" discards unsaved edits. Only one form is open at a time.
  - **Messages: two separate fields.** The form has two message fields, each rendered as its own element and only while it holds text. The alert field (`role="alert"`) holds the text of the last failure in the form: a failed create's or update's message, the key-save message of D6 (a failed `key/set`), or the Remove error of D8; a new failure replaces its text. The status field (`role="status"`) holds `Saved.` or nothing; `Saved.` is set when a Save's first request (the create or the update) succeeded and its key step succeeded or was not needed. Writing one field never changes the other. A Save clears both fields when it starts (in either mode, before its first request). The only other points that clear them are the form opening and the form closing; nothing else does, in particular not the switch from add to edit mode at the end of an add (D6 step 3) and not a Remove. So after a failed key save the alert field holds the D6 message and the status field is empty; the next Save clears both as it starts, and when it succeeds only `Saved.` shows (E6). If a Save did not clear the fields when it starts, the D6 message would still show after a successful retry, next to `Saved.` (control M16). The inline validation messages of D13 belong to their inputs and are not these fields.
