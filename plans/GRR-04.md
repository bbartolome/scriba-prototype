## 1. Decisions this plan follows

### 1a. Settled by the unit, the module, the contract and the done plans

- **S1 Start route.** `POST /api/graph-runner/runs` (`RUNS_ROUTE`), body `runStartRequestSchema` (`graphId`, `inputs`, optional `target`, optional `targets`), answer `runStartResultSchema` `{runId}`. Source: unit line 18; `packages/contracts/src/graph-runner/runs.ts`; `routes.ts`; GRR-01 plan D11, D16.
- **S2 Scope.** No target: every node of the recipe. With a target: that node and every node upstream of it, following wires backwards. Results are never reused. Source: unit line 19.
- **S3 Output nodes and tool targets.** Output nodes outside the scope produce nothing. A tool-node target shows its result inline and makes no pending change. The pending change of an in-scope output node is GRR-06's step; GRR-04's output-node step is P21 (open point 1, decided). Source: unit lines 19 and 27.
- **S4 Refusals and codes.** `GRAPH_VIEW_NOT_RUNNABLE` (story graph), `GRAPH_VALIDATION_FAILED` (blocking errors), `GRAPH_INPUT_MISSING` and `GRAPH_INPUT_INVALID` (inputs and file references), `GRAPH_RUN_ACTIVE` (one active run per project). Statuses from `errors.ts` `GRAPH_ERROR_STATUS`: `GRAPH_VIEW_NOT_RUNNABLE` 409, `GRAPH_RUN_ACTIVE` 409, the other codes 422. `GRAPH_TARGET_INVALID` (422) and `GRAPH_RUN_NOT_FOUND` (404) exist in the contract. Source: unit line 20; module lines 43 and 45; `errors.ts` lines 5 to 15 and 38 to 48.
- **S5 Blocking validation.** A blocking issue is an issue with `severity: 'error'`. It is computed by `GraphRunnerService.issuesOf` on the graph that `readGraph(id)` returns. GRR-04 adds no rule of its own. Source: GRR-03 plan S1, S3 and section 5 (its GRR-04 entry); GRR-02 plan P13.
- **S6 Input values.** `{kind:'text', text}`, `{kind:'file', ref}` (any file of the active project, path-safety checked, not limited to `drafts/`), `{kind:'entities', refs}`, `{kind:'style', ref}`. Source: unit line 21; `runs.ts` `inputValueSchema`.
- **S7 Reads at start.** Every file reference is read once through the Project store before any tool runs. Its path and content are kept for the run's lifetime. The path and a `sha256:` hash are logged; logging is GRR-07. The content is the captured base GRR-06 uses. Run state never holds file contents (`runs.ts` `inputValueSchema` comment; GRR-01 plan D12). Source: unit line 22; GRR-01 plan C15.
- **S8 Order.** In-scope nodes run one at a time in topological order, ties broken by node id. Every in-scope node starts `queued`. Source: unit line 23; module line 45.
- **S9 Tool step.** Gather port values (upstream results, pinned values, input values) and the settings from `params`. Resolve every entity reference, style included, to contents through the Project store. Call the Tool registry executor, which is cancellable. Keep `{output, sourcesUsed}` in memory. Source: unit line 24; TRG-12 plan line 215; `executor.service.ts` `execute(name, request, signal?)` lines 72 to 76.
- **S10 Run state.** The contract shape `runStateSchema`. `GET` current-run-state returns the active run for the project, else the last finished one, else `null`. Source: unit line 25; `runs.ts` `runStateSchema`, `currentRunSchema`; GRR-01 plan D12 and C10.
- **S11 SSE.** Members of module `graph-runner`: `run-started` (run state), `node-status` on every change, `run-ended`. Source: unit line 26; `events.ts` `graphRunnerEventSchema`; GRR-01 plan D14.
- **S12 Out of scope.** Output nodes (GRR-06), stop and fail-fast (GRR-05), run logs and recovery (GRR-07). GRR-04 still needs an error branch and an output-node step; section 6 gives the decisions and why they agree with this line. Source: unit line 27.
- **S13 Module rules.** One active run per project. Fail-fast on error is the module's design choice. The API seam is the composed app with the mock OpenAI server. Source: `modules/graph-runner.md` lines 45 and 50.
- **S14 Statuses.** Node statuses `idle`, `queued`, `running`, `done`, `error`, `stopped`. Run statuses `running`, `done`, `error`, `stopped`. Source: `constants.ts` `NODE_RUN_STATUSES`, `RUN_STATUSES`.
- **S15 Entities.** An id with no valid entity (`unknown`) and an id with two (`duplicate`) are not resolved and are never guessed. Source: PST-08 plan line 155; `entities.service.ts` `resolve` lines 36 to 60.
- **S16 HTTP.** Every POST answers 200; every GET never mutates. Source: module line 41; GRR-02 plan P8; GRR-03 plan P3.
- **S17 Testing.** External behaviour only: HTTP responses, SSE events, files on disk, what the mock model received. Source: module lines 49 to 51; `units/README.md` line 139.

### 1b. Small choices this plan makes (names, layout, rule details)

- **P1 Files.** `run-scope.ts` holds the pure scope and order rules (P14, P15). `runs.service.ts` holds class `RunsService`: the start, the current read, the engine, the node steps and the events (P2 to P13, P21). `runs.controller.ts` holds class `RunsController`. Two small edits go to `graph-runner.service.ts` (section 2). The engine stays out of the 316-line service.
- **P2 Order of the start refusals.** (1) `readGraph(body.graphId)`: `GRAPH_NOT_FOUND`, `GRAPH_SCHEMA_INVALID` or `GRAPH_SCHEMA_VERSION_UNSUPPORTED`, as GRR-02 (and `PROJECT_NO_ACTIVE` without an active project). (2) View not `recipe`: `GRAPH_VIEW_NOT_RUNNABLE`. (3) `issuesOf(graph)` has an error: `GRAPH_VALIDATION_FAILED`. (4) Targets (P3): `GRAPH_TARGET_INVALID`. (5) Inputs (P4): `GRAPH_INPUT_MISSING` or `GRAPH_INPUT_INVALID`. (6) File references (P5): `GRAPH_INPUT_INVALID`. (7) An active run of the project: `GRAPH_RUN_ACTIVE`. The unit lists the refusals in this order (unit line 20). Step (7) is the last check, so no run is registered on any refusal.
- **P3 Targets.** `target.nodeId` must name a node of the graph; any kind (input, tool or output) is allowed, because unit line 19 ("if the target is a tool node") presupposes other kinds, and an output-node target is GRR-06's pending-change case (open point 1). Each key of `targets` must name an output node. Otherwise `GRAPH_TARGET_INVALID`. The values of `targets` are stored as given. Their path and kind-folder checks are GRR-06's (GRR-06 unit line 23).
- **P4 Input values.** Every in-scope input node needs a value, or `GRAPH_INPUT_MISSING`. Pairing with the input node's `params.type`: `text` takes `{kind:'text'}` or `{kind:'file'}` (the file's text); `entity` takes `{kind:'entities'}`; `style` takes `{kind:'style'}`. Any other pair is `GRAPH_INPUT_INVALID`. A key that names no input node of the graph is `GRAPH_INPUT_INVALID`. Values of input nodes outside the scope are not stored. An empty `refs` array is an empty list.
- **P5 File references.** One `FilesService.read(projectId, path)` per distinct path among the in-scope file inputs. A map keyed by path makes two nodes that name one file share one read. `PROJECT_PATH_INVALID`, `PROJECT_PATH_OUTSIDE`, `PROJECT_PATH_RESERVED`, `PROJECT_NOT_FOUND`, `PROJECT_NOT_TEXT`, `PROJECT_FILE_TOO_LARGE` and `PROJECT_SCHEMA_TOO_NEW` (a too-new root `project.yaml`, `files.service.ts` line 265) map to `GRAPH_INPUT_INVALID`. Any other error is rethrown. The store's `read` calls `this.store.resolvePath` itself (`files.service.ts` lines 257 to 269; a missing file is `PROJECT_NOT_FOUND` from `readFileAt`, line 141), so GRR-04 calls `read` only and not `resolvePath` itself. `read` is synchronous (checked), which P7 relies on.
- **P6 Private run record.** An in-memory `RunRecord` in `runs.service.ts` holds: `state` (the public `RunState` shape); `files` (captured reads by input node id: `{path, content, hash}`, where `hash` is `FileRead.hash`, the `sha256:` form of `files.service.ts` `hashOf`); `results` (tool results by node id, kept in memory); `controller` (an `AbortController` whose `signal` the tool step passes to the executor). None of these is part of a contract. The registry is `Map<projectId, {active?: RunRecord; last?: RunRecord}>`.
- **P7 Start.** Steps (1) to (7) of P2, the reads and the registration run in one synchronous call with no `await` in between, so two starts cannot both pass the active check (`readGraph`, `issuesOf`, `GraphValidatorService.issues` and `FilesService.read` are all synchronous, checked). Then the call publishes `run-started` (the run state), then one `node-status` `queued` per in-scope node in topological order, then starts the engine without awaiting it. The answer is 200 `{runId}`, with `runId` from `randomUUID()` (`node:crypto`). An error that escapes the engine ends the run with status `error` and no reason, so that no promise is left unhandled.
- **P8 Run state.** `nodes` holds every node of the graph: `idle` for nodes outside the scope, `queued` for in-scope nodes at the start. `target` is present only when the request had one. `targets` is the request's `targets`, or `{}`. `pendingChangeIds` is `[]`. `startedAt` and `endedAt` are ISO datetimes. `reason` is never set in GRR-04.
- **P9 Node steps.** An input node in scope goes `running`, then `done` with no result. Its value for a wire is: text, the text; file, the captured content; entities, the ids (an array for a list port, the one id otherwise); style, the id. A tool node goes `running`, then the tool step (P10), then `done` with `result`. An output node goes as P21 says. If the step of any node throws, the node goes `error` with `error` (P11), then every in-scope node still `queued` goes `stopped` in topological order (one `setStatus` each), and the run ends `error` (open point 2, decided: GRR-05's fail-fast rule, GRR-05 unit line 18).
- **P10 Tool step.** (1) The port keys come from `CatalogService.ports(name).inputs`. (2) A wired port takes the upstream value (P9 for input nodes; the upstream `output.content` for tool nodes, read from `results`). A pinned port takes `params[key]`. The other keys of `params` are settings. (3) `CatalogService.validate(name, {arguments, mode: 'full'})` returns the arguments with defaults and the `entityRefs`. (4) The distinct ids of `entityRefs` go to `EntitiesService.resolve(projectId, ids)`. Any `unknown` or `duplicate` id is a node error with code `TOOL_ENTITY_UNRESOLVED` and a fixed message. Each resolved entry becomes `{ref: id, type, path, content}`. (5) `ExecutorService.execute(name, {arguments, entities}, controller.signal)` returns `{output, sourcesUsed}`, which goes to `results` and to the node's `result`.
- **P11 Node errors.** A `ModuleError` becomes `{code, message}` with its own code and message. Any other error becomes `{code: 'PLATFORM_INTERNAL', message: <fixed text>}` (`packages/contracts/src/platform/errors.ts` line 40). No input value is echoed in a message.
- **P12 Events.** One `setStatus(run, nodeId, status, extra?)` function is the only place a node status changes. It updates `state` and publishes one `node-status` `{runId, nodeId, status, result?, error?}` through `EventsPublisher.publish` (`events.publisher.ts` line 61). `run-started` is published once, and `run-ended` once with `{runId, status, reason?}` and no reason. The status at the end is `done` when every in-scope node is `done`, and `error` after a node error (P9). `endedAt` is set and the record moves from `active` to `last` before `run-ended` is published, so a `GET` current after the event sees the finished run.
- **P13 Current run.** `GET RUN_CURRENT_ROUTE` returns `{run}` for the active project: the active run if there is one, else the last finished run, else `null`. Without an active project it answers 409 `PROJECT_NO_ACTIVE` through `activeProjectId()`, as the graph routes do.
- **P14 Topological order.** Kahn's algorithm over the in-scope nodes, using only the wires whose two ends are in scope. Among the ready nodes the smallest node id goes first (plain string comparison). Pure function in `run-scope.ts`.
- **P15 Scope.** With a target: the target and every node reached by walking wires backwards from it. A wire's `from` and `to` are port ids `<nodeId>.<key>`; the node id is the part before the first dot (`graph.ts` `portIdSchema` comment). P14 uses the same split. Without a target: every node of the recipe. Pure function in `run-scope.ts`.
- **P16 Module wiring.** `RunsService` and `RunsController` are added to `graph-runner.module.ts`. No new import is needed, because `PlatformModule`, `ProjectStoreModule` and `ToolRegistryModule` are already imported. The module still exports nothing (GRR-02 P15).
- **P17 Routes.** `RUNS_ROUTE` (POST, 200, body through the Zod pipe over `runStartRequestSchema`, as the graph create route pipes its body) and `RUN_CURRENT_ROUTE` (GET). `RUN_STOP_ROUTE` is GRR-05's and is not added here.
- **P18 Stop is not here.** `RunRecord.controller` exists so that GRR-05 can abort the running model call. GRR-04 never calls `abort()`.
- **P19 Test seam.** A kit `apps/api/test/graph-runner-run.kit.ts` and one test file. Each test boots its own library, its own mock server with its own scenario folder, and its own app, and removes all three (as GRR-03 does).
- **P20 Tool fixture.** The user tool `gr_text` of GRR-03 section 4: one text input `topic` (`x-scriba-port: true`, required), one setting `words` (integer, minimum 1, required), output `draft`, `enabled: true`. Written as YAML to `<library>/.scriba/packs/user/tools/gr_text.yaml`, with the text that `toolYaml('gr_text')` of `apps/api/test/graph-runner-validation.test.ts` lines 70 to 110 produces (copied into the kit, because that helper is private to its test file); its prompt is `Write about {{topic}}.`. No file of `examples/` is named.
- **P21 Output-node step (open point 1, decided).** An in-scope output node goes `running`, then `done` with no `result`, and creates no pending change. GRR-06 replaces this step with its propose step. `nodeRunStateSchema.result` is optional, so the state fits the contract.

## 6. Open points

Both open points of the draft are decided by the reviser from the unit files and the contract; no Navigator decision was needed. Neither changes a criterion; C1 to C5 do not depend on either.

1. **Output nodes in scope before GRR-06 lands. Decided: option (a), P21.** An in-scope output node goes `running`, then `done` with no `result`, and creates no pending change; a target may name an output node (P3). Why: unit line 23 says the nodes in scope run, and every in-scope node starts `queued`, so an in-scope output node must run and must not be left `queued` in a finished run (this excludes option (c)). Option (b) needs a refusal code that the contract does not have; adding one changes GRR-01's done contract, which is outside this unit; and GRR-04 line 18 (`targets` per output node) and GRR-13 line 19 (the dialog lists the output nodes in scope) make a run with an output node in scope a valid request (this excludes (b)). Unit line 19 ("if the target is a tool node") presupposes targets of other kinds, so an output-node target is allowed. `nodeRunStateSchema.result` is optional, so (a) fits the contract. GRR-06 replaces the step.
2. **A failing node before GRR-05 lands. Decided: option (a), P9.** The failing node goes `error`, every in-scope node still `queued` goes `stopped`, and the run ends `error` with no reason. Why: the engine must have an error branch (an executor call can throw, GRR-03 S5), and the module makes fail-fast the engine's rule (module line 45), so continuing after an error is excluded. Any error branch does part of GRR-05's fail-fast, so unit line 27 cannot pick between the options; the only text that says what the other nodes and the run become is GRR-05 line 18. Option (b) would end runs with nodes left `queued`, a state that GRR-05 line 18 forbids, while (a) produces only states that the settled texts allow. GRR-05 keeps its criterion and its test (section 5).
