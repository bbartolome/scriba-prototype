## 1. Decisions this plan follows

- **Enforcement point:** the root `eslint.config.mjs`, so `npm run lint` enforces the rule (unit line 21). Rules R1 to R3 are the unit's Decisions (lines 18 to 20). R1 (line 18): an API module imports another module only through its `<m>.module.ts` and through `@bbartolome/scriba-contracts/<m>`. R2 (line 19): `agent-loop` and `graph-runner` import neither each other nor each other's `@Module` file ("at all"). R3 (line 20): feature folders in `apps/web/src/app/features/<m>/` follow the same rule.
- **Entry files:** API `apps/api/src/modules/<m>/<m>.module.ts` (unit line 22). Web `apps/web/src/app/features/<m>/<m>.routes.ts`. The web name is this plan's choice (section 6, point 4).
- **Interpretation:** the "at all" ban (line 19) also covers the web features `agent-loop` and `graph-runner` (section 6, point 7).
- **Fixture folder, Option A (DECISIONS 2026-11-11, mismatch 3):** the pinned path is `lint-fixtures/` at the repo root, outside `packages/` and `apps/`. Two "don't ship" mechanisms: (1) `lint-fixtures/**` is added to the root `ignores` array (`eslint.config.mjs` line 7), so `eslint .` never lints it; (2) the folder is not an npm workspace: it is not in the root `workspaces` array and has no `package.json`, so `npm run build --workspaces` and `npm test --workspaces` never reach it. Fixtures stay `.ts`. The test lifts the ignore (section 3, step 6). No criterion text changes.
- **Plugin:** `eslint-plugin-boundaries` 7.4.2 (latest on the registry on 2026-11-11), pinned exact as a new root devDependency. Its peer `eslint >=6.0.0` admits eslint 10.14.0. It declares no typescript-eslint peer, and its engines `node >=18.18` admit Node 26. It brings six direct dependencies (`@boundaries/config`, `@boundaries/elements`, `@boundaries/policies`, `eslint-module-utils`, `eslint-import-resolver-node`, `chalk`). With their transitive dependencies, the lockfile gains 28 entries (162 to 190 at 333399b; revision 3). The version is re-resolved at implementation (step 2).
- **Rejected alternative:** `no-restricted-imports`. Its patterns match the raw import string. A relative import such as `../agent-loop/agent-loop.service` cannot be matched reliably against file paths without resolving it, and the plugin resolves it.
- **Root devDependencies only** (PLT-01 Decisions; workspaces have no dependencies).
- **Runtime:** Node 26 (DECISIONS 2026-11-10, "Node runtime for the tests"). The test uses `node:test` and ESLint's Node API.
- **Test location and root script (decided, DECISIONS 2026-11-11):** `scripts/boundaries.test.mjs`, root-owned like `scripts/pins.test.mjs` (DECISIONS 2026-11-10, "location and coverage"). The root `test` line is the glob `node --test 'scripts/*.test.mjs'`, set by PLT-03 on batch/current (commit 506e1f8). It is not on main: main's `test` line is still `node --test scripts/pins.test.mjs`. PLT-09 runs on a branch rebased onto batch/current. PLT-09 edits no `test` line. It adds only its file, which the glob picks up.
- **Prettier:** the fixture folder is NOT in `.prettierignore`. That file excludes documents and the lockfile, which are not formatted code. The fixtures are ordinary TypeScript, so `prettier --check .` checks them. The approved `.prettierignore` does not change.
- **`tseslint.config()` (PLT-01 implementation review, note 4):** switch to `defineConfig()` imported from `eslint/config`, the ESLint core helper that the typescript-eslint deprecation notice names. Behaviour is not changed silently: section 3, steps 5 and 7 save `npx eslint --print-config` output before and after, and the diff must add only the boundary rules and settings (revision 3 adds `import/resolver` and `boundaries/files`).
- **Criterion 4 scope:** section 4, criterion 4 is passed by part 4a alone (DECISIONS 2026-11-11).

## 6. Open points

1. **Plugin selectors not confirmed.** The v7 Elements page returned HTTP 404 during planning. The policies page documents selectors, captured values (`{{from.element.captured.<name>}}`), negation with `!`, and last-match-wins. It does not say how a descriptor captures the module slug or how a file category separates entry files from internal files. Section 3, step 4 confirms both. Confirmed at revision 3 by the implementer's config (333399b) and the Opus plan review: the capture key is `capture` on the element descriptor, and entry files come from `boundaries/files` with `category: entry`. If the plugin cannot express rules R1 to R3, the implementation stops for the Navigator, and the plugin is not switched silently. The named fallback is in section 3, step 4 and DECISIONS 2026-11-11.
2. **Path base.** The plugin's base for matching paths (cwd or config directory) is not documented in the pages read. Revision 3: element patterns match from the right, so they work from any base. File patterns (`boundaries/files`) match the path relative to `process.cwd()`, which is why they keep `**/` (section 2). The lint that really runs on module files is each workspace's `eslint .`, with cwd inside the workspace. The criteria do not test that cwd, and the root negative control (step 9) does not either. Step 12 now runs `npm run lint -w @bbartolome/scriba-api`, which uses the workspace as cwd, so that path is exercised once. The Opus plan review (revision 3) checked the fixture cases from the repository root and with `apps/api` and `apps/web` as the cwd; step 12 confirms the in-repo case.
3. **Resolver extensions.** `eslint-import-resolver-node` must resolve `../x` to `x.ts`. The bad fixtures prove it: they must error. If they do not, the resolver setting is wrong, not the rule. Decided (revision 3): `eslint.config.mjs` sets `settings['import/resolver'] = { node: { extensions: ['.ts', '.mjs', '.js', '.json', '.node'] } }`. The default extensions are in `eslint-import-resolver-node/index.js` (`['.mjs', '.js', '.json', '.node']`, no `.ts`). The bad fixtures must still error with the setting in place.
4. **Web routes file name.** Decided (DECISIONS 2026-11-11, smaller choices item 5): `<m>.routes.ts`. No document names it, and the feature units confirm the name when they are planned.
5. **Cross-module providers.** The unit allows importing `<m>.module.ts` but does not say how a module gets another module's exported provider type (a re-export from the entry file, or a type in contracts). The rule does not decide this. The Navigator must decide before `GRR-02` or `AGL-03` needs it.
