### 1b. Decisions this plan makes (the unit leaves them open)

- **D1 Files and names.** Feature folder `apps/web/src/app/features/agent-loop/` with: `agent-loop.routes.ts` (the entry, exports `chatRoutes`), `chat-page.ts` (component `ChatPage`, selector `app-chat-page`), `chat-state.ts` (pure view state and mapping), `agent-contract.ts` (route paths, response guards, event guard), `chat-page.spec.ts` and `agent-contract.spec.ts`. `chatRoutes` follows the `<segment>Routes` rule of S4. No other name is chosen.
- **D2 Route entry.** One entry appended to `PROJECT_ROUTES` (replacing `[]` at `app.routes.ts` line 11): `path: 'chat'`, `pathMatch: 'full'`, `data: { scope: 'project', minDeviceClass: 'phone', nav: { label: 'Chat', icon: 'chat', order: 10 } } satisfies ShellRouteData`, `loadChildren` to `chatRoutes`. The child is `{ path: '', pathMatch: 'full', component: ChatPage }`, the shape of the core-gate entry (`apps/web/src/app/app.routes.ts` lines 37 to 49; `apps/web/src/app/shell/core-gate/core-gate.routes.ts` lines 4 to 6). The nav order 10 and the icon `chat` (a Material icon name, as `apps/web/src/app/shell/app-nav.spec.ts` line 59 uses) are this plan's choice.
- **D3 Copies and guards.** `agent-contract.ts` holds literal copies of the paths: `AGENT_RUNS_PATH` `/api/agent-loop/runs`, `AGENT_RUN_STOP_PATH` `/api/agent-loop/runs/stop`, `AGENT_RUN_CURRENT_PATH` `/api/agent-loop/runs/current`, `AGENT_CONVERSATIONS_PATH` `/api/agent-loop/conversations`, `AGENT_CONVERSATION_PATH` `/api/agent-loop/conversations/:conversationId` (a template), `AGENT_SETTINGS_PATH` `/api/agent-loop/settings`. It also has `conversationPath(id)`, which fills the template with `encodeURIComponent(id)` (the HTTP client's `params` are query parameters, not path parameters). It also copies the three codes the page reads: `AGENT_NO_PROVIDER_CODE`, `AGENT_RUN_ACTIVE_CODE` and `AGENT_RUN_NOT_FOUND_CODE` (`errors.ts` lines 5 to 10). Response guards are `ResponseSchema` objects (`apps/web/src/app/shell/api-client.ts` lines 17 to 21) for: the start reply; the run state or `null`; the conversation list; the conversation history; the settings (the same guard for GET and POST); and `anyReply`, which accepts every body, for the stop reply (D8), because `ApiClient.post` needs a schema (`api-client.ts` lines 30 to 34). `isChatEvent(envelope)` accepts exactly the eight types the page handles (D4); the grounding types are refused (D18). The guards check every field the page reads, with the contract's bounds. For the fields the page only keeps or passes on, they check the outer kind and not the contents: `arguments` and `output` (any value), `diffPreview` (an object), `sourcesUsed` (an array), `provenance` (an object) and `groundingResults` (an array). AGL-09, AGL-14 and AGL-18 tighten these when they read them (section 5). Types come from type-only imports of the contract's `*Data` and state types.
- **D4 Event reducer.** `applyChatEvent(state, event)`. A turn is keyed by `runId`. `run-started` opens a turn for an unknown run id. Any other event for an unknown run id is ignored. Then the `seq` rule: an event with `seq <= turn.lastSeq` is ignored; any other is applied and sets `lastSeq`. The counter is per run (`ids.ts` lines 8 to 9), so the rule is per turn.
- **D5 Card mapping.** `tool-call-started` gives status `pending`. `tool-call-args` gives `running`, with `arguments` (the parsed value or the raw string, as `events.ts` line 30 notes) and `valid`. `tool-call-result` gives `done`, with `summary`; `output` becomes `{ kind: 'markdown', text }` for a string and `{ kind: 'json', value }` for any other value, and is absent when the event has none. `tool-call-error` gives `error` with `Attempt <attempt>: <message>`, plus ` (withdrawn)` when `withdrawn` is true (the mapping of `plans/SHL-10.md` line 117). `collapsed` is never set. `sources` stays absent (D16). The page's card state also keeps `diffPreview` and `sourcesUsed` from the result, for AGL-09 and AGL-14. A card of a run state or a conversation history (`agentCardSchema`, `cards.ts` lines 17 to 36, whose status is `running`, `done` or `error`, `constants.ts` line 53) maps by the same rules: the status as it is; `arguments`, `summary` and `output` as above; `error` as `Attempt <attempt>: <message>`, plus ` (withdrawn)`.
- **D6 Load and reconcile.** The page subscribes to `stream('agent-loop')` and to `reconcile$` when it is created, then refreshes (GET `AGENT_RUN_CURRENT_PATH`) at load and on every tick. The refresh is a `switchMap`, so a newer tick replaces an older request. While a refresh is in flight, events are buffered. On success the state's run turn is replaced (or added) with the state's status, step, cap, text, cards, `pendingChangeIds`, `lastSeq`, `reason` and `conversationId`; then the buffer is applied with the D4 rule. On failure the page shows the error, keeps the view and applies the buffer with the same rule. "No run" is a 2xx `null` body or a 404 `AGENT_RUN_NOT_FOUND` (section 6, point 3); it changes nothing in the view and shows no error. A refresh is also requested after each applied `tool-call-started` (D12), through the same `switchMap`. When `ActiveProjectSignal.projectId()` changes while the page is shown (the Shell's project-switch follower reuses the component for `/projects/<new id>/chat`), the page clears its turns, `conversationId`, `activeRunId` and error, and loads again (settings, conversations, run state).
- **D7 Active run.** `activeRunId` is set by a start reply (unless that run's `run-ended` has already been applied), by `run-started`, or by a state with `status: running`. It is cleared by `run-ended` of that run or by a state with `status: ended`. The Stop button shows while `activeRunId` is set, and Send is disabled then.
- **D8 Stop.** `POST AGENT_RUN_STOP_PATH` with `{ runId: activeRunId }`, with the `anyReply` guard. The reply is ignored (section 6, point 4). Stop stays until `run-ended` arrives, which the loop sends with `stopped` (AGL-03 line 24).
- **D9 Continue.** Shown when no run is active and the latest finished turn ended `capped`. It sends `POST AGENT_RUNS_PATH` with `{ intent: 'Continue', conversationId }` (S12; section 6, point 5).
- **D10 Start.** `POST AGENT_RUNS_PATH` with `{ intent }`, plus `conversationId` when the page has one. The reply sets the page's `conversationId` and `activeRunId` (D7). The page shows the sent intent above that run's text; a turn from a history shows its `intent`.
- **D11 Errors.** `AGENT_NO_PROVIDER` shows "Set up a model provider first." with a link `href="/providers"` (a plain href; MPR-11 adds that route, and `plans/MPR-09.md` line 224 names it). `AGENT_RUN_ACTIVE` shows "An agent run is already active in this project." Any other error of a read or a command (an `ApiError` with another code, an `ApiSchemaError`, or any other `Error`, such as the fake's "No canned response") shows its `message`. Every subscription has an error handler, and no error is rethrown: `landing.spec.ts` C1 and `project-route.spec.ts` C2 render this page through `APP_ROUTES` at `/projects/a/chat` and `/projects/b/chat` with no canned agent-loop reads, and they must pass unchanged (step 11). All in a `role="alert"` paragraph (S18). The wording is this plan's.
- **D12 Step counter.** "step {step} of {cap}" for the latest turn, shown once the turn has a `step`. `step` and `cap` come from the latest run state or `step-cap-reached` (`events.ts` lines 63 to 66). No other event carries `step`, and one step can hold several tool calls (AGL-03 line 22), so the page does not count events. Instead each applied `tool-call-started` requests a run-state refresh (D6): the call's step has started by then, so the state's `step` is the current one (Check B2). A step with text and no tool call is the run's last; the counter reaches it only at a later refresh (a reconcile tick). Before a state arrives, `cap` is the `stepCap` read from the settings at load. Section 6, point 1.
- **D13 Settings sheet.** A section (`aria-label="Agent settings"`) opened by a "Settings" button. Fields: step cap (a number, minimum 1), research enabled (a checkbox), search endpoint (a URL input). The page loads `GET AGENT_SETTINGS_PATH` at start. Save sends `POST` with only the changed fields; the reply replaces the form values. An emptied endpoint is not sent (section 6, point 7). The research controls take effect at AGL-21, which names them as AGL-07's (AGL-21 unit line 21).
- **D14 Conversations.** The list (`GET AGENT_CONVERSATIONS_PATH`) loads at start and after each `run-ended`. Choosing an entry loads its history (`GET conversationPath(id)`) and replaces the stream. "New conversation" clears the stream and the page's `conversationId`.
- **D15 Review link.** When `run-ended` carries a non-empty `pendingChangeIds`, the page shows a link `href="/projects/<projectId>/review?run=<runId>"`. `projectId` comes from `ActiveProjectSignal.projectId()` (`apps/web/src/app/shell/project-scope.ts` lines 75 to 83). The link cannot appear before AGL-12 (S14).
- **D16 Sources.** No id-to-path mapping in AGL-07. The card's `sources` stays absent. AGL-09 owns the links (its unit line 21).
- **D17 Layout.** One column at every width (S16). The intent form and the Stop button sit in a footer with `position: sticky; bottom: 0`. Buttons, inputs and the card header are at least 44 px tall (CSS in the component). The page has no `aside` element. The inline styles stay under the 4 kB `anyComponentStyle` warning budget (`apps/web/angular.json` lines 39 to 41).
- **D18 Grounding events.** `grounding-started` and `grounding-result` are not handled. `isChatEvent` refuses them, so the reducer never sees them. AGL-18 adds them, with its own guard and reducer branch. The run state's `groundingResults` is accepted as an array and its contents are not inspected.

- **D20 Test setup.** Each spec registers `provideRouter([{ path: 'projects/:projectId', children: PROJECT_ROUTES }])`. That is the real chat entry, and it avoids the Shell's guard, which sits on the parent in `APP_ROUTES` (`app.routes.ts` line 34; `plans/SHL-08.md` line 179).
