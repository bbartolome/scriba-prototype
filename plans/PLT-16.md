## 1a. Variant B design

**Source.** Unit line 21 ("if it fails, run the CLI loop"). PLT-15 unit line 22: containerboot runs; then wait indefinitely for an IP; then `tailscale serve --bg --https=443 http://127.0.0.1:8080`; "no 60-second give-up, no `--http=80` handler". Navigator decision ee18308211d34b28bbf2915f60373be9 (DECISIONS line 1724): B in revision 2, compose ships if B passes, and the teardown before the retest (line 1748). Tride's loop (`/Users/bbartolome/workspace/tride/src/installer/docker-compose.yml` lines 30 to 48) has the same shape with a 60-second bound and `--http=80`. This plan keeps the shape and drops those two parts.

**What the image does (checked, FACT).**

- The image has no ENTRYPOINT. Its CMD is `/usr/local/bin/containerboot` (`docker image inspect tailscale/tailscale:v1.104.4`, `Config.Cmd`). `sh` is at `/bin/sh`.
- `/usr/local/bin` holds three binaries: `containerboot`, `tailscale` and `tailscaled`, all 1.104.4 (`tailscale version`, commit 27047635f). The image has no documentation files (`find` finds no `.md` file).
- The containerboot binary carries the env names `TS_BOOT_TIMEOUT`, `TS_SERVE_CONFIG`, `TS_CERT_DOMAIN`, `TS_EXTRA_ARGS` and `TS_AUTHKEY`, and the messages `error parsing TS_BOOT_TIMEOUT value %q`, `serve proxy: applying serve config`, `serve proxy: no serve config at %q, skipping`, `error waiting for cert domain %s`, `failed to bring up tailscale: %w` and `shutdown signal`. These are read with `grep -a`, so the code paths behind them are not confirmed.
- `tailscale up --timeout` defaults to `0s`, which "blocks forever" (`tailscale up --help`). So the 60-second give-up is not the CLI's own default.
- The string `60s` or `1m0s` is not in the containerboot binary. The default of `TS_BOOT_TIMEOUT` is therefore not confirmed (D22).
- `tailscale --help` gives the socket default `/var/run/tailscale/tailscaled.sock`, which equals `TS_SOCKET` in compose line 15. `tailscale ip -4` exists.
- `tailscale serve --help` (1.104.4) lists `--bg`, `--https` (the default mode), `--yes` ("Update without interactive prompts"), `reset`, `get-config` and `set-config`.

**Compose changes, by line of `deploy/compose.yaml` on `main`.**

- Line 16, `TS_SERVE_CONFIG: /config/serve/serve.json`: removed (D26).
- A new line after line 15 (`TS_SOCKET`): `TS_BOOT_TIMEOUT: 8760h` (D23; ASSUMED value).
- A new `command:` block after the `environment:` block: the wrapper below. It replaces the image's CMD (D21).
- Line 28, `- ./serve:/config/serve:ro`: removed. `deploy/serve/` is deleted (D26).
- Unchanged: line 6 `init: true` (tini is PID 1, so signals reach containerboot); line 7 `restart: unless-stopped`; lines 8 to 10 `env_file`; lines 17 to 22 (`cap_add`, `devices`, `extra_hosts`); lines 23 to 24 (the loopback publish `127.0.0.1:${SCRIBA_PORT:-8080}:8080`); lines 26 and 27 (the state and socket volumes); the whole `scriba` service (lines 30 to 59); the top-level `volumes:` (lines 61 to 63); the healthcheck.
- `deploy/compose-version` line 1: `1` to `2` (D4).

The wrapper the code stage writes (this plan does not change `deploy/compose.yaml`; it fixes the text):

```yaml
    command:
      - sh
      - -c
      - |
        (
          until [ -n "$$(tailscale ip -4 2>/dev/null)" ]; do sleep 2; done
          tailscale serve reset
          tailscale serve --bg --https=443 http://127.0.0.1:8080 || echo "serve step failed, exit $$?" >&2
        ) &
        exec /usr/local/bin/containerboot
```

What each part relies on:

- `exec`: containerboot is the foreground process. When it exits, the container exits and Docker restarts it, as today (D21). ASSUMED: containerboot handles SIGTERM (`shutdown signal` is in the binary; text only).
- The background subshell waits for an IP with no counter and no timeout (D24). ASSUMED: `tailscale ip -4` prints nothing while there is no IP (not run).
- The serve step runs only after an IP appears. In the retest the node stays in `NeedsLogin`, so the serve step is not reached (step C6, M2).
- `tailscale serve reset` makes a restart idempotent (D25). ASSUMED: the serve config is kept in tailscaled's state, so it survives a restart of the container. Not run.
- The serve step runs once, when the IP first appears, with no retry (D28). If it fails or does not configure Serve (for example, HTTPS certificates are off, open point 4), the `||` clause logs a non-zero exit to stderr as `serve step failed, exit N`. ASSUMED: that line reaches `docker compose logs tailscale`, and HTTPS off makes `tailscale serve --bg` exit non-zero (section 7b). A stale state is possible: if the step fails once, or the node is logged out and back in after the loop has exited, Serve stays unconfigured until the container restarts (section 5, SAU-20 and SAU-21). The step is checked at steps 12a-CERT and 12b-SERVE.
- `--https=443 http://127.0.0.1:8080` is a Web handler, as the Web entry of `deploy/serve/serve.json` is, so Tride's comment on Web handlers (lines 17 to 29) applies, and D27 holds. The handler shape is checked at step 12b-SERVE.

**Alternatives rejected.**

- `TS_BOOT_TIMEOUT` alone, with no wrapper: no serve step, and no wait for an IP.
- The wrapper alone, without `TS_BOOT_TIMEOUT`: containerboot still gives up at about 60 s, and the container exits with it (DECISIONS 8b3dec6). Rejected on the observed evidence.
- Keeping `TS_SERVE_CONFIG` next to the CLI: two writers of one config. Rejected (D26).
- Running `tailscaled` directly and dropping containerboot: not chosen. It changes the wording "run containerboot" of PLT-15 line 22, and the Navigator's decision names the containerboot loop. It is the next design only if the retest shows containerboot still gives up at about 60 s. That case needs a Navigator decision (open point 2).
- Tride's 60-second bound and `--http=80` handler: rejected by PLT-15 line 22.
