### 1c. Choices of this plan

- **D1 Files.** New `apps/api/src/modules/compile-export/export-settings.service.ts`: two exported pure functions, `settingsRevisionOf(raw)` and `effectiveSettingsOf(stored, genrePack)`, and the class `ExportSettingsService`. New `apps/api/src/modules/compile-export/export-settings.controller.ts`. The copy default is a method of `ExportService` (D7), because the built-in path lookup `templateOf` is private there. No new contract, no new built-in file.
- **D2 Settings revision.** `settingsRevisionOf(raw)` is `sha256:` plus the SHA-256 hex of `JSON.stringify(raw ?? null)`, where `raw` is the `export` key as the YAML document holds it, before any schema default. It is the same form as `ManuscriptService.revisionOf` (`manuscript.service.ts` lines 267 to 271). It covers only the `export` key.
- **D3 GET.** `GET` returns `{revision, settings}` (`exportSettingsViewSchema`). `settings` is the stored `export` keys plus two read-time defaults: `lang` is `EXPORT_LANG_DEFAULT` when the stored value is absent or `''`; `bibliography` is the stored value, else `BIBLIOGRAPHY_DEFAULT_BY_PACK[genrePack]` (own key only), else `BIBLIOGRAPHY_DEFAULT`. That is the rule of `assembly.service.ts` lines 144 to 151, written again because the method is private (open point 6). No other default is shown. The author's fallback to the preferences (`assembly.service.ts` line 97) is not shown; the assembly keeps it.
- **D4 POST write.** (1) The active project; no active project gives `PROJECT_NO_ACTIVE`, as in the other services. (2) When `request.revision` differs from the current settings revision, refuse with `COMPILE_ORDER_CONFLICT` (409); nothing is written. (3) `merged` is the stored raw `export` object with the body's `settings` laid over it: keys present in the body replace the stored value, absent keys stay, unknown keys survive. (4) `exportSettingsSchema.parse(merged)`. (5) One `files.updateProjectYaml(projectId, {export: merged})`. (6) The response is the fresh view. No event is published: the unit names no settings event, and the Project store publishes `files-changed` itself. `''` is unset for the text and override keys, as `nonEmpty()` in the assembly treats it (open point 3). The write does not check the overrides: the check is before Pandoc (U2).
- **D5 Override check.** `OVERRIDE_KEY: Record<PandocFormat, 'docxReferenceDoc' | 'epubCss' | 'typstTemplate'>` maps `docx`, `epub` and `pdf` (typed by `PandocFormat`, which no sibling extends). `ExportService.overrideOf(projectId, root, format)` returns `undefined` when the key is absent or `''`. Otherwise it calls `this.store.resolvePath(root, value)`; any refusal of that call (PATH_INVALID, PATH_RESERVED, PATH_OUTSIDE) becomes `COMPILE_TEMPLATE_INVALID`. A target that is the root, that does not exist, or that is not a regular file (`statSync(realPath).isFile()`) also becomes `COMPILE_TEMPLATE_INVALID`. The result is the absolute `realPath`, passed to Pandoc through the file flag and never returned to the client. Fixed message: "The project template is missing or not allowed. Check its path in the export settings." No input value is echoed.
- **D6 Template resolution.** `templateOf(format, override?: string)`: its first line is `if (override !== undefined) return override;`, then the existing switch, unchanged, which siblings extend. The call in `export()` (main line 151) becomes `template`, computed after the project root is known (line 127) and before the exports folder is created (line 133): `const template = format === 'md' ? undefined : this.templateOf(format, this.overrideOf(projectId, root, format));`. A template error therefore creates no folder and no partial file, and Pandoc is never started. `md` is not checked, because it has no Pandoc run. This changes the signature by one optional parameter; the sibling plans say "changes only the body of templateOf", and section 6a states why the parameter is needed.
- **D7 Copy default.** `ExportService.copyDefault(request: CopyDefaultRequest): FileWriteResult`, with this order: (1) the active project; (2) `this.store.resolvePath(root, request.path)`, whose refusals are kept (`PROJECT_PATH_INVALID` for `..` or empty segments, `PROJECT_PATH_RESERVED` for `.scriba/` and `drafts/.versions/`); (3) the root file `project.yaml` is refused with `PROJECT_PATH_RESERVED` (400) and the fixed message "project.yaml is not a template path."; (4) a target that exists is refused with `PROJECT_FILE_EXISTS` (409), so an author's file is never overwritten (open point 7); (5) the source is `this.templateOf(request.format)` (built-in only); `undefined` gives `COMPILE_TEMPLATE_INVALID` (422) with the message "This format has no built-in template in this build."; for `docx`, until open point 1 is decided, the source is refused with `COMPILE_TEMPLATE_INVALID` and the message "The DOCX reference cannot be copied yet."; (6) for `epub` and `pdf`, `this.files.write(projectId, {path: target.relativePath, content: readFileSync(source, 'utf8')})`. The response is the Project store's `FileWriteResult` (`{path, hash, mtime}`, files.ts lines 49 to 53), so no new response schema is needed. The file API creates the parent folders of a chosen path (P7); the suggested root path creates none.
- **D8 Routes.** In `export-settings.controller.ts`: `@Get(EXPORT_SETTINGS_ROUTE)`; `@Post(EXPORT_SETTINGS_ROUTE)` with `@HttpCode(200)`, body through `ZodValidationPipe(exportSettingsWriteSchema)`; `@Post(EXPORT_COPY_DEFAULT_ROUTE)` with `@HttpCode(200)`, body through `ZodValidationPipe(copyDefaultRequestSchema)`, calling `this.exports.copyDefault(body)`. The pattern is `export.controller.ts` lines 29 to 35 and `snapshot.controller.ts` lines 27 and 28. `compile-export.module.ts` registers the new service (providers) and the new controller (controllers, lines 25 to 38). `ExportService` receives `ExportSettingsService` as a constructor parameter, so `ExportService.overrideOf` can read the stored `export` key. The dependency is one way: the settings service imports no compile-export service.
- **D9 Test file and seams.** `apps/api/test/compile-export-templates.test.ts` (new). Helpers stay in that file. It reuses `withManuscript` (`compile-export-manuscript.kit.ts` line 53), `withExport`, `fakePandoc` and `removeFake` (`compile-export-export.kit.ts` lines 69, 81 and 90), `binaryDownload` and `readZip` (`compile-export-docx.kit.ts` lines 100 and 18), `putFile` (`project-store-files.kit.ts` line 70), `postJson` (`project-store-projects.kit.ts` line 111) and `send` (`guard-request.ts` line 27). No kit file changes.
- **D10 Comment on lines 206 and 207.** After CEX-12 the comment reads "CEX-13 adds its case, and CEX-14 puts the project override first, before the built-in path." CEX-14 keeps that sentence unchanged, because the override is now checked first (D6). CEX-13 removes "CEX-13 adds its case, and" (`plans/CEX-13.md` at `83a5095`, D4). CEX-14 names no other unit in its own comments.
- **D11 Fake Pandoc marker.** A fake Pandoc (`fakePandoc('touch "$0.ran"')`) creates `<fake path>.ran` when it runs. The marker sits in the fake's own temp folder, so `removeFake` removes it. A test checks that the marker does not exist when a template error is returned.
