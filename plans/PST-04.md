## 1. Decisions this plan follows

- **D1 Persistence.** The active id is stored in the `projects` section of `settings.yaml` as `{schemaVersion: 1, active: <projectId> | null}`. It is read and written through Platform's `SettingsService`. Source: unit line 18; module line 76 (settled); the section is already registered with that default (`apps/api/src/modules/project-store/project-store.section.ts` lines 5, 8 and 10); contract `packages/contracts/src/project-store/settings.ts` lines 8 to 10.
- **D2 Routes and answers.** `GET /api/project-store/active` answers `{active}`. `POST /api/project-store/active` with `{projectId}` activates the project and answers `{active}` with status 200. Source: unit line 19; `packages/contracts/src/project-store/routes.ts` line 12 (`ACTIVE_PROJECT_ROUTE`; the comment at lines 1 to 4 says the route names no project); `project.ts` lines 72 to 74 (`activateRequestSchema`) and 77 to 79 (`activeProjectSchema`); `plans/PST-01.md` line 63 (GET and POST, answers `{active}`); `plans/SHL-08.md` lines 177 and 237, which require the POST to answer `{active}` (`plans/DECISIONS.md` line 2532). Status 200 follows the import command (`projects.controller.ts` lines 38 and 39).
- **D3 Refusals of the target.** A `too-new` project is refused with 409 `PROJECT_SCHEMA_TOO_NEW`. An `invalid` project is refused with 422 `PROJECT_INVALID`, and the Zod issues go in `details`. Source: unit lines 20 and 30; statuses in `errors.ts` lines 72 and 73. Import already maps these two states the same way (`projects.service.ts` lines 125 and 131).
- **D4 Lookup by id.** The requested id is looked up in the discovered list only, through `ProjectsService.find` (`projects.service.ts` line 66). It is never joined to a path. An id that is not found is refused with 404 `PROJECT_NOT_FOUND` (`errors.ts` line 62). Source: `plans/PST-02.md` line 63 (S12, the hand-off on project ids); `plans/PST-03.md` line 166.
- **D5 Importable folder.** A folder with no `project.yaml` is refused with 404 `PROJECT_NOT_FOUND`. Planner's choice (open point 1). The unit names only `too-new` and `invalid`. The list status `importable` means "no project.yaml" (`units/PST-03-discovery-new-import.md` line 20; `project-discovery.ts` line 85).
- **D6 Activating the active project again.** The request is validated as in D3 to D5. Then nothing changes: no hook, no write, no event. The answer is `{active}`. Planner's choice (open point 2).
- **D7 Order of a switch.** (1) Find the target and refuse it as in D3 to D5. (2) If the target is already active, answer (D6). (3) A comment marks where PST-23 runs the `project.yaml` migrations; no code now. (4) Call every hook with `{from, to}`. (5) Persist the section. (6) Publish `project-switched`. (7) Answer `{active}`. Source: unit lines 20 to 23 (validate, migration point, hooks synchronously before publishing, publish); `units/PST-12-files-gate.md` line 26 (publish "after the in-process hooks"). The place of step 5, after the hooks, is planner's choice (open point 3).
- **D8 Hooks.** `ProjectStoreService.onProjectSwitched(handler)` adds a handler. Each handler receives the contract's `ProjectSwitchedData`, `{from, to}` (`events.ts` lines 19 to 22 and 66). Handlers run synchronously, in registration order. An exception from a handler is not caught: the POST answers 500 `PLATFORM_INTERNAL` (`packages/contracts/src/platform/errors.ts` lines 40 and 48; `apps/api/src/modules/platform/errors/platform-exception.filter.ts` lines 94 and 95), and nothing is persisted or published. Source: unit lines 22 and 25; module line 52. The rule for exceptions is planner's choice (open point 3).
- **D9 Event.** After step 5, `EventsPublisher.publish({module: 'project-store', type: 'project-switched', data: {from, to}})` (unit line 23). `from` is `null` when no project was active before (`events.ts` line 18 comment). Member schema: `events.ts` lines 48 to 52. Publisher: `apps/api/src/modules/platform/events/events.publisher.ts` line 61.
- **D10 Active-project check.** `ProjectStoreService.requireActive(projectId)`: when no project is active it throws 409 `PROJECT_NO_ACTIVE`; when the named project is not the active one it throws 409 `PROJECT_NOT_ACTIVE` (codes `errors.ts` lines 16 and 17; statuses lines 69 and 70). The check compares ids only and does not look up the folder (open point 4). `propose` and `appendLog` never call it. Source: unit line 24; module line 47; the exemption is also in unit `PST-15` line 19 and in the DECISIONS line 2297 quote of PST-04 line 24.
- **D11 Exported provider and layout.** The hook registry, `activeId()` and `requireActive()` live on `ProjectStoreService`, the exported provider (module line 52; unit line 25). `ProjectStoreService` takes `SettingsService` in its constructor. It does not take `ProjectsService`, because `ProjectsService` already takes `ProjectStoreService`, and that would be a cycle. The activation itself is in a new class, `ActiveProjectService`. Source: `plans/PST-02.md` line 311 (each later unit adds its own `@Injectable()` file and only the delegating methods other modules call) and `plans/PST-03.md` line 184 (a delegating method on `ProjectStoreService` for the active check). The layout is planner's choice.
- **D12 Messages and paths.** Fixed strings only. No input value is echoed and no container path appears (`projects.service.ts` line 34 comment; module line 48; `units/PST-02-module-skeleton-path-safety.md` line 30). The two new messages are `ACTIVE_MESSAGES.NO_ACTIVE` = `No project is active. Activate a project first.` and `ACTIVE_MESSAGES.NOT_ACTIVE` = `That project is not the active project.` The other refusals reuse the strings of `PROJECT_MESSAGES`.
- **D13 Guard.** The new routes sit behind Setup & auth's global guard, which is registered as `APP_GUARD` (`apps/api/src/modules/setup-auth/setup-auth.module.ts` line 44). The guard needs a setup cookie for every route that is not public, and the Origin of its own Host for every mutation, public or not (`setup-auth.guard.ts` lines 35 and 36). Source: module line 46; `units/PST-12-files-gate.md` line 17. This module adds no guard of its own.
- **D14 No contract change.** The routes, schemas, the `project-switched` member and the codes exist from PST-01 (`units/PST-01-contract-slice.md` lines 27 and 48; `plans/PST-01.md` line 63). This unit changes nothing under `packages/contracts/`.
- **D15 Migration point.** PST-04 leaves the comment only. PST-23 puts the migration call at step (3) of D7 (`units/PST-23-lazy-migrations.md` line 21; unit line 21).
- **D16 Test seam.** The module's default seam: the composed app, or one module in `create-test-app`, against a temp library, over HTTP and SSE only. Never `examples/` (module lines 56 and 58). The test-only route follows the path-safety kit (`apps/api/test/project-store-path-safety.kit.ts` lines 230 and 247 to 251; booted by `project-store-path-safety.test.ts` line 153 with `modules: [PathSafetyKitModule]`). ## 6. Open points

1. **Importable target (D5).** Recommended: 404 `PROJECT_NOT_FOUND`. The alternative is 422 `PROJECT_INVALID`, but a folder with no `project.yaml` has no issues to report. The picker unit lists Import for importable folders (unit line 21) and does not mention switching to one (unit line 22), so only a crafted request reaches this case.
2. **Re-activating the active project (D6).** Recommended: a no-op with no hook, no write and no event. A second event with `from` equal to `to` would tell the Agent loop and the Graph runner to stop their runs on the project that stays active.
3. **Hook order and failures (D7, D8).** Recommended: hooks run before the write, so a failing hook leaves the state unchanged and publishes nothing (E3). The alternative, writing first, leaves the new project active with no event after a failing hook. The cost is that a hook sees the old active id; check 5 covers the consumers.
4. **The check compares ids only (D10).** A stale active id whose folder was removed passes the check, and PST-06 maps the missing folder to 404 (check 1).
