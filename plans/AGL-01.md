### 1b. Decisions this plan makes (the unit leaves them open)

- **D1 Layout.** Twelve files under `packages/contracts/src/agent-loop/`: `constants.ts`, `ids.ts`, `routes.ts`, `errors.ts`, `grounding.ts`, `provenance.ts`, `cards.ts`, `events.ts`, `runs.ts`, `transcript.ts`, `settings.ts` and `index.ts` (`export * from './<file>.js'` for the eleven, as `project-store/index.ts` does). Files import each other in this order, so no cycle arises: constants, ids, grounding, provenance, cards, events, runs, transcript, settings.
- **D2 Names.** Every exported `fooSchema` has an exported type `Foo = z.infer<typeof fooSchema>`. Names that could clash in a file that imports two slices carry the `agent` prefix (`agentStartRequestSchema`, `agentRunStateSchema`, `agentSeqSchema`). Constants are `SCREAMING_SNAKE`. Each enum is an exported `as const` tuple plus a `z.enum` over it (the pattern of `PROJECT_ERROR_CODE_VALUES`); the seven enum schemas are named in section 2 and checked by C1b and E1.
- **D3 `seq`.** `agentSeqSchema` is an integer at least 1; the first item of a run is 1. `lastSeq` in the run state is an integer at least 0 (0 means "no event yet"), so the reconcile rule `seq > lastSeq` (`units/AGL-05` line 19) works from the first event. The unit says only "increasing".
- **D4 Event data.** `agentEventBaseSchema = {runId, seq}`. Eight data schemas extend it (`token-delta`, `tool-call-started`, `tool-call-args`, `tool-call-result`, `tool-call-error`, `grounding-started`, `step-cap-reached`, `run-ended`). `run-started` is the base itself, because the unit lists no field for it (open point 1). `grounding-result` data is the grounding result (`groundingResultSchema.extend({seq})`), not an extension of the base: the unit writes "`grounding-result` (grounding result)", and the result already carries `runId`.
- **D5 Tool-call events.** `tool-call-started {callId, name, family}`. `tool-call-args {callId, arguments, valid}` with `arguments: z.unknown()` (a required key; Zod 4.6.7 treats a `z.unknown()` key as required, `plans/PLT-02.md` section 1), because the unit says "final, validated or raw": the parsed value when the JSON parsed, otherwise the raw string. `tool-call-result {callId, summary, output?, diffPreview?, sourcesUsed?, provenance?}`. `tool-call-error {callId, message, attempt, withdrawn?}` with `attempt` an integer at least 1. `summary` (`tool-call-result`), `message` (`tool-call-error` and `run-ended`) and `text` (`token-delta`) are strings (`z.string()`; `text` may be empty, because a provider can stream an empty delta). **`output` is `z.unknown().optional()`, on the event and on the card (D7).** Reason: the field is the result of a tool of any of the five families. `list_files` returns a listing, `read_file` returns text, `search_notes` returns passages, and only a narrative tool returns the Tool registry's `toolOutputSchema` value `{kind, content}` with `kind` one of `draft | entity | claims | graph | check` (`units/TRG-12-executor.md` line 27; `plans/TRG-01.md` line 106). A structural `{kind, content}` would refuse every project, research and compile result. The slice cannot import `/tool-registry` (AGL-01's `blocked_by` does not name TRG-01; `plans/TRG-01.md` lines 181 and 195), so it does not repeat that shape; the comment on the field says that for the `narrative` family the value has the `{kind, content}` shape, and a consumer narrows on `family`. C2 tests the three value kinds.
- **D6 Result fields.** `diffPreview = {path, base, proposed}`, all strings; `base` is the empty string for a file that does not exist yet (`units/SHL-12-readonly-diff.md` line 18 takes base and proposed text). `sourcesUsed` is an array of entity references (ids), not paths: the Tool registry returns `sourcesUsed: EntityRef[]` (`units/TRG-01-contract-slice.md` line 30; `units/TRG-12-executor.md` line 29), the Graph runner stores the same (`units/GRR-01` line 29), and the review queue shows both runs' provenance the same way (`units/PST-20` line 16). `provenance` is the draft provenance of D12.
- **D7 Card state** (the unit writes "cards: [...card state]" without fields). `agentCardSchema`: `callId`, `name`, `family`, `status` (`running | done | error`), and the optional accumulated fields `arguments` (unknown), `valid`, `summary` (string), `output` (`z.unknown().optional()`, as D5), `diffPreview`, `sourcesUsed`, `provenance`, `error {message (string), attempt, withdrawn?}`. It is the sum of the `tool-call-*` events of one call. The Shell's own card model (`pending | running | done | error`, `units/SHL-10` line 18) is the Agent loop's mapping target, not this shape (SHL-10 line 20).
- **D8 Run state** (unit line 28). `agentRunStateSchema`: `runId`, `conversationId`, `status` (`running | ended`), `step` (integer at least 0), `cap` (integer at least 1), `assistantText`, `cards` (array of D7), `groundingResults` (array of results), `pendingChangeIds` (array of non-empty strings), `lastSeq` (D3) and `reason?` (the run-end reason, present when `status` is `ended`). It has no `message?`, no `intent?` (open point 1).
- **D9 Conversations** (unit line 28). `conversationTurnSchema = {runId, intent, assistantText, cards, endedAt (ISO datetime with Z), reason}`; `conversationHistorySchema = {conversationId, turns}`, finished turns only; the active run is in the run state. The unit gives no fields for the conversation list. `conversationSummarySchema = {conversationId, intent (the first intent, as a label), updatedAt (ISO), turnCount (integer at least 1)}` and `conversationListSchema = {conversations: summary[]}` (the wrapper the other slices use, for example `fileListSchema`).
- **D10 Transcript entry** (unit line 31). `{schemaVersion: literal 1, at (ISO datetime with Z), runId, conversationId, seq (D3), kind (the nine), data}`. `data` is `z.unknown()` (required key): the unit fixes no payload per kind (open point 3). The entry's `seq` is the same per-run counter as the stream's, so that the run state rebuilt from a transcript (`units/AGL-05` line 20) yields `lastSeq`. Path constants: a template text and a pattern for each path rule (D11).
- **D11 Path constants.** `GROUNDING_ARTEFACT_PATH_PREFIX = 'logs/grounding/'`, `GROUNDING_ARTEFACT_PATH_SUFFIX = '.json'`, `GROUNDING_ARTEFACT_PATH_TEMPLATE = 'logs/grounding/<targetPath>.json'`, `GROUNDING_ARTEFACT_PATH_PATTERN = /^logs\/grounding\/.+\.json$/`; `AGENT_TRANSCRIPT_PATH_TEMPLATE = 'logs/agent-runs/<yyyymmddThhmmssZ>-<runId>.jsonl'`, `AGENT_TRANSCRIPT_PATH_PATTERN = /^logs\/agent-runs\/\d{8}T\d{6}Z-[^/]+\.jsonl$/`. No path-building function: that would be runtime logic (criterion 1). AGL-04, AGL-16 and CEX-06 each join the prefix, the path and the suffix.
- **D12 Grounding and provenance schemas.** `groundingPassageSchema = {path, offset (integer ≥ 0), snippet}` (the Project store's search passage without `score`, `project-store/search.ts` lines 12 to 17). `groundingClaimSchema = {text (non-empty), span {start, end} (integers ≥ 0), verdict, passage?, reason}`. `passage` stays optional as the unit writes it; the engine's rule that supported and weak verdicts must cite one (`units/AGL-16` decision 3) is AGL-16's, not the contract's. No refinement and no `.transform`. `groundingResultSchema = {schemaVersion: literal 1, targetPath, contentHash (contentHashSchema), checkedAt (ISO), runId, claims}`. `groundingSummarySchema` is defined on its own with the four fields; a parity test (E2) checks it against `pendingGroundingSchema`, because a drift between the two would break `propose`. `groundingRequestSchema = {path}`. `draftProvenanceSchema = {runId, toolCallId, tool, entityIds (entity references), sourcesUsed (entity references), model (string), at (ISO)}`. Imports: `projectPathSchema`, `contentHashSchema`, `entityRefSchema`, by the file paths `../project-store/files.js` and `../project-store/entities.js` (the project-store precedent imports `../platform/events.js` the same way).
- **D13 Settings.** `agentSettingsSchema` is a `z.looseObject` (unknown keys pass through, as `projectsSectionSchema` and Platform's sections do, `project-store/settings.ts` line 8; `platform/settings.ts` lines 15 to 17): `schemaVersion` literal 1, `stepCap` integer at least 1, `research` `{enabled: boolean, searchEndpoint?: http(s) URL}`, and `research` is also a `z.looseObject`, so an unknown key inside `research` is kept as well. `searchEndpoint` is `z.url({ protocol: /^https?$/ })`, not `z.httpUrl()`, because `httpUrl` also requires a dotted domain name and would refuse `http://localhost:8888` (FACT 7a-14), the usual address of a local SearXNG (`units/AGL-21` line 20). `AGENT_SETTINGS_DEFAULTS = {schemaVersion: 1, stepCap: 12, research: {enabled: false}}` and `AGENT_DEFAULT_STEP_CAP = 12`; the defaults are data, and `units/AGL-06` line 15 registers them. `agentSettingsUpdateSchema` is the POST body, a plain `z.object` (unknown keys are stripped): every field optional, no `schemaVersion` (`units/AGL-06` line 16: "field-level merge"), and `research` in it is a partial object, `{enabled?, searchEndpoint?}`, so `{research: {searchEndpoint}}` alone is accepted by the update body and refused by the section schema; precedent `allowlistUpdateSchema` (`setup-auth/settings.ts` line 20). AGL-06 and AGL-07 both need it and are parallel, so it lives in the contract, not in either unit.
- **D14 Routes** (seven constants, all under `/api/agent-loop/`; reads GET, commands POST, `units/README.md` line 126): `AGENT_RUNS_ROUTE` `/api/agent-loop/runs` (POST start; `units/AGL-03` line 18), `AGENT_RUN_STOP_ROUTE` `/api/agent-loop/runs/stop` (POST; AGL-03 line 24), `AGENT_RUN_CURRENT_ROUTE` `/api/agent-loop/runs/current` (GET; `units/AGL-05` line 18), `AGENT_CONVERSATIONS_ROUTE` `/api/agent-loop/conversations` (GET list), `AGENT_CONVERSATION_ROUTE` `/api/agent-loop/conversations/:conversationId` (GET history), `AGENT_GROUNDING_ROUTE` `/api/agent-loop/grounding` (POST `{path}`; `units/AGL-17` line 19), `AGENT_SETTINGS_ROUTE` `/api/agent-loop/settings` (GET and POST; AGL-06 line 16). The two conversation paths are this plan's (open point 4).
- **D15 Error statuses.** `AGENT_ERROR_STATUS`: `AGENT_RUN_ACTIVE` 409, `AGENT_NO_PROVIDER` 409, `AGENT_NO_ACTIVE_PROJECT` 409, `AGENT_RUN_NOT_FOUND` 404. Reasons: `PROVIDER_NOT_CONFIGURED` is 409 (`providers/errors.ts` line 46), `PROJECT_NO_ACTIVE` is 409 (`project-store/errors.ts` line 69), unknown ids are 404 (`PROJECT_NOT_FOUND`, line 62). Shape of the exports: `AGENT_ERROR_CODES` (short key to code), `AGENT_ERROR_CODE_VALUES` (literal tuple), `agentErrorCodeSchema`, `AGENT_ERROR_STATUS`, as `PROJECT_ERROR_CODES` and its siblings are laid out.
- **D16 No examples file and no helper functions.** Tests build their inputs inline, as `project-store.schema.test.ts` does. The setup-auth and providers slices export an examples constant (`setup-auth/examples.ts`, `providers/examples.ts`) because their plans chose to; the unit here names none, and a second copy of every event in the package is a second thing to keep in step.
- **D17 Source style.** The sources use no `function`, no arrow function, no `.refine` and no `.transform`, so criterion 1's "no runtime logic" can be checked mechanically (section 4, C1b).
