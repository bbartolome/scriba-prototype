## 1. Decisions this plan follows

### 1a. Settled by the unit, the module, the contracts, DECISIONS and earlier plans

- **S1. Which files are entities.** Every Markdown file directly or recursively under `entities/` and `sources/` (unit lines 18 to 20). In `entities/`, front matter with a `type` is required. In `sources/`, front matter is optional, and a file with no front matter, or with front matter but no `type`, is type `source`.
- **S2. Base front matter.** Parsed with `{id?, type, links?}`; unknown keys pass through; pack schemas belong to the Tool registry (unit line 21). The contract's `entityBaseSchema` is that base (`packages/contracts/src/project-store/entities.ts` lines 11 to 15), and this plan validates with it.
- **S3. Effective id.** The front-matter `id` wins; otherwise the file stem. An effective id that does not match `ENTITY_ID_PATTERN` (`packages/contracts/src/project-store/constants.ts` line 4) makes the file invalid (unit line 22).
- **S4. Response shapes.** Resolution: `{resolved: [{id, type, path, content}], errors: [{id, code, paths?}]}` with `code` `unknown` or `duplicate` (`entities.ts` lines 31 to 47). List: `{entities: [{id, type, path, title?}], invalid: [{path, reason}]}` (`entities.ts` lines 55 to 70; unit line 23). The unit's line 22 names other codes for resolution errors. This conflict is open point 1.
- **S5. Query shapes.** Resolution takes `ids` as a repeated query parameter; a single id arrives as a string and is wrapped in an array (`entities.ts` lines 22 to 28). That wrap is on `main` as the PST-01 correction (`plans/DECISIONS.md` lines 2349 and 2356). List takes an optional `type` (`entities.ts` lines 50 to 52). Unit line 24.
- **S6. Routes and verbs.** `GET /api/project-store/projects/:projectId/entities` and `GET /api/project-store/projects/:projectId/entities/resolve`. The constants exist (`packages/contracts/src/project-store/routes.ts` lines 27 to 30). Both are GET, and no other verb is used (unit line 24; module line 45; `units/README.md` line 129).
- **S7. Reads only.** Both GETs never mutate and publish no event (unit line 32; module line 45; `units/README.md` line 129). `plans/PST-04.md` line 85 asks the PST-08 plan to call `requireActive` and write nothing on these paths. This plan does.
- **S8. Active-project rule and lookup.** Each request names a `projectId`, and a non-active project fails with "project not active" (module line 47). The lookup is the file API's two steps (PST-06 S2): `ProjectStoreService.requireActive(projectId)` (`apps/api/src/modules/project-store/project-store.service.ts` lines 65 to 82), then `ProjectsService.find(projectId)`, where `undefined` gives `PROJECT_NOT_FOUND` (`projects.service.ts` lines 34 to 43 and 59 to 61).
- **S9. One path check.** Every path goes through `ProjectStoreService.resolvePath` (module lines 44 and 48; `path-safety.ts` lines 118 to 196). PST-02 hands this to PST-08: the manifest builder passes each found file through `resolvePath` and skips it, or lists it as invalid, when the check fails (`plans/PST-02.md` line 297). This plan skips (P2).
- **S10. Provider.** The two operations are exported as an injectable provider from the module, for in-process callers (module line 52). The callers named in the units are the Agent loop (`units/AGL-09-narrative-tools.md` line 19), the Graph runner (`units/GRR-04-run-engine-core.md` line 24) and the Tool registry executor (`units/TRG-12-executor.md` line 24). Compile & export also resolves links (`units/CEX-07-entity-links-banned-phrases.md` line 15).
- **S11. The manifest.** The ID-to-path map is rebuilt from a `(path, mtime, size)` manifest of `entities/` and `sources/`, diffed against disk on each request, so host edits show up with no rebuild. The manifest is a reusable component, and search reuses it (unit line 25; `units/PST-13-fts5-search.md` line 21). PST-19's watcher relies on the same diff (`units/PST-19-optional-watcher.md` line 16).

### 1b. Choices made by this plan

- **P1. Code layout.** Three new source files, and one edit to the module file. `entity-manifest.ts` holds class `EntityManifest` (`@Injectable`, constructor takes `ProjectStoreService`): the walk, the front-matter parse, the parse cache and `readText`. `entities.service.ts` holds class `EntitiesService` (constructor takes `ProjectStoreService`, `ProjectsService` and `EntityManifest`): `list` and `resolve`. `entities.controller.ts` holds class `EntitiesController`. `EntitiesService` and `EntityManifest` are providers, exported from `ProjectStoreModule` and re-exported from the module's entry file, the same pattern as PST-06 P1. `EntityManifest` is exported so that PST-13 injects the same component.
- **P2. The walk.** Roots are `entities` and `sources`, each passed to `resolvePath` from the project root. A root that does not exist or is not a folder contributes nothing. A root that the path check refuses throws that refusal (it is not hidden). Within a folder: an entry whose name starts with `.` is skipped (PST-06 P5b). Each entry is passed to `resolvePath`; a `ModuleError` skips it (the PST-02 hand-off, and PST-06 P5c); any other error is rethrown. An entry that does not exist, or whose `statSync` gives `ENOENT`, is skipped. A folder is entered only when its dirent is a real directory, not a link (PST-06 P5d). A file is an entity candidate when its name ends in `.md` (exact, lower-case suffix; P10) and `statSync(realPath).isFile()`. Other files are ignored and not listed as invalid. Each candidate is `{path, mtimeMs, size}`, where `mtimeMs` is `stat.mtimeMs` (P15). The entries are sorted by path in code-unit order (PST-06 P5g).
- **P3. Parse cache and the diff.** `EntityManifest` keeps an in-memory map from project-relative path to `{mtimeMs, size, result}` for the current project root. A different root clears the map. Each request walks the disk, reuses `result` where `mtimeMs` and `size` are unchanged, parses the rest, and drops the entries whose path has gone. The cache holds front-matter results only, never file content, and nothing is written to disk.
- **P4. Parsing one file (fixed rule).** In this order:
  - (a) A size over `FILE_SIZE_CAP_BYTES` (`constants.ts` line 23) is invalid with `TOO_LARGE`. The size is checked before the bytes are read.
  - (b) The bytes are decoded with the file API's rule (`decodeText`, `files.service.ts` lines 70 to 79; exported by P12). A NUL byte or invalid UTF-8 is invalid with `NOT_TEXT`. A BOM stays as U+FEFF in the decoded text.
  - (c) One leading U+FEFF is removed for the parse.
  - (d) Front matter: the first line is exactly `---` (a trailing `\r` is ignored for this comparison, so CRLF files work). The block ends at the first later line that is exactly `---`. No opening line means no front matter, and the value is `{}`. An opening line with no closing line is invalid with `NOT_CLOSED`. The rule is the one of PLT-20 D10 (`plans/PLT-20.md` line 36), the examples check's rule. The Shell's rule differs (open point 2).
  - (e) The lines between the fences go to `parseDocument` from `yaml`, as `project-yaml.ts` line 1 does. A parse error is invalid with `NOT_YAML`. An empty block gives `{}`. A value that is not a mapping (a list, a scalar) is invalid with `NOT_MAPPING`.
  - (f) In `sources/` only: when the key `type` is absent, it is set to `'source'` before validation (unit line 20; PLT-20 D10; `plans/DECISIONS.md` line 2278).
  - (g) The object is validated with `entityBaseSchema`. The first issue gives the reason: path `type` with `type` absent gives `NO_TYPE`; path `type` otherwise gives `TYPE_INVALID`; path `id` gives `ID_INVALID`; path `links` gives `LINKS_INVALID`; any other gives `BASE_INVALID`.
  - (h) The effective id is the front-matter `id` when present (the base has checked it), else the file stem (the name without `.md`). A stem that fails `ENTITY_ID_PATTERN` is invalid with `NAME_INVALID`.
  - (i) The title is the `title` key, else the `name` key, when it is a non-empty string. Otherwise there is no title.
  - Every reason is a fixed string in one map (P14). No reason echoes an input value.
- **P5. Resolution.** The `ids` (already parsed by the contract) are de-duplicated, keeping the first occurrence. For each id, look at the valid entities whose effective id is that id:
  - none gives an `errors` item `{id, code: 'unknown'}`, with no `paths` key;
  - two or more gives an `errors` item `{id, code: 'duplicate', paths}`, with every path listed in sorted order;
  - one gives a `resolved` item `{id, type, path, content}`, where `content` is the file's whole text, front matter included, with a BOM kept. The text is read at request time through `EntityManifest.readText`. If the file is now over the cap or not text, the id is reported `unknown`.

  `resolved` and `errors` each keep the request order. Invalid files are never in the id map, so an id that names only an invalid file is `unknown` (unit line 30: "isn't resolvable").
- **P6. List.** `entities` holds every valid entity, sorted by path, as `{id, type, path}` plus `title` when there is one. The `type` filter (an exact string match) applies to `entities` only. `invalid` holds every invalid file, sorted by path, and is never filtered, because an invalid file may have no `type`. Its items are `{path, reason}`.
- **P7. Refusals.** Both GETs run S8 first, so a missing or non-active project gives the file API's codes. Unknown and duplicate ids are entries in the body of a 200 answer, not HTTP errors (open point 1). A malformed `ids` value, one that is not an entity id, is refused by the contract's query schema through `ZodValidationPipe` (`apps/api/src/modules/platform/errors/zod-validation.pipe.ts` lines 5 to 11). That is a validation error, not an `unknown` entry.
- **P8. Reads only.** Neither service writes to disk, publishes an event, or touches `.scriba/`. The manifest's cache lives in memory.
- **P9. Folder status is not a gate.** The list and the resolution work whatever `project.yaml` says (PST-06 P3).
- **P10. Markdown files only.** The manifest lists files with the exact suffix `.md`. Open point 3 asks whether search needs more.
- **P11. Provider.** `EntitiesService.list(projectId, {type?})` and `EntitiesService.resolve(projectId, ids)` take the same arguments as the HTTP handlers and go through the same checks (the pattern of PST-06 P17). `EntityManifest.snapshot(projectRoot)` and `EntityManifest.readText(projectRoot, path)` are exported for PST-13 and for in-process callers that need the file list. The `projectRoot` is the `root` of the `DiscoveredProject` that `ProjectsService.find` returns.
- **P12. Shared rule.** `decodeText` in `files.service.ts` gets the `export` keyword and nothing else. The rule is not copied. This is the one edit to a file of another unit.
- **P13. Controller.** `EntitiesController` uses `@Controller()` with the two route constants. `@Get(PROJECT_ENTITIES_ROUTE)` takes `@Query(new ZodValidationPipe(entityListQuerySchema))`. `@Get(PROJECT_ENTITY_RESOLVE_ROUTE)` takes `@Query(new ZodValidationPipe(entityResolveQuerySchema))`. The project id comes from `@Param('projectId')`. This follows `files.controller.ts` lines 33 to 70.
- **P14. Messages.** One map `ENTITY_MESSAGES` in `entity-manifest.ts`, `as const`, with the eleven reasons of P4: `NOT_TEXT`, `TOO_LARGE`, `NOT_CLOSED`, `NOT_YAML`, `NOT_MAPPING`, `NO_TYPE`, `TYPE_INVALID`, `ID_INVALID`, `NAME_INVALID`, `LINKS_INVALID` and `BASE_INVALID`. The project messages come from `PROJECT_MESSAGES`.
- **P15. The manifest key.** `mtimeMs`, a number, stands for the unit's `mtime`. It carries the same information. PST-13 must use the same key (section 5).
- **P16. Test names.** Tests are named with a letter and a number: E1 to E5 for the criteria, X1 to X3 for the extra rules (the pattern of PST-06 P20).
- **P17. Test kit.** `project-store-entities.kit.ts` exports `entitiesKitModule()`. It imports `PlatformModule` and `ProjectStoreModule`, as `filesKitModule` does (`project-store-files.kit.ts` lines 21 and 25). It has a controller under `api/project-store-test` with two POST routes, `entities/list` and `entities/resolve`, which call the in-process provider with the body unchecked. It is not in `COMPOSED_MODULES` and has no guard (PST-06 P18). X2 uses it.
- **P18. Invariant fixtures.** Two `FIXTURE_PATHS` entries (S13): `'/api/project-store/projects/:projectId/entities'` and `'/api/project-store/projects/:projectId/entities/resolve'`, each with a path under `no-such-project`, with no seed.
