### The nav slot

- **D4. Filling the slot.** The Shell's nav has one projected slot, `<ng-content select="[nav-project]" />` (`apps/web/src/app/shell/app-nav.ts` line 167; `plans/SHL-05.md` line 52). `plans/DECISIONS.md` line 1285 says PST-09 fills it. Content can be projected only by the template that contains `<app-nav>`, which is `apps/web/src/app/app.html`. So this unit changes `app.html` line 7 from `<app-nav />` to `<app-nav><app-active-project-nav nav-project /></app-nav>`, and `app.ts` imports `ActiveProjectNav` (`app.ts` lines 4-10 and 13-20). This is an edit to the Shell's composition root; open point 2 asks for confirmation.
- **D5. What the widget shows.** The widget (`ActiveProjectNav`, selector `app-active-project-nav`) shows the title of the active project, or its id when it has no title, as a read-only `<span>`. It renders nothing when no project is active, when the list read fails, or when the URL has no project id; on such a page it sends no request at all (planner's choice; the reason follows). It renders no `<a>` (the nav specs read `nav a` hrefs, `apps/web/src/app/shell/app-nav.spec.ts` line 116). Its CSS truncates the text: `min-width: 0; max-width: 9rem; overflow: hidden; text-overflow: ellipsis; white-space: nowrap`, so the 390 px bottom bar does not grow (planner's choice). The phone e2e specs check that the page does not scroll sideways (`e2e/specs/phone-toolbar.e2e.ts`, `expectFitsViewport`; `e2e/specs/setup-phone.e2e.ts`, `expectPhoneLayout`). **Why no request without a project id:** the Shell's client sends a visitor to `/setup` on any 401 (`apps/web/src/app/shell/api-client.ts` line 105), and the phone specs visit `/core-gate` and `/setup` in fresh browser contexts with no session (`e2e/specs/phone-toolbar.e2e.ts` line 55 starts a test that goes straight to `/core-gate`). An eager list read would move those pages to `/setup`. The widget finds the URL's project id through the Shell's `ActiveProjectSignal` (`apps/web/src/app/shell/project-scope.ts` lines 75-78; exported by `shell/index.ts` line 11).

### Data, state and endpoints

- **D6. Endpoints.** GET `/api/project-store/projects` (`packages/contracts/src/project-store/routes.ts` line 5), POST `.../projects/new` (line 6), POST `.../projects/import` (line 7), POST `.../projects/start-from-sample` (line 9), GET `/api/project-store/samples` (line 11), GET and POST `/api/project-store/active` (line 12). Source: unit lines 20-22; `modules/project-store.md` lines 45-46 (GET never mutates; every command is a POST; routes under `/api/project-store/`).
- **D7. Response shapes, copied by hand.** The list `{projects}` (`project.ts` line 48), the summary (line 39), the status enum `ok | invalid | too-new | importable` (line 30), the active answer `{active}` (line 77) and the samples, which are a plain array (line 88). The feature copies them in `project-store-contract.ts` and imports only types from the contract, the precedent of `features/agent-loop/agent-contract.ts` lines 1-4 and `shell/project-store-copies.ts` lines 11-12. A run-time import of the contract is not allowed in the browser bundle: its CommonJS build exposes only `default` after a dynamic import (`plans/DECISIONS.md` line 3957 and the `contract-chunks.ts` note at lines 1-5).
- **D8. Shared state.** A root-provided service `ProjectsState` (feature-internal) holds the list. The picker reads the list when it opens; the widget reads it when the URL has a project id (D5). Once a page has read the list, it re-reads on each `project-switched` envelope of the `project-store` stream (`apps/web/src/app/shell/sse-client.ts` line 78, `stream(slug)`) and on each reconcile tick (`reconcile$`, `sse-client.ts` line 59). A page that has not read the list sends nothing on an event or a tick. The service itself does not read on construction, because the App creates the widget on every page. The tick rule comes from the module convention: "no replay; reconnecting clients reconcile through state endpoints" (`units/README.md` line 131). The `project-switched` data is not read; the list is re-read (planner's choice). A response that is not the newest request is ignored, so an older reply cannot overwrite a newer one. Requests are cancelled when the component is destroyed.
- **D9. Copies, not the Shell's.** The Shell's `shell/project-store-copies.ts` (lines 15, 18, 50, 65) is not exported from `shell/index.ts` (lines 1-21). The feature keeps its own copies rather than changing the Shell's public index (planner's choice). Spec K1 checks them against the contract, as `shell/project-store-copies.spec.ts` does.

### Picker behaviour

- **D10. Rows and actions by status.** Unit line 20 names the four statuses; each row shows the status as its contract value. `ok` and not active: a **Switch** button. The active row: the text "Active". `invalid`: an **Import** button, plus the entry's one-line `error` (the first issue) verbatim. `importable`: **Import**. `too-new`: no action. Each row also shows the folder name, which is the project id (`packages/contracts/src/project-store/project.ts` line 8: "A project id is the folder name under the library"). Switching is offered only for `ok` entries (`plans/PST-04.md` line 86 asks the PST-09 plan to say which entries offer it).
- **D11. Switch.** POST `/api/project-store/active` with `{projectId}` (`activateRequestSchema`, `project.ts` line 72); the answer is `{active}` (line 77). On success the page navigates to `/projects/<id>/chat`, the same target the Shell's landing uses (`apps/web/src/app/shell/landing.ts` line 70). A refusal (for example `PROJECT_SCHEMA_TOO_NEW` or `PROJECT_INVALID`) shows its message verbatim and the page stays. Source: unit line 22; `plans/PST-01.md` line 38 (D8: the activate POST is how PST-09 switches); `plans/PST-04.md` line 86.
- **D12. New.** The form has Title (required), Folder name (optional) and Genre pack (optional). The POST body is `{title}` with the title trimmed, plus `folderName` and `genrePack` only when they are not blank. A blank folder name is left to the server, which derives it from the title (`apps/api/src/modules/project-store/projects.service.ts` line 66; `slugFromTitle` in `project-folders.ts` lines 22-35), so the picker does not copy the slug logic. A 201 is success (`projects.controller.ts` line 30). The folder-name field has to exist: a title with no letters or digits gets a 400 with the message "A folder name cannot be made from this title. Give a folder name." (`projects.service.ts` lines 66-72; `plans/PST-03.md` line 170). The default genre pack is `nonfiction` (`constants.ts` line 26; `project.ts` line 56), so a blank field sends nothing.
- **D13. Import.** POST `/api/project-store/projects/import` with `{projectId}` for an `importable` or `invalid` row; a 200 answers the summary (`projects.controller.ts` line 39). Errors are shown verbatim: the server message, then each `details` issue as `path: message` (the path joined with "." and omitted when empty). An issue has the shape `{path, message}` (`apps/api/src/modules/project-store/project-yaml.ts` lines 8-11). Source: unit lines 21 and 29; `plans/PST-03.md` line 170.
- **D14. Start from sample.** The cards come from GET `/api/project-store/samples`, and each card uses only `id`, `title` and `description` (`plans/PST-05.md` line 112, check (a)). Each card is a `<section>` labelled by its title (so the e2e can select it by name; `plans/PST-11.md` line 154). Its button "Start from sample" opens a form with Folder name (default: the sample id) and Title (default: the sample title). The POST always sends `{sampleId, folderName, title}` (`plans/PST-05.md` line 113, check (b); `startFromSampleRequestSchema` requires `folderName`, `project.ts` line 65). A 201 is success (check (c); `samples.controller.ts` lines 24-25).
- **D15. Landing after creation (planner's choice; open point 1).** After a 201 from New or from Start from sample, the page POSTs `/active` with the new id and navigates to `/projects/<id>/chat`. Import does not activate. Reasons: the API does not activate on create (`samples.controller.ts` line 14; `samples.service.ts` line 79); `plans/PST-05.md` lines 139-140 ask the PST-09 plan to say how the picker lands in the new project, and to call the activate POST after the create; the unit's e2e step says "land in the project" (unit line 26); the PST-12 demo keeps working in the new project (`units/PST-12-files-gate.md` lines 34-36).
- **D16. Errors.** Every failed request shows `ApiError.message` or `ApiSchemaError.message` as text, verbatim, in an element with `role="alert"` (`apps/web/src/app/shell/api-error.ts` lines 10-31; the fallback text "The request failed." follows `switch-project.ts` line 117). A failed list read is shown on the page; in the nav widget it shows nothing (planner's choice).
- **D17. project-switched on this page.** The page does not navigate on the event. The Shell's follower ignores non-project URLs: `remainderOf` returns `undefined` for `/projects` (`apps/web/src/app/shell/project-scope.ts` line 38; `project-switch-follow.ts` line 26 is the class).
- **D18. Phone.** The page is `phone` class (D2). Each action is a DOM button or a labelled input, with a single-column layout (planner's choice). Only `phone`-class behaviour is tested at 390 by 844 (open point 3).
