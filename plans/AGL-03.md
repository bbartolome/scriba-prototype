### 1b. Decisions this plan makes

- **D1 Start order.** `POST /api/agent-loop/runs` checks, in this order, all synchronously: (a) the body (`agentStartRequestSchema`; 400 `PLATFORM_VALIDATION_FAILED` otherwise); (b) `ProjectStoreService.activeId()` is null, so 409 `AGENT_NO_ACTIVE_PROJECT`; (c) the active project already has an active run, meaning status `running`, which includes a run that has been asked to stop but has not yet published `run-ended`, so 409 `AGENT_RUN_ACTIVE` (the unit's rule is per project, line 19; a run of another project that is still ending after a switch does not block); (d) `AgentSettingsService.current()` (an invalid stored section gives 400 and no run); (e) `ModelResolver.hasChoice({projectId})` is false, so 409 `AGENT_NO_PROVIDER` (D17). Then, in the same synchronous step, the run is registered, `run-started` (seq 1) is published, and `{runId, conversationId}` is returned. The model work starts after the reply. Nothing is awaited before the registration, so two starts cannot both pass (c). `conversationId` is the body's value when given, with no lookup (AGL-04 checks history), and otherwise `randomUUID()` (the kit already imports it, `apps/api/test/agent-loop-tools.kit.ts` line 1).
- **D2 Run record.** One in-memory record per run holds the fields of `agentRunStateSchema` (`runs.ts` lines 25 to 37: runId, conversationId, status, step, cap, assistantText, cards, groundingResults, pendingChangeIds, lastSeq, reason), plus projectId, the resolved target (`ResolvedModel`, which AGL-04 needs for `contextSize`), the enabled families, the abort controller and the requested end reason. The service keeps, per projectId, the active run and the most recent ended run, and nothing else (AGL-05 line 18 reads "the project's active agent run, or the most recent finished one"). Every emitted event updates the record (D9), so AGL-05 reads it without new state. A Stop looks the runId up over all projects; a run that is in no slot is `AGENT_RUN_NOT_FOUND`.
- **D3 Ending.** A run is active until its `run-ended` is published. At the end: mark it ended, release the active slot, then publish `run-ended`. Reasons: `completed` (a reply with no tool calls, whether or not it has text); `capped` (D6); `stopped` (D4); `project-switched` (D5); `error` (any other failure: the `ModuleError` message, with `details.hint` appended when present; any other exception gives the message "The agent run failed."). When an abort surfaces as an error, the requested reason wins. `pendingChangeIds` is `[]` until AGL-12.
- **D4 Stop.** `POST /api/agent-loop/runs/stop` with `{runId}`. For the active run without a requested end: set the requested reason to `stopped`, abort the run's controller, and reply 200 `{}` at once. For a run that already has a requested end or has ended: 200 and no event, so stopping twice is a no-op. Unknown run: 404 `AGENT_RUN_NOT_FOUND`. The same signal goes to the model request (`ChatRequest.signal`, `providers/client/types.ts` line 35) and to each tool dispatch (`ToolContext.signal`, `tools/tool-types.ts` lines 40 to 44). The loop checks the signal before each call.
- **D5 Project switch.** `AgentRunsService` registers `ProjectStoreService.onProjectSwitched` once, in its constructor. The handler is synchronous and catches everything (a throw would fail the switch). If the active run's projectId equals `event.from`, it sets the requested reason to `project-switched` and aborts. It does nothing else: the run's log and pending changes are AGL-04's and AGL-12's.
- **D6 Resolution and cap.** Each run resolves its target once, at the start of its loop, with `resolve({projectId})`. The model is fixed for the run, and a per-step resolve would repeat the auto listing on every step when the choice has an empty model (`providers.resolution.ts` lines 64 to 68; the seeded app default has an empty model, `plans/MPR-08.md` S3, CITED). The resolve is raced against the run's abort (D7). A step is one model call; `step` in the record counts the calls started, so the first call is step 1. After a reply: no tool calls gives `completed`. Tool calls with step equal to the cap give `step-cap-reached {step, cap}`, then `run-ended capped`, and the reply's tool calls are not run, because the model would never see their results. Otherwise the calls run (D8) and the next step starts. Continue is a new run (D12).
- **D7 Stop during the resolve.** The loop races the resolve against the run's abort. If the abort wins, the run ends `stopped` at once. The listing request goes on in the background until its own bound, and its result is dropped; no write follows. `plans/DECISIONS.md` line 1955 gives this choice to AGL-03 ("AGL-03 decides how a Stop meets it"), so the race is decided here; no signal is added to `resolve` or `listModels` (that would edit MPR-04 and MPR-05 code). Residual, recorded: an orphaned listing can run for up to about six minutes with the defaults (`plans/MPR-05.md` D9). TRG-12 faces the same choice (`plans/MPR-05.md` line 113).
- **D8 Calls.** For each call of a reply, in order. If the run offers the name (a new `ToolRun.familyOf(name)`, D15), emit `tool-call-started {callId, name, family}`, then `tool-call-args {callId, arguments, valid}` from the `DispatchResult`, then `tool-call-result {callId, summary, output}` or `tool-call-error {callId, message, attempt, withdrawn?}` from its outcome. Every call, offered or not, is answered to the model as a `role: 'tool'` message whose content is `modelText` or `message`. The assistant message with its tool calls is appended before the tool messages. Calls that are not offered get no card events: `tool-call-started` needs a `family` from the contract enum (`events.ts` line 27), and an unknown name has none. AGL-07's reducer ignores a card event whose `callId` has no card (`apps/web/src/app/features/agent-loop/chat-state.ts` lines 124 to 130), so nothing breaks. **Call ids.** The loop issues each call's `callId` itself, with `randomUUID()`, and uses it everywhere: in the card events, as `ToolCallInput.callId` for `dispatch`, as the `id` of the call in the appended assistant message, and as the tool message's `toolCallId`. The provider's `ToolCall.id` (`providers/client/types.ts` lines 50 to 54) is not used, because it is not unique within a run: the client fills a missing id with `call_mock_<index>` (`client/openai-compatible-client.ts` line 427) and the mock does the same (`e2e/fixtures/mock-openai/server.mjs` line 356), so each step's first call would be `call_mock_0`, and AGL-07's `startCard` replaces a card with the same `callId` (`chat-state.ts` lines 132 to 138). A UUID is also unique across the runs of a conversation, which AGL-04's history replays. This keeps `plans/AGL-10.md` line 154 true (the assistant call's `id` equals the events' `callId`, and the tool message has the same `tool_call_id`). `valid` is passed through from the `DispatchResult` as it is; the loop never reads it as "the arguments failed the schema" (`plans/DECISIONS.md` line 4204).
- **D9 Events.** One `emit(run, type, data)` function. It assigns `seq` (run-started is 1, then +1 for each event), updates the record (D2), publishes `{module: 'agent-loop', type, data: {runId, seq, ...}}` through `EventsPublisher` (`events.publisher.ts` lines 61 to 68), and is the only place events leave the loop. AGL-04 hooks its transcript line here. `token-delta` is sent for each text delta. The tests validate every published envelope against the contract's `agentLoopEventSchema`.
- **D10 Messages.** Each step's request has, in order: (1) the system prompt, a fixed text in `agent-prompt.ts` that states the role, the confinement to the active project with project-relative paths, "writes become pending changes the author accepts", and "cite sources with `[@id]`"; (2) a second system message holding the project summary, built once at run start: `Project: <title> (genre pack: <genrePack>).` and then `Top-level folders: <name> (<n> files), ...` over the top-level folders that `FilesService.list(projectId, {path: '.', recursive: true})` returns, in name order, where n counts the `kind: 'file'` entries under that folder, and the word is `file` when n is 1 (so `sources (1 file)`) and `files` otherwise (`files.service.ts` lines 232 to 255; `collect` skips dot entries and reserved paths, lines 576 to 586; the kinds are `file` and `dir`, `packages/contracts/src/project-store/files.ts` lines 15 to 17). `logs/` is listed like any other folder: the unit says "per top-level folder" (line 21), and the list is what the file tools see; no exclusion is added (YAGNI). A project with no top-level folder gets `Top-level folders: none.`; (3) the conversation history, which is empty until AGL-04; (4) the intent as the last user message, which is the position `plans/AGL-10.md` line 270 relies on; (5) the run's assistant and tool messages so far. `tools` is `ToolRun.schemas()` on every step.
- **D11 Families.** `enabledFamilies` is `['project']`, plus `'research'` when `settings.research.enabled` is true. Narrative, grounding and compile are added by their own units. At M1 the offered tools are `list_files` and `read_file` in both cases, since `builtin-tools.ts` line 27 is the only family in use. The filter itself is `ToolRun`'s constructor (`tool-run.ts` lines 64 to 69), covered by AGL-02's tests. This is a recorded limit of the M1 seam, not a gap in C6: no other family has a tool to leak.
- **D12 Continue.** A start with a `conversationId` reuses it. The continued run has a new runId and reads the settings again at its start, so it has a fresh cap. AGL-03 sends no history (AGL-04).
