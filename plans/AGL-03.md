### 1b. Decisions this plan makes

- **D1 Start order.** `POST /api/agent-loop/runs` checks, in this order, all synchronously: (a) the body (`agentStartRequestSchema`; 400 `PLATFORM_VALIDATION_FAILED` otherwise); (b) `ProjectStoreService.activeId()` is null, so 409 `AGENT_NO_ACTIVE_PROJECT`; (c) an active run exists, meaning status `running`, which includes a run that has been asked to stop but has not yet published `run-ended`, so 409 `AGENT_RUN_ACTIVE`; (d) `AgentSettingsService.current()` (an invalid stored section gives 400 and no run); (e) `ModelResolver.hasChoice({projectId})` is false, so 409 `AGENT_NO_PROVIDER` (open point 1). Then, in the same synchronous step, the run is registered, `run-started` (seq 1) is published, and `{runId, conversationId}` is returned. The model work starts after the reply. Nothing is awaited before the registration, so two starts cannot both pass (c). `conversationId` is the body's value when given, with no lookup (AGL-04 checks history), and otherwise `randomUUID()` (the kit already imports it, `apps/api/test/agent-loop-tools.kit.ts` line 1).
- **D2 Run record.** One in-memory record per run holds the fields of `agentRunStateSchema` (`runs.ts` lines 25 to 37: runId, conversationId, status, step, cap, assistantText, cards, groundingResults, pendingChangeIds, lastSeq, reason), plus projectId, the resolved target (`ResolvedModel`, which AGL-04 needs for `contextSize`), the enabled families, the abort controller and the requested end reason. The service keeps the active run and the most recent ended run, and nothing else. Every emitted event updates the record (D9), so AGL-05 reads it without new state. A Stop for a run that is neither is `AGENT_RUN_NOT_FOUND`.
- **D3 Ending.** A run is active until its `run-ended` is published. At the end: mark it ended, release the active slot, then publish `run-ended`. Reasons: `completed` (a reply with no tool calls, whether or not it has text); `capped` (D6); `stopped` (D4); `project-switched` (D5); `error` (any other failure: the `ModuleError` message, with `details.hint` appended when present; any other exception gives the message "The agent run failed."). When an abort surfaces as an error, the requested reason wins. `pendingChangeIds` is `[]` until AGL-12.
- **D4 Stop.** `POST /api/agent-loop/runs/stop` with `{runId}`. For the active run without a requested end: set the requested reason to `stopped`, abort the run's controller, and reply 200 `{}` at once. For a run that already has a requested end or has ended: 200 and no event, so stopping twice is a no-op. Unknown run: 404 `AGENT_RUN_NOT_FOUND`. The same signal goes to the model request (`ChatRequest.signal`, `providers/client/types.ts` line 35) and to each tool dispatch (`ToolContext.signal`, `tools/tool-types.ts` lines 40 to 44). The loop checks the signal before each call.
- **D5 Project switch.** `AgentRunsService` registers `ProjectStoreService.onProjectSwitched` once, in its constructor. The handler is synchronous and catches everything (a throw would fail the switch). If the active run's projectId equals `event.from`, it sets the requested reason to `project-switched` and aborts. It does nothing else: the run's log and pending changes are AGL-04's and AGL-12's.
- **D6 Resolution and cap.** Each run resolves its target once, at the start of its loop, with `resolve({projectId})`. The model is fixed for the run, and a per-step resolve would repeat the auto listing on every step when the choice has an empty model (`providers.resolution.ts` lines 64 to 68; the seeded app default has an empty model, `plans/MPR-08.md` S3, CITED). The resolve is raced against the run's abort (D7). A step is one model call; `step` in the record counts the calls started, so the first call is step 1. After a reply: no tool calls gives `completed`. Tool calls with step equal to the cap give `step-cap-reached {step, cap}`, then `run-ended capped`, and the reply's tool calls are not run, because the model would never see their results. Otherwise the calls run (D8) and the next step starts. Continue is a new run (D12).
- **D7 Stop during the resolve.** The loop races the resolve against the run's abort. If the abort wins, the run ends `stopped` at once. The listing request goes on in the background until its own bound, and its result is dropped; no write follows. The residual is open point 2.
- **D8 Calls.** For each call of a reply, in order. If the run offers the name (a new `ToolRun.familyOf(name)`, D15), emit `tool-call-started {callId, name, family}`, then `tool-call-args {callId, arguments, valid}` from the `DispatchResult`, then `tool-call-result {callId, summary, output}` or `tool-call-error {callId, message, attempt, withdrawn?}` from its outcome. Every call, offered or not, is answered to the model as a `role: 'tool'` message whose content is `modelText` or `message`. The assistant message with its raw tool calls is appended before the tool messages. Calls that are not offered get no card events (open point 3). The `callId` is the provider's tool-call id (`ToolCall.id`, `providers/client/types.ts` lines 50 to 54).
- **D9 Events.** One `emit(run, type, data)` function. It assigns `seq` (run-started is 1, then +1 for each event), updates the record (D2), publishes `{module: 'agent-loop', type, data: {runId, seq, ...}}` through `EventsPublisher` (`events.publisher.ts` lines 61 to 68), and is the only place events leave the loop. AGL-04 hooks its transcript line here. `token-delta` is sent for each text delta. The tests validate every published envelope against the contract's `agentLoopEventSchema`.
- **D10 Messages.** Each step's request has, in order: (1) the system prompt, a fixed text in `agent-prompt.ts` that states the role, the confinement to the active project with project-relative paths, "writes become pending changes the author accepts", and "cite sources with `[@id]`"; (2) a second system message holding the project summary, built once at run start: `Project: <title> (genre pack: <genrePack>).` and then `Top-level folders: <name> (<n> files), ...` over the non-dot top-level folders, in name order, where n counts the `kind: 'file'` entries of that folder recursively (`files.service.ts` lines 232 to 255; the kinds are `file` and `dir`, `packages/contracts/src/project-store/files.ts` lines 15 to 17); (3) the conversation history, which is empty until AGL-04; (4) the intent as the last user message, which is the position `plans/AGL-10.md` line 270 relies on; (5) the run's assistant and tool messages so far. `tools` is `ToolRun.schemas()` on every step.
- **D11 Families.** `enabledFamilies` is `['project']`, plus `'research'` when `settings.research.enabled` is true. Narrative, grounding and compile are added by their own units. At M1 the offered tools are `list_files` and `read_file` in both cases, since `builtin-tools.ts` line 27 is the only family in use.
- **D12 Continue.** A start with a `conversationId` reuses it. The continued run has a new runId and reads the settings again at its start, so it has a fresh cap. AGL-03 sends no history (AGL-04).
- **D13 Model errors.** Any failure of `resolve` or `streamChat` that is not an abort ends the run `error` (D3). The loop adds no retry (`plans/MPR-04.md` line 184).
- **D14 HTTP.** `POST /api/agent-loop/runs` answers 201, because it creates a run (the providers create route and `POST /api/project-store/projects/new` answer 201, `providers.controller.ts` line 56, `projects.controller.ts` line 30). `POST /api/agent-loop/runs/stop` answers 200 with `{}`, as a command (`agent-settings.controller.ts` line 23). No GET is added. Both routes sit behind the guard. Neither has a `:` in its path, so no `FIXTURE_PATHS` entry is needed (`apps/api/test/invariant-sweep.ts` line 4).
- **D15 Changes outside the module, additive only.** (a) `providers/providers.module.ts`: export `streamChat` from `./client` and the types `ChatMessage`, `ChatRequest`, `ToolSchema`, `ToolCall`, `StreamEvent` (`client/index.ts` lines 1 to 5 export them). (b) `project-store/project-store.module.ts`: export `ProjectsService`, whose `find(id)` (`projects.service.ts` line 59) returns a `DiscoveredProject` with a `summary` holding title and genrePack (`project-discovery.ts` lines 15 to 20). The module's exports (lines 59 to 65) do not list it today. The rule is the same as in (a): the entry file. (c) `agent-loop/tools/tool-run.ts`: a new method `familyOf(name): AgentToolFamily | undefined`, answering only for offered tools. No existing member changes. (d) `providers/providers.resolution.ts` and the entry file: `ModelResolver.hasChoice(input)`, which returns true when `projectChoice ?? appDefault` names a stored provider, with no network call (open point 1).
- **D16 Module wiring.** `AgentLoopModule` adds `ProvidersModule` to `imports` (`agent-loop.module.ts` line 28), registers `AgentRunsService` and `AgentRunsController`, and replaces the comment at lines 25 and 26 ("The loop itself lands in later units"). `AgentToolsService` is not changed.

## 6. Open points

1. **The no-provider check cannot use `resolve` without a network call (D1(e)).** POST must return at once (`units/AGL-03-loop-core.md` line 18), and AGENT_NO_PROVIDER must come before the run starts (line 20). The default is the race: the run ends at once, and the listing request goes on for up to its bound (about six minutes with the defaults, `plans/MPR-05.md` D9), with its result dropped. The Navigator should confirm the race for M1 and record the residual.
3. **Calls to names that are not offered get no card (D8).** `tool-call-started` needs a `family` from the contract enum (`events.ts` line 27), and an unknown name has none. The default: the model gets the NOT_OFFERED answer, and the UI gets no card. The alternative: a `tool-call-error` with no started card.
