# TRG-13 plan — Tools list: grouping, enable toggles, phone view, live refresh

Revision 1, written at main `b46861c` from the repository alone. Status stays draft until the plan review approves it.

Summary. TRG-13 turns the `/tools` route from the TRG-05 dev page into the Tools list. The list groups tools by origin, shows validity, lint counts and the "overrides built-in" marker, carries an enable switch per row, refreshes on `catalog-changed`, and on a phone shows only the list and the switches. The TRG-05 preview becomes the Preview tab of a tool's detail. The unit is web-only: no API, contract or Shell change. Facts found while planning:

- **F-A. The route entry is already on main.** The `tools` entry of the Shell route table exists from TRG-05 with the right owner, class and nav (`apps/web/src/app/app.routes.ts` lines 115 to 127). TRG-13 changes no route-table file.
- **F-B. The API is complete.** `GET …/tools` (summaries), `GET …/tools/:name` (detail) and `POST …/tools/:name/enabled` (answers the effective summary) are on main (`apps/api/src/modules/tool-registry/tools.controller.ts` lines 53 to 58 and 86 to 94). The list and the switch need nothing from TRG-12.
- **F-C. Two rows can share a name.** A valid user copy replaces its built-in row, and an invalid user copy is listed beside it (`catalog.service.ts` lines 429 to 447). The switch is keyed by name only, so the open points of section 6 turn on this.
- **F-D. The unit text on validity was changed without a note.** `units/TRG-13-tools-page-list.md` line 16 says validity is the summary's `valid` field. Commit `ea65447` had said "derived from `output` being null", and `bb76e4a` corrected it. No "Reworded by" line exists. The plan follows the current text (section 7).

- **C5 Refresh.** One `Subject` of read requests, piped through `switchMap` to `api.get(TOOLS_PATH, toolListCopy)`, so only the newest answer is kept (`projects-state.ts` line 22). Each inner read catches its own error, so the stream survives it. Triggers: the first render; each `catalog-changed` envelope (`events.stream('tool-registry')`, filtered by `type`, as `projects-state.ts` lines 55 to 60 does); each reconcile tick (`events.reconcile$`, `projects-state.ts` line 61). A read can publish `catalog-changed` itself (`plans/TRG-10.md` D14, `catalog.service.ts` lines 175 to 181), but the next read finds no change, so the loop ends.
- **C6 Groups.** One `<section>` with an `<h2>` per origin that has at least one row, in the order of the copy `TOOL_ORIGIN_ORDER` (`core`, `nonfiction`, `fiction`, `user`). Headings read Core, Nonfiction, Fiction and User. Rows keep the server's order, which is by name (`catalog.service.ts` line 436).
- **C7 Row.** Each row is an `li` with `data-tool` (the name) and `data-origin`. It shows the description, the origin, the status ("Valid", or "Invalid" with `error.message` when present), the lint counts ("N errors, M warnings"), "Overrides the <origin> built-in" when `overrides` is set, and the switch. On tablet and desktop the name is a `button` with the attribute `data-open`. On phone it is a `span`.
- **C8 Phone.** When `deviceClass() === 'phone'` (`device-class.ts` lines 56, 57 and 71), the names are not buttons and no detail is rendered. The selection is kept, so a larger class shows the same detail again.
- **C9 Messages.** Loading reads "Loading the tools". A failed list read reads "The tools could not be read.". A failed switch reads "The switch could not be saved." and reads the list again. An empty list reads "No tools.".
- **C10 Copies.** `tool-copy.ts` gains `TOOLS_PATH` (`/api/tool-registry/tools`), `TOOL_ENABLED_PATH_TEMPLATE`, `toolEnabledPath(name)` (the name encoded as one segment), `TOOL_ORIGIN_ORDER` (a copy of `TOOL_ORIGINS`), `toolListCopy` and `toolSummaryCopy`. Both response copies share one row check. S1 checks each against the contract.
- **C11 Origins.** The list GET has no query, so it shows every origin. This is the default until open point 3 is settled.
- **C12 Detail for valid rows only.** A row opens the detail only when `valid` is true. This is the default until open point 2 is settled.

## 6. Open points

1. **Which rows carry a switch.** Unit line 16 asks for enable toggles on the list. TRG-09 C9 allows toggling an invalid tool. The switch is keyed by name (`catalog.service.ts` lines 232 to 246), and `resolve` (lines 374 to 382) picks the built-in when the user copy is invalid. So a switch on an invalid user copy that sits beside its built-in changes the built-in's effective switch, and the two rows can then disagree. Options: (a) every row has a switch, which is the procedure's default (C4 and C7) and the literal reading of unit line 16; (b) only the row that the name resolves to has a switch; (c) an invalid row has no switch. Effects: TRG-14, where an invalid copy's Customize and Revert live, and TRG-17's demo step 1. The unit files do not settle it.
2. **Which rows open the detail.** TRG-14 (unit line 16) says an invalid user copy opens from `GET …/tools/:name/user`. The procedure's default (C12) opens only valid rows, because the Preview tab reads `GET …/tools/:name`, and for a name with an invalid user copy that call returns the built-in (`catalog.service.ts` lines 374 to 382; `tools.controller.ts` lines 71 to 74).
