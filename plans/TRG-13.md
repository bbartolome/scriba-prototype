# TRG-13 plan — Tools list: grouping, enable toggles, phone view, live refresh

Revision 3. Revision 1 was written at main `b46861c` from the repository alone. Revision 2 is the Opus reviser's correction on 2026-11-16 at main `d7105d4`. Revision 3 is the Opus reviser's application of the Navigator's decision on open point 2 (`plans/DECISIONS.md`, entry of 2026-11-16, option (b)) at main `78a1678` (notes in sections 9 and 10). The reviser changed no code and ran no test; the unit changes of revision 3 are in commit `78a1678`. Open points 1, 2 and 3 are settled (section 6). Status stays draft until the orchestrator sets it.

Summary. TRG-13 turns the `/tools` route from the TRG-05 dev page into the Tools list. The list groups tools by origin, shows validity, lint counts and the "overrides built-in" marker, carries an enable switch on each row that its name resolves to, refreshes on `catalog-changed`, and on a phone shows only the list and the switches. The TRG-05 preview becomes the Preview tab of a tool's detail. The unit is web-only: no API, contract or Shell change. Facts found while planning:

- **F-A. The route entry is already on main.** The `tools` entry of the Shell route table exists from TRG-05 with the right owner, class and nav (`apps/web/src/app/app.routes.ts` lines 115 to 127). TRG-13 changes no route-table file.
- **F-B. The API is complete.** `GET …/tools` (summaries), `GET …/tools/:name` (detail) and `POST …/tools/:name/enabled` (answers the effective summary) are on main (`apps/api/src/modules/tool-registry/tools.controller.ts` lines 65 to 70, 83 to 86 and 98 to 106). The list and the switch need nothing from TRG-12.
- **F-C. Two rows can share a name.** A valid user copy replaces its built-in row, and an invalid user copy is listed beside it (`catalog.service.ts` lines 429 to 447). An invalid user copy beside its built-in always carries `overrides` (`rowOf`, lines 417 to 427), and a user row with no `overrides` has no built-in of that name. The switch is keyed by name only (`setEnabled`, lines 232 to 246), and `resolve` (lines 374 to 382) picks the built-in when the user copy is invalid. So a POST for that name changes the built-in row's switch. Choice C4 follows from this (open point 1, settled).
- **F-D. The unit text on validity was corrected by the orchestrator.** `units/TRG-13-tools-page-list.md` line 16 says validity is the summary's `valid` field. Commit `ea65447` had said "derived from `output` being null"; the TRG-01 review of revision 4 corrected it (`plans/DECISIONS.md` lines 3438 and 3448), and `bb76e4a` applied the correction (DECISIONS line 3473). The plan follows the current text.

### 1b. Choices this plan makes (the simplest option; each names its source)

- **C1 Page and preview input.** `ToolsListPage` in a new file `tools-list.ts`; `toolsRoutes` points to it. `ToolsPreviewPage` takes a required input `tool` in place of the constant `PREVIEW_TOOL` (`tools-preview.ts` line 34). Source: `diff-view.ts` line 290 (`input.required` is the Shell's style).
- **C2 Selection is page state, not a route.** A row's name opens the detail below the list. The selection key is `origin + '/' + name`. It is unique, because a name has at most one built-in row and at most one user row (`catalog.service.ts` lines 429 to 447; the contract comment, `catalog.ts` lines 24 and 25). The Shell route table is not changed. Source: `modules/shell.md` line 52; ADR 0002 line 42.
- **C3 Detail tab strip.** One hand-written tab, `Preview`: a `div role="tablist"` holding a `button role="tab" aria-selected="true"`, and a `div role="tabpanel"`. The panel holds `@for (row of selectedList(); track row.key) { @if (row.valid) { <app-tools-preview [tool]="row.name" /> } @else { <p data-detail-status>…</p> } }`, where `row.key` is the C2 key computed in the page's row view, so a new selection creates a new preview and re-reads it. For an invalid row the panel makes no read and shows the status only: `Invalid`, then `error.message` when present, then the lint counts ("N errors, M warnings") (C12). A list refresh that keeps the selected key keeps the preview as it was read; TRG-15 owns live previews. TRG-14 and TRG-16 add tabs to this strip. No Material tabs: the app uses none. Source: unit line 15; `tools-preview.ts` lines 251 to 269 (the preview reads once, in `ngOnInit`).
- **C4 Switch (open point 1, settled: option (b)).** A row carries the switch when its name resolves to it, that is, every row except an invalid user copy beside its built-in. The rule reads the row alone: no switch when `origin === 'user' && !valid && overrides !== undefined` (F-C). That row shows, in place of the switch, the text `The <overrides> built-in is used.` The switch is `mat-slide-toggle`, as the tool form uses it (`apps/web/src/app/features/tool-registry/tool-form.ts` line 14 and lines 456 to 467), with `[checked]="row.enabled"` and `(change)` posting `{enabled: checked}` to `toolEnabledPath(name)`. Its `aria-label` is `Enabled: <name>`. Reason for (b): it changes no criterion and no settled decision (unit line 16 asks for enable toggles on the list, not one per row; `modules/tool-registry.md` line 3 says "a Tools page with enable switches"), and each shown switch posts to the entry that the row is, so a click always changes the row that was clicked. Option (a), a switch on every row, puts on the invalid copy a switch that changes the built-in's row instead (F-C). Option (c), no switch on any invalid row, also removes it from an invalid user-only tool, whose switch does act on that row and which TRG-09 C9 allows to be toggled. Source: `tool-form.spec.ts` lines 418 to 432 (the switch is `button[role="switch"]` and is clicked in tests); `units/TRG-06-pack-loader-catalog.md` line 22 (the built-in is used).
- **C5 Refresh.** One `Subject` of read requests, piped through `switchMap` to `api.get(TOOLS_PATH, toolListCopy)`, so only the newest answer is kept (`projects-state.ts` lines 22 and 29 keep the newest read by a counter; `switchMap` is the same rule). Each inner read catches its own error, so the stream survives it. Triggers: the first render; each `catalog-changed` envelope (`events.stream('tool-registry')`, filtered by `type`, as `projects-state.ts` lines 55 to 60 does); each reconcile tick (`events.reconcile$`, `projects-state.ts` lines 61 to 63). The reconcile tick is not in the unit's text; README line 133 says reconnecting clients reconcile through state endpoints, and `projects-state.ts` already does so. Each switch answer also triggers a read. A read can publish `catalog-changed` itself (`plans/TRG-10.md` D14, `catalog.service.ts` lines 175 to 181), but the next read finds no change, so the loop ends.
- **C6 Groups.** One `<section data-group="<origin>">` with an `<h2>` per origin that has at least one row, in the order of the copy `TOOL_ORIGIN_ORDER` (`core`, `nonfiction`, `fiction`, `user`). Headings read Core, Nonfiction, Fiction and User. Rows keep the server's order, which is by name (`catalog.service.ts` line 436).
- **C7 Row.** Each row is an `li` with `data-tool` (the name) and `data-origin`. It shows the description, the origin, the status ("Valid", or "Invalid" with `error.message` when present), the lint counts ("N errors, M warnings"), the marker, and the switch or the C4 text. The marker reads `Overrides the <overrides> built-in` for a valid row with `overrides`, and `Invalid copy of the <overrides> built-in` for an invalid one (TRG-06 line 22: the copy is shown invalid with a warning; the built-in is used). On tablet and desktop the name is a `button` with the attribute `data-open` on every row (C12). On phone it is a `span`.
- **C8 Phone.** When `deviceClass() === 'phone'` (`device-class.ts` lines 56, 57 and 71), the names are not buttons and no detail is rendered. The selection is kept, so a larger class shows the same detail again.
- **C9 Messages.** Loading reads "Loading the tools". A failed list read reads "The tools could not be read.". A failed switch reads "The switch could not be saved." and reads the list again. An empty list reads "No tools.".
- **C10 Copies.** `tool-copy.ts` gains `TOOLS_PATH` (`/api/tool-registry/tools`), `TOOL_ENABLED_PATH_TEMPLATE`, `toolEnabledPath(name)` (the name encoded as one segment), `TOOL_ORIGIN_ORDER` (a copy of `TOOL_ORIGINS`), `toolListCopy` and `toolSummaryCopy`. Both response copies share one row check. S1 checks each against the contract.
- **C11 Origins (open point 3, settled: every origin).** The list GET has no query, so it shows every origin. Reason: it changes no criterion and no settled decision, and it is the literal reading of the unit. Unit line 16 names the four groups; the route is app-level (unit line 15, `modules/shell.md` line 59), not under a project; and the switch it shows is library-wide (`modules/tool-registry.md` line 43: the `tools` section of `settings.yaml`), so a tool of another genre is still the author's to switch. The other option needs the active project's genre, which the page does not read, and would hide built-in rows that C4 relies on (an invalid user copy whose built-in is filtered out). The project offering stays where TRG-06 line 26 and TRG-09 line 15 put it: `GET …/functions`.
- **C12 Detail for every row (open point 2, settled by the Navigator: option (b)).** Every row opens the detail. A valid row's Preview tab reads `GET …/tools/:name`, which is the row's own entry, because it resolves to a valid user copy, and to the built-in when the user copy is invalid (`catalog.service.ts` lines 374 to 382). An invalid row's detail makes no preview read and shows its status only (C3). A selected row that turns invalid stays open and shows its status. The editor for an invalid user copy is TRG-14's tab, which reads `GET …/tools/:name/user` (TRG-14 unit line 16); the Try tab is hidden on an invalid row (TRG-16 unit line 18). Source: `plans/DECISIONS.md`, "TRG-13 — the Navigator's decision on open point 2" (2026-11-16).
