## 3. Decisions this plan obeys

### 3.1 Settled by the unit, the module or DECISIONS (obeyed)

- **D1. Side list.** The project's entities, searchable, grouped by type, as draggable chips, with mouse and touch. Source: unit Decisions, bullet 1. Touch is given by the mechanism (D2) and checked by GRR-15 criterion 1 (D19).
- **D2. Mechanism.** Angular CDK drag and drop, one mechanism for mouse and touch (pointer events). Native HTML drag and drop is ruled out. Source: DECISIONS 2026-11-15 TRG-04 O7 (line 4220, lines 4222 to 4224), which names GRR-12 and allows `cdkDropListGroup` or connected IDs.
- **D3. Pinning.** A drop onto an entity or style port pins the value in the tool node's `params`, after three checks: the port type matches, the port's entity-kind filter, and the port has no wire. Source: unit Decisions, bullet 2; module "Validation in one place" (chip-drop checks stay client-side); module "Design choices" (pinned port values in `params`).
- **D4. Refusal.** A refusal shows a short reason and leaves the file unchanged. Source: unit Decisions, bullet 2, and criterion 2; DECISIONS TRG-04 O7 (line 4222).
- **D5. Removal.** A pinned chip can be removed from its port, and removal clears it from `params`. Source: unit Decisions, bullet 3; criterion 3.
- **D6. Two seams for the drop rules.** The drop handler's outcome on the saved graph (Vitest), and the rules as a real gesture (Playwright). Source: unit criterion 4; module Testing principles (UI seam; gesture checks).
- **D7. Kind filter comes from the form field.** The entity-kind filter of a port is the `entityKinds` of its form field (same key, `port: true`). The port descriptor has none. Source: `views.ts` lines 12 to 19 and 53 to 70; `emit.ts` lines 71 and 72.
- **D8. Style ports.** A style port takes a `style-profile` entity, the kind the executor checks for a style reference. Source: `executor.service.ts` lines 43 and 136.
- **D9. Writing.** A pin or a removal writes through the same path as a settings edit: `replaceNode`, the vflow node's `data` set in place (so the form stays mounted), and one scheduled validation. Source: GRR-11 plan, C-10 and C-13 (`plans/GRR-11.md` section 1); `canvas-page.ts` lines 710 to 725.
- **D10. Drop targets.** Only the input rows of ready tool nodes take chips. A tool node that is not ready has no rows and so no targets. Source: GRR-11 plan, C-12 and C-3 (`plans/GRR-11.md` section 1); `portRowsOf` line 184.
- **D11. Recipe only.** Story graphs have no palette, no side list and no Run. Source: module ("It never runs a story graph"); GRR-14 unit Decisions ("Story graphs never offer Run"); GRR-11 plan section 1 (no palette on a story graph).
- **D12. Module boundaries.** The feature imports no file of tool-registry or project-store except the entry routes. It keeps its own copies of the routes and response schemas, and imports only types from the contracts. Source: `eslint.config.mjs` R1; the header comment of `graph-runner-contract.ts`.
- **D13. Read-only HTTP.** The entity list is a GET and only reads. The project id is the one in the URL. Source: module "HTTP"; PST-08; `entities.service.ts` lines 25 to 32.
- **D14. No reflow while dragging.** A refusal reason is written only in the drop handler, never in an enter predicate, and nothing a drag adds or marks changes the size of a row. Source: DECISIONS 2026-11-15 TRG-05, observation (line 4331): a reason line written at drag start reflows the lists, and CDK's cached rectangles go stale. The same holds for CDK's placeholder, which `enter` appends into the entered list (CDK lines 1542 to 1567), so it is hidden inside rows (C-4).
- **D15. Duplicate on a list port is a no-op.** Source: TRG-04 picker precedent (`entity-picker.ts` line 343, and O7 "appends with no duplicate ID").

### 3.2 Choices made here (names, layout, shapes the unit leaves open)

- **C-1. Files.** A pure module `entity-chips.ts` with no library import and no Angular import. It holds `groupEntitiesOf(entities, query)`, `chipDropRefusalOf(file, portId, chip, views)`, `pinnedParamsAfterDrop(params, port, chip)` and `pinnedParamsAfterRemoval(params, key, list, index)`. It reuses `splitPort`, `isPinned` and `pinnedValuesOf` from `tool-nodes.ts`, which is not changed. Its spec runs without the library.
- **C-2. Read.** `entitiesPath(projectId)` (the id encoded) and `entityListCopy` in `graph-runner-contract.ts`. In `load()`, the `switchMap` after the graph read joins `readTools(graph)` and a new `readEntities(graph)` with `forkJoin`. `readEntities(graph, projectId)` returns `of(undefined)` for a story graph or an empty project id, and otherwise GETs the list with `catchError` to `undefined`. The project id comes from the canvas's own `ActivatedRoute`, not from `ActiveProjectSignal` (revision 3): a module-level function `projectIdOfRoute(snapshot)` in `canvas-page.ts` returns the first string `projectId` param of `snapshot.pathFromRoot`, else `''`. In the constructor's `paramMap` pipeline, the `switchMap` calls `this.load(id, projectIdOfRoute(route.snapshot))`, and `load` sets a `projectId` signal (a plain `signal('')`, which the aside's "No active project" branch reads) before it reads. Why this source: the canvas route is always under `projects/:projectId` (section 2.1), and the router sets every route's snapshot before it creates the component, so the id is current when `load()` runs; `ActiveProjectSignal` is refreshed only on NavigationEnd, which comes after. A reactive read (`toObservable`, as `graph-list-page.ts`) was not chosen: it would first emit the previous navigation's id when the canvas is reached from another project's URL, and would need a second load trigger. `ActiveProjectSignal` is not injected by the canvas. A failed read shows "Entities could not be read." in the aside; an empty id shows "No active project". The list is read once per graph load; it does not refresh while the canvas is open (the unit does not require it).
- **C-3. Side list.** A flex wrapper holds an `aside` beside the vflow. In the recipe view only, the aside holds a search input (`data-entity-search`) that filters by id or title, case-insensitively, by substring. Groups are sorted by type, and entries keep the server's order. Each chip is a `span[cdkDrag]` with `[cdkDragData]="{ id: entity.id, type: entity.type }"` and `data-entity`, inside a `div[cdkDropList][cdkDropListSortingDisabled]` slot, the same shape as `tools-preview.ts` lines 146 to 160. Valid entities only; `invalid` entries are not shown.
- **C-4. Drop mechanism.** The wrapper is `div[cdkDropListGroup]`, so every aside slot and every row is connected. The drop targets are the input rows of ready tool nodes: `div.port-row` gets `cdkDropList`, `data-drop-port` (the port id) and `(cdkDropListDropped)="onChipDrop(portIdOf(ctx.node.id, row.key), $event)"`, only when `row.side === 'input'`. There is no `cdkDropListEnterPredicate` and no `cdkDropListData`. The handler `onChipDrop(portId, event)` acts only when `event.isPointerOverContainer` is true (CDK lines 1068 to 1098); any other drop does nothing and writes no reason. One CSS rule, `:host ::ng-deep .port-row .cdk-drag-placeholder { display: none; }`, keeps a row's size when the chip enters it (D14). Revision 3: the component uses Angular's default emulated encapsulation (no `encapsulation` key), which would add the component's `_ngcontent` attribute to both parts of a plain selector; `::ng-deep` after `:host` scopes the rule to this component's host and leaves `.port-row .cdk-drag-placeholder` unscoped, so it matches the CDK placeholder (a clone of the chip, CDK lines 1166 to 1179) inside any row of this page whatever attributes the clone carries. It is the rule the failing worktree already has; S1 checks it (A9). The page has no row of another component, so the unscoped part reaches only this page's rows. No other CSS targets the `.cdk-drop-list-*` or `.cdk-drag-*` classes. Note: a tool with a non-port entity or style input would render an `EntityPicker` in the node body, and it would join the group (its `admits` would then run at drag start). No shipped tool has one (section 2.1); this plan does not change that and records it for GRR-15.
- **C-5. Refusal order and texts.** The first failing check gives the reason: (1) a text port: "Text ports take no entities."; (2) a style port and a chip whose type is not `style-profile`: "Style ports take style profiles."; (3) a port already wired (an edge's `to` equals the port id): "This port is already wired."; (4) a form field with a non-empty `entityKinds` that does not list the chip's type: "This port takes {kinds} entities." with the kinds joined by " or "; (5) a port the views do not give: "This port takes no entities.". A duplicate on a list port is a no-op (D15), with no reason. An empty `entityKinds` is no filter, as the TRG-04 picker treats it (TRG-04 review, line 4244).
- **C-6. Accepted drops.** A scalar port: `params[key] = chip.id` (D16). A list port: `[...pinnedValuesOf(params, key), chip.id]`, unless the chip id is already there (no-op). A `style-profile` chip on an entity port with no `entityKinds` is accepted, which mirrors the executor's check (it applies a kind check only when the field lists kinds). A pin creates `params` when the node has none. An accepted drop clears the reason line.
- **C-7. Writing.** As D9: `replaceNode(file, next)`, `vflowNode.data.set(next)` on the matching vflow node, `scheduleValidation()`. A refusal sets the reason signal only; it writes nothing.
- **C-8. Removal.** Each pinned value is `span.chip[data-pinned=<portId>]` with a `button[data-remove]` (its `aria-label` is "Remove" followed by the value). A scalar port loses its key. A list port loses the item at the chip's index, and its key goes when the list is empty. A `params` object left empty is removed (D18). Then the write and validation are as C-7.
- **C-9. Drop seam in Vitest.** The test takes the row `root.querySelector('[data-drop-port="<portId>"]')`, gets its `CdkDropList` with `getDebugNode(row)!.injector.get(CdkDropList)`, and calls `dropped.emit(event)` with `event = {item: {data: {id, type}}, isPointerOverContainer: true} as unknown as CdkDragDrop<unknown>`, as `tool-form.spec.ts` lines 946 to 965 do. The fallback is named in A2.
- **C-10. Attribute names.** `data-entity`, `data-drop-port`, `data-pinned`, `data-remove`, `data-entity-search` and `data-drop-reason`. None is named `data-port`: GRR-11's T1 counts `[data-port^="tool-1."]` and expects six.
- **C-11. Reason placement.** `p[role=status][data-drop-reason]` sits inside the aside, outside the vflow, and keeps one line of height when empty, so writing it moves no row. It is set only by the drop handler (D14).
- **C-12. Fixtures.** Vitest: the canned entity list holds `anna` (person), `claim-1` (claim) and `house-style` (style-profile), each with `path` and `title`, and `invalid: []`. `respondTools()` also answers `entitiesPath('p1')` with it. The canned `person` field of `COLD_OPEN_VIEWS` gets `entityKinds: ['person']`, as the real server emits it (`cold_open.yaml` line 39). e2e: entity files `entities/anna.md` (`type: person`), `entities/claim-1.md` (`type: claim`) and `entities/house-style.md` (`type: style-profile`), each with front matter `type` and `title` only; the id is the file stem (`entity-manifest.ts` lines 304 and 305). Graph files are canonical text (`JSON.stringify(graph, null, 2)` and a final newline).
- **C-13. Gesture.** The TRG-05 sequence (`tools-preview.e2e.ts` lines 194 to 209): mouse down on the chip's centre, a 12 px move in 4 steps, wait for `.cdk-drag-preview`, two animation frames, then measure the target row's `boundingBox()` (no scroll during the drag), move to its centre in 12 steps, and release. Before each drag, `hitsAtCentre` is true for the chip (`hit.matches`) and for the row (`hit.closest(selector)`, because the element at the centre is usually a child of the row).
- **C-14. Counting the criteria.** One test per criterion, named as the criterion text (as GRR-11 did, `d72b02b`). Criteria 1 to 3 are tested at the Vitest UI seam (T1 to T3). Criterion 4 is a test-seam criterion: its one test is the Playwright gesture test T4, which makes the drop rules of criteria 1 and 2 by real mouse gestures; its Vitest half is T1 and T2 (the drop handler's outcome on the saved graph), so criterion 4 holds when T1, T2 and T4 pass. Removal (criterion 3) is a click, not a drop rule, and has no gesture test.
- **C-15. Read-only while running (GRR-13).** GRR-12 adds no run state and no guard. GRR-13's decision makes the whole canvas read-only during a run, so it covers chip drops and removal whatever GRR-13 names its state. Rule, correct in either merge order: whichever of GRR-12 and GRR-13 merges second makes `onChipDrop` and `removeChip` obey GRR-13's read-only state in the same way as the other edit handlers. GRR-13's plan (draft) names that state `editable()`, a `computed` (its C-3); the guard is `if (!this.editable()) return;` as the first statement of `onChipDrop` and `removeChip`, and `[cdkDragDisabled]="!editable()"` on each chip of the aside (GRR-13 plan step 5(g) and section 7). Both are read when the user acts, not at load time, so they do not have the load-time problem of C-2. If GRR-13 is on main when step 0 of this plan runs, step 0 does it (see step 0), using the name GRR-13 merged with. If GRR-12 is on main first, the GRR-13 plan must include the two handlers; section 7 records it. Before GRR-13 there is no Run click on the canvas, so GRR-12 alone adds no edit during a run that the canvas does not already allow.
