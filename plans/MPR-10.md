### 1b. Decided here

- **D1 Target of the test.** Edit mode (a saved provider) sends `{providerId, key?}`. Add mode sends `{draft, key?}`, the form's `draft` computed value (it includes `kind`), when the draft is valid. The button is disabled in add mode while the draft is undefined. Edit mode shows the note `testSavedNote` above the button: the test uses the saved settings. Reason: the contract has no shape for "saved id with unsaved changes", and a draft has no `keyRef`, so a draft test could not use the stored key. Open point 1.
- **D2 The typed key.** The key control's value (`typedKey`, `provider-form.ts` line 282). It is sent only in the test request, and only when it is not empty. It is never stored, and the test does not clear the control.
- **D3 Request states.** `testing` (a signal): the button is disabled and reads `testingButton` while the request is in flight. A test start clears the previous result and the form's alert field. A failed request (an `ApiError` or any `Error`) goes to the alert field with `failureMessage` (`providers-store.ts` line 47), as MPR-09 D7 says for every failure in the form. No store state changes and no list is re-read. The waiting state is the UI's concern (`plans/MPR-07.md` line 48 and its section 5, the MPR-10 bullets).
- **D4 Result view.** A new presentational component `ConnectionTestResultView` (selector `app-connection-test-result`, file `connection-test-result.ts`), with inputs `result` (a `ConnectionTestResult` or undefined) and `omitHint` (a string or undefined). It renders:
  - three stage rows in order, `<stage label>: <state>`, where the state is `passed`, `failed` or `not run`. When `ok` is true all three pass. When `ok` is false the stages before the failing stage pass, the failing stage fails, and the later stages are not run.
  - for a passed test, `testPassed`;
  - for a failure, `error.message`, and `error.hint` unless it equals `omitHint` (D8);
  - `latency(latencyMs)` always, and `modelCount(n)` when `modelCount` is present (it is present whenever the list stage passed, including 0; `providers.connection-test.ts` lines 145 and 151).
- **D5 Ollama rule in the browser.** `isOllamaProvider(baseURL, id?)` in `providers-copies.ts`: true when `new URL(baseURL).port === '11434'`, or when `id` is given and starts with `ollama`. It returns false for an unparsable URL. In edit mode it is called with the saved provider's id and stored baseURL. In add mode it is called with the typed baseURL and no id, because the server's draft test uses the id `draft` (`providers.connection-test.ts` line 110), so only the port applies there. Reason: the browser cannot import `apps/api`, and the contracts subpath is one entry with zod, which the browser must not load (`plans/MPR-09.md` S13). Open points 2 and 3.
- **D6 The two Ollama notes.** When the rule is true:
  - `OLLAMA_CONTEXT_NOTE` (a copy) is shown under the context-length field, after `texts.contextHint`. Its text is the Ollama preset's first hint sentence plus one sentence: "Context length is set in Ollama, not in Scriba. Start Ollama with OLLAMA_CONTEXT_LENGTH=64000 or higher." It is shown in add mode and in edit mode.
  - `OLLAMA_PULL_NOTE` (a copy) is shown directly under the model picker, and only when the model list state is `empty`. Its text is the Ollama preset's pull line, exactly: "Pull a model on the host with `ollama pull <model>`." (`packages/contracts/src/providers/defaults.ts` line 42). Add mode never has an empty list state (its state is `unsaved`), so the pull note is an edit-mode note.
- **D7 One copy of the hints per screen.** The preset's own `hints` (`preset.hints`, `provider-form.ts` lines 88 to 92) are shown only while `providerId` is undefined (before the create), when the preset exists and the rule is false. The template condition is therefore `providerId() === undefined && preset() && !ollama()`. The check on `providerId` is needed because the target input stays in add mode after an add, so `preset()` would still hold the preset. For the Ollama preset the two sentences of the contract are replaced by the notes of D6: the context note at once, and the pull note once the list is empty. Non-Ollama presets (LM Studio, OpenAI, OpenRouter) keep their hints in add mode, unchanged. Open point 7.
- **D8 No duplicate pull text.** When the pull note is on screen, the result view does not repeat a server hint that equals `OLLAMA_PULL_NOTE` (the server sends that text for an empty Ollama list: `providers.connection-test.ts` lines 186 to 195 and `providers.resolution.ts` lines 123 to 131). The result view receives `omitHint = OLLAMA_PULL_NOTE` in that case, and `undefined` otherwise. Open point 4.
- **D9 Copies in `providers-copies.ts`.** The new copies are: `CONNECTION_TEST_PATH` (`/api/providers/test`, a plain constant like the others); `PROVIDER_ERROR_CODE_NAMES` (the ten codes as a literal tuple); `connectionTestResultCopy`, a `ResponseSchema<ConnectionTestResult>` built with the existing `guard` helper; `isOllamaProvider` (D5); `OLLAMA_CONTEXT_NOTE` and `OLLAMA_PULL_NOTE` (D6). The guard rebuilds the result from the fields the contract knows, as the other guards do: `ok` is a boolean; `stage` is one of the three; `latencyMs` is a finite number of at least 0; `modelCount`, when present, is a safe integer of at least 0; `error`, when present, is an object with a `code` from the ten, a string `message` and an optional string `hint`. An absent `error` or `modelCount` is left out. A `null` for either is refused, as zod refuses it.
- **D10 Store method.** `ProvidersStore.testConnection(body: ConnectionTestRequest): Observable<ConnectionTestResult>`, which posts to `CONNECTION_TEST_PATH` with `connectionTestResultCopy`. It has no `tap` and changes no signal. It is the only call the panel makes that sends a key outside `key/set` (see section 5, the MPR-09 statements this plan supersedes).
- **D11 Texts.** New keys in `TEXTS` (`providers-texts.ts`), listed in section 2. The stage labels are `Reach the server`, `List the models` and `Send a test message`. The states are `passed`, `failed` and `not run`.
- **D12 Placement and unchanged files.** The test button sits in the form's action row, after Save and before Close (`provider-form.ts` lines 195 to 207). The result view sits directly below the action row. The panel (`providers-panel.ts`), its routes, its spec and the host helper stay unchanged. No request is sent on open: the test runs only on a click, so the request counts asserted by `providers-panel.spec.ts` (lines 279, 294, 304, 355, 441, 502, 697, 788 and 886) do not change.
