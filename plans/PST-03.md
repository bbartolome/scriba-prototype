### 1b. Small decisions this plan makes

- **P1. What the list contains.** Unit line 18 defines a project as an immediate, non-dot subfolder containing `project.yaml`. Unit line 20 gives one entry per folder, with status `importable` for a folder without `project.yaml` (checked). The wording "lists exactly the non-dot immediate subfolders with `project.yaml`, marks the others `importable`" is criterion line 27 (PST-12 line 22 repeats it). It lists the others too, so the lines do not conflict (checked). This plan lists every non-dot immediate directory, with `importable` for the ones without `project.yaml`. Reason: the contract comment at `project.ts` lines 8 and 9 says discovery "lists every subfolder, including importable folders" (checked). Open point 1, closed.
- **P2. Symlinks at the top level.** A symlink whose target resolves inside the library is followed and listed under its link name (a control row). A symlink whose target is outside the library is skipped, not listed, because it is not a subfolder of the library. The skip uses `store.resolvePath(libraryRoot, name)`: a `ModuleError` drops the entry. A symlink whose real path is not a directory is also dropped. Open point 3.
- **P3. Classification of `project.yaml`** (`project-yaml.ts`, a pure function of the text), in this order:
  1. No `project.yaml`: `importable`.
  2. YAML syntax error (`parseDocument(text).errors.length > 0`): `invalid`, with one issue whose path is `[]` and whose message is the first line of the YAML error.
  3. The top level is a mapping whose `schemaVersion` is an integer greater than `PROJECT_YAML_SCHEMA_VERSION` (`1`, defined in the module): `too-new`. This check runs before the schema, so a newer file with other faults is `too-new`.
  4. `projectYamlSchema.safeParse(value)` fails: `invalid`, with the Zod issues unchanged.
  5. Otherwise `ok`, with `title` and `genrePack`.
  The contract accepts any integer `schemaVersion` of 1 or more (`project.ts` line 21), so the too-new rule lives in the module (open point 14).
- **P4. The one-line `error`** of an `invalid` summary is the first issue, written `path.joined: message`, or just the message when the path is empty. Example, checked by the probe (F26): `title: Invalid input: expected string, received undefined`. Only `ok` summaries carry `title` and `genrePack`; `too-new` and `invalid` summaries carry neither (the contract allows both to be absent, `project.ts` lines 41 and 42).
- **P5. An unreadable `project.yaml` does not fail the whole list.** A read error other than "not found" makes that folder `invalid`, with the message `project.yaml could not be read (<errno code>).` The message holds no path (PST-02 P10 style). A failure to read the library folder itself is not caught and gives a 500.
- **P6. Size cap.** A `project.yaml` larger than `FILE_SIZE_CAP_BYTES` (`constants.ts` line 23) is `invalid` with the message `project.yaml is larger than the 5 MiB cap.`, and is not read.
- **P7. Reads and writes of files go through the path function.** Discovery calls `store.resolvePath(root, 'project.yaml')`. A `ModuleError` makes the folder `invalid` with that error's fixed message. New and Import write to `realPath`, the target of a within-project link, as PST-02 P3 defines it for the caller's fs calls. PST-06 must follow the same rule (open point 9).
- **P8. Order of the list.** Sorted by folder name in plain code-unit order (`Array.prototype.sort()`), so the output does not depend on the locale.
- **P9. The `active` flag** is `true` for the folder whose name equals the `active` value of the section, whatever its status. An active project that is now invalid is still marked.
- **P10. New** (`ProjectsService.create`), in this order:
  - (a) Folder name: the request's `folderName`, or `slugFromTitle(title)` (P11). The request's `folderName` is already checked by the contract pattern through the Zod pipe.
  - (b) An empty derived name is refused before the disk is touched: 400 `PLATFORM_VALIDATION_FAILED` with a fixed message. Only the derived slug is capped (P11). An explicit `folderName` is not capped: `PROJECT_FOLDER_NAME_PATTERN` (`constants.ts` line 14) has no length, and PST-05's `folderName` (`project.ts` line 67), PST-09 and SAU-14 would not know about a cap. The contract's `PROJECT_VALIDATION_FAILED` (422) is not used: no unit gives it a meaning here, and this app answers a refused request with Platform's validation code and status (F13).
  - (c) `mkdirSync(join(libraryRoot, name))` without `recursive`. `EEXIST` (for a folder, a file or a dangling link of that name, checked by F26) gives `PROJECT_EXISTS` (409). `ENAMETOOLONG` (a name over the filesystem limit, for example 300 characters) gives `PROJECT_PATH_INVALID` (400) with `PATH_MESSAGES.TOO_LONG`, as `path-safety.ts` lines 167 to 169 does (checked; the limit itself is assumed, A9). This is the one reservation of the folder, and PST-05 reuses it (section 5).
  - (d) Create the five folders, then `.gitignore` (`.scriba/` and a line feed), then `project.yaml` last, each through `writeFileAtomic`. The `project.yaml` write is the commit point.
  - (e) If anything fails after (c), remove the folder with `rmSync(folder, {recursive: true, force: true})` and rethrow. Only the folder this request created is removed.
  - (f) Answer 201 with the summary. `active` is computed as in the list (P9).
- **P11. Folder name from a title** (`slugFromTitle`): `title.normalize('NFKD')`, remove the combining marks (`/\p{M}/gu`), lowercase, replace each run of characters outside `a-z0-9` with one `-`, trim `-` from both ends, cut to 64 characters, trim `-` again. An empty result gives no name. Examples in the New test (E1): `My New Book` gives `my-new-book`; the title built in the test as `Caf` + String.fromCharCode(0xe9, 0x20, 0xdc) + `n` + String.fromCharCode(0xef) + `code!` gives `cafe-unicode`; `   --   ` gives none; the title built in the test as String.fromCharCode(0x65e5, 0x672c, 0x8a9e) gives none, so the author must name the folder. Open point 5.
- **P12. The minimal `project.yaml` for Import** is `schemaVersion: 1`, `title` (the folder name, verbatim) and `genrePack: nonfiction`. Unit line 22 says "a minimal one (title from folder name, `schemaVersion: 1`)". Read as the minimal valid file, it must carry `genrePack`: `projectYamlSchema` requires it (`project.ts` line 23; PST-01 plan line 34, D4), and the default pack is `DEFAULT_GENRE_PACK`, which is `nonfiction` (`constants.ts` lines 25 to 26; unit line 21). Without `genrePack` the new file would list as `invalid` at once. No criterion tests the keys of this file: PST-12 line 23, the downstream gate, asks only that Import leaves every other file byte-identical. Open point 2, closed.
- **P13. Import** (`ProjectsService.importProject(projectId)`):
  - (1) Find `projectId` in the discovered list. No match, including `..`, `.` and the names of dot-folders, gives `PROJECT_NOT_FOUND` (404) with a fixed message.
  - (2) By status: `ok` gives `PROJECT_EXISTS` (409), because the folder already holds a project (open point 4). `too-new` gives `PROJECT_SCHEMA_TOO_NEW` (409). `invalid` gives `PROJECT_INVALID` (422), with `details` set to the issues array (the Platform filter uses the same shape for its validation errors, F13). Nothing is written in these three cases.
  - (3) `importable`: append `.scriba/` to `.gitignore` first (P14), then write the minimal `project.yaml` (P12) last. The order means that a refused `.gitignore` write, for example a link out of the project, leaves no `project.yaml`, and the folder stays importable.
  - (4) Answer 200 with the summary (`status: ok`).
- **P14. Appending `.scriba/` to `.gitignore`.** The line is present when some line, trimmed, equals `.scriba/`. If it is absent, the new text is the old text, plus a line ending when the old text is non-empty and does not end with a newline, plus `.scriba/` and a line ending. The line ending is CRLF when the old text contains CRLF, otherwise LF. When the file does not exist, the new text is `.scriba/` and LF. The line is therefore added once. The write uses `resolvePath(root, '.gitignore').realPath` (P7).
- **P15. `writeFileAtomic(target, text)`** (`atomic-write.ts`): `mkdirSync(dirname(target), {recursive: true})`; write `${target}.tmp`, the pattern of the Platform settings file (`settings.file.ts` line 51); `renameSync` over the target (line 54); remove the temp file if anything fails (line 56). Module line 50 gives the rule (temp file in the same folder, then rename, missing parents created). Two concurrent writes to one file could share the temp name. That is accepted for a single-user app (assumed; open point 10).
- **P16. No new contract constant.** `PROJECT_YAML_SCHEMA_VERSION = 1` lives in `project-yaml.ts`. Open point 14.
- **P17. Where the service lives.** `ProjectsService` (`projects.service.ts`) injects `ProjectStoreService` (for `libraryRoot` and `resolvePath`) and `SettingsService` (exported by `platform.module.ts` line 40). It is provided only inside `ProjectStoreModule` and is not exported from the entry file, because no other module needs it yet (open point 6). `ProjectStoreService` is unchanged, so there is no cycle. `activeId()` is a public method of `ProjectsService` for PST-04 to reuse.
- **P18. Errors.** Every message is a fixed string in one map, `PROJECT_MESSAGES`, in `projects.service.ts`. Every error is `new ModuleError(code, status, message, details?)` (`module-error.ts` lines 2 to 17), with the code from `PROJECT_ERROR_CODES` and the status from `PROJECT_ERROR_STATUS` (contract `errors.ts` lines 58 to 79), except P10(b), which uses `PLATFORM_ERROR_CODES.VALIDATION_FAILED` and 400 (contract `platform/errors.ts` lines 36 and 44 to 45). No input value is echoed. `details` are the Zod issues (they carry field names, not host paths) or nothing.
- **P19. Routes and bodies.** `ProjectsController` (`projects.controller.ts`) uses `@Controller()` with the full route constants, as `providers.controller.ts` line 43 does. Bodies are parsed with `new ZodValidationPipe(schema)` (`zod-validation.pipe.ts` lines 5 to 11), with `newProjectRequestSchema` and `importRequestSchema`. The list answers `{projects}` with `projectListSchema` as its shape.
- **P20. Test seam.** The composed app (`createTestApp({libraryDir})` with the default modules, `create-test-app.ts` line 86), a setup cookie from `sessionCookie` (`guard-request.ts` line 80), and requests from `send` (`guard-request.ts` line 27) with `LOOPBACK_HOST` and `LOOPBACK_ORIGIN` (`invariant-sweep.ts` lines 38 and 39). The provider is not reached through a kit route: the criteria are HTTP responses and files on disk. PST-02 had no route in the composed app; PST-03 is the first.
- **P21. Snapshots.** `snapshotLibrary(dir)` (`invariant-sweep.ts` lines 224 to 228) records, for each file, its size, times, inode and SHA-256, and a `directory` entry for each folder (lines 235 and 236). It is reused for C4 and C5.

### 1c. The algorithm in short (the implementer follows P-items for the detail)

Discovery, `ProjectsService.discover()`:
1. `readdirSync(libraryRoot, {withFileTypes: true})`; skip names that start with `.`; sort (P8).
2. For each entry: a real directory is used. A symlink is used only when `store.resolvePath(libraryRoot, name)` succeeds and its real path is a directory (P2). Anything else is skipped.
3. `root = join(libraryRoot, name)`. Read `project.yaml` through `store.resolvePath(root, 'project.yaml')` (P5 to P7), then classify it (P3).
4. Build the summary (P4, P9). `DiscoveredProject = {id, root, summary, yaml}`. `root` and `yaml.issues` never leave the service; the controller maps `summary` only (S5).
