### 1b. Decisions this plan makes

Each is the smallest option that meets the unit. None changes a settled decision or a criterion. Section 6 names the ones a reviewer may want to change.

- **D1 Files and names.** `tool-form.ts` (class `ToolForm`, selector `app-tool-form`), `tool-registry.routes.ts` (the entry file: it re-exports the component and its types), and `tool-form.spec.ts`. No `Routes` array yet: TRG-05 adds the dev route and TRG-13 adds `toolsRoutes`.
- **D2 API.** Inputs: `form` (required, `FormDescriptor`), `ports` (`PortDescriptor | null`, default `null`), `layout` (`'form' | 'node-body'`, default `'form'`), `issues` (`ToolArgsIssue[]`, default `[]`), `handle` (`TemplateRef<{ $implicit: ToolFormPortRow }> | null`, default `null`). A two-way model `value` (`ToolArguments`, default `{}`), so `[(value)]` works and emits `valueChange`. Output `submitted` (`ToolArguments`). `ToolFormPortRow` is `{side: 'input' | 'output', key, title, type, list, required}`. The Graph runner's template reads `let-port` (`port.key`, `port.side`) and builds the port id `<nodeId>.<key>` itself (`views.ts` line 37 gives the id rule).
- **D3 Rows.** Node body: one row per `ports.inputs` entry in order, then one output row last (`side: 'output'`, key `output`, type `text`, title `Output`, from `ports.output`). Each row shows its title, its type (with "list" when `list` is true), its required mark, the handle template when one is supplied, and the issues of its key. Params: the form fields with `port: false`, in form order. Form layout: every field, in form order. TRG-03 renders every port row of the node, the output row included; the Graph runner (GRR-11) supplies the handle template and renders no port row of its own (section 6 point 3).
- **D4 Field rendering.** The first rule that matches wins:
  - (a) `control` is `entity-picker` or `style-picker`: a placeholder `div.picker-slot` that shows the current ids as read-only text.
  - (b) `list: true`: one input row per item, typed by `valueType` (`string` gives a text input; `integer` or `number` gives a number input), each with a Remove button, and an Add item button under the list. This rule replaces the scalar control of a list field. The emitter derives a list's control from its item type, because the array property has no bounds or enum (`emit.ts` lines 41 to 52), so the result is `text` or `number`.
  - (c) Scalars: `text` gives a text input; `textarea` a textarea; `select` a native `select` with `matNativeControl`, an empty option and the `enum` options (a select with no enum renders as text); `number` a number input; `slider` a native range input when both `minimum` and `maximum` are present, otherwise a number input (the emitter's rule, `emit.ts` lines 43 to 47); `toggle` a `mat-slide-toggle`.
  - Material is used for form fields, inputs, the select, the toggle and the buttons. The range is native, see section 6 point 5.
- **D5 Values, no coercion.** Text and textarea emit strings. Number and slider emit JavaScript numbers, read with `valueAsNumber`. Toggle emits a boolean. Select emits its option string. A cleared scalar (text, textarea, number, select) removes its key, so a missing required field reads "received nothing" from the server (`validate.ts` line 152). Empty list rows emit `''` for text items and `null` for number items; the server refuses `null` for an integer or number ("received null"). The component reads a DOM value only in response to a user event (`input` or `change`), never on render, so a value the slider grid cannot show is kept until the user moves the slider. The range step is 1 for an integer valueType and `(max - min) / 100` for a number. A slider without both bounds renders as a number input (the emitter does the same, `emit.ts` lines 43 to 47). An absent `valueType` (optional in the contract, `views.ts` line 69; always set by the emitter, `emit.ts` line 67) is read as `number` for number and slider controls and as `string` for the others.
- **D6 Defaults and required.** At `ngOnInit`, each rendered field whose `default` is not `null` and whose key is absent from `value` gets its default in one update, so the emitted value holds the defaults that are shown. `null` means no default (`emit.ts` line 64 sets `null` when the property has none; the comment at `views.ts` line 52 says a `null` default means no default). A later change of `value` from outside is shown as given, and no defaults are added back. A required field shows a `span` with `aria-hidden="true"` and text `*` after its title, and its control has `aria-required="true"`. There is no native `required` attribute, so the server alone decides. A non-empty `description` shows as hint text.
- **D7 Issues.** For each issue, the key is the first JSON Pointer segment, unescaped (`~1` to `/`, then `~0` to `~`, as `validate.ts` lines 285 to 291 do). The message shows under that field's control, with an id, and the control's `aria-describedby` names that id. An item issue (a second segment that is an index) gets the prefix `Item N: `, where N is the index plus one, and shows under the list. An issue whose key matches no rendered field (path `''`, or an unknown field such as `/extra`) is listed once above the fields, with its message as given. The component never validates. The paths and messages come from `validate.ts` lines 129, 151 to 152, 158 to 159 and 163 to 164.
- **D8 Submit.** In the form layout, a `form` element with a `Submit` button emits `submitted` with `value()`. No validation happens here: TRG-05 and TRG-16 send the value to validate or execute. The node body has no submit control.
- **D9 Test seam.** The spec renders the component through TestBed, in a host component that binds the inputs and `[(value)]`. It imports `ToolForm` from `./tool-registry.routes`, so the Graph runner's import path is the one tested. The TestBed providers include the Shell fakes through `createShellTestDoubles().providers` (`apps/web/src/app/shell/testing/test-doubles.ts` lines 165, 168 and 184 to 193), as `project-picker.spec.ts` lines 89 to 93 do, because the unit's heading and the module's UI seam (`modules/tool-registry.md` line 51) name them. The component reads neither the API nor the event source, so no test drives them; this is the reading of the SHL-06 precedent (`plans/DECISIONS.md` lines 1195 to 1199, 2026-11-13: the fakes are available to features and are not required by a component with no I/O). Decided in section 6 point 2.
- **D10 Fixtures.** The spec has its own fixtures, written in the spec and shaped as the merged emitter's output. No test reads `apps/api` or `packages/packs`. Source: `modules/tool-registry.md` line 52. The form fixture has these eleven fields, in this order, so that every control and every test can name them: `coreIdea` (text, string, required), `notes` (textarea, string, `maxLength` 500), `tone` (select, string, enum `warm`, `dry`), `length` (slider, integer, minimum 200, maximum 2000, default 800), `count` (number, integer, no bounds), `moody` (toggle, boolean), `person` (entity-picker, string, `elementType` entity), `styleProfile` (style-picker, string, `elementType` style), `entityIds` (entity-picker, list, string items), `tags` (text, list, string items) and `numbers` (number, list, integer items). Every other `default` is `null`. The node-body fixture has the cold-open ports in property order (coreIdea, entityIds, styleProfile, person, moment) and the params length and tone.
- **D11 Test style.** `describe`, `it` and `expect` come from `vitest`, as in `project-picker.spec.ts` line 5. The spec awaits `fixture.whenStable()` and calls `fixture.detectChanges()` after each event, because the app is zoneless (`app.config.ts` line 19).
