### 1b. Choices

- **P1 Files.** Four new files and two edits (section 3). The panel is a standalone component `SnapshotsPanel`, selector `app-snapshots-panel`, in `snapshots-panel.ts`, the same shape as `ManuscriptPage`.
- **P2 Confirm dialog is `window.confirm` (O1, decided).** The unit asks for "a confirm dialog that names the `pre-restore` snapshot" and the criterion for a dialog that names it; it does not name a form. The native dialog is the smallest code (one call, no state, no template) and has a tested seam in this app: `vi.spyOn(window, 'confirm')` (`tools-actions.spec.ts` line 162; F13). The inline form (`role="alertdialog"` in `review-page.ts` line 259, a confirm group in `version-history.ts` line 151; F26) needs a state signal, two buttons and their tests, and was chosen there because those units asked for an explicit confirmation step on the page. A native `<dialog>` is excluded: jsdom has no `showModal` (`plans/PST-20.md` line 162). CEX-18's unit asks for "a confirm dialog ("N errors. Export anyway?")" (unit line 16), which either form satisfies, so this choice does not conflict with CEX-18; matching it there is a recommendation for CEX-18's planner, not a rule of this plan.
- **P3 Dialog text.** `Restore <id>? The current manuscript is saved first as a snapshot labelled pre-restore. Files that are not in this snapshot are deleted.` The word `pre-restore` comes from the copied constant `PRE_RESTORE_LABEL`. The server names the new snapshot `pre-restore-<UTC stamp>` (F7, `snapshot.service.ts` `create(PRE_RESTORE_LABEL)`), so the label is the name the client can give before the restore. The text states both effects of the server's restore: the pre-restore snapshot and the deletions (F7).
- **P4 Create.** A text input with `aria-label="Snapshot label"` and a button with the text `Snapshot`. The button is disabled when the trimmed label is empty or the panel is not editable. The trimmed label is sent. The panel does not change its list from the answer. The `snapshot-created` event (D5) refreshes it, and the server publishes that event on every create (F7).
- **P5 Restore.** A button with the text `Restore` and `aria-label="Restore <id>"`, drawn only on readable rows, and disabled when the panel is not editable. The answer is a manuscript view. It is parsed with `manuscriptViewCopy` and not used, because the server publishes `manuscript-updated` for the page and `snapshot-restored` for the panel (F7).
- **P6 Rows.** Each row is `li[data-snapshot-id="<id>"]`. It shows the label, a `<time datetime>` holding `createdAt` as the server gives it (UTC ISO text), `N files`, and `Words: <total> (<body> in the body)`. An unreadable row shows `Unreadable: cannot be restored`, `Words: unknown` and no button. The rows keep the server's order; the panel does not sort them again.
- **P7 Reads are not gated on the project id.** The list read has no project id in its path, because the server uses the active project (F7). `ActiveProjectSignal.projectId()` can be `''` when a component is constructed (F11, F12). So the read is never gated, and the event filter compares the event's project id with `projectId()` when the event arrives, as the page does.
- **P8 Errors and writes.** Failures show in a `role="alert"` paragraph of the panel, with the `ApiError` message or `The request failed.`. The panel copies the page's `outcomeOf` and `failureMessage` helpers, which the page does not export (F8). There is no in-flight lock, as CEX-17 D11 has none.
- **P9 Phone (O5, decided).** On the `phone` device class, the label input, the Snapshot button and each Restore button are disabled, and `create()` and `restore()` return without a request. The list is still read and shown. Source: the unit and `modules/compile-export.md` are silent; the rule is inherited by analogy from the page that hosts the panel, whose phone layout is read-only (`units/CEX-17-manuscript-route-outline.md` Decisions, Phone bullet: "outline, counts and statuses read-only"; `plans/CEX-17.md` D14) and from PST-21's restore, which has no control on the phone class (`plans/PST-21.md` C2). It is a choice of this plan, not a settled decision; no other unit depends on it (CEX-20 has no phone step).
- **P10 Copies (O6, decided).** `snapshot-contract.ts` holds the two route paths, the `PRE_RESTORE_LABEL` copy, the list and summary copies with one shared entry guard, and the event-data guard. `PRE_RESTORE_LABEL` stays a web copy: the API's constant is in `apps/api/src/modules/compile-export/snapshot-names.ts` and the contract does not export it (F7), and exporting it from the contract would not help, because a value import from the contract does not load in the browser (D9), and it would change a contract and a CEX-16 file that this unit does not own. The parity is held by two literal pins: CEX-16's API test asserts the label `'pre-restore'` and the id prefix `pre-restore-` (F24), and S1 asserts the literal text `pre-restore` in the dialog (it does not compare with the imported constant). A change of either side fails a test. No new parity spec is needed.
- **P11 Tests in a new spec.** The panel's tests go in `snapshots-panel.spec.ts`, not into `manuscript-page.spec.ts`, so that CEX-18's tests on the same route do not collide with them. The new spec copies the page spec's small helpers.
- **P12 Harness.** The tests render `provideRouter([{ path: 'projects/:projectId/manuscript', children: manuscriptRoutes }])` with `createShellTestDoubles()` and no active-project guard, as the page spec's `renderPage` does (F9).
- **P13 M4 keeps its strength (O2, decided).** M4's request assertion becomes a list of method and path pairs: `[['GET', MANUSCRIPT_PATH], ['GET', SNAPSHOTS_PATH]]`. Every request list that the old assertion `['GET']` refused because it held a write is still refused (any POST makes the list differ), and the new assertion also pins the paths, which the old one did not. The only list it newly accepts is the one with the panel's list read, which D3 requires on every device class. The rest of M4 (the disabled selects, the disabled drag, the attempted drop and status change, the link) does not change. So CEX-17's criterion 4, "The phone viewport is read-only.", is tested by the same steps and is not weaker. Order: the page's GET is first, because the page's constructor sends it; the panel's GET is second, because the panel is created in the page's first change detection (F8, F10: `FakeApiClient.requests` is in subscription order).

Panel design, for the implementer:
- Injects `API_CLIENT`, `SSE_CLIENT`, `ActiveProjectSignal` (its `projectId`), `DeviceClassService` and `DestroyRef`.
- Signals: `snapshots` (undefined until the first read), `failure`, `label`. A computed `editable` is true for `tablet` and `desktop`, as in the page (P9).
- Reads: a `Subject` with `switchMap` over `outcomeOf(api.get(SNAPSHOTS_PATH, snapshotListCopy))`, the page's pattern. A successful read sets `snapshots` and clears `failure`; a failed one sets `failure`. The constructor calls `reads.next()` once.
- Triggers: `events.stream('compile-export')` where the type is `snapshot-created` or `snapshot-restored`, the data passes `isSnapshotEventData`, and `data.projectId === projectId()`. No other trigger: no `reconcile$` subscription (D5, D8).
- `create()`: when editable and the trimmed label is not empty, `api.post(SNAPSHOTS_PATH, { label }, snapshotSummaryCopy)`; on error, `failure` is set.
- `restore(row)`: when editable, the row is readable, and `window.confirm(message)` returns true (P2, P3), `api.post(SNAPSHOT_RESTORE_PATH, { id: row.id }, manuscriptViewCopy)`, where `manuscriptViewCopy` comes from `./manuscript-contract`; on error, `failure` is set.
- Template: a `<section>` with `<h2>Snapshots</h2>`, the label input, the Snapshot button, the alert, then either the list or `No snapshots yet.`
