### 3.2 Choices made here (names, layout and shapes the units leave open)

- **C-1. Files.** `run-state.ts`, a pure module with no library and no Angular import, holds the rules (C-2, C-3, D2, D4, D13, the request of C-7). `run-dialog.ts` is the dialog component. Type imports only from the contract.
- **C-2. Run state.** A signal `run` holds `RunState | null` from the current-run GET (`currentRunCopy`). Events fold into it:
  - `node-status` whose `runId` equals the run's: that node's state becomes `{status, result?, error?}`. Other run ids are ignored. The data is checked by `nodeStatusDataCopy` (C-13).
  - `run-ended` whose `runId` matches: `status` and `reason` are set.
  - `run-started`: a read. The event carries the full state, but the read reuses `currentRunCopy` and needs no new copy.
  - Every event increments `eventSeq`. Reads go through a Subject with `switchMap`, so the latest read wins. A read's answer is applied only if no event arrived after the read was sent; otherwise a new read starts.
  - Reads start on load, on every reconcile tick, on `run-started`, and after a successful start.
- **C-3. Lock.** `currentGraphId` is a signal set in `load()` (it replaces the plain field `graphId` of line 525). `running` is true when the page is a recipe and `runOfGraph(run, id)` has status `running`. `starting` is true from the Start click until the first current-run read after the start answers (so the canvas does not become editable between the start reply and the read), or until the start fails. `editable = !running && !starting`, a `computed` named `editable` (the name GRR-12's step 0 will find, section 7). A story view is always editable.
- **C-4. Guards.** The connection validator returns false when not editable. `onConnect`, `onMove`, `add`, `addTool`, `deleteSelected`, `onSettings` and `save` each begin with `if (!this.editable()) return;`. Disabled controls: Add, Delete selected, Save, every palette button, Run (`runBlocked() || !editable()`), and Run to here (`!editable() || runBlocked()`). The `app-tool-form` of a node sits in `<fieldset [disabled]="!editable()">`. While the canvas is not editable, the vnodes are rebuilt undraggable, and they are rebuilt as before once it is editable again (C-11). The edits of GRR-12 and GRR-14, when they are on main, get the same guard (steps 5g and 5h).
- **C-5. Dialog.** `app-run-dialog` renders an inline `section[role=dialog][data-run-dialog]`, not a native `<dialog>`, because jsdom has no `showModal`. It sits in the recipe branch right after `div.controls`, outside the vflow and outside GRR-12's `div[cdkDropListGroup]` wrapper, so the pickers' drop lists do not join the side list's group (GRR-12 C-4 note; DECISIONS line 4331). Inputs: `title`, `fields`, `projectId`, `busy`, `failure`. Outputs: `start` (the values) and `cancel`. Each field is `div[data-run-field=<nodeId>]`:
  - text input: a `select[data-text-mode]` (`text` or `file`), then a `textarea` for text or an `input` with a `datalist` of project files for a file;
  - entity input: `app-entity-picker` with a synthesized `FormField`: `control: 'entity-picker'`, `list: true`, `entityKinds` from D4, `port: false`, `required: false`, `default: undefined`;
  - style input: the same with `control: 'style-picker'`, `list: false`, no kinds;
