### 1b. Small decisions this plan makes

1. **Files and names.** Section 2 lists them. They follow the module shape (`units/README.md` line 125) and the boundaries lint, whose entry files are `features/*/*.routes.ts` (`eslint.config.mjs` line 41). Reason: the existing layout.
2. **Route entry.** The entry follows SHL-01 decision 9 and copies the `core-gate` entry (`apps/web/src/app/app.routes.ts` lines 37 to 49): `path: 'setup'`, `pathMatch: 'full'`, `data: { scope: 'app', minDeviceClass: 'phone' } satisfies ShellRouteData` (no `nav`), `loadChildren: () => import('./features/setup-auth/setup-auth.routes').then((feature) => feature.setupRoutes)`. Reason: `minDeviceClass` must be written, because an absent value means `tablet` (`route-data.ts` lines 12 and 13; `device-class.ts` line 162).
3. **Page states.**
   - Loading: no identity block, no Continue.
   - Identity 200: the identity text, "You're in." and the Continue button.
   - Any 401 (from the identity read or from Continue): the sign-in notice only. The identity text, "You're in." and Continue are hidden. Reason: a POST without a session is refused with 401 (`setup-auth.guard.ts` lines 58 to 63).
   - A tailnet code (`AUTH_TAILNET_IDENTITY_MISSING` or `AUTH_TAILNET_NOT_ALLOWED`, any status) from either call: its explanation only, with the same hiding.
   - Any other error from the identity read: its message in a `role="alert"` paragraph (the landing's pattern, `landing.ts` lines 21 to 23), and no Continue.
   - Any other error from Continue: its message in a `role="alert"` paragraph, the identity text stays, and Continue is enabled again.
   Reason: the unit does not name these states; Continue is offered only once the server has confirmed who the caller is.
4. **Identity and button texts.** Heading `<h2>Setup</h2>`. Loopback identity: "Signed in from this computer (loopback)." Tailnet identity: "Signed in over the tailnet as <login>." Then "You're in." and a `mat-flat-button` "Continue" (`MatButton` is already used by `notice-banners.ts` line 2). Reason: the unit fixes the content, not the wording (open point 1).
5. **Continue request and result.** The body is `{}` (`ApiClient.post` takes a body, `api-client.ts` lines 30 to 34; the server reads none, `setup-status.controller.ts` lines 29 to 33). The response is parsed with `setupStatusSchema` (`status.ts` lines 34 to 38). On success the page calls `navigateByUrl(LANDING_PATH, { replaceUrl: true })`. Reason: `routes.ts` lines 20 to 22 name `LANDING_PATH` as the target after setup, and the landing then picks the active project (`landing.ts` lines 63 to 74). `replaceUrl` follows the landing (`landing.ts` line 54). The button is disabled while the POST is in flight.
6. **The command texts.** `SIGN_IN_COMMAND = 'cat ~/Books/.scriba/setup-url'` and `DOCKER_LOGS_COMMAND = 'docker compose logs scriba'`, each alone in a `<code>` element. Reason: the unit's wording. The service name is `scriba` (`deploy/compose.yaml` line 39), and the URL is printed on stdout at each start (`setup-token.store.ts` line 109), so the docker logs show it.
7. **Heading rule.** No heading on the page or in a notice may contain the word "Scriba". Reason: the journey's "app loads" step finds the heading `Scriba` by a case-insensitive substring match (`e2e/specs/journey.e2e.ts` line 18; `node_modules/playwright-core/types/types.d.ts` lines 3277 and 3278), the toolbar already has `<h1>Scriba</h1>` (`apps/web/src/app/app.html` line 2), and with no cookie the landing sends that very step to `/setup` (the 401 path), so a second match would break strict mode. C2 asserts the rule directly (section 4).

Open Scriba through its tailnet address, with Tailscale Serve running." `AUTH_TAILNET_NOT_ALLOWED`: "This Tailscale login is not on the owner's allowlist. Use the computer that runs Scriba and its setup link to change the allowlist." The code is matched against `contract.SETUP_AUTH_ERROR_CODES` from the dynamic load, never against a literal copy.
