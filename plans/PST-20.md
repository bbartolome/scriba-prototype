### 1c. Choices this plan makes (the unit leaves them open)

- **C1 Nav entry (open point 1):** `{label: 'Review', icon: 'rate_review', order: 25}`. Order 25 sits between Projects (20) and Files (30), the order of the `modules/shell.md` route table (review before files); the orders are at `app.routes.ts` lines 18, 31, 70, 95, 108, 121 and 134. The icon exists in the font the Shell loads (F-R1). At 390 px a project route shows eight links (F-R2).
- **C2 Groups:** key `agent-run:<runId>` or `recipe-run:<runId>:<nodeId>`. Heading (`h3`) "Agent run <runId>" or "Recipe run <runId>, output <nodeId>". The page heading is `h2` "Review", as `files-page.ts` line 198 has `h2` "Files". Groups appear in the order of their first change in the list, which is id order (`pending.service.ts` lines 100 to 101; `pending-store.ts` line 53 sorts the names).
- **C3 Rows and the open change:** each change is an `li` that shows its `targetPath` in a `code` element, the badges of C6 and C8, and an "Open" button with `aria-expanded`. One change is open at a time; opening one closes the other. The open change's panel (its `DiffView`, its notices and its action bar) renders inside its own `li`, under the row, at every device class, so the page is one column. The action bar is `position: sticky; bottom: 0`, and its buttons are at least 48 px high (unit line 20). The selection is component state, not a URL parameter. A change that leaves the list closes its panel.
- **C4 Texts:** `path` = `targetPath`; `base` = `capturedBase?.content ?? ''` (an empty base for a file that does not exist, as `plans/AGL-14.md` D2 has it); `proposed` = the text of C5. The `diff` string is not shown: `DiffView` draws its own diff. The page passes strings, so an equal string does not rebuild the editor.
- **C5 Edits (open point 5):** `editable` is true for every open change.
  - The page keeps the last text that `contentChange` emitted, per change id (the held edit). Accept and Accept anyway send `{content: <held edit>}` when the change holds one, and `{}` otherwise. Reject and refresh send no body: `api.post(path, undefined, copy)`, as `apps/web/src/app/features/providers/providers-store.ts` line 170 does.
  - Shown text is sent text. The page binds `DiffView`'s `proposed` to the committed edit of the change, or to `change.proposed` when there is none. It commits (copies the held edit into the committed edit) on a `focusout` of the `app-diff-view` element, on a `click` in it whose target is not inside `.cm-editor`, and when the panel closes. It never commits on each emitted edit, because a rebuild per keystroke would lose the cursor. Reason: the layout toggle rebuilds the view from `proposed` (1b), so an edit that only the editor holds would vanish from the view while Accept still sent it.
  - Drop rule. When a `pending-updated` event, a refresh answer or a list read changes the change's `proposed` or its `capturedBase?.content`, the page drops the held and the committed edit of that change and shows, in its panel, "The proposal changed, so your edit was discarded." (`role="status"`). An update that changes neither (a conflict or a grounding update) keeps the edit. Tests R10a to R10c.
- **C6 Conflict copy:** a "Conflict" badge in the row, and by reason the message `base-changed`: "The file changed after this change was proposed."; `target-missing`: "The file this change would edit is missing."; `target-exists`: "A file already exists at this path." The same message goes to `DiffView`'s `conflict` (true) and `conflictMessage`. Refresh and Accept anyway show only when `conflict` is not null. Accept and Reject show for every open change.
- **C7 Accept anyway (open point 6):** pressing it opens an inline panel with `role="alertdialog"`, `aria-labelledby` its heading "Accept anyway?", and the text "The file on disk is saved first: as a version for a top-level draft, otherwise as a backup under .scriba/backups/." (`plans/PST-17.md` line 167; `pending.service.ts` lines 200 to 202). Buttons: "Confirm accept anyway" and "Cancel". When it opens, focus moves to "Cancel". No request is sent before Confirm. It is not a native `<dialog>`: `apps/web/src` has no dialog precedent (no `MatDialog`, `<dialog>` or `alertdialog`), and jsdom 30.1.3 does not implement `showModal` (F-R5).
- **C8 Grounding chip (open point 8):** a summary built in this feature from the counts, with the agent-loop chip's wording `"<supported> supported · <weak> weak · <unsupported> unsupported"` (`apps/web/src/app/features/agent-loop/chat-state.ts` line 508), the `checkedAt` time, and a badge "Unsupported claims" when `unsupported` is above 0. No chip when `grounding` is absent. It is not the agent-loop chip (rule R1).
- **C9 Provenance:** `entityIds` and `sourcesUsed` are shown as lists, but only when they are arrays and only their string items. Other keys are ignored. The shapes come from `packages/contracts/src/agent-loop/provenance.ts` lines 6 to 14 and from the recipe provenance `{graphId, nodeId, entityIds, sourcesUsed}` (`units/GRR-06-output-nodes-pending-changes.md` line 25).
- **C10 Live events:** a change is kept only when `projectId` matches the active project, and, when `?run=` is set, only when `origin.runId` equals it. `pending-created` inserts; `pending-updated` replaces by id, or inserts when the id is absent; `pending-resolved` removes by id. Each action's answer is applied the same way: an answer whose status is not `pending` removes the row. The store is keyed by id, so a duplicate from the event and from the answer is harmless.
- **C11 Reconcile:** a reconcile tick (`apps/web/src/app/shell/sse-client.ts` line 59), a project switch and a change of `?run=` re-read the list. A project switch also clears the list, the edits and the selection. The files page re-reads the same way (`apps/web/src/app/features/project-store/files-page.ts` lines 393 to 414).
- **C12 Busy and errors:** while a POST for a change is in flight, its buttons are disabled, so a double accept cannot reach the server (a second accept would get 409 `PROJECT_PENDING_NOT_OPEN`, `pending.service.ts` lines 358 to 363). A failed action shows the server's message in the panel (`ApiError.message`, which the HTTP client takes from the error body: `apps/web/src/app/shell/api-client.ts` lines 107 to 109) and re-reads the list. A failed list read shows "Could not load the open changes." with the error's message, if it is an `ApiError`, in a `role="alert"` element, and shows no rows. Every subscription has an error handler: no error leaves the page.
- **C13 Unsaved text (open point 2):** while a change holds an edit, the page is an `UnsavedSource` registered with `UnsavedTextRegistry`. Its `flush()` returns `of(false)`, because only Accept saves an edit, so leaving the page asks the author (`confirmUnsavedLeave`). The `review` route gets `canDeactivate: [unsavedTextGuard]`, as the files route does (`project-store.routes.ts` line 22). The interface is `apps/web/src/app/shell/unsaved-text.ts` lines 6 to 11 and 41 to 49. `UnsavedTextRegistry` is not in the Shell barrel (`apps/web/src/app/shell/index.ts`), so the page imports it from `'../../shell/unsaved-text'`, as `unit/TRG-14`'s `tool-editor.ts` line 39 does.
- **C14 Empty states:** "No open changes." and, with `?run=`, "No open changes from this run."
