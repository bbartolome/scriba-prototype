## 1. Decisions this plan follows

### 1a. Settled by the unit, the module, the contracts, DECISIONS and earlier plans

- **S1. Two surfaces, one check.** HTTP (project-scoped) and the in-process provider both go through the path check and the active-project check. Source: unit line 18; module line 52.
- **S2. Active check, then lookup.** Every call runs `ProjectStoreService.requireActive(projectId)` (ids only), then `ProjectsService.find(projectId)`. An undefined result is `PROJECT_NOT_FOUND` (404). Source: unit line 18; module line 47; `plans/PST-04.md` D10 (line 25) and section 5 check 1 (line 84).
- **S3. One path function, fixed messages.** Every path goes through `ProjectStoreService.resolvePath`. Responses and errors carry project-relative paths and fixed strings only. Source: module lines 44 and 48; `plans/PST-02.md` P3 and P11, S8.
- **S4. Routes and shapes.** `GET .../files` with query `{path, recursive?}` answers `{entries}`. `GET .../file` with query `{path}` answers `{path, content, hash, mtime}`. `POST .../file/write` with `{path, content, baseHash?}` and `POST .../file/edit` with `{path, old, new}` both answer `{path, hash, mtime}`. Source: unit lines 19 to 22; contract `packages/contracts/src/project-store/routes.ts` lines 14 to 21 and `files.ts` lines 15 to 60; module line 45 (only GET and POST). A POST command answers 200, as an action does (`plans/PST-03.md` S1).
- **S5. Hashes.** `sha256:` followed by the lower-case hex SHA-256 of the file's bytes. Source: unit line 20; module line 49; `constants.ts` line 11.
- **S6. Read refusals.** A file over the cap gives `PROJECT_FILE_TOO_LARGE` (413). A file that is not UTF-8 text gives `PROJECT_NOT_TEXT` (415). Both stay in the list. A missing file gives `PROJECT_NOT_FOUND` (404). Source: unit lines 20 and 31; `constants.ts` lines 22 and 23 (`FILE_SIZE_CAP_BYTES`, the binary megabyte, `plans/PST-01.md` D12).
- **S7. Stale base.** A `baseHash` that does not match the disk gives `PROJECT_WRITE_CONFLICT` (409). Source: unit line 21; contract `errors.ts` line 66.
- **S8. Atomic writes.** Temp file in the same folder, then rename; missing parents are created. The existing `writeFileAtomic` does this, so it is reused unchanged. Source: unit line 21; module line 50; `apps/api/src/modules/project-store/atomic-write.ts` lines 6 to 16; `plans/PST-03.md` P15 (line 63).
- **S9. Edit.** Exact replacement. Zero matches gives `PROJECT_EDIT_NO_MATCH` (409); more than one gives `PROJECT_EDIT_AMBIGUOUS` (409). Source: unit line 22; contract `errors.ts` lines 67 and 68.
- **S10. project.yaml writes.** Validated against the schema before the write; comments and key order preserved; an invalid one fails validation. Invalid project.yaml uses `PROJECT_INVALID` (422) with the issues in `details`. Source: unit line 23; `packages/contracts/src/project-store/project.ts` lines 18 to 28 and 37 to 38.
- **S11. Too-new refusal.** A too-new `project.yaml` is refused for reads and for writes with `PROJECT_SCHEMA_TOO_NEW` (409). "Too-new" means `readYamlState(text).status === 'too-new'`. Source: unit line 24; `project-yaml.ts` lines 21 to 38; `errors.ts` line 73.
- **S12. Events.** Every successful write and edit publishes `files-changed` with `{projectId, paths}`, after the rename. Source: unit line 25; contract `events.ts` lines 12 to 16; `events.publisher.ts` line 61; the publish pattern at `active-project.service.ts` lines 81 to 86.
- **S13. GET never mutates.** Every GET only reads; only GET and POST are used. Source: module line 45; unit line 36.
- **S14. Author writes only.** `write` and `edit` are for author actions. Agent and recipe changes use `propose` (PST-15). Source: unit line 26.
- **S15. Dot-entries hidden in list.** Source: unit line 19.
- **S16. The editor's BOM rule.** The read returns U+FEFF as the first character of `content` when the file has a BOM, and the write stores `content` unchanged. The Shell editor depends on it (`plans/SHL-13.md` lines 165 and 173). `plans/DECISIONS.md` line 3492 makes it a downstream requirement that this plan state and test the rule. Source of the rule: P6 and P7 below; test X1.
- **S17. Points PST-02 left to PST-06.** `plans/PST-02.md` line 295, items (a) to (f), are answered in section 5 (the first bullet of the other checks), from S3, P5, P7 and S18.
- **S18. Writes through a link.** A write through a within-project link writes the link's target, and the link is kept. Source: `plans/PST-03.md` P7 (line 45) and open point 9 (line 187); `plans/PST-02.md` line 295, item (f).

### 1b. Choices made by this plan

- **P1. Code layout.** New files `apps/api/src/modules/project-store/files.service.ts` (class `FilesService`) and `files.controller.ts` (class `FilesController`). `FilesService` is registered in `project-store.module.ts`, exported from it, and re-exported from the module's entry file, so in-process callers take it from the entry file. The methods are not added to `ProjectStoreService`, because that class cannot take `ProjectsService` (the cycle of `plans/PST-04.md` D11). Same pattern as `ProjectsService`, `ActiveProjectService` and `SamplesService`.
- **P2. Synchronous.** The file calls are sync `node:fs`, as the path check is. `plans/PST-02.md` open point 8 (line 315) recommends sync.
- **P3. Folder status is not a gate.** The active folder is served whatever its `project.yaml` status is (ok, invalid, too-new or importable). Only `project.yaml` itself is held to the schema rules (P12 to P14). The active-id and folder checks of S2 still apply. The unit does not gate the file API on folder status, and this plan adds no such gate.
- **P4. Lookup with an absent folder.** A folder that is not `isDirectory` where a directory is needed gives `PROJECT_NOT_FOUND` (404) with the message "No folder was found at that path." A path that is not a file where a file is needed gives `PROJECT_NOT_FOUND` with "No file was found at that path." The contract has no other code for "wrong kind", so no new code is added.
- **P5. The list.** (a) `.` is the project root (`isRoot`, `plans/PST-02.md` P4). (b) An entry whose name starts with `.` is omitted at every depth, and the walk does not enter it. Reserved folders are dot-folders, so they are omitted too. (c) Every other entry is checked with `resolvePath` before it is listed; an entry that the check refuses is omitted (a link out of the project, a dangling link, a name with a backslash, a link into a reserved folder). (d) A link to a folder is listed as `dir` but not entered, so a loop cannot run forever. (e) `size` is the stat size of a file and 0 for a folder. `kind`, `size` and `mtime` of a link are those of its target. (f) `mtime` is `stat.mtime.toISOString()`. (g) Entries are sorted by `path` in code-unit order, the rule of `plans/PST-03.md` P8. (h) An entry that is neither a file nor a folder is omitted. (i) `recursive` defaults to false.
- **P6. The read.** Order: (1) the active check and the folder (S2); (2) `resolvePath`; (3) a missing path or a non-file gives `PROJECT_NOT_FOUND`; (4) the stat size is checked before any bytes are read: over `FILE_SIZE_CAP_BYTES` gives `PROJECT_FILE_TOO_LARGE`; (5) the bytes are read; a byte 0x00 anywhere, or bytes that are not valid UTF-8, gives `PROJECT_NOT_TEXT`. The text is decoded with `new TextDecoder('utf-8', {fatal: true, ignoreBOM: true})`, so a BOM stays as U+FEFF (probed, section 7); (6) for `project.yaml` at the root, a too-new text gives `PROJECT_SCHEMA_TOO_NEW`; (7) the answer, with `hash` over the bytes read and `mtime` from the stat. No line-ending conversion is made.
- **P7. The write.** Order: (1) the active check and the folder; (2) `resolvePath`; (3) when the target is an existing folder (this includes the project root), `PROJECT_PATH_INVALID` (400); (4) for `project.yaml` at the root, a disk text that is too-new gives `PROJECT_SCHEMA_TOO_NEW`; (5) when `baseHash` is given, a missing file or a `hash` of the current bytes that differs gives `PROJECT_WRITE_CONFLICT`; (6) the content's UTF-8 length over `FILE_SIZE_CAP_BYTES` gives `PROJECT_FILE_TOO_LARGE` (P10); (7) for `project.yaml` at the root: a too-new content gives `PROJECT_SCHEMA_TOO_NEW`, and an invalid content gives `PROJECT_INVALID` with `details` set to the issues (the same rule as `plans/PST-03.md` P13); (8) the write (P14): `writeFileAtomic(target.realPath, content)`. An errno of `ENOTDIR`, `EEXIST` or `EISDIR` gives `PROJECT_PATH_INVALID` with "The path names a folder, or runs through a file, so no file can be written there." Any other errno gives a plain `Error` with the errno code and no path, which Platform answers as 500 `PLATFORM_INTERNAL`; (9) `files-changed` is published with `paths: [relativePath]`; (10) the answer `{path, hash, mtime}`, where `hash` is `sha256` of `Buffer.from(content, 'utf8')`. The content is stored as those bytes, with no change to line endings or the BOM (S16).
- **P8. The edit.** Order: (1) the active check and the folder; (2) `resolvePath`; (3) `old` of length 0 gives `PLATFORM_VALIDATION_FAILED` (400), as `plans/PST-03.md` P10(b) does for an empty name; the contract allows the empty string, so the service refuses it; (4) the read rules of P6 apply to the target (not found, too large, not text, too-new); (5) the number of matches of `old` is counted at every start position, so overlapping matches count (`aa` in `aaa` is two matches). Counting stops at two. Zero gives `PROJECT_EDIT_NO_MATCH`; two or more gives `PROJECT_EDIT_AMBIGUOUS`; (6) the one match is replaced, and steps (6) to (10) of P7 apply to the new content.
- **P9. Writing over a non-text file is allowed.** A write replaces the whole file. The unit gives the size and text refusals for reads only (unit line 20). The write does not read the old file as text; it hashes its bytes only when `baseHash` is given.
- **P10. Write size cap (planner's choice, open point 3).** A content over `FILE_SIZE_CAP_BYTES` is refused with `PROJECT_FILE_TOO_LARGE` (413). Without it, a saved file could be one that the read then refuses. The unit states the cap for reads only.
- **P11. Lone surrogates.** Not refused. `Buffer.from` stores them as U+FFFD, and the returned hash covers the bytes stored (open point 8).
- **P12. project.yaml is the root file only.** `project.yaml` at the project root is the one held to the schema rules. A file of that name deeper in the project is plain text.
- **P13. Too-new check.** Only `project.yaml` at the root has a registered maximum version (`PROJECT_YAML_SCHEMA_VERSION`, `project-yaml.ts` line 5). PST-23 adds the registry; this plan keeps the check in `files.service.ts` as one function of the relative path, so PST-23 can extend it.
- **P14. Atomic write.** `writeFileAtomic` is reused as it is (`atomic-write.ts` lines 6 to 16): temp file `${target}.tmp` in the same folder, then `renameSync`. The temp name is the one accepted by `plans/PST-03.md` open point 10 (line 188). No fsync is added (open point 7).
- **P15. Messages.** One map `FILE_MESSAGES` in `files.service.ts`, `as const`, fixed strings: `NO_FILE` "No file was found at that path."; `NO_FOLDER` "No folder was found at that path."; `NOT_TEXT` "The file is not UTF-8 text."; `TOO_LARGE` "The file is larger than the 5 MiB limit."; `CONFLICT` "The file changed since it was read. Read it again before saving."; `NO_MATCH` "The text to replace was not found in the file."; `AMBIGUOUS` "The text to replace occurs more than once in the file."; `EMPTY_OLD` "The text to replace must not be empty."; `NOT_A_FILE` "The path names a folder, or runs through a file, so no file can be written there." The existing `PROJECT_MESSAGES` (`projects.service.ts` lines 34 to 43) supply the project-not-found, too-new and invalid messages.
- **P16. Routes and bodies.** `files.controller.ts` (class `FilesController`, `@Controller()` with the full route constants, as `projects.controller.ts` does). List: `@Query(new ZodValidationPipe(fileListQuerySchema))`. Read: `@Query(new ZodValidationPipe(fileListQuerySchema.pick({ path: true })))`, a local constant in the controller, so no contract change is needed. Write: `@Body(new ZodValidationPipe(fileWriteSchema))`, `@HttpCode(200)`. Edit: `@Body(new ZodValidationPipe(fileEditSchema))`, `@HttpCode(200)`. The project id comes from `@Param('projectId')`.
- **P17. Provider methods.** `FilesService` exposes `list(projectId, {path, recursive?})`, `read(projectId, path)`, `write(projectId, {path, content, baseHash?})` and `edit(projectId, {path, old, new})`. The HTTP handlers call these and nothing else. The in-process callers receive the same shapes.
- **P18. Test-only kit route.** A test module `FilesKitModule` (in the kit file) has a controller under `api/project-store-test`, not `/api/project-store/`, and it is not in `COMPOSED_MODULES`. This is the precedent of `plans/PST-02.md` P16. Its `fill-write` route builds a content of a given byte length on the server, because the HTTP body limit is 100 KB (`plans/DECISIONS.md` lines 513 and 514, the PLT-05 entry), so a 5 MiB body cannot be sent.
- **P19. Invariant fixtures.** This unit adds four `FIXTURE_PATHS` entries to `apps/api/test/invariant-sweep.ts`, because a route template with `:` and no entry fails the sweeps by name (`invariant-sweep.ts` lines 4 and 5, 71 to 84, 145 to 155). `units/SAU-07-*.md` line 19 says that a module with a path parameter adds its own entry. The reason the entries cannot wait for PST-12 is in open point 1.
- **P20. Test names.** Tests are named with a letter and a number, as the tests `C1` and `C2` of `apps/api/test/project-store-active.test.ts` (lines 66 and 95) are.
- **P21. Contract unchanged, no dependency added.** Every code and shape the unit needs is in the contract (`errors.ts` lines 5 to 26 and 58 to 79; `files.ts`; `events.ts`). No file under `packages/contracts/` changes. `apps/api/package.json` does not change: `yaml` is already a dependency (line 19).
