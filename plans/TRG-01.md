### 1b. Decisions this plan makes (the unit leaves them open; each is the plan's choice)

- **D1 Layout.** Ten source files and an `index.ts` in `packages/contracts/src/tool-registry/`: `constants.ts`, `spec.ts`, `views.ts`, `lint.ts`, `catalog.ts`, `call.ts`, `errors.ts`, `routes.ts`, `events.ts`, `settings.ts`. Each schema `xSchema` also exports its type `X = z.infer<typeof xSchema>`. No `examples.ts`: the unit lists no example payloads, and the cold-open-shaped fixture lives in the test (module line 52). No function is exported.
- **D2 Cross-slice imports through the slice indexes.** `events.ts` imports `sseEnvelopeSchema` from `../platform/index.js`. `call.ts` imports `entityRefSchema` and `projectPathSchema` from `../project-store/index.js`. The index is the slice's public face, so an internal file move in `/project-store` does not break this build. Neither slice imports `tool-registry`, so there is no cycle.
- **D3 Envelope strictness and version range.** `toolSpecSchema` and `entityTypeSchema` are `z.strictObject`: a stray top-level key is refused, so a typo is an issue and the schema can only be loosened later (expand). `schemaVersion` is an integer at least 1, not the literal 1: the supported version is the constant `TOOL_SPEC_SCHEMA_VERSION = 1`, so a file that differs from a version 1 file only by a higher `schemaVersion` still parses, and the loader refuses it with `TOOL_SCHEMA_VERSION_UNSUPPORTED` (`units/TRG-06-pack-loader-catalog.md` line 23). A newer file that also adds a key does not parse with this schema, because `strictObject` refuses the key. Hand-off to TRG-06 (lines 23 and 30): read `schemaVersion` from the parsed YAML before parsing with `toolSpecSchema`, so a newer file is refused and listed with `TOOL_SCHEMA_VERSION_UNSUPPORTED`, not reported as an unknown key. The same holds for entity types with `ENTITY_TYPE_SCHEMA_VERSION = 1`, a constant the unit does not list.
- **D4 Field rules.** `name`: `TOOL_NAME_PATTERN` (the unit's regex, anchored). `description`: non-empty, at most 200 characters, no line break (`z.string().min(1).max(200).regex(/^[^\r\n]*$/)`); "one line" is read as non-empty, and lint repeats the rule. `enabled`: boolean. `prompt`: `z.string()` with no minimum (the unit says "string"); an empty prompt is lint's question. `inputs`: a loose record (`jsonSchemaObjectSchema`, `z.record(z.string(), z.unknown())`), which refuses an array, a string and null. The file name `<name>.yaml` is not an envelope field; lint checks it against the stem.
- **D5 Hint vocabulary.** `HINT_KEYS` is the tuple of the four closed keys. `PORT_TYPES`, `CONTROL_TYPES`, `OUTPUT_KINDS` are tuples; `portTypeSchema`, `controlTypeSchema`, `outputKindSchema`, `hintKeySchema` are `z.enum` over them. `toolHintsSchema` is a `z.strictObject` of the four optional hints (`x-scriba-type`: port type; `x-scriba-port`: boolean; `x-scriba-entity-kinds`: non-empty strings; `x-scriba-control`: control type). It is an addition so that lint, emission and tests share one executable definition of the closed vocabulary. `ENTITY_KIND_PATTERN` is `/^[a-z][a-z0-9]*(-[a-z0-9]+)*$/` (lower kebab-case, the shape of Platform's event-type pattern); it applies to entity-type `kind`, not to the hint list, so lint can warn about an unknown kind instead of the schema refusing it.
- **D6 Port descriptor.** `{inputs: PortInput[], output, params: string[]}`. `PortInput` is `{key, type: PortType, list, required, title}`. `output` is `{key: 'output', type: 'text', kind: OutputKind}`, with `type` a `z.literal('text')` (module line 45: always `text` in v1; widening later is an expand). The derivation rule is a `/** */` comment on `portDescriptorSchema`, so it reaches the `.d.ts`. It says, in this wording:

  ```
  /**
   * Port descriptor of one tool, derived from its `inputs` schema. Derivation rule:
   * - An input port is a property of `inputs` with `x-scriba-port: true`. Ports keep the property order.
   * - The port `type` is the property's `x-scriba-type` (`text`, `entity` or `style`).
   * - `list` is true when the property's schema type is `array`. `required` is true when the key is in `required`.
   * - `title` is the property's `title`, or its key when it has none.
   * - There is exactly one output port. Its key is `output` and its type is `text` in v1. It carries the tool's output kind. The type may be widened by expand-contract.
   * - Every other property is a param. `params` lists their keys in property order.
   * - A port id is `<nodeId>.<key>`.
   * - A port type is an element type: an `entity` list port accepts a list of entities. A wire carries one value per input.
   * - The descriptor does not check shapes. Ajv checks the arguments when a run starts.
   */
  ```

  The unit gives every line except the `title` fallback and "in property order" for `params`, which are the plan's choices (the type of `title` is a required string, so something must fill it; `units/TRG-02-emission-validate.md` line 19 lists `title` as an annotation).
- **D7 Form descriptor.** `{fields: FormField[]}`: an object, so a later field next to `fields` is an expand, where a bare array could not grow. `FormField` has the unit's fifteen names. `default` is a required key typed `z.unknown()`; `null` means "no default", which is unambiguous because the subset has no nullable type (zod 4.6.7 requires the key, section 7a). `description` is a string (empty when none). `enum` is a list of strings (the subset gives `enum` to `string` only, `units/TRG-02-emission-validate.md` line 19). `minimum` and `maximum` are numbers; `minLength` and `maxLength` are integers at least 0; `entityKinds` is a list of non-empty strings; `elementType` is a `PortType`: the field's `x-scriba-type`, present when the field declares one, whether or not it is a port. This reads "port types are element types" (unit line 25) and the TRG-02 field list "list flag, entity kinds, port flag, element type" (TRG-02 line 21) together. The reading is provisional: neither it nor the JSON item type tells an integer from a number or a string from a number, which TRG-03's slider and number controls need (TRG-02 lines 19 and 24), so open point 1 asks the Navigator for the reading and for an optional `valueType`.

The name is the module's own term, "model function schema" (`modules/tool-registry.md` line 3). `parameters` is loose, so the Agent loop can add a `target` property (`units/AGL-13-output-routing.md` line 18).
