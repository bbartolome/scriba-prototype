### 1b. Decisions this plan makes (the unit leaves them open)

- **D1 Files and names.** New `apps/web/src/app/features/agent-loop/grounding-chip.ts`: standalone `GroundingChip`, selector `app-grounding-chip`, required input `entry: ChatGrounding`. The pure types and helpers go in `chat-state.ts`. The literal `AGENT_GROUNDING_PATH` goes in `agent-contract.ts`. Tests: G1 to G6 appended to `chat-page.spec.ts`; the two X1 tests amended in `agent-contract.spec.ts`; F12 appended to `files-page.spec.ts`.
- **D2 Placement: outside the Shell card.** A chip is never in the card's content slot, so it shows while its card is collapsed on a phone (S8). No Shell change is needed.
- **D3 Grouping and place.** Each turn holds one grounding entry per `targetPath`, in order of first appearance; each entry holds the latest result for its path, or the `checking` state. In the stream, an entry is shown right after the first card of the turn whose `diffPreview.path` equals its `targetPath` (unit line 18, "per draft card"). An entry that matches no card of its turn (for example the entry of an on-demand run, whose turn has no card) is shown after the turn's cards, before the review link.
- **D4 Summary text.** `N supported · N weak · N unsupported` (unit line 18), counted from the claims, because the result has no summary field (`grounding.ts` line 33). While a check runs the text is `Checking <path>`. The chip button holds only this text in a `span.summary`; it has no `mat-icon` (a ligature would add its name to `textContent`). Its state is shown by `aria-expanded` and by a CSS marker (`::after`, `▸` collapsed and `▾` expanded).
- **D5 Verdict badge.** A `span` with `data-verdict` set to the verdict, holding a `mat-icon` (`aria-hidden="true"`) and a `span.label` with `Supported`, `Weak` or `Unsupported`. Icons (Material ligatures, as the Shell's status icons are, `tool-call-card.ts` lines 28 to 35): `check_circle`, `warning`, `cancel`. Colour tokens the web app already uses (F13): supported `--mat-sys-tertiary-container` with `--mat-sys-on-tertiary-container`; weak `--mat-sys-secondary-container` with `--mat-sys-on-secondary-container`; unsupported `--mat-sys-error-container` with `--mat-sys-on-error-container`. Contrast is SHL-19's check (open point 6).
- **D6 Expansion.** The chip is a `button` with `aria-expanded` and `aria-controls`, as the card header is (`tool-call-card.ts` lines 165 to 167). The list is inside `@if (expanded())`, so a collapsed chip has no claim row in the DOM. The default is collapsed on a phone (`DeviceClassService.deviceClass() === 'phone'`) and expanded on other devices, held in a `linkedSignal` on that default, as the card does (`tool-call-card.ts` lines 258 to 269). Unit line 20 reads "the chip (its list) is collapsed; the chip shows" (open point 2).
- **D7 Claim rows.** Each row (`li.claim`) shows the verdict badge, the claim `text` and, when the claim has a passage, the `snippet` and a link to its `path` (S7) whose text is the path. A claim with no passage shows `No source passage cited.` The claim's `span` and `reason` are not shown: unit line 18 lists four items.
- **D8 Check grounding on a card.** `checkPathOf(card)` returns `card.diffPreview.path` when it is a string that starts with `drafts/`, otherwise `undefined` (the guard checks `diffPreview` as a record only, `agent-contract.ts` line 349, so the type is checked here). A card with a check path shows a `button.control` with the text `Check grounding` right after the card element (after its chip, if any). The button is disabled while `running()`. `checkGrounding(path)` posts `{path}` to `AGENT_GROUNDING_PATH` with `startReply`. On success, `applyStart` records the run with the intent label `Check grounding: <path>` (not sent). A failure goes through `showError` (which uses `noticeOf`, `chat-page.ts` line 85).
- **D9 Grounding events.** `grounding-started` (`{runId, seq, targetPath}`) sets a `checking` entry for its path in its run's turn (the result, if any, is kept until the new one arrives). `grounding-result` replaces the entry for its path with `{targetPath, checking: false, result}`. Both apply under S12 through `changeTurn`. `isChatEvent` accepts both, which replaces D18 of AGL-07. A grounding event asks for no run-state read.
- **D10 Run state.** `applyRunState` builds the turn's entries from `groundingResults`, one per path, the last one winning, and keeps an existing `checking` entry whose path has no result. History turns carry `grounding: []`, because `conversationTurnSchema` has no such field (`runs.ts` line 40; open point 5).
- **D11 Guards.** `isGroundingResult` checks: `schemaVersion` 1; `targetPath` a string (an empty string is accepted, as the contract's `projectPathSchema` is `z.string()`, F17); `claims` an array whose items have `text` a non-empty string (the contract has `min(1)`), `verdict` one of the three values, and `passage` optional, with `path` a string (empty accepted, F17), `offset` an integer of at least 0 and `snippet` a string. `isRunState` checks each `groundingResults` item with it, in place of the array-only check (`agent-contract.ts` lines 175 and 176). The event guards add the base `runId` and `seq`, plus `targetPath` (a string, as above) for `grounding-started` and `isGroundingResult` for `grounding-result`.
- **D12 Test seam and phone setup.** The chat route against the fakes, as AGL-07 D20. A phone test calls `restoreMatchMedia()` and `stubMatchMedia(390, 844)` before it renders, as T4 does (`chat-page.spec.ts` lines 324 and 325).
- **D13 Tap targets.** The chip button, each passage link, the card's Check grounding button and the query button of D14 have `min-height: 44px` (the buttons by the existing `.control` class, `chat-page.ts` line 143; the chip and links in `grounding-chip.ts`; the Files page link in `files-page.ts`).
- **D14 Check grounding from the Files view (unit line 19).** The Files page shows, while the selected file (`selected()`) starts with `drafts/` and the project is known, a link `a.check` with the text `Check grounding` to `['/projects', projectId, 'chat']` with `queryParams` `{ check: path }`. It sits at the top of the `section.preview`. It is a link only; the Files page makes no request for it, so its T10 ("only GET requests") holds. The chat page reads the `check` query parameter (`ActivatedRoute.queryParamMap`, as a signal with `toSignal`); when it starts with `drafts/`, a `button.control` with the text `Check grounding: <path>` shows above the stream, disabled while `running()`, and calls `checkGrounding(path)` (D8). Loading the chat URL never posts by itself, so a reload or a back navigation starts nothing. The query is not cleared.
