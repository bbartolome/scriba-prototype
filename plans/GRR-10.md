### 1.2 Small choices made by this plan (names, layout, shapes the unit leaves open)

- **C1 Library and peers.** `ngx-vflow` `2.7.0`, exact, in `apps/web` `dependencies`. Its three peers `d3-drag` `3.0.1`, `d3-selection` `3.0.1` and `d3-zoom` `3.0.1` are added as exact `dependencies`. The three `@types/d3-*` peers (`3.0.7`, `3.0.12`, `3.0.9`) are added as exact `devDependencies`. Reason: the module names the library and no version (module lines 3 and 71), the evaluation branch `spike/canvas-library-8` is not in this clone (`git branch -a`), and `2.7.0` is the npm `latest` tag. Its peer range `@angular/core >=19.2.17` admits the installed Angular `22.2.5`. Module line 71 makes a later renderer change a UI change, so the version is a small decision (open point 2).
- **C2 Files.** The adapter is `vflow-adapter.ts`, a file of plain functions with no Angular value import except `signal`. The page is `canvas-page.ts`, class `CanvasPage`, selector `app-canvas-page`. The GRR-09 placeholder file is deleted. The names follow the GRR-09 naming (`graph-list-page.ts`).
- **C3 Model.** The state is the graph file object, held in a signal. The vflow `nodes` array is built from the file on load, and it is built again only when a node is added or removed. The vflow `edges` array is built on load and rebuilt on connect, on remove and on add or remove of a node. Positions are read by the library and written back only from the `nodesChanges.position` output. Every change returns a new file object by object spread, so the key order of the file is kept. Nothing is ever read back from the vflow nodes or edges into the file except a position.
- **C4 Position rule.** A position change writes the file only where the new point differs from the file's position. The library emits position changes for every selected node when one node's point changes, with a TODO that says so (`ngx-vflow.mjs` lines 2251 to 2265). Without this rule a move could write positions of nodes that did not move.
- **C5 Ids.** A new node id is `<kind>-<n>`, with the smallest `n >= 1` that is free in the file. A new story edge id is `e<n>` and a new recipe wire id is `w<n>`, each with the smallest free `n >= 1`. These follow the contract's examples (`examples.ts`: story edges `e1` to `e6`, wires `w1` to `w5`; `plans/GRR-01.md` lines 180 and 182).
- **C6 Add.** The controls hold a kind select, a label input and an "Add" button. The story view offers `entity`, `scene` and `beat`; a new story node is `{id, kind, label, position}`, with the label input's text or the kind name when it is empty, and no `path` (GRR-14 adds the file picker). The recipe view offers `input` and `output`; a new input node is `{id, kind: 'input', position, params: {type: 'text', label}}` (label: the input's text, or `Input`), and a new output node is `{id, kind: 'output', position}`, with `params: {label}` only when the label input is not empty. Tool nodes are not added, because the palette is GRR-11's (unit GRR-11 line 19). GRR-11 adds the type choice and the output path (unit GRR-11 line 20). A new node is placed at `x = y = 40 * (node count + 1)`. Open point 4.
- **C7 Connect.** In the recipe view, `onConnect` adds the wire `{id, from: sourceHandle, to: targetHandle}` when both handles are set, and ignores the connection otherwise. In the story view it adds an edge `{id, from: source, to: target}` with no `relation`, which `storyEdgeSchema` allows (`graph.ts` line 68). The relation picker is GRR-14's (unit GRR-14 line 19). GRR-10 adds no connection validator: the library's defaults (no self connection, no connection between two handles of one type; `ngx-vflow.mjs` lines 104 to 141) apply. GRR-11 supplies `ConnectionSettings.validator` through the `[connection]` input, which GRR-10 binds to an empty object. Open points 4 and 5.
- **C8 Remove.** A "Delete selected" button removes the selected nodes (with every wire and edge that touches them) and the selected edges. The selection comes from the `nodesChanges.select` and `edgesChanges.select` outputs. There is no keyboard shortcut, because the library's keyboard actions cover only `multiSelection` and `selection` (`keyboard-action.type.d.ts` line 1). Open point 4.
- **C9 Issues panel.** The panel lists the `issues` of the latest response: the detail on load, or the save response. Each row shows `severity`, `code` and `message`. The panel is hidden when the list is empty. A refused save (an `ApiError`) shows the line `The graph was not saved.` and the error's message in the panel. A failed load shows `The graph could not be loaded.` and no canvas. A failed load is any error of the read, not only an `ApiError`: the fake client refuses an unregistered route with a plain `Error` (`test-doubles.ts` lines 90 to 93), and X2 (C14) depends on that case.
- **C10 Browser copies.** `graphDetailCopy` refuses any top-level key other than `graph` and `issues`, and checks the fields the page reads: `schemaVersion` (`1`), `view` (`story` or `recipe`), `name` (non-empty string), `nodes` and `edges` (lists), for each node `id` (string), `kind` (string) and `position` (`x`, `y` numbers), and for each edge `id`, `from` and `to` (strings), and each issue as `validationResultCopy` does. On success it returns `{graph: data.graph, issues}` with the graph object as received, not rebuilt, so its keys and values reach the save unchanged. `validationResultCopy` refuses any top-level key other than `issues`, and checks each issue's `code` and `message` (strings), `severity` (`error` or `warning`) and the optional `nodeId`, `edgeId`, `portId` (non-empty strings). The server's parse is the authority for the rest of the shape. This is the depth of the existing copies (S18). Open point 6.
- **C11 No dirty tracking.** The Save button is always enabled. There is no navigation guard. Open point 7.
- **C12 Handle template.** Each port handle is a `<handle>` element (the library's selector) with `id` set to the port id, `type` set to `source` or `target`, and `position` (a required input) set to `right` for a source and `left` for a target. Its `[template]` is the `svgHandle` template: an SVG `circle` with `data-port` set to the port id and `cx` and `cy` taken from the handle context's `point()`. Story nodes have one `target` handle on the left and one `source` handle on the right, both without `id` and without `data-port`. Every node element carries `data-node` set to the node id.
- **C13 Node templates.** One `<ng-template let-ctx vflowNodeHtml>` covers both views. Its context is the library's `NodeContext` (`template-context.interface.d.ts` line 19): `ctx.node` is the vflow node (`ctx.node.id` is the file node id) and `ctx.data()` is the file node that `vflowNodesOf` put in `data`. It draws a header with the kind and the label read from `ctx.data()` (story: `label`; input: `params.label`; output: `params.label` or `Output`; tool: the `tool` name), then one row per port. The rows come from one `ng-template #portRow let-row`, declared inside the node template so that `ctx` (and so `ctx.node.id`) is in scope, with context `{ $implicit: {side: 'input' | 'output', key: string} }`: a `div` row holding `<handle [id]="portIdOf(ctx.node.id, row.key)" [type]="row.side === 'input' ? 'target' : 'source'" [position]="row.side === 'input' ? 'left' : 'right'" [template]="svgHandle">` (workaround 2). GRR-10 renders it for the input node (`{side: 'output', key: 'out'}`), the output node (`{side: 'input', key: 'in'}`) and the tool node (`{side: 'output', key: 'output'}`). A tool node has no input handle in GRR-10: its input keys come from the registry (unit GRR-11 line 18). A wire into a tool input stays in the file and is not drawn, because the library marks an edge whose named handle is missing as detached (`ngx-vflow.mjs` lines 2014 to 2035). The context type is declared in `canvas-page.ts`; it is a structural subset of `ToolFormPortRow` (`tool-form.ts` lines 29 to 36), and GRR-10 does not import `tool-form.ts` (S19). Open point 3.
- **C14 GRR-09 spec X2.** The assertion `The canvas is not built yet.` in `graph-list-page.spec.ts` (line 320) is replaced by `The graph could not be loaded.`: X2 registers no detail, so the fake client refuses the read (`test-doubles.ts` lines 90 to 93) and the page shows its load message (C9) without the canvas library. The title becomes `X2 on a tablet the canvas route is not gated and shows the canvas page`. The gate-absent and URL assertions stay. X2 is not one of GRR-09's criterion tests (`plans/GRR-09.md` line 177).
- **C15 Layout.** `:host` takes `display: block` and `height: 100%`. The `vflow` element takes `height: 70vh`. These are CSS only. GRR-15 owns the styling.
- **C16 Test 1 seam.** Test 1 renders the real library under jsdom, with no-op stubs for the DOM calls jsdom lacks, set in `canvas-page.spec.ts` only (A1). If the real library cannot render there, the fallback is the library's own testing entry: `TestBed.overrideComponent(CanvasPage, {remove: {imports: [Vflow]}, add: {imports: [VflowMocks]}})` with `VflowMocks` from `ngx-vflow/testing` (`testing/vflow-mocks.d.ts`; `package.json` export `./testing`). The test's steps and pass condition do not change. The real library's file output is then checked on disk by tests 2 and 3. Open point 1.
