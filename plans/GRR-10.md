### 1.2 Small choices made by this plan (names, layout, shapes the unit leaves open)

- **C1 Library and peers.** `ngx-vflow` `2.7.0`, exact, in `apps/web` `dependencies`. Its three peers `d3-drag` `3.0.1`, `d3-selection` `3.0.1` and `d3-zoom` `3.0.1` are added as exact `dependencies`. The three `@types/d3-*` packages (`3.0.7`, `3.0.12`, `3.0.9`) are added as exact `devDependencies`. Reason: the module names the library but no version, and the evaluation branch `spike/canvas-library-8` is not in this clone (`git branch -a` lists no such branch and `git log --all` has no canvas spike commit), so the evaluated version is unknown. `2.7.0` is the npm `latest` tag (published 2026-09-03). Open point 2.
- **C2 Files.** The adapter is `vflow-adapter.ts`, a file of plain functions with no Angular import. The page is `canvas-page.ts`, class `CanvasPage`, selector `app-canvas-page`. The GRR-09 placeholder file is deleted. The names follow the GRR-09 naming (`graph-list-page.ts`, `canvas-placeholder-page.ts`).
- **C3 Model.** The state is the graph file object, held in a signal. The vflow `nodes` array is built from the file on load, and it is built again only when a node is added or removed. The vflow `edges` array is built on load and rebuilt on connect, remove and add or remove of a node. Positions are read by the library and written back only from the `nodesChanges.position` output. Every change returns a new file object by object spread, so the key order of the file is kept.
- **C4 Position rule.** A position change writes the file only where the new point differs from the file's position. The library emits position changes for every selected node when one node's point changes, with a TODO that says so (`ngx-vflow.mjs` lines 2255 to 2265). Without this rule a move could write positions of nodes that did not move.
- **C5 Ids.** A new node id is `<kind>-<n>`, with the smallest `n >= 1` that is free in the file. A new wire or edge id is `e<n>` with the smallest free `n >= 1`. Both follow the examples in `plans/GRR-01.md` 2c (`e1`).
- **C6 Add.** The story view adds `entity`, `scene` and `beat` nodes (label defaults to the kind name, no `path`). The recipe view adds `input` nodes (`params: {type: 'text', label: 'Input'}`) and `output` nodes (no `params`). Tool nodes are not added, because the palette is GRR-11's. A new node is placed at `x = y = 40 * (node count + 1)`. Open point 4.
- **C7 Connect.** In the recipe view, `onConnect` adds the wire `{id, from: sourceHandle, to: targetHandle}` when both handles are set, and ignores the connection otherwise. In the story view it adds an edge `{id, from: source, to: target}` with no `relation`. The relation picker is GRR-14's. GRR-10 adds no connection validator: GRR-11 supplies `ConnectionSettings.validator` through the `[connection]` input, which GRR-10 binds to an empty object.
- **C8 Remove.** A "Delete selected" button removes the selected node (with every wire and edge that touches it) or the selected edge. The selection comes from the `nodesChanges.select` and `edgesChanges.select` outputs. There is no keyboard shortcut, because the library's keyboard actions cover only `multiSelection` and `selection` (`keyboard-action.type.d.ts`).
- **C9 Issues panel.** The panel lists the `issues` of the latest response: the detail on load, or the save response. Each row shows `severity`, `code` and `message`. The panel is hidden when the list is empty.
- **C10 Browser copies.** `graphDetailCopy` checks the envelope `{graph, issues}` and the fields the page reads: `schemaVersion`, `view`, `name`, and for each node `id`, `kind`, `position`, and for each edge `id`, `from`, `to`. `validationResultCopy` checks `{issues}` as `validationResultSchema` does. The server's parse is the authority for the rest of the shape. The spec checks only the samples that the copy decides (step 8). Open point 6.
- **C11 No dirty tracking.** The Save button is always enabled. There is no navigation guard. Open point 8.
- **C12 Handle template.** Each port handle is a `<handle>` element (the library's selector) with `id` set to the port id and `type` set to `source` or `target`. Its `[template]` is an SVG element with `data-port` set to the port id and `cx` and `cy` taken from the handle context `point()`. Story nodes have one unnamed `source` handle and one unnamed `target` handle. Every node element carries `data-node` set to the node id.
- **C13 Node templates.** One `ng-template nodeHtml` covers both views. It draws a header with the kind and label, and then one `div` row per port, each row holding its handle (workaround 2). Input nodes have one `out` source handle on the right. Output nodes have one `in` target handle on the left. A tool node shows the tool name and one `output` source handle on the right. Its input handles come with GRR-11 (open point 3). The row template that GRR-11 needs (section 5) is declared in this same node template, so that `node.id` is in scope.
- **C14 GRR-09 spec X2.** The assertion `The canvas is not built yet.` in `graph-list-page.spec.ts` (line 320) is replaced by a check on the canvas heading, which shows the graph name from a canned detail. The gate-absent and URL assertions stay. The placeholder text no longer exists, and X2 is not one of the GRR-09 criteria.
- **C15 Layout.** `:host` takes `display: block` and `height: 100%`. The `vflow` element takes `height: 70vh`. These are CSS only. GRR-15 owns the styling.
