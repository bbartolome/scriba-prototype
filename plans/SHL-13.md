## 1. Decisions this plan follows

1. **A standalone shared component, `MarkdownEditor`.** Selector `app-markdown-editor`, file `apps/web/src/app/shell/markdown-editor.ts`, exported from `shell/index.ts`. It is a shared component of the Shell (module line 3 lists "lossless CodeMirror 6 editor" among them; unit line 18 says "thin standalone wrapper"). Sources: `modules/shell.md` lines 3 and 82; unit line 18; the placement follows `plans/SHL-12.md` line 57. [decision]

2. **Inputs: `reference` and `readOnly`.** `reference` is required, `{projectId: string; path: FileReference}`, where `FileReference` is the contract's project-relative path string (`packages/contracts/src/project-store/files.ts` lines 9 and 75; `plans/DECISIONS.md` line 2295 is the PST-01 review item on the file reference). `readOnly` is a boolean, default `false`. The unit's list of inputs also names "the save mode" (unit line 18). SHL-13 has one save, the manual one, and the saving mechanics, including any mode, belong to SHL-14 (unit line 20). So SHL-13 adds no mode input, and SHL-14 adds it. The reason is that a mode input with one value would be dead code. Open point 6 asks the Navigator to confirm. [decision]

3. **Outputs.** `contentChange` (string: the full text, emitted once after the load and then on every document change), `dirtyChange` (boolean: the text differs from the last loaded or saved text), `saveStateChange` (`SaveState`: `'saved' | 'saving' | 'unsaved' | 'failed' | 'conflict'`, the five values of unit line 18), and `errorChange` (string or `null`, the message of the last failed request). SHL-13 reaches `saved`, `unsaved`, `saving` (set during its manual save), `failed` (any error except a write conflict) and `conflict` (the write error code `PROJECT_WRITE_CONFLICT`, which is `packages/contracts/src/project-store/errors.ts` line 13 with HTTP status 409 at line 66, and is listed in `units/PST-01-contract-slice.md` line 52). Debounce, coalescing and the leave guards are SHL-14 (unit lines 19 and 22). Sources: unit lines 18 and 20. [decision]

4. **The file API goes through the typed client and its paths are copies.** The client is injected through `API_CLIENT` (`apps/web/src/app/shell/tokens.ts` lines 6 to 9). The read is `client.get(readPath, readCopy, {path})`, a `GET` whose `path` travels in the query (`apps/web/src/app/shell/api-client.ts` lines 61 to 67; `packages/contracts/src/project-store/routes.ts` lines 16 and 17). The write is `client.post(writePath, {path, content, baseHash}, writeResultCopy)` (`api-client.ts` lines 75 to 87; `routes.ts` lines 18 and 19; the request schema `files.ts` lines 42 to 46). Sources: unit line 18 ("Loads via the Project store file API read (through the typed API client)"); `modules/shell.md` line 43 (the Shell consumes the file-API read and write shapes of `/project-store`). [decision]

5. **No runtime zod in the Shell: the response copies are hand-written.** The read and write-result responses are checked by `readCopy` and `writeResultCopy`, added to `apps/web/src/app/shell/project-store-copies.ts` (which already holds `ACTIVE_PROJECT_PATH`, `PROJECTS_PATH`, `activeProjectCopy` and `projectListCopy`, lines 9 to 72). The copies are checked against the contract by a parity test in `project-store-copies.spec.ts` (E7), which imports the contract's runtime values in the test build, as that spec already does (lines 1 to 6 and 58 to 61). The rule: all contract imports in the Shell are type-only, except in tests. Sources: `plans/DECISIONS.md` lines 1084 to 1086 (Navigator decision, no runtime zod); `apps/web/src/app/shell/sse-envelope.ts` lines 6 and 7; `apps/web/src/app/shell/project-store-copies.ts` lines 9 and 10. The new copies are path constants `PROJECT_FILE_PATH` (`'/api/project-store/projects/:projectId/file'`) and `PROJECT_FILE_WRITE_PATH` (`'/api/project-store/projects/:projectId/file/write'`), two helpers `projectFilePath(projectId)` and `projectFileWritePath(projectId)` (replace `:projectId` with `encodeURIComponent(projectId)` and return an `ApiPath`), and the two guards. [decision]

6. **The line model is the dominant separator, as the unit says.** The editor state's `EditorState.lineSeparator` facet is set to the separator the loaded text uses most: `\r\n` only when CRLF outnumbers LF; LF on a tie and for a file with no line break. A lone CR is not a separator. Because CodeMirror splits and joins on that one separator, the other separator stays inside its line's text and is written back unchanged. This is the rule of unit line 19, and it is the rule of the other local Shell prototype (section 7a, F13). The probe in section 7a (F12, rows 2 to 5) shows that both a CRLF file and a mixed file round-trip byte for byte under this rule. The unit's sentence "CRLF and mixed endings survive" is correct, so the unit needs no change for it. Cost: a minority-separator line carries a control character, and editing at its end has an effect that open point 1 records. [decision, checked by F12]

7. **The text sent is `state.sliceDoc()`, never `state.doc.toString()`.** `Text.toString` joins lines with LF, so it would rewrite every CRLF line (`@codemirror/state` 6.7.6 in `/tmp/md-roundtrip/node_modules`: `dist/index.js` line 179, where `sliceString` joins with `"\n"` by default, which is what `toString` uses; line 2779 for `lineBreak` and line 2698 for `sliceDoc`; probe row 8 in F12). Nothing else is applied to the text: no trim, no reformat, no added or removed trailing newline. Source: unit line 19. [decision, checked by F12]

8. **A BOM stays in the document as its first character (U+FEFF).** It is not stripped and not stored elsewhere. The write sends it, so the bytes match. Source: unit line 19 ("Keep a BOM if the file API returns one"). The preview of SHL-11 drops a leading BOM before it reads front matter (`plans/SHL-11.md` line 105), so the editor and the preview both handle it. Whether the file API returns the BOM at all is assumed (open point 4). [decision]

9. **Front matter, `_emphasis_` and `*emphasis*` are plain text.** The Markdown language only highlights them. No special node is added. Source: unit line 19 ("Front matter is plain text in the editor"). [decision]

10. **Read-only.** The state gets `EditorState.readOnly.of(readOnly)` and the view gets `EditorView.editable.of(!readOnly)`, both inside one `Compartment` that an `effect` reconfigures when the input changes. The Save button is disabled while `readOnly` is set or a save is in flight. CodeMirror sets the content element's `contenteditable` from the `editable` facet (`@codemirror/view` 6.43.15, `dist/index.js` line 8345, in the other local prototype's `node_modules`; F14). Source: unit line 24; the same two facets as the other local prototype, `apps/web` `markdown-editor.ts` lines 58 to 60 (F13). The reconfiguration on a later change is not covered by a criterion. [decision, checked by F14]

11. **Saving in SHL-13 is one manual save.** The Save button sends `{path, content, baseHash}`, where `baseHash` is the hash of the last load or the last successful save (`files.ts` lines 42 to 46; unit line 20 of SHL-14 fixes the rule). The returned `hash` becomes the next base. A save is sent even when the text is unchanged, because criterion 1 asks for a write. On success the saved text is updated and `saveStateChange` moves to `saved`, or back to `unsaved` if the text changed during the save. Source: unit line 23; SHL-14 unit lines 19 and 20. [decision]

12. **Load on reference change.** The effect that loads the file runs again when `reference` changes; it destroys the old view and loads the new file. Unsaved text in the old view is lost. SHL-14 adds the leave guard; until then, the consumer keys the component by file. Open point 5. [decision]

13. **Styling through CodeMirror's theme, not component CSS.** `EditorView.theme` sets the background and the text colour from `var(--mat-sys-surface)` and `var(--mat-sys-on-surface)`, the tokens of `apps/web/src/material-theme.scss` lines 37 and 38. Component styles are not used: with emulated encapsulation they would not reach the DOM that CodeMirror creates. The component adds no stylesheet of its own, so the 4 kB component style budget (`apps/web/angular.json` lines 39 to 42) is not touched. [decision]

14. **Editor extensions, one list.** `history()` and `historyKeymap`, `defaultKeymap` (from `@codemirror/commands`); `markdown()` (from `@codemirror/lang-markdown`); `syntaxHighlighting(defaultHighlightStyle, {fallback: true})` (from `@codemirror/language`); `highlightSpecialChars()` and `EditorView.lineWrapping` (from `@codemirror/view`), so that a stray CR or BOM is visible and long prose lines wrap on a phone; and `EditorView.contentAttributes` with `aria-label` set to `Markdown source for <path>`. The label answers the review advice of `plans/DECISIONS.md` line 3322 for this component; the accessibility pass as a whole is SHL-19's (`units/SHL-19-polish-gate.md` line 21 names the editor in its automated check). [decision]

15. **No CodeMirror call at module level.** `markdown-editor.ts` and `markdown-document.ts` build their extension lists inside functions. Then an import through `shell/index.ts` does not put CodeMirror in another chunk, as `plans/SHL-12.md` decision 12 (line 79) requires for the diff view. No route imports the editor in this unit (`apps/web/src/app/app.routes.ts` is unchanged), so the initial bundle does not change. [decision]

16. **Fixtures are escape sequences.** The byte fixtures are written as `'\r\n'`, `'\n'`, `'\r'` and `'﻿'` in TypeScript source, so no raw CR, LF-only text or BOM byte is in any file. Then `prettier --check .` (root `lint`, `package.json` line 26) and ESLint pass without a `.prettierignore` entry. `plans/DECISIONS.md` lines 92 and 104 expected SHL-13 to need one; the decision here is that it does not, because `.prettierignore` (lines 1 to 4) lists only `/units/`, `/modules/`, `/plans/` and `/package-lock.json`. ## 6. Open points

1. **Editing at a CRLF line end in a mixed file whose LF lines dominate.** With the facet set to LF, a CRLF line's CR is the last character of its line text. Insertion at the end of that line puts the text after the CR, so the saved file holds a bare CR in the middle of a line. This is shown by F12, row 9 (`alpha\rX\nbeta\r\n`). A deletion that joins such a line with the next one, which removes the LF, leaves a bare CR too; that case was not probed. The byte criteria hold, because the untouched text round-trips. The default here is to accept and record this limit. The Navigator decides whether a guard is needed (a transaction filter and a rule for deletions), and in which unit. Owner: Navigator.
2. **Paste.** The other prototype has a paste filter that rewrites every line break in pasted text to the document's separator (`apps/web/src/app/shared/editor/markdown-document.ts` lines 26 to 32 and 39 to 44 in `/Users/bbartolome/workspace/scriba`). It is not in this unit's criteria, so it is not in this plan; without it, pasting LF text into a CRLF file mixes the endings. Owner: Navigator (SHL-14 or a later unit).
3. **Two line models in the Shell.** SHL-12 splits its two documents on LF only, so that an LF to CRLF change is visible (`plans/SHL-12.md` decision 5 and its criterion 3; open point 5 there). This unit uses the dominant rule (decision 6). With a single separator for both sides, the LF to CRLF change of SHL-12 criterion 3 would not show, because both documents would be split alike. So the diff keeps its rule. Unit line 21 of SHL-16 says SHL-16 uses "the same handling as SHL-13"; the plan of SHL-16 must say which part of the handling it takes (the editing side can use the dominant rule; the diff side must keep the LF split). No change to SHL-12 is needed. Owner: Navigator, and the plan of SHL-16.
4. **The BOM from the file API (assumed).** The read returns the BOM in `content` (U+FEFF as the first character), and the write stores `content` unchanged. Neither is written down in the project-store documents: `units/PST-06-file-api-core.md` line 20 says "UTF-8 text only" and gives no BOM rule, and `modules/project-store.md` line 49 says hashes are over the UTF-8 bytes. Node's UTF-8 decoding keeps the BOM, but the implementation is not written. If the API strips the BOM on read, the wire test here still passes (the fixture is the fake's answer), but the file loses its BOM on save. Owner: the PST-06 plan must state the rule and test it (a file with a BOM read and written back byte for byte).
5. **Reload loses unsaved text (decision 12).** Until SHL-14's leave guard exists, a consumer must key the component by file. Owner: SHL-14.
6. **The save-mode input is not added (decision 2).** Unit line 18 lists "the save mode" as an input of this wrapper. SHL-13 has one manual save, so the plan adds no mode input, and SHL-14 adds it with its modes. Owner: Navigator, to confirm or to move the input here.
7. **The edit seam (decision 17).** Criteria 2 and 3 edit through `EditorView.findFromDOM` and `dispatch`, not through typing, because the wrapper has no edit input and jsdom typing is not reliable. The real keyboard path is checked by hand in step 10 and by SHL-19's e2e phone check. Owner: Navigator, to accept the seam.
8. **Package versions.** `@codemirror/state` 6.7.6 and `@codemirror/view` 6.43.15 are the versions recorded by the SHL-12 registry check (`plans/DECISIONS.md` line 2959). The other packages (`commands`, `lang-markdown`, `language`) are the versions the other local prototype lists (its `apps/web/package.json` lines 19 to 26). The code stage runs `npm view` (step 2) and records the versions it installs.
9. **Who creates `testing/dom-range.ts`.** Decision 20 and section 2c: whichever unit merges second reuses the first's file. Owner: the coordinator of the batch.
10. **Dark theme.** The colours come from Material tokens (decision 13). How the editor looks in the dark theme and on a tablet is for SHL-15 and SHL-19 to check. Owner: SHL-15.
