### 1b. Decisions this plan makes

- **D1 Source of the state.** `AgentRunsService.current()` (new). Order: (1) the active project's `active` run, else its `ended` run, served as the run's `state` (D9); (2) else the latest transcript run of the active project, that is the last of `AgentTranscriptsService.runs(projectId)` in run order, rebuilt by `runStateOfTranscript` (D4); (3) else no run (D3). Memory comes first, because it holds the text and outputs that the transcript cuts at 8,192 characters (D6, open point 5).
- **D2 No cache.** The rebuilt state is not stored. The GET changes no slot and writes no file. The cost: while the registry holds nothing for the project (after a restart, or the first read of a project with no run in memory), each GET reads that project's transcripts. Settled: no cache (section 6, point 4).
- **D3 "No run" is the JSON body `null`.** Nest's Express adapter answers a `null` handler result with an empty body (`node_modules/@nestjs/platform-express/adapters/express-adapter.js` lines 94 to 96). The page would still read that as `null`, because Angular's HTTP client maps an empty 200 body to `null` (`node_modules/@angular/common/fesm2022/_module-chunk.mjs` line 1854). The plan writes the JSON `null` itself, because `runStateReply` documents a `null` body (`agent-contract.ts` line 253). The 404 `AGENT_RUN_NOT_FOUND` is not used for "no run": that code stays the stop route's refusal.
- **D4 Rebuild rules** (new file `apps/api/src/modules/agent-loop/transcript-run-state.ts`, pure function `runStateOfTranscript(run: TranscriptRun): AgentRunState`):
  - `runId`, `conversationId`: the run's own.
  - `status`: `ended`, for every transcript-rebuilt state.
  - `reason`: the `run-end` reason; `stopped` when the run has no `run-end` (unit line 20).
  - `step`: the largest `step` in `run.steps`; 0 when the run has no step line.
  - `cap`: the `cap` of the last `step` line; `AGENT_DEFAULT_STEP_CAP` (12, `packages/contracts/src/agent-loop/constants.ts` line 6) when there is no step line (section 6, point 2).
  - `assistantText`, `cards`: as the reader builds them (AGL-04 plan D13; `transcript-reader.ts` lines 101 to 205), with no further rule (section 6, point 3).
  - `groundingResults`: `[]`. No `grounding` line exists yet; `runOf`'s default branch ignores such lines (`transcript-reader.ts` lines 198 to 200).
  - `pendingChangeIds`: from the `run-end` line; `[]` when there is none. AGL-12 extends this (section 5).
  - `lastSeq`: the largest `seq` of the run's lines. For a finished run this is the `run-ended` seq (U5).
- **D5 Reader fields (additive).** `TranscriptRun` (`transcript-reader.ts` lines 40 to 52) gains `lastSeq: number`, `cap?: number` and `pendingChangeIds: string[]`. `runOf` (lines 101 to 205) fills them: `lastSeq` from the lines' `seq` (`parseLines` keeps it, lines 79 to 98), `cap` from the last `step` line (the `case 'step'` at lines 130 to 132), `pendingChangeIds` from the `run-end` case (lines 191 to 197). No other output of the reader changes: `turns()`, `conversations()` and `replayTurns` read explicit fields. CHECKED: no file in `apps/api/src` or `apps/api/test` builds a `TranscriptRun` literal (`grep -rn TranscriptRun` finds only the reader and `conversation-history.ts`, which takes the type), so the new fields can be required.
- **D6 Truncation accepted.** The rebuilt `assistantText` and tool outputs are the transcript's copies, cut at 8,192 characters per string (AGL-04 plan D8). After a restart a long answer can show shorter than it did live (section 6, point 5).
- **D7 Route.** `@Get(AGENT_RUN_CURRENT_ROUTE)` goes into `agent-runs.controller.ts` (AGL-04 plan section 5 says AGL-05's GET goes there; AGL-04's own two GETs are in `agent-conversations.controller.ts`). The handler is `current(@Res() response: ServerResponse): void`; it sets status 200 and `application/json`, then `response.end(JSON.stringify(this.runs.current()))`. The repository already uses `@Res()` in two controllers (`apps/api/src/modules/platform/events/events.controller.ts` line 12; `apps/api/src/modules/setup-auth/setup-session.controller.ts` line 74). A refusal thrown by `current()` is thrown before any write, so Platform's filter still answers it.
- **D8 No active project.** `current()` checks `store.activeId()` first and throws `AGENT_NO_ACTIVE_PROJECT` (409), the way `start()` and AGL-04's conversation GETs do (`agent-runs.service.ts` lines 58 to 64; `agent-conversations.controller.ts` lines 40 to 51). Settled in section 6, point 1.
- **D9 No copy.** `current()` returns the run's `state` itself (public and readonly, `agent-run.ts` line 98). The controller serializes it with `JSON.stringify` in the same synchronous call, so no event can change it between the read and the write, and nothing keeps the reference. `agent-run.ts` does not change. (The draft's `snapshot()` with `structuredClone` is withdrawn: it guarded against nothing.)
- **D10 Side effects.** `current()` reads the settings (`store.activeId()`), the registry's slots and the transcripts through the reader. It writes no file, emits no event (the invariant sweep's event allowlist is empty, `apps/api/test/invariant-sweep.ts` lines 144 to 151), and changes no slot.
- **D11 Nothing else changes.** No contract change (`routes.ts` line 5 and `runs.ts` lines 25 to 37 already publish the route and the state). No web change (AGL-07 is done and calls the route). No module wiring change: `agent-loop.module.ts` already registers `AgentRunsController` and `AgentTranscriptsService` (lines 35 to 53).
