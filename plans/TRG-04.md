## 1. Decisions this plan obeys

### 1a. Settled by the unit, the module, the README and earlier decisions

- **Entity picker contents.** It lists the active project's entities from the Project store's entity list, `{id, type, path, title?}`, filtered by `x-scriba-entity-kinds`; a single ID, or chips for a list field; it accepts dropped entity chips. Source: unit lines 18, 23 and 24; module line 45 (the list is "filterable by `type`").
- **Style picker.** It lists style-profile entities and defaults to the project's `styleProfile` from `project.yaml`. Source: unit lines 19 and 25. The kind name `style-profile` is a core entity type of GNP-03 (`units/GNP-03-core-entity-types.md` lines 15 and 16, as `plans/TRG-01.md` line 223 cites; not on main as code).
- **Test seam.** Component tests use the Shell's fake API; the running app uses the real Project store. Source: unit line 20; module line 51 (the UI seam is the tool-form component with Angular's Vitest runner against the Shell's fakes, SHL-07). The unit heading has no parenthetical, so the module's default seam applies (`units/README.md` line 57).
- **Fixtures.** The mixed-type fixture belongs to this unit and lives in its spec file. Unit tests never read `examples/` or the real packs. Source: module line 52; `units/README.md` line 136.
- **Values are IDs.** The picker holds entity IDs and never resolves them to contents. Callers resolve (module line 60); the Try panel resolves in the browser (`units/TRG-16-try-panel.md` line 15). TRG-03's tests already use ID strings and ID arrays (`tool-form.spec.ts` T4, line 438).
- **No validation in the form.** The server's issues are shown next to their fields; the form never validates (TRG-03 unit line 23; TRG-03 plan section 1b, D8).
- **Callers fill an empty style field** before a call (`plans/TRG-02.md` line 41, D4; `units/TRG-12-executor.md` line 31; `units/AGL-09-narrative-tools.md` line 19; `units/TRG-16-try-panel.md` line 15). The preselect (P15) fills the field earlier when it can; a caller's fill still covers every case where it cannot.
- **ToolForm's API is TRG-03's.** Inputs `form`, `ports`, `layout`, `issues`, `handle`, two-way `value`; output `submitted` (`plans/TRG-03.md` section 1b, D2). No input is added (P12).
- **Feature boundary.** A web feature imports another only through its entry file (`eslint.config.mjs` line 41 for the entry pattern; the web policy at lines 60 to 67). TRG-04 therefore cannot import the copies in `features/project-store/`; it writes its own.
- **Browser contract route.** The browser ships no runtime zod. Contract imports in the browser are type-only, and hand-written copies of paths, patterns and guards are checked by a Vitest parity spec. Source: `plans/DECISIONS.md` lines 1084 to 1089 (the Shell rule) and lines 2546 to 2549 (the Navigator's SHL-08 decision: the settled route for other contract values is the parity pattern); `plans/TRG-01.md` line 225 (web units that follow it need hand-written copies checked by a parity test). This settles draft O11 (P19).
- **No new dependency in `apps/web`.** A YAML library in `apps/web` is forbidden by the no-new-dependency rule (the Navigator's SHL-11 decision, `plans/DECISIONS.md` line 3465, citing lines 1084 to 1089). The SHL-11 precedent replaces a YAML parse with a line rule. This settles draft O4 (P14).
- **Entity list shape.** GET `PROJECT_ENTITIES_ROUTE` (`packages/contracts/src/project-store/routes.ts` line 27); query `type`, a single optional string (`entities.ts` line 50); response `{entities: [{id, type, path, title?}], invalid: [{path, reason}]}` (`entities.ts` lines 55 to 70). An invalid file is "not resolvable" (PST-08 unit, Decisions).
- **Active project.** GET `ACTIVE_PROJECT_ROUTE` (`routes.ts` line 12) answers `{active: string | null}` (`project.ts` lines 76 to 78, `activeProjectSchema`). `apps/web/src/app/shell/project-scope.ts` lines 70 to 73: the URL's id is not the server's active project; features that need the server's answer read GET active.
- **File read.** GET `PROJECT_FILE_ROUTE` (`routes.ts` line 16) with query `path`, answer `{path, content, hash, mtime, upgraded?}` (`files.ts` lines 33 to 39, `fileReadSchema`). The server reads `project.yaml` like any text file and refuses a too-new one (`files.service.ts` lines 256 to 268).
- **`styleProfile` is an entity ID.** `projectYamlSchema.styleProfile` is `entityRefSchema.optional()` (`project.ts` line 24), which is `entityIdSchema` with `ENTITY_ID_PATTERN` `/^[a-z0-9][a-z0-9-]*$/` (`entities.ts` lines 6 and 8; `constants.ts` line 4).
- **Chips are the Graph runner's.** The drag source, the pinning rules on ports, and chip removal from ports belong to GRR-12 (its unit lines 18 to 20). This plan takes only the drop onto the Tool form's picker (O7, decided: CDK drag and drop, section 7).

### 1b. Decisions this plan makes

Each is the smallest reading that meets the unit.

- **P1 Shape.** One new standalone component, `entity-picker.ts`, renders both `entity-picker` and `style-picker` fields. `ToolForm` renders it in place of the `picker` branch (`apps/web/src/app/features/tool-registry/tool-form.ts` lines 85 to 86 choose the branch; lines 292 to 306 draw the read-only slot). The `idsOf` helper (lines 129 to 130, and its binding at line 516) and the `.picker-slot` rule (line 211) go. Basis: TRG-03 plan line 98 (TRG-04 replaces the slot) and its section 1b, D4(a).
- **P2 The browser filters by kind.** The picker filters the rows it shows by the field's kinds itself. Basis: the Shell's fake answers by method and path only (`apps/web/src/app/shell/testing/test-doubles.ts` lines 34 and 89), so a test can prove the filter only in the browser; and the list's `type` takes one value (draft O1, settled by P10).
- **P3 Kinds are read reactively.** The picker reads `entityKinds` from its input through a `computed`, so a changed descriptor re-filters the list. Basis: `units/TRG-15-live-previews.md` line 21.
- **P4 Invalid files are not offered.** The picker lists `entities` only. Basis: the PST-08 unit (not resolvable) and the list shape in section 1a.
- **P5 Value shape.** A scalar entity or style field holds one ID string. A list field holds an array of ID strings. Removing a chip removes its ID and leaves the array (`[]` when it is empty), as TRG-03's `removeItem` does (`tool-form.ts` line 670). Basis: TRG-03 plan D5 and T3.
- **P6 Issue association.** The picker control keeps `aria-describedby` with the field's hint and issue IDs, as TRG-03 does. `ToolForm` keeps rendering the issue paragraphs. Basis: TRG-03 spec T7 (`tool-form.spec.ts` lines 516 to 525) reads the control's `aria-describedby`.
- **P7 No validation and no resolution in the picker.** Basis: module line 60; TRG-03 plan D8.
- **P8 One write path.** The picker writes through the `value` model that `ToolForm` already owns (`tool-form.ts` line 511), so `[(value)]` and `submitted` keep their behaviour.
- **P9 Where the tests live.** The criterion tests are in `tool-form.spec.ts`, through the host component (the TRG-03 seam). The copies have a parity spec. There is no HTTP test: TRG-04 adds no endpoint, and the reads are tested by PST-08 and the Project store's file units.
- **P10 (draft O1) One list GET with no `type`.** The picker sends no `type` and filters every row in the browser (P2). Basis: module line 45 says the list is "filterable", not that callers must filter on the server; PST-08's plan (line 153) offers exactly this choice to this plan; the fake ignores params either way. Effect on other units: none (GRR-12 does the same, PST-08 plan line 152).
- **P11 (draft O2) No kinds means every kind.** An `entity-picker` field without `entityKinds` offers every valid entity, and a drop onto it accepts a chip of any kind. Basis: the hint is a filter (unit line 18), and TRG-07 makes it optional on `entity` fields (`units/TRG-07-lint-pack-lint-cli.md` line 19); GRR-12 checks "the port's entity-kind filter" (its line 19), which is a no-op when there is none. A style picker always uses the style kind (P13), whatever the field holds.
- **P12 (draft O3) The project is the server's active project.** The picker reads GET `ACTIVE_PROJECT_ROUTE` once, then the list (and, for the style picker, the file) of that project. With `active: null` the picker shows "No active project" and offers nothing. No `ToolForm` input is added; `ActiveProjectSignal` is not used. Basis: unit line 18 ("the active project's entities"); `modules/project-store.md` line 3 (one active project); `project-scope.ts` lines 70 to 73; `units/TRG-16-try-panel.md` line 15 ("pickers on the active project"); `/tools` has no project in its URL (`units/TRG-13-tools-page-list.md` line 15), and TRG-05's dev route is on `/tools` (its line 17). Effect: TRG-05, TRG-13 and TRG-16 need no project input; GRR-11's canvas page reads the same answer.
- **P13 (draft O6) The style kind is a constant of the feature.** `STYLE_PROFILE_KIND = 'style-profile'` in `project-store-copy.ts`. The contract has no such constant (`style-profile` appears in `packages/contracts` only in a pattern test, `packages/contracts/test/tool-registry.consumers.test.ts` line 118), so there is nothing to compare it with; the parity spec checks that it matches the contract's `ENTITY_KIND_PATTERN` (`packages/contracts/src/tool-registry/constants.ts` line 11), as the contract's own test does for this kind. No contract or vocabulary change. Basis: unit line 19 names the kind.
- **P14 (draft O4) The style profile is read from `project.yaml` by a line rule.** The style picker reads GET `PROJECT_FILE_ROUTE` with `path=project.yaml` and takes the first line that matches `^styleProfile:[ \t]*(["']?)(<id>)\1[ \t]*(#.*)?$`, where `<id>` is `ENTITY_ID_PATTERN` without its anchors, at column 0. No match, a failed read or no active project gives no preselect. Basis: the unit names `project.yaml` (line 19); no Project store read returns the value (`projectSummarySchema`, `project.ts` lines 39 to 46; no route in `routes.ts`); a YAML library in `apps/web` is forbidden (section 1a); the SHL-11 precedent (a line rule in place of a YAML parse). A project.yaml whose `styleProfile` is written in a form the line rule does not read (a flow mapping, a block scalar, an alias) gets no preselect, and the caller's fill of an empty style field (section 1a) still applies on the server side. Effect: TRG-16 can reuse the same helper (same feature).
- **P15 (draft O5) The preselect enters `value`.** When the style profile is known and `value` has no key for the field (or the key holds `''` or `undefined`), the picker writes the ID into `value`, so the control shows it and `submitted` carries it. An existing value is never replaced. Basis: unit line 19 says the style picker "defaults to" the profile, and TRG-03 prefills defaults into `value` while the key is absent (`tool-form.ts` `ngOnInit`, line 578; TRG-03 unit line 23, "defaults prefilled"). Effect: TRG-02 D4, TRG-12, AGL-09 and TRG-16 fill an empty style field; after the preselect the field is not empty, so their fill is a no-op there and still covers the cases P14 lists. In GRR-11's node body a non-port style field gets the default in `params` as TRG-03's numeric defaults do; a port style field renders as a port row, not a picker, so nothing is written.
- **P16 (draft O8) A refused drop leaves `value` unchanged and shows a short reason.** The reason is one line inside the field, `role="status"`, for example "A place cannot go here." It clears on the next accepted drop or change. No Shell notice. Basis: unit line 24 ("refused"); GRR-12 line 19 ("Refusals show a short reason") for the same chips.
- **P17 (draft O9) Widget details.** (a) The single-ID control is a native `select` with `matNativeControl`, as TRG-03's `select` control (`tool-form.ts` lines 363 to 372); its first option is empty ("None"). (b) An entity's label is its `title` when present, else its ID; the option value and the chip's `data-id` are always the ID. (c) A list field shows one chip per ID, each with a Remove button (as TRG-03's list items, `tool-form.ts` lines 347 to 353), and a select to add one more entity of the field's kinds. (d) A drop onto a single-ID field of the right kind replaces the value; TRG-05 criterion 2 (its line 22) needs a drop onto the cold-open fixture's `person`, which is a single string (`apps/api/test/fixtures/packs/core/tools/cold_open.yaml` lines 36 to 41). (e) The reads run once at init. While they run, the picker shows "Loading entities"; after a failed read it shows "Entities could not be read" and offers nothing, and keeps the existing value. No reconcile on SSE (not asked by the unit).
- **P18 (draft O10) The unit's front matter is not changed.** `blocked_by` holds PST-01 and PST-08 in one quoted string (unit line 7). It does not stop a correct plan, so no unit action applies (`prompt.md`, "Do not change a part that is not in the way").
- **P19 (draft O11) The copy route.** Settled by `plans/DECISIONS.md` lines 2546 to 2549 and `plans/TRG-01.md` line 225 (section 1a).

## 7. Decided point

- **O7 The drop mechanism and payload — decided: option (b), Angular CDK drag and drop.** The decision lives in `plans/DECISIONS.md` (entry of 2026-11-15, "TRG-04 — Navigator decision: O7", commit `1e27f30`). Decision: the picker is a `cdkDropList` whose `cdkDropListEnterPredicate` checks the dragged chip's type against the field's allowed kinds (any kind under P11; `style-profile` for a style picker). A chip is a `cdkDrag` whose `cdkDragData` is `{id: string, type: string}`. An accepted drop (`cdkDropListDropped`) appends in list mode with no duplicate ID, or replaces in scalar mode, and writes through the value model (P8). A refused drop shows the one-line reason (P16) and leaves `value` unchanged. Tests call the `cdkDropListDropped` output with a fake `CdkDragDrop`. Reason: GRR-12 requires chips that work with mouse and touch; native HTML drag and drop (a) is mouse-only by the browser spec (its Safari touch support is the Navigator's unverified claim); CDK drag uses pointer events, one mechanism for mouse and touch; `@angular/cdk` 22.2.7 is already a direct dependency of `apps/web`; option (c) adds an exported API without solving the touch gap. The orchestrator checked `cdkDropListEnterPredicate`, `cdkDropListDropped`, `cdkDragData` and `CdkDropListGroup` (selector `cdkDropListGroup`) in `@angular/cdk` 22.2.7; there is no `DragDropGroup` class. The facts and options below are the record of what was considered.
- Facts at the time of the choice: no drag-and-drop code exists in `apps/web/src` (checked by grep for `dataTransfer`, `dragover`, `CdkDrag`, `cdkDrag`, `ondrop` and `(drop)`); `@angular/cdk` 22.2.7 is a dependency of `apps/web` (`apps/web/package.json`); jsdom has no `DataTransfer` or `DragEvent`; the unit names the chips as "the Graph runner's drag-to-input chips" (line 18) and its criterion 2 tests the drop, so the decision is protected and cannot be reworded; GRR-12 (M4) requires chips that work "with mouse and touch" (line 18) and a real gesture in Playwright (line 26), GRR-15 a touch drop in Playwright's touch emulation (line 20) and GRR-17 a chip drop on an iPad in Safari (line 18); TRG-05 needs a chip in the running app before GRR-12 exists. A split of criterion 2 into a subunit blocked by GRR-12 would make a cycle (TRG-05 needs it; GRR-12 is behind GRR-11, which is behind TRG-05), so TRG-04 must define the drop now.
- Options considered:
  - **(a) Native HTML drag and drop** with a JSON `{id, type}` under a custom MIME type exported from the feature's entry. Not chosen: native drag from touch is uneven, so GRR-15 and GRR-17 might need a second gesture.
  - **(b) Angular CDK drag and drop** (`cdkDropList` with an enter predicate, `cdkDrag` chips). **Chosen.**
  - **(c) A mechanism-neutral accept API plus (a) in the form.** Not chosen: one more exported API, and the touch gap remains.
